# Go 微服务架构与技术选型设计

确认边界：用户于 2026-11-14 通过 [SRC-GO-MS-02](../requirement/29-Go微服务架构需求.md#src-go-ms-02) 确认“四个业务服务＋轻量 Gateway”，并授权开始分阶段拆分；不表示全部服务已经独立，也不扩大为生产发布或存量数据库变更授权。原始来源：[SRC-GO-MS-01](../requirement/29-Go微服务架构需求.md#src-go-ms-01)。实施状态、顺序与未决事项统一见[BACKLOG](../../../BACKLOG.md#go-microservices-20261114)。

[SRC-GO-MS-03](../requirement/29-Go微服务架构需求.md#src-go-ms-03) 进一步要求先提交 main 并推送已有切片，再继续拆分，并重申目录遵循 Google Go；不改变业务域独立门禁或生产边界。

## 1. 摘要

建议采用 **同仓、单 Go module、按业务边界拆分、渐进独立部署** 的方案：

- 目标为 **Gateway + Identity + Creation + Media + Execution**，即一个轻量入口、四个 Go 业务服务；这是目标责任图，不要求一次启动五套新服务。
- **Operation、Catalog、Billing 同属 Execution**。先保留报价确认、额度预占、派发和结算的本地事务，不为追求服务数量强拆钱包。
- 继续使用 Gin、GORM/PostgreSQL、Redis、Kafka、数据库任务记录和现有观测基础；新增 Go 内部强类型 RPC 时采用 gRPC-Go/Protobuf。不同时引入另一套微服务框架和基础设施体系。
- 保留已接受的 Agent/Pi Durable 和 Canvas/Yjs 独立运行时；研发 Workspace 继续遵循[设计43](43-Workspace知识库与研发工作流服务设计.md)。这些非 Go 边界是否改写，须单独确认，不能由本设计替代既有决定。
- 先建立契约和数据所有权，再拆进程。**分离 API、worker、relay 只是运行角色隔离，不等于已经完成微服务拆分。**

Google Go 指南约束清晰性、包设计、接口、错误和并发等工程质量，不指定唯一微服务框架或目录模板。以下服务划分属于结合本仓库事务与职责的架构判断，不冠以“Google 官方微服务架构”。

据此，当前更准确的描述是“**Go 模块化业务后端 + 独立专用运行时**”，而非四个 Go 业务微服务已经存在。尚未取得生产容量、调用链基线、故障统计及团队独立发布需求，不能断言微服务必然更快、更省或更高可用。

### 3.2 不可绕过的约束

1. [AGENTS](../../../AGENTS.md) 中 Google Go 与 `adapter → application → domain` 规则继续有效。
2. `backend/db/schema.sql` 是唯一结构规范，`backend/db/data.sql` 是唯一公共种子来源；不新增其他 SQL 文件、`migrations/`、自动迁移框架或运行时 DDL。
3. 现有业务与安全语义不因网络拆分而降低；幂等、权限撤销、原请求恢复、预算与真实费用均按所属领域合同执行。
4. 前端继续通过同站代理访问当前 `/api` 合同；沿用 Handler/DTO 注解 → swag → 前端生成客户端链路，不手改生成文件。
5. Agent 的会话和运行状态仍由 Agent 单独拥有；Go 不镜像其执行状态、不监督其 Node 进程，不重新引入 Temporal。

### 3.3 需要在拆分前处理的现状差距

- **普通维护必须只有 DML 能力。** 初始调研发现 flow 分区维护可达动态 DDL；对应约束是[应用服务](../../../backend/internal/infra/maintenance/application/service.go)只能消费 PrunePublished / PruneExpired 端口，[历史分区任务](../../../backend/internal/infra/maintenance/adapter/task/maintenance.go)只允许完成收束，不能再执行 DDL 或重排。管理员显式操作使用的 [PartitionStore](../../../backend/internal/infra/outbox/adapter/postgres/partitions.go)仍含分区 DDL，不得重新接回普通生命周期；分区预建、保留与存量库角色变更须由管理员受控执行，不能换成常驻自动 DDL 进程。代码门禁不等于存量库权限已经核验。
- **身份与项目创建也有强事务耦合。** [请求作用域适配](../../../backend/internal/app/scope/scope_access.go)在消费者事务中保留身份/成员锁；[项目创建](../../../backend/internal/workspace/adapter/postgres/create_project.go)会一并创建画布、预算并确保钱包。Identity 并不是因为名称清晰就能立即物理拆出的低风险服务。
- **已有 Saga 不等于已分库。** credit saga 仍受 schema 中跨 operation/workspace/billing/infra 的约束与事务保护；是否启用某开关不改变必须清点这些依赖的要求。
- **测试布局与门禁须区分规范和现状。** PROJECT 要求测试集中 backend/tests，但源码中仍存在生产目录内的测试；CI 的 race 套件也不代表完整 lint/vuln 门禁均已执行。本设计描述目标规则，不声明当前工作区已经全面合规。

## 4. 目标

### 4.1 本设计的目标

- 为每个业务服务定义职责、权威数据、依赖方向、通信方式和可独立发布条件。
- 将现有模块映射到服务，而非照表、照队列或照页面一对一拆服务。
- 明确事务、任务、事件、权限与文件交接的边界，防止形成“多个进程共同读写一套业务表”的分布式单体。
- 给出尽量复用现有能力的技术选型和 Go 工程结构。
- 为 [PRD30](../prd/30-Go微服务拆分.md) / [Plan39](../plan/39-Go微服务拆分执行计划.md) 提供可验证的技术接受条件；不扩展未获确认的产品范围。

### 4.2 非目标

- 不以预建四个空进程代替业务拆分；实施限于 SRC-GO-MS-02 和验收合同，不包含生产发布、存量业务库变更或未经确认的业务重写。
- 不因拆分统一改写所有语言、HTTP 框架、ORM 或公共 API。
- 不把组织、团队、画布、剧本、主体、通知、搜索、计费分别预建成独立服务。
- 不承诺未经测量的 QPS、延迟、SLO、副本数、分片方案或灾备目标。

## 5. 使用场景

| 场景                  | 角色及触发                    | 必须保持的结果                                                         |
| --------------------- | ----------------------------- | ---------------------------------------------------------------------- |
| 登录后访问创作项目    | 用户经同站入口请求项目或画布  | 身份验证与项目授权分离，失效身份不能因内部调用绕过限制                 |
| 确认报价并执行生成    | 用户或获授权 Agent 确认原报价 | 一次预占、一次业务受理；未知回执查询原请求，不另建收费请求             |
| 上传、处理并采用素材  | 用户上传或 Execution 交付输出 | 对象归档与资产发布有明确回执，未发布资产不被当作可用结果               |
| 关闭项目或撤销权限    | 项目管理员或账号所有者操作    | 禁止新准入，可靠收束在途工作，不能在删除后重新落入有效作品             |
| 重启 worker、重放事件 | 部署或故障恢复                | 原任务及资金身份不变，过期 worker 不能覆盖新 owner，事件重放不重复结算 |

故事对应需求29的 FR-GOMS-01/02 与 NFR-GOMS-01；这些是架构场景，不新增各领域产品范围。

## 6. 价值

- 保留已经建立的业务一致性，把拆分成本集中到确实需要独立扩缩、隔离故障或独立发布的边界。
- 将媒体重任务、生成出站和账户入口的资源与权限隔离，减少共享超级数据库角色及组合根耦合。
- 用契约、权限和故障验证证明可独立运行，而不是以目录或容器数量作为完成指标。

代价是增加网络故障、事件延迟、部署版本、凭据和运维成本；只有相应隔离收益成立时才继续物理拆分。

## 7. 方案

### 7.1 边界原则

1. **业务不变量优先于模块名。** 必须同事务成立的规则，默认留在同一部署和数据库事务内。
2. **一个事实只有一个写入权威。** 其他服务使用 API、命令或带来源版本的只读投影。
3. **服务内部调用不绕远路。** 同一 Execution 内的 operation/catalog/billing 使用消费方接口和本地事务，不经 Gateway 或自调用 RPC。
4. **独立服务不共享应用层与 ORM 模型。** 可共享生成协议与无业务的基础设施能力，不共享领域实体和业务仓储。
5. **无可靠边界，不拆进程。** 暂时无法替代跨领域 JOIN、外键或事务时，保留相应组合部署；不能以“最终一致”掩盖语义缺口。

### 7.2 目标责任图

```text
浏览器
  │ 同站 HTTP / SSE / WebSocket
前端同站代理
  │
Go Gateway ───────────── Identity
  ├──────────────────── Creation ─── Canvas / Yjs（既有 Node 运行时）
  ├──────────────────── Media
  └──────────────────── Execution
                          ├─ Operation：报价、确认、原请求与执行
                          ├─ Catalog：模型、供应商、凭据与路由
                          └─ Billing：预占、账本、结算与补偿

Agent / Pi Durable（既有独立服务）
  └─ 经受限 Go 业务入口调用 Creation / Execution / Media

业务服务之间：必要的同步 RPC + Kafka 事件
每个服务内部：API / worker / relay 按实际任务分开运行
PostgreSQL 同集群起步：按所有权分 schema / role / 任务与事件记录
```

这是调用与权威示意，**不表示每对服务都要建立双向 RPC，也不表示每个服务都必须有三类进程**。Gateway 不承接 Agent 的内部业务权威，外部模型供应商凭据仅进入所属服务。

### 7.3 服务职责与现有模块映射

| 建议服务  | 权威职责及现有模块                                                                                                              | 数据归属与对外能力                                                                      | 明确不承担                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Gateway   | 公共路由、请求标识、入口限流、粗粒度身份验证、流式代理                                                                          | 无业务数据库；按路由转发既有 HTTP 合同，必要时做明确的只读聚合                          | 钱包、报价、项目授权决策、跨服务数据库事务、全局业务编排   |
| Identity  | `identity`：账号、认证、会话、平台身份、账号安全与邮件任务                                                                      | 拥有身份数据；提供验证、会话和撤权合同                                                  | 项目/团队成员与资源级权限、直接删除他域业务表              |
| Creation  | `workspace` 的组织/创作空间/项目与团队，`canvas`、`script`、`bible`、`subject`、创作编辑侧 `prompt`；承接相应 Go Agent 业务适配 | 拥有项目生命周期、协作接受、剧本/主体和编辑草稿；提供资源授权、版本快照、采用与项目命令 | 模型供应商出站、媒体物理对象权威、资金结算、Agent 执行状态 |
| Media     | `media`、`mediatool`：上传、资产/版本、对象位置、归档、转移、清理及媒体处理任务                                                 | 拥有媒体表与对象生命周期；提供资产发布/读取/处理及精确版本引用                          | 项目编辑权威、报价、模型路由、按媒体处理结果自行退款       |
| Execution | `operation`、`catalog`、`billing` 及相应任务：冻结报价、准入、供应商路由/提交/查询、原请求恢复、预占和结算                      | 拥有执行、目录与账本数据；提供报价、确认、取消意图、查询和实际费用事实                  | 项目文档、Yjs 权威、媒体物理清理、Agent 会话与规划状态     |

补充边界：

- Creation 中的现有 `workspace` 是创作空间业务模块，**不是**根目录拟建的研发知识库 `workspace/` 服务，两者不能合并数据所有权。
- `prompt` 当前部分表位于 `workspace` schema，操作确认又使用事务绑定的编译/草稿适配。目标区分“编辑草稿”与“Execution 冻结快照”，但不能仅改包名或表前缀就认定分离完成。
- `agent_business` 及 Go `internal/agent` 业务边界须按工具实际修改的权威分配；审批、项目、资金分别调用所属端口，不另建一个拥有全部业务库权限的“Agent 万能服务”。
- 通知邮件先归 Identity；分析/观测先沿现有领域事实与投影，不预建通用通知、报表或日志微服务。
- 账务保持独立模块和访问控制，但**不作为本轮独立进程目标**。确有独立合规、隔离或组织责任需求时再评估 Billing 服务及跨服务资金协议。

### 7.4 技术选型与取舍

下表是建议基线。已安装版本以 [go.mod](../../../backend/go.mod) 和各锁文件为准；新增依赖在获准实施时核对支持期、安全公告和许可并固定版本，不把调研日期当作永久版本承诺。

| 能力               | 建议                                                             | 选择理由与限制                                                                                                     |
| ------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Go 版本            | 沿用当前 Go 工具链基线并通过安全门                               | 当前 `go.mod` 声明 Go 1.26.0 / toolchain go1.26.11；构建镜像与 CI 必须实际一致，不能仅凭文件声明认定运行环境已升级 |
| HTTP               | 继续 Gin，使用标准 `net/http.Server` 生命周期                    | 已有 Handler、鉴权和生成合同；Gin 仅存在于 adapter，不泄漏到 application/domain                                    |
| 微服务组织         | 普通 Go 包 + 显式装配，不新增综合框架                            | 现有平台能力已覆盖连接、任务和事件；Kratos/go-zero 并非不可用，但本轮无法证明换框架收益足以覆盖合同和接线重写成本  |
| Go 内部 RPC        | 新增契约采用 gRPC-Go + Protobuf，实际拆边界时引入                | 强类型、取消和 deadline 传播；只生成确有消费者的协议，不先给所有内部函数套 RPC                                     |
| 浏览器与 Node 通信 | 保留 HTTP/JSON、SSE、WebSocket；Node 内部合同继续现有 HTTP/SSE   | 不强制将 Yjs 或 Agent 流式边界改成 gRPC；公共 `/api` 与前端生成链继续有效                                          |
| 数据访问           | 继续 GORM/PostgreSQL；锁、队列及关键 SQL 显式表达                | 保留已有事务语义，不在拆服务同时改 ORM；新热点如需 pgx/sqlc，另以测量和具体查询评估，不全量双栈                    |
| 缓存/短期协调      | Redis                                                            | 不作为钱包、任务和授权的唯一持久权威；缓存包含租户/资源范围、版本、TTL 与失效策略                                  |
| 异步事件           | Kafka + Transactional Outbox + Inbox/业务幂等                    | 复用已有依赖；采用至少一次投递，Kafka 自身的幂等生产不等于外部数据库业务只执行一次                                 |
| 长任务             | PostgreSQL 工作记录 + Go worker，保留 lease / owner / epoch 围栏 | API 与长任务解耦，保留持久身份与恢复；不重新引入 Temporal、Redis 队列或第二套调度中心                              |
| 依赖注入           | 新服务手写构造函数及显式装配；存量 Wire 接线受控维护             | Wire 官方已于 2025-08-25 归档且说明不再维护；不为本次设计全量替换存量，也不作为新服务基础扩展                      |
| 配置与密钥         | 显式服务配置结构，继续 `GLOWLOOM_*`；部署注入密钥                | 启动校验各自必须依赖，按服务分配 DB/MQ/对象存储权限；不新增一套配置中心或记录真实凭据                              |
| 日志与观测         | 继续 zap、OpenTelemetry；经 OTLP 接 Collector                    | 贯通 trace、指标及结构化日志；按需接已有或选定的 Prometheus/Grafana 等后端，不同时搭两套观测平台                   |
| 部署与发现         | 继续 Compose / OCI，服务名 DNS 与显式地址配置                    | 先证明独立进程、健康与权限边界；没有容量或多集群证据前不默认上 Kubernetes、Consul/etcd、Service Mesh               |
| 质量门禁           | 现有 Go 格式、vet、lint、race、vuln + 合同和边界检查             | 工具不能完全验证 Google Go 的清晰性与设计质量，仍需要包职责、错误和并发评审                                        |

不叠加 LiteLLM、第二个供应商网关、全局事务协调器或统一“企业基础框架”。Execution 是本业务已有模型出站权威，不与网络入口 Gateway 混称。

### 7.5 Go 项目结构

建议继续使用现有 `backend/go.mod`，多个进程可来自一个 module。服务可以独立构建、发布和回退，并不要求每个服务一个仓库或 `go.mod`。只有明确出现跨仓库版本与依赖隔离需求时才考虑多 module。

下图是**目标布局示意，不是本次创建清单**；新增文件仅在对应能力落地时建立：

```text
backend/

    glowloom/                 # 现有入口，边界迁出前继续承载未拆职责
    gateway/                  # 对应独立入口获准后才增加
    identity/
    creation/
    media/
    execution/
  api/proto/glowloom/         # 新增 Go RPC 的唯一协议源，仅按领域分包
  internal/
    app/                      # 仅组合根、进程生命周期与装配
      identity/
      creation/
      media/
      execution/
    identity/                 # 以下沿用现有业务模块布局
      domain/
      application/
      adapter/
    workspace/
    canvas/
    script/
    bible/
    subject/
    prompt/
    media/
    mediatool/
    operation/
    catalog/
    billing/
    contract/gen/             # 仅实际需要的生成 RPC 类型，不放领域实体
    platform/                 # 配置、连接、遥测、任务技术机制

    schema.sql                # 仍是唯一完整结构，不拆服务 SQL
    data.sql                  # 仍是唯一公共种子
  tests/
    <业务模块>/               # 沿项目测试约定，不搬成 Java 式测试树
    contracts/                # 有真实协议测试时才创建
    boundaries/               # 服务依赖/权限测试
```

- 不新建 `services/<服务>/` 同时复制一遍现有模块，不创建空 `repository`、`service`、`model` 或 `manager` 层。
- `internal/app/<职责>` 继续装配端口和适配器，领域规则不得搬进组合根。现有文件与包名在实施中按真实责任核对，不因示意图批量移动。
- 每个服务只能导入其拥有的业务模块和技术平台；其他服务仅通过协议 adapter。跨服务 package import 由静态依赖门禁禁止。
- Go 的 `internal` 限制基于父目录树，并不会自动隔离这个 module 内的不同服务，不能把它误当作服务边界门禁。
- protobuf 仅在协议 adapter 中转换；不让领域类型带 GORM、Gin 或 Protobuf 依赖。
- 服务内多个角色可继续来自同一二进制；多套镜像可共享构建基础，但应有各自依赖闭包、配置和发布验证。

### 7.6 Google Go 规范的具体落点

| 规则                 | 在本项目中的落点                                                                                      | 检查方式                                 |
| -------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 清晰、简单、最少机制 | 按领域职责组织包，保留必要层，不为每个实体生成一套接口和空实现                                        | 设计评审与依赖图，不以目录数量验收       |
| 消费方定义小接口     | application 按用例需要声明端口；adapter 返回可直接使用的具体类型；只为真实边界或替换需求定义接口      | 禁止通用大 Repository、`Ixxx`、`Impl`    |
| 单向依赖             | `adapter → application → domain`；跨模块通过小端口并在 app 装配                                       | AST/import 门禁及编译                    |
| 明确错误链           | 仅增加语义时用 `%w` 包装，应用错误在边界映射 HTTP/gRPC 码；使用 `errors.Is/As` 判定，不比较文案       | 重复、冲突、拒绝、依赖超时场景测试       |
| Context 首参         | 从 `c.Request.Context()` 进入应用，传给 SQL/RPC；不把 `*gin.Context` 作为业务参数，不长期存储 Context | 代码评审、取消/超时测试                  |
| 受控并发             | 后台任务明确 owner、cancel、退出和 wait；队列与并发有界                                               | race、停机和泄漏检查                     |
| 命名与包职责         | 短而清晰的小写包名，避免 `utils/common` 和反复重复包名的 API；不复制 Java 全局分层                    | gofmt/goimports、lint 与人工评审         |
| 可测试               | 领域规则纯粹、构造注入；测试通过项目约定的 `backend/tests` 入口验证                                   | 单元测试、真实隔离 PostgreSQL 与协议测试 |

**请求生命周期与任务生命周期必须分开：** HTTP 取消应停止本次等待，但已经在事务中受理的持久任务由服务生命周期管理。任务使用带有持久授权、截止与幂等身份的工作记录，不能仅把请求 Context 换成 `context.Background()` 后裸起 goroutine。

### 7.7 API 与通信合同

**外部入口：** 同站代理继续转发 `/api` 到 Gateway，再由其路由到对应业务 HTTP adapter。Gateway 以路由转发为主，避免同时维护第二份公共 DTO。现有授权、Cookie、CSRF/Origin 和 SSE/WebSocket 合同逐项保持；若公共接口确需变更，应沿所属产品主链单独批准。

**内部同步：** Go 服务新增 RPC 仅按领域分包，目录、Go 包名和 gRPC 服务标识不带业务版本后缀；同一功能只保留一份当前合同，避免源码、生成物与调用方形成多套不一致路径。proto 为这类 RPC 的单一来源，使用固定版本的 `protoc`/Go 插件生成并核对差异。删除字段号不得复用，破坏性变化必须先评审兼容性与发布顺序，再同步更新服务端和全部消费方，不保留重复业务实现或双权威。已有 Node HTTP 合同按自身生成链维护，不再手写一份同名 RPC。

**调用规则：**

- 每次调用有显式 deadline，并传播剩余预算；gRPC 默认没有 deadline，不能依赖默认值。建立连接、单次调用、队列等待和长期流式连接分开限制。
- 读请求或明确幂等命令才允许有界重试；只由一层负责，退避加抖动，服从整体 deadline。超时不代表对端未写入。
- 有副作用命令携带稳定 `command_id`、资源范围、请求内容摘要及调用者/授权来源；同身份同内容返回原回执，同身份不同内容拒绝冲突。
- 未知回执先按原 ID 查询；没有供应商原请求幂等或确定未发送证据，不得重发收费提交。
- 应用错误区分未认证、无权限、不存在、状态冲突、额度不足、依赖不可用和超时；不可全部变成 HTTP 500 或 gRPC Internal。
- 不把 SSE/WebSocket 当作可靠任务事实库；重连以有序游标/版本和持久回执补齐，限制慢消费者并支持停机收束。

**同步依赖收敛：** Gateway 可依赖领域服务，Creation/Execution/Media 通过有目的的端口交接；禁止任意循环调用和逐资产串行 RPC。列表使用批量查询或有版本只读投影；写入授权与资金判断不能仅依赖可陈旧投影。

#### 7.7.1 Media 无状态规范化计算边界

`cmd/media` 承接原上传 WebM→H264 MP4 规范化计算，是可独立部署的 Media 计算切片，不取得资产发布权，也不代替 §7.9 的持久准入与排空协议。生产上传通过消费者 `UploadNormalizer` 的 gRPC adapter 调用；资产最终授权、审阅、对象路由、原子提交与未知回执核对继续由原 owner 执行。服务及依赖闭包不得引入业务组合根、GORM、数据库、Redis、Kafka 或对象存储驱动，不加载业务 `.env`。

- 协议唯一源为 `backend/api/proto/glowloom/media/normalization.proto`，生成到 `backend/internal/contract/gen/media/`；固定 protoc 35.1、protoc-gen-go v1.36.12、protoc-gen-go-grpc v1.6.1。调用 `Normalization.Normalize` 双向流，但严格先上传、半关闭，再下载；不接受路径、任意 URL、对象密钥或用户身份。
- 首帧只包含源大小、SHA-256、MIME；后续为每帧至多 256KiB 的字节块。源及产物各至多 500MiB，实收大小、摘要、magic、真实探测与完整解码均须一致。仅接收单 VP8/VP9 视频轨、无音轨的 WebM；产物为单 H264、无音轨的 MP4。时长不超过 60 秒、帧率不超过 60 FPS，边长不超过 8192、总像素不超过 4000 万；不能靠截断时间或字节数制造成功。
- 两端各自创建并拥有临时文件，不共享挂载或传递本机路径。接收器在短流、额外帧、摘要不符、取消及失败时清理；客户端即使收到全部字节，也必须等到最终 gRPC 成功状态才交给原上传流程。调用方输入仍由调用方关闭。没有持久写入命令、应用重试或本地转码回退。
- API 单次总预算 150 秒，原生计算上限 120 秒，服从上游更短 deadline。服务拒绝缺 deadline 或大于 180 秒的调用；全局有界在途名额覆盖接收、计算、发送全部阶段，不设置无界队列。身份/准入、格式/大小、过载、取消/超时、依赖不可用分别映射明确 gRPC 状态，诊断不泄露 FFmpeg 输出或本机路径。
- 每次调用使用独立 API→Media 令牌，32～4096 字节可见 ASCII 且无空白，三处配置与协议构造一致校验。非 local 两端必须完整 TLS 1.3 mTLS，仍须令牌；local 明文只适用于隔离私有网络。仅传递服务自身认证及 W3C trace 关联，不转发任意调用者元数据、用户认证或 baggage；服务完成日志关联 trace ID、方法、状态和时长，不记录媒体内容或令牌。
- 运行时仅私有 RPC/健康监听与所需原生工具，启动核验依赖和可写临时盘，停机先撤 readiness，再有界排空，超时取消 RPC/子进程并等待退出。Compose 默认并发 2、CPU 2、内存 3GiB、只读根、有界 2100MiB 的不可执行临时盘，端口不发布到宿主；提高并发须重新核算临时盘、原生内存与实例容量。Media 不等待业务基础设施，其他 worker/relay 不因该切片增加启动依赖。

无地址且无令牌的非 Compose API 明确禁用 WebM 规范化，其他上传类型不变；配置一半则启动失败，不静默退回单体。此约定不代表独立数据角色、跨域授权屏障、分布式提交、完整采集器观测或四个业务域已完成。

### 7.8 数据所有权与数据库隔离

建议先**同 PostgreSQL 集群、按服务 schema/受限角色隔离**，不立即多实例。Execution 可以在本服务拥有的 operation/catalog/billing 数据之间使用单事务；Creation 可在其项目/文档领域内维持事务。

| 数据类别                               | 目标所有者           | 拆分要求                                                                       |
| -------------------------------------- | -------------------- | ------------------------------------------------------------------------------ |
| 身份、会话、认证安全                   | Identity             | 外部服务不能 JOIN 身份表或自行更新会话；账号删除通过权威撤权与生命周期合同传播 |
| 项目、团队、文档、剧本、主体及编辑草稿 | Creation             | 将跨服务身份/资产引用改为显式 ID/版本及验证合同，不保留跨所有者级联删除        |
| 资产、对象位置、上传和媒体工具工作     | Media                | 使用受控资产发布回执及引用版本，不把私有对象 URL 当授权依据                    |
| 报价、执行、目录、钱包与账本           | Execution            | operation 与 billing 本地一致；外部服务不能写 ledger 或修改执行状态            |
| Agent 执行状态                         | 既有 Agent           | 保持受限 `agent` schema；Go 业务回执与 Agent 恢复状态不混存为两个权威          |
| Outbox、Inbox、任务记录                | 各写入所属业务的服务 | 技术机制可复用，记录必须有明确归属、权限与唯一性范围                           |

具体规则：

1. 当前 `infra.outbox`、`infra.processed_event`、`infra.task_work` 等共享记录是演进对象，**不能给所有新服务继续分配全表写入权限并宣称数据已独立**。物理拆分时在唯一 `schema.sql` 内为所属服务声明自有记录/约束，或证明等效的数据库强制隔离；未满足前仍属过渡组合部署。
2. 拆服务前清点所有跨所有者 JOIN、外键、触发器、事务与删除路径。保留同一服务内的外键；跨服务引用改由权威 API、发布回执、版本校验和对账维护，不能简单删除约束而不补语义。
3. 业务更新与所属 Outbox/任务入队使用同一本地事务。Inbox 去重与业务效果同事务提交，成功后再确认消费；幂等保留期须覆盖业务与重放窗口。
4. 事件至少含 `event_id`、类型/版本、聚合 ID、聚合版本、发生时间、资源范围和 trace 关联。分区键按聚合选取，只承诺所需范围的顺序；不假定跨 topic/分区全局有序。
5. 消费者处理重复、乱序、版本缺口、毒消息与 DLQ；授权撤销和资金不以“稍后投递成功”代替安全合同。过大事件只携带受控引用，不复制凭据、整段私有文档或二进制。
6. Redis、分析投影和前端缓存不是权威；投影必须可定位来源版本、显示延迟并能受控重建。
7. 新库只从 `schema.sql` 初始化。已有库由管理员基于实际结构与该文件的 diff 离线核验、备份及受控变更，验证后才启动服务；禁止重放空库 SQL 或由应用执行 DDL。

[Schema 来源测试](../../../backend/tests/db/schema_source_test.go)约束 SQL 文件来源，但不自动证明结构语义、角色隔离、跨库恢复或无动态 DDL；这些需要另外的测试和评审。

### 7.9 关键业务链与不能直接拆开的事务

**生成确认与结算：**

```text
Creation 给出当前可用的项目授权、输入版本与采用上下文
    → Execution 生成冻结报价及输入快照
    → 用户确认稳定 quote_id / command_id
    → Execution 本地事务：验证报价 + 预占额度 + 写 operation + 入队 + Outbox
    → worker 以原身份领取、准备派发、提交或查询原供应商请求
    → Media 幂等归档并返回精确资产发布回执
    → Execution 按真实费用证据本地更新账务与操作状态
    → Creation 幂等采用资产版本；前端按回执和事件刷新
```

该图表达目标交接，不把现有项目锁和草稿事务自动替换成一次“授权查询”。必须满足：

- Creation 的输入/草稿版本及授权必须冻结为可验证的交接事实；Execution 不再在确认事务里 JOIN Creation 的表。校验与使用之间的撤权、项目关闭和输入变化须有明确围栏。
- 资金预占、operation 受理、任务入队和事件写入继续在 Execution 本地事务内原子成立；结算与操作资金状态亦如此。
- 供应商提交可能已发生而回执丢失时，保留原供应商请求身份及未知责任，不创建新请求；有真实成本也不能因下游归档失败而虚构零费用。
- Media 归档和 Creation 采用各自有持久命令/结果回执。未归档、不可读、未采用、未审阅与完成分别表达，不能因供应商返回成功就宣告作品交付成功。
- 资产发布与资金结算跨服务时以显式状态和恢复协调，不假装一个 PostgreSQL 事务覆盖三者。若既有产品不变量要求共同原子提交，相关职责必须继续组合部署，直到等价合同被接受和验证。

**项目关闭/删除：** Creation 必须先以持久状态关闭新准入并推进生命周期版本，再可靠通知相关执行和媒体所有者建立禁止旧版本写入的围栏；收集在途任务、费用责任和清理回执后才能完成删除。迟到命令、重复关闭、消费者中断和关闭中重启都必须可恢复。

关闭过程中不得向用户报告“已全部删除”却仍允许新收费/发布。同步返回、等待状态、在途动作能否继续及取消责任须沿项目主链明确；**仅靠一条异步 ProjectDeleted 事件或短 TTL 缓存不足以替代当前项目锁语义**。不能证明等价时，不拆 Creation 与 Execution 的该条事务边界。

**项目创建、复制与媒体清除：** 当前项目创建把初始画布、预算/钱包一并准备，复制及素材清除也检查多个领域引用。拆分后必须由各 owner 幂等准备并交回持久回执，只有所需权威均确认后才能向用户报告“创建可用”或“清除完成”；失败、超时、半成品可见性与补偿沿项目/资产主链明确。不得把超时当作对象不存在，也不得漏查他域引用就物理删除仍在使用的素材。若接受新的 preparing 状态，应明确作为产品语义变更确认，而非偷偷替换原原子创建。

主体媒体绑定、批量采用等同理：先明确权威、不可变输入和命令回执，再设计跨服务协调；不用通用 Saga 框架替代业务状态与补偿规则。

### 7.10 身份、授权与跨服务安全

- 延续现有登录/会话体系，不因微服务直接更换 Keycloak 或将所有会话改成长期 JWT。
- Gateway 只做入口身份检查和明显非法请求拒绝；Creation/Media/Execution 必须各自校验服务身份、用户/团队/项目范围与当前操作权限，不能信任可伪造的 `X-User-ID`。
- 生产跨进程使用 TLS 及受限服务身份/短期凭证；选用 mTLS 还是部署平台身份由环境决定，不在文档记录密钥。内部端口不发布为匿名公共 API。
- 权限授予与撤销涉及权威版本、截止和明确失效策略。高风险写入无法确认授权时拒绝，不以陈旧缓存继续收费、删除或采用；账号“即时软删除并撤权”的既有规则不能被降级为仅异步最终生效。
- 一次远程 `CheckActive` 后继续本地写入，并不等价于当前身份/成员锁。跨服务准入与撤权须在共同权威上形成可串行化的顺序，并在撤权成功回执前确认所需写入围栏与在途责任；否则仍保留相关事务组合部署。短期 JWT、异步失效事件和 fail-closed 声明本身都不能消除检查后写入的竞态。
- Identity 不可用时是否允许已验证的低风险读取，由会话与权限合同决定；不笼统规定所有请求依赖一次远程认证，也不默认失效后仍开放。
- 服务分别获得 DB role、Kafka topic/group ACL、对象存储前缀和供应商出口权限；Gateway 无业务 DB，Creation 无供应商密钥，Agent 无资金账本写权限。
- 当前 local/loopback 保护变为服务间网络准入前，需要专项威胁评审、监听/Origin/代理头配置及鉴权测试；不能简单删除限制后对外监听。

### 7.11 运行、恢复与可观测性

- **角色隔离：** 先按现有 API/worker/relay 拆容器和资源；`all` 可用于受控本地场景，但多副本任务正确性仍由数据库 claim/fence 和幂等保证，不由“只启动一份”保证。
- **任务恢复：** 保留 `owner + lease + epoch` 等围栏，业务发布在验证有效 owner 的事务窗口执行；过期 worker 即使恢复也不得写入。数据库围栏不能撤回已经发往供应商的请求，外部提交仍依赖原请求身份和恢复合同。
- **健康：** liveness 只看进程是否可继续；readiness 核对本角色必要依赖。下游降级不应触发所有服务相互健康等待与循环重启。
- **优雅停机：** 停新流量/claim，给在途调用与流式连接有界收束，等待已拥有 goroutine，安全交还或等待租约，最后刷新观测并关闭连接。停机期限由真实任务和部署窗口核定。
- **过载：** 每个队列、租户和供应商有并发、速率与等待上限，重试不突破总体预算；CPU/内存型媒体任务与网络型供应商任务分别配置资源。
- **发现与发布：** Compose 服务名提供发现，显式服务地址注入。上线前验证新旧依赖的契约可配合；每个时点只有一个业务写入 owner，不以长期双写实现切换。
- **回退：** 代码回退须确认与现有数据/事件版本兼容；数据所有权转移后不能直接启动旧进程恢复写入。所有权切换需要停写/排空、围栏和审计，可由管理员受控转交，禁止两个 owner 同时活跃。
- **观测：** HTTP/RPC/Kafka/worker 传播 trace 关联，日志记录 service/role/version、原命令/operation 与资源范围。用户/项目/operation 等高基数 ID 留在受控日志或 trace，不作为无界指标标签。
- **最小指标：** 请求错误与延迟、RPC deadline、队列深度与最长等待、租约过期、Outbox lag、Inbox 重复/DLQ、供应商未知回执、资金预占超龄、结算差异、资产发布与采用失败。指标阈值根据基线另定。

### 7.14 首个独立入口切片的技术合同

- 独立入口为 `backend/cmd/gateway`，配置与生命周期在 `internal/app/gateway`，协议转发在 `internal/gateway`；不导入原 `internal/app` 全量组合根，不创建数据库、Redis、Kafka 或对象存储连接。仅有入口职责，不预建领域/仓储空层。
- 本地 Compose 的公开链路为 frontend → gateway:8080 → backend:18080；宿主 1123 仅发布 Gateway，业务后端不发布宿主端口。现有业务后端继续 local、loopback API 与 socat 内网桥接；Agent 的 `/internal` 调用直接使用业务后端，Gateway 不开放该路径。此合同不是跨主机或生产放行。
- Gateway 只转发 `/api` 及其子路径；保留方法、有效路径/查询原始编码、请求体、Cookie、Authorization、Origin、Host、幂等身份与上游状态/响应，不替代业务鉴权。不调用路径清理后把含 `..`、重复分隔符或非法查询的请求改送其他端点。
- 使用标准库 ReverseProxy 的 Rewrite；不信任客户端 Forwarded、X-Forwarded-*、X-Real-IP 或伪造身份头，不自行声明用户/项目权威。普通请求不设置总体写超时截断上传/流；连接和响应头等待有界。SSE 立即刷新、WebSocket 保持原升级协议。
- 无应用级自动重试。非安全方法使用不复用连接的 Transport，避免标准 Transport 因 `Idempotency-Key` 在复用连接故障时自动重放未知写入；原回执查询与恢复仍归业务 owner。此折中可能增加连接开销，不能无证据宣称容量改善。
- `/healthz` 是 Gateway 进程存活，`/readyz` 有界探测业务后端就绪，不回显下游诊断或地址。网关自身 4xx/502/504 沿用公共 Problem 形状及 request ID、no-store，不改写后端已返回的业务错误。
- SIGTERM 停止接入，取消请求生命期使 SSE/WebSocket 一并关闭，等待所拥有的服务协程和代理 handler 后关闭空闲连接；Docker 宽限期覆盖进程收束窗口。Compose 声明与纯协议测试不等于容器部署、真实登录或供应商接受。

### 7.15 API、任务与中继的运行角色隔离合同

这是运行隔离，不是业务域独立：

| Compose 服务 | 业务命令                               | 单角色健康端口                 | 所有权说明                                       |
| ------------ | -------------------------------------- | ------------------------------ | ------------------------------------------------ |
| backend      | `glowloom --role=api`                  | 18080，经内网桥接 loopback API | 仍承载现有全部业务 HTTP 适配器及 API 自有维护    |
| worker       | `glowloom --role=worker --queues=auto` | 8081                           | 持久任务仍在原队列与数据库中，租约/幂等身份不变  |
| relay        | `glowloom --role=relay`                | 8082                           | 原 Outbox/Inbox 与 Kafka consumer group 保持不变 |

- 三者共用业务镜像、配置和数据库角色；编译依赖也未隔离，不能据此声称四个数据 owner、最小权限或故障完全独立。业务表/基础设施故障仍可能同时影响多个角色。
- 各自健康探针只检查本角色；不将 API/worker/relay 互设为启动健康依赖。Gateway 只调用 API；完整 Compose 启动用 `--wait` 检查全部角色，API 就绪不代表异步任务已经完成。
- `auto` 与原 `--role=all` 的选择相同：默认 flow、media，配置凭据私钥后加入 provider；agent.codex 仍须显式选择。保留独立 worker 空参数默认 flow 与显式队列校验。`all` 仅保留为明确选择的组合运行方式，不再是镜像或 Compose 默认。
- 选中的任务队列先放在同一 worker，避免未经验证改变本机临时产物/原生工具交接。只有 API 开启 loopback 的公开业务桥；worker/relay 不开该桥、不发布宿主端口。开发 overlay 对三个角色应用同一源码重建规则。

实际目录按职责组织，不为三个角色复制三套空模块：

```text
backend/
  cmd/gateway/main.go       # 独立入口，不依赖业务组合根
  cmd/glowloom/main.go      # 业务角色/管理员命令的薄入口
  internal/app/            # 角色生命周期与组合入口
    queues.go              # 队列能力选择与规范化，all/worker 共用
    gateway/               # Gateway 自有配置与生命周期
  internal/gateway/        # HTTP 转发协议
  internal/<业务模块>/     # 已有 domain/application/adapter，逐域核对依赖
  internal/platform/       # 具体技术能力，不承接业务规则
  tests/app/               # 队列兼容与运行合同
  tests/deployment/        # 普通/开发部署角色接线门禁
```

`cmd`/`internal` 取自 Go 官方服务端惯例；Google Go 规范落实为包内聚、小接口、显式注入、错误链和可收束并发，而非机械增加 `services/`、多 module 或 Java 式全局分层。新增接线留在真实职责包；本阶段不宣称存量模块已经全部消除跨域依赖。

### 7.16 Media 两个候选用例的事务阻塞事实

限定核对项目本地上传与视频深度处理，不据此外推整个 Media 域：

- [上传提交](../../../backend/internal/media/adapter/postgres/upload.go)在最终事务重新校验操作者、锁定项目，再写资产/派生、存储接受、幂等回执和审计；未知提交后的对象清理也受同一项目锁约束。
- [ScopeAccess 装配](../../../backend/internal/app/media/media_scope_access.go)把同一事务交给 Identity 会话/活动校验和 Creation 项目内容授权；不是可以直接替换成普通 HTTP 预检的独立授权端口。
- [深度命令](../../../backend/internal/mediatool/adapter/postgres/depth_commands.go)与[控制权威](../../../backend/internal/mediatool/adapter/postgres/depth_control_authority.go)还涉及 Canvas 来源、任务/事件、控制人、复核和 Media 发布；原生处理停止事实不等于撤权后的业务发布授权。

物理拆分须先证明等价的持久提交授权栅栏：关闭/撤权关闭新准入，已准入提交及未知结果得到排空/核实后才能确认完成，旧授权不可继续发布。该协议仍待具体设计与并发测试，不在此直接实现或放行；RPC 检查一次、JWT/TTL 缓存和异步失效不等价。原同库事务在门禁通过前保留。

### 7.17 项目上传的 Creation owner 端口合同

项目上传将业务表查询收回 owner，不改变事务边界、HTTP DTO 或现有权限语义：

- Media application 定义消费方小接口 [`UploadProjectAccess`](../../../backend/internal/media/application/upload_project_access.go)，只表达 `AuthorizeUploadProject` 与 `AwaitUploadProjectCommit` 两种不同责任；不导入 Creation 领域类型，也不把所有 Media ScopeAccess 实现强迫扩成通用接口。
- [`Creation owner`](../../../backend/internal/workspace/adapter/postgres/upload_access.go)在调用方真实事务内复用项目内容授权：身份/Scope 后取项目 UPDATE 锁、锁后检查 active，再读上传所需 aspect。沿用旧锁顺序与写入准入，不经包含封面/模型检查的完整项目快照扩展失败条件。
- [`组合适配器`](../../../backend/internal/app/media/upload_project_access.go)显式使用同一事务：请求端保留 CheckSession，worker 端保留 CheckActive；错误沿既有映射传播。Media 缺少该能力、owner 缺少真实事务或项目事实时失败关闭，不回退为 Media 自行查询 Creation 表。
- 未知提交核对不等于新的上传授权。owner 仅用项目 UPDATE 锁等待先前提交结果，不要求当前会话有效或项目 active，也不滤掉 archived/软删项目；随后 Media 只查询自己的资产事实。若无法锁定或项目不存在，返回未知错误，不能把“查不到项目”解释成允许删除对象。
- 原上传流水线仍在最终事务重新授权；准入后、对象创建后撤权/关闭都不能靠旧 Principal 获得发布权。提交响应丢失时，独立、有界的结果核对上下文不随原请求取消；资产已经存在或结果未明时保留对象，不重发写命令。

实际文件仍在 `internal/media/{application,adapter/postgres}`、`internal/workspace/adapter/postgres` 与 `internal/app/media`；测试在 `tests/{media,workspace,boundaries}`。接口留给消费方、SQL 留给数据 owner、跨模块映射留给组合适配器，符合 Google Go 的职责内聚与显式依赖，不增加空服务目录、远端伪事务或公共 utils。

这只是本地 owner 责任收敛：Media 上传路径不再包含跨域表查询，但组合进程、事务连接、数据库角色与 Identity/Creation 锁仍共享。并未实现 §7.16 的分布式持久授权屏障，也不证明整个 Media 域已独立；正式物理拆分仍受 §8.1 门禁约束。

### 7.18 Creation 原文提取的独立计算服务合同

- `cmd/creation` 只承载 TXT/DOCX → 富文本、编码、来源映射和警告的真实提取，不导入旧全量组合根、Media application、Identity、任务、数据库、Redis 或对象存储。纯计算留在 `internal/creation/document`，可复用 Creation 自有 `script/domain`；旧提取适配器仅做类型/错误映射，不保留两份解析实现。HTML 编辑器转换仍是原本地领域适配能力，不属于本切片。
- 唯一内部协议源为 `api/proto/glowloom/creation/extraction.proto`，生成包 `internal/contract/gen/creation`，服务 `glowloom.creation.Extraction`；统一领域命名，不添加数字版本目录、包或服务名。双向流先接收唯一的 size/SHA/MIME 头与字节，half-close 后才返回完整结果 JSON 字节流；不接受路径、URL、对象 key、用户凭据或持久发布命令。
- 源文件上限 20MiB，单帧 256KiB；真实 size/hash 验证后才解析。富文本沿既有闭合 schema（8MiB、150 万 Unicode scalar 等限制）校验，结果 JSON 上限 32MiB，消费方验最终 RPC OK 后才解码与再校验，不接受截断成功、替代文本或隐式重试。RPC 全程 60 秒预算且不得无 deadline，取消沿解析传递，源文件仍由调用方关闭；全局并发槽覆盖接收、解析、响应，不能靠每连接 stream 上限替代全局有界量。
- 使用独立专用服务令牌（32～4096 可见 ASCII、无空白），非 local 必须双向 TLS1.3；仅传 W3C traceparent/tracestate，不能继承任意用户身份 metadata。无本地回退。独立配置只读 Creation 字段，不加载业务 `.env`；健康与停止各自有界，不泄漏原文、临时文件名或认证材料。
- 生产文档导入 worker 注入远端 `SourceExtractor`；文件读取、任务认领、顺序/幂等、最终发布授权和未知结果恢复保持原 owner。远端返回内容只代表提取事实，不是发布权，失败/取消不得继续持久发布。无新表、无 DDL。本合同不宣称整个 Creation 域或其数据已经迁出。

## 8. 实施与验收

### 8.1 允许物理拆分的门禁

不以新目录、容器启动或 HTTP 200 作为服务完成证明。每个候选服务至少满足：

| 门禁             | 必须证明的条件                                                                    | 对应需求接受条件 |
| ---------------- | --------------------------------------------------------------------------------- | ---------------- |
| G-GOMS-01 所有权 | 拥有的模块/表/任务/事件/密钥可枚举；没有越权 JOIN、外键、应用导入或隐式全库写权限 | AC-GOMS-01/02    |
| G-GOMS-02 事务   | 原本同事务的不变量有本地保留或已接受的等价交接协议，未知回执有查询与恢复路径      | AC-GOMS-03       |
| G-GOMS-03 合同   | 公共生成客户端一致，内部协议兼容；错误、deadline、幂等及流式重连经过验证          | AC-GOMS-04       |
| G-GOMS-04 故障   | 重试、崩溃、重复/乱序事件、lease 过期、关闭及撤权不造成越权、重复收费或丢失责任   | AC-GOMS-05       |
| G-GOMS-05 运行   | 独立构建、配置、角色权限、健康、观测、停机和受控回退都有对应验证                  | AC-GOMS-05       |

### 8.2 最小技术场景

| ID           | 前置与动作                                            | 可观察接受结果                                                          |
| ------------ | ----------------------------------------------------- | ----------------------------------------------------------------------- |
| CASE-GOMS-01 | 同一确认命令并发重放，包含回执丢失后重试              | 返回同一 operation/预占，不多建任务、不重复收费；同 ID 异内容冲突       |
| CASE-GOMS-02 | operation 写入后、事件发布前杀死进程                  | 业务与 Outbox 同在或同无；恢复后能投递且 Inbox/业务去重                 |
| CASE-GOMS-03 | 供应商已接收但响应丢失，重建 worker                   | 保留未知责任并查询原请求，不再提交一个新收费请求                        |
| CASE-GOMS-04 | 原 worker 租约过期，新 owner 接管，原 worker 恢复写入 | 旧 epoch 的业务发布被拒绝，最终结果与结算保持一份                       |
| CASE-GOMS-05 | 归档延迟或失败、供应商已产生费用                      | 成本事实仍保留；未发布资产不被报告成品，恢复不重复归档/采用             |
| CASE-GOMS-06 | 项目关闭同时存在确认、派发、媒体发布和迟到消息        | 关闭围栏生效，状态真实反映在途责任；完成删除后无新有效写入              |
| CASE-GOMS-07 | 账号软删除/撤权后复用缓存、旧令牌与内部请求           | 高风险命令及应撤销访问按原安全合同拒绝，不依赖异步投递最终成功          |
| CASE-GOMS-08 | 用服务 A 的角色访问 B 的业务表/队列，或伪造用户头     | 数据库/消息权限与服务端鉴权均拒绝，不能绕过网关获得业务权限             |
| CASE-GOMS-09 | RPC deadline、依赖不可用与流式断开/重连               | 重试有界，任务不因断开重复启动，状态可查询且流式可补齐                  |
| CASE-GOMS-10 | API/worker/relay 独立启动和收束                       | 无相互健康依赖死锁、无失控 goroutine，持久任务可恢复                    |
| CASE-GOMS-11 | 项目创建/复制中断，或清除时他域仍持有素材引用         | 不报告半成品可用；不误删被引用对象，重试沿原命令恢复                    |
| CASE-GOMS-12 | 普通服务启动并执行维护任务，数据库角色禁止 DDL        | 任务不尝试创建/挂接/删除分区等 DDL，业务角色无 DDL 权限且必要业务可运行 |

后续实现遵循 Red → Green → Refactor，使用隔离 PostgreSQL、受控对象存储/供应商与真实协议验证。修改 Go 时执行适用的格式、vet、lint、race、govulncheck 及生成/边界检查；涉及结构时额外执行 schema 来源、角色与结构语义测试。
