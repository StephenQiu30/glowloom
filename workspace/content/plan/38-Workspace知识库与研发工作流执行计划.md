# Workspace 知识库与研发工作流执行计划

唯一来源：[PRD29](../prd/29-Workspace知识库与研发工作流.md)。技术合同沿其来源[设计43](../design/43-Workspace知识库与研发工作流服务设计.md)展开；原始诉求不直接越过 PRD 形成实现任务。实施状态、负责人、优先级、排期和阻塞只在 [BACKLOG](../../../BACKLOG.md#workspace-20261114) 维护。

SRC-WS-08已授权本地实施，执行状态与证据只在根BACKLOG维护。SRC-WS-09暂不启用真实TTS：T-WS-13～15不执行供应商接入／收费调用，T-WS-14仅实现纯缓存决策与未知回执合同，不建立空供应商。CASE-WS-12的仅文档边界适用于SRC-WS-04～07历史交付；本轮改为核验SRC-WS-08与09的实施授权和禁止项。

## 1. 目标、约束与执行规则

按SRC-WS-07已确认技术路线交付同仓独立Workspace：Markdown／Git、Next App Router／React／TypeScript strict、Tailwind／shadcn／Geist／Neutral、Node24／pnpm、Pagefind、Mermaid、export静态包与standalone在线包、PostgreSQL独立schema和原生音频／cue播放器；TTS供应商仍待明确。按“无损迁移与静态知识 → Skill／流程定义 → 静态讲读 → 在线协作与执行 → 授权 TTS → 联合接受”推进。静态讲读仅依赖静态内容管线，不必等待在线运行引擎。

1. 每项任务开始前确认当时的 Git 状态和文件责任；只修改明确允许的文件。当前脏工作区不作为覆盖、批量暂存、清理或重置的理由。需要独立分支／工作树时按届时授权创建。
2. 一项任务先固定输入与接受断言，再实现最小可用路径，运行对应检查，审阅差异后交接。失败照实记录；不因后续任务需要而跳过门禁。
3. 文档正文、工程契约、Skill 定义、流程定义和运行记录各保留唯一权威。任务包引用修订；页面和搜索不得维护另一套可写正文。
4. 提案落地、Git 提交、合并、静态产物发布、业务部署和产品接受分别留回执。任务授权不能自动延伸为这些动作的全部授权。
5. 代码、文档、Skill、流程或权限变化时，重新计算受影响输入指纹，旧检查不能直接接受新版本。
6. 执行日志、截图、测试报告和音频留在受控产物目录／存储，只在 Plan 或 BACKLOG 引用证据位置；不把临时材料批量迁入知识正文。

### 3.3 已确认的双构建与部署合同

完整技术边界唯一维护于设计43 §7.6.1；本节确定实施文件与验证责任，不维护另一套框架选型。

| 项目       | 静态构建                                                                      | 在线构建                                                                            |
| ---------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 脚本       | `build:static`                                                                | `build:online`                                                                      |
| 来源入口   | 共用`src/app/`阅读路由、组件和允许知识快照                                    | 共用阅读路由加`src/online/app/`、`src/server/`                                      |
| 生成工程   | `.build/static/`，独立配置、标准app入口及Next缓存                             | `.build/online/`，独立配置、标准app入口及Next缓存                                   |
| Next输出   | `output: 'export'`                                                            | `output: 'standalone'`                                                              |
| 交付目录   | `dist/static/<release_id>/`完整静态站                                         | `dist/online/<release_id>/`完整运行包                                               |
| 打包重点   | 页面、Pagefind、SVG、raw、manifest、字体、允许的音频／cue；排除在线入口和依赖 | 启动器／追踪依赖、`.next/static`、必要public、受控只读知识／索引快照及OnlineRelease |
| 部署要求   | 纯HTTP托管；不挂仓库、凭据，不运行Node                                        | Node24、PG受限角色、运行配置；按能力接执行桥和外部服务                              |
| 镜像与变更 | 可选`glowloom/workspace:static-<release_id>`，整包原子切换                    | `glowloom/workspace:online-<release_id>`，兼容schema后独立升级／回退                |

T-WS-02在`workspace/scripts/`建立入口准备／配置／打包职责，使用显式清单组装标准Next工程；模式输入输出互不覆盖，派生目录忽略且不可手工维护。T-WS-04证明静态产物无在线依赖；T-WS-09证明online实际完整打包，public不承载未保护私有知识；T-WS-16验证交替构建与两版独立发布／回退。

两种构建不读取在线生产凭据，不连接PG、业务API、主机或TTS；构建时Node工具不等于静态部署需要Node。生产配置仅在线运行时注入，私有快照放受控目录而非公开public。Pagefind均从同版允许范围预渲染HTML生成；提案／工作树预览不进入共享搜索索引。构建产物必须在无源码工作区的环境启动或托管后验收，不能借开发机文件补漏包。

### 3.4 实施入口与复核命令

实际文件以工程为准：解析与链接在`src/content/parse.ts`、`catalog.ts`，上下文／流程在`src/workflows/`；持久存储在`src/server/store.ts`，执行桥在`src/server/bridge/`，Codex在`src/server/executors/codex.ts`。命令均从`workspace/`执行：

```bash
pnpm install --frozen-lockfile
pnpm test
pnpm typecheck
pnpm lint
pnpm check:content
pnpm build:static
pnpm build:online
```

DB测试必须显式提供名称以`glowloom_workspace_test_`开头的隔离库，使用根schema初始化、受限角色运行；未配置的skip不算通过。静态与在线浏览器用例分别检查`tests/browser/static.spec.ts`、`narration.spec.ts`、`online.spec.ts`。朗读浏览器使用明确标记的静音PCM fixture，只验证原生媒体、定位和交互；Codex协议fixture不代替真实主机原句柄恢复。

选版使用`pnpm release:select static|online <release-id>`，只接受完整校验的对应模式产物；无远程部署动作。纯静态Nginx与无源码standalone运行分别验证后才能记录CASE-WS-18。构建不继承运行时密钥，公开范围、交替模式、源变更拒绝及资产完整性由对应测试和打包检查门禁覆盖。

## 4. 分项执行任务

### T-WS-01｜建立当前基线并核对已确认决策

**依赖／责任：** G0，知识维护者与工程维护者；对应AC-WS-01～02、10～11。

**输入与产出：** 当前Git、设计43 DEC-WS-01～07 → 完整迁移映射、保护清单、决策记录、任务及性能基线。清单报告放受控产物；长期路径和选型结论更新所属规范。

1. 重扫受跟踪及未跟踪知识文件、附件、CSV、入链出链、显式／自动锚点、忽略项、dirty与staged内容；逐项确定迁移、保留或排除及理由。不搬本机Obsidian配置和执行日志。
2. 记录旧路径→文档ID→目标路径、原始摘要及允许路径改写；对根规则、业务SQL、生成契约、个人配置和已有并行修改建立精确保护集。
3. 按已确认框架及双构建核对版本／许可，明确静态范围／入口、首个主机接口和迁移窗口。在线身份／PG参数可延期到G4，但不得提前显示相应能力可用；端口不占用现有业务端口。
4. 用真实全量知识和固定问题集记录定位／审阅／交接基线，确定目标设备、托管方式和资源预算。不能从演示视频推定供应商或自动滚动实现。

**验证与出口：** 人工双向核对文件清单和Git差异；引入故意重名ID、遗漏附件和基线变化，均应阻止切换。CASE-WS-01、12、13的前置齐备；实施项未决不能以“待定”进入有副作用步骤。

### T-WS-02｜打通全量内容解析与构建检查

**依赖／责任：** 01；内容管线维护者。文件：`workspace/src/content/`、`catalog.json`、`scripts/`、包配置及`tests/content/`。

**输入与产出：** 当前docs清单与根引用允许集 → ContentSnapshot。候选实现可以只读旧docs验证；不得复制两份正文或支持长期双写。

1. 按已确认Next App Router／Node24／pnpm建立独立工程最小配置，落实§3.3的暂存入口、独立配置及忽略输出；先用真实文档样本验证解析器，再扩大到全部有效知识。锁定运行时及依赖版本，不增设空的模型引擎服务。
2. 支持GFM、表格、代码、显式HTML锚点、中文重复标题、相对链接和CSV。净化有限HTML，禁止脚本和任意MDX执行；根文件通过明确允许集引用。
3. 从正文显式唯一来源声明提取主链；一般引用单独建边。catalog只补稳定ID／路径／可见性／别名，不全库改frontmatter或另存手写标题。
4. 检查文件、锚点、主链和版本；问题指向具体文件／锚点。不可达外链区分受限／外部，不能编造本地正文。

**拟验证：** `tests/content/snapshot.test.ts`断言全量清单一致、dirty影响摘要；`links.test.ts`覆盖根引用、CSV、显式锚点及重复中文标题；`sanitize.test.ts`证明脚本不能执行；`source-chain.test.ts`证明普通链接不被误判为唯一来源。运行§6内容检查和对应单元测试。

**出口：** 全量内容可生成稳定ContentSnapshot，错误阻止构建且指向来源；CASE-WS-01、04、13解析部分满足。

### T-WS-03｜原子迁移与最小知识阅读器

**依赖／责任：** 02；知识及阅读器维护者。文件：`workspace/content/`、阅读路由／布局、根及模块规范中的相关路径、文档导航，以及实际引用docs的脚本／CI／忽略规则。

1. 先在候选变更验证目录、正文、页内目录、原文和来源版本可读取目标路径；路由按稳定文档ID／别名定位，不以标题变化制造第二份文章。
2. 重新核对01基线并停止或协调冲突编辑；按一对一映射保留名称、编号、语义正文、CSV和有效附件，使用Git可识别的移动。只改必要相对路径，逐项解释摘要差异。
3. 同次修改根入口、模块规则、各级导航及所有实际入链；对Git历史路径、外部URL和代码中的同名docs逐条判断，禁止全仓字符串盲替换。保留根规范、SQL与契约原位。
4. 迁移后全量双向核对并确认旧docs无第二可写正文；旧站点URL的别名／映射由托管合同处理，不留文件系统双写桥。切换前发现并行变化须重放并复核，不能覆盖。

**拟验证：** `tests/content/migration.test.ts`按当前清单断言唯一去向、附件完整、语义正文仅批准的链接改写；`tests/browser/reader.spec.ts`核对正文、主链、原文、中文深链刷新和未知页面404。迁移差异检查需同时记录原始字节摘要和批准变换后的比对，不用Git rename百分比代替无损证明。

**出口：** CASE-WS-01、04迁移部分通过，当前内容唯一；未授权业务改动为零。阅读器和入口未齐备不能切换主分支知识目录。

### T-WS-04｜补齐搜索、图表、静态产物与独立托管

**依赖／责任：** 03；静态管线和阅读体验维护者。文件：搜索／关系视图、预渲染脚本、构建入口、`tests/static/`及`tests/browser/static.spec.ts`。

1. 对允许范围先过滤再解析／索引／导出raw；生成目录、全文搜索、来源关系和Mermaid SVG及文字替代。外部设计链接保持外部属性，图表错误阻止发布候选。

## 6. 检查命令与证据口径

以下为实施检查合同；真实脚本以`workspace/package.json`为准。结果和未覆盖项只在BACKLOG维护，不把未运行命令标成通过。

| 场合               | 未来命令（仓库根执行）                                                                                                | 必须验证的内容                                                                |
| ------------------ | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 类型、代码与格式   | `pnpm -C workspace exec tsc --noEmit`；`pnpm -C workspace exec eslint .`；`pnpm -C workspace exec prettier --check .` | 当前所选工程基线；不能替代功能接受                                            |
| 内容清单和引用     | `pnpm -C workspace check:content`                                                                                     | 全量清单、ID、主链、链接、锚点、范围与指纹                                    |
| 静态产物           | `pnpm -C workspace build:static`                                                                                      | 范围过滤→静态入口export／预渲染→SVG→Pagefind→StaticRelease；输出无在线依赖    |
| 在线构建           | `pnpm -C workspace build:online`                                                                                      | 在线暂存入口、standalone、完整资源／受控快照及OnlineRelease；不连接生产数据库 |
| 任务单元／集成测试 | `pnpm -C workspace exec vitest run tests/content`等对应任务目录                                                       | §4指定的实质故障断言；服务集成需真实测试存储                                  |
| 浏览器接受         | `pnpm -C workspace exec playwright test tests/browser`                                                                | 实际托管URL、媒体、窄屏和权限；环境与产物版本明确                             |
| SQL唯一来源        | `go -C backend test ./tests/db -run TestBackendSQLHasCanonicalSchemaAndPresetData -count=1`                           | 仅当改SQL或相关约束时运行；不代替新库初始化／旧库受控变更接受                 |
| 差异核对           | `git diff --check`及允许文件集审阅                                                                                    | 保护并行修改、无越界文件，无自动commit／push                                  |

静态独立性不能仅靠mock API：需在单独托管进程或容器中只加载产物，记录实际网络。主机发现不能仅靠目录存在。供应商接受不能仅靠样本或模拟响应。发布演练不等于生产已发布。

每份证据引用至少绑定`commit + dirty摘要 + 内容／配置摘要 + 产物版本 + 环境 + 命令／动作 + 时间 + 结果 + 未覆盖项`；实际接受人和接受范围另记。涉及费用只记录实际可核对回执，未知不写零。

## 7. 迁移切换、发布与恢复

| 事件                           | 恢复动作                                                               | 保护边界                                              |
| ------------------------------ | ---------------------------------------------------------------------- | ----------------------------------------------------- |
| 迁移前基线变化／出现未归属文件 | 停止切换，更新映射并协调该文件后重验                                   | 不覆盖／删除用户修改，不用reset或clean处理            |
| 候选迁移失败                   | 保留证据并仅撤销本次获准候选路径；若已落地须提出精确恢复差异           | 不对整个共享工作区做回滚，不遗留双写正文              |
| 静态构建／上传失败             | 保留完整旧产物；修复后重新生成同版全包                                 | 不发布半份页面与索引，不更改业务部署                  |
| 新静态版有问题                 | 切换到原完整StaticRelease，保留新候选供诊断                            | 正文Git历史、用户代码和业务数据不随站点回退           |
| 在线运行包回退                 | 先核对现有schema及执行接口兼容，兼容后切旧镜像；不兼容则停止并受控修复 | 不反向DDL，不抹除运行记录或重复派发；静态版保持原产物 |
| 在线存储／执行器失联           | 停新派发，查询原句柄／事件游标；未知交人工处理                         | 不自动重放有副作用动作，不篡改历史结果                |
| 提案已落地但回执丢失           | 按幂等键查询，核对实际正文摘要                                         | 不重复应用或自动提交                                  |
| TTS部分失败／收费未知          | 保留成功片段，查原请求，只在明确授权下补缺片                           | 不整篇重合成，不静默换音色，不把临时URL发布           |

正式切换前确认：内容唯一、链接与权限门禁通过、候选可追溯、旧产物可恢复、写入与发布权限明确。公开发布、域名变更、业务部署及管理员数据库变更各按其授权执行，不由本计划自动授予。
