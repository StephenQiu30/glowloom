# PRD：模型商业计费与积分系统

唯一来源设计：[设计36](../design/36-模型商业计费与积分钱包设计.md)。需求：[SRC-CREDIT-01、FR-CREDIT-01～06](../requirement/21-模型商业计费与积分系统需求.md)及[SRC-CREDIT-05、FR-CREDIT-16～24](../requirement/21-模型商业计费与积分系统需求.md#src-credit-05)。执行：[Plan32](../plan/32-模型商业计费与积分系统实施计划.md)。状态：评审稿；不是价格发布或支付开通。状态和调度仅见[BACKLOG](../../../BACKLOG.md#commercial-credits)。

## 1. 摘要

让创作者清楚地购买、使用和追踪积分，让团队控制项目投入，让平台能解释每笔销售与采购差异。基础服务同时为授权系统调用方提供可幂等的积分命令和可恢复账本。首版按量消费与通用积分购买沿用原商业政策；会员、年付与复杂促销不阻塞基础钱包。

## 2. 参与者

个人创作者、组织付款管理员、团队成员、模型管理员、财务核查人员、受限Agent及经授权的内部服务调用方。权限与技术保证由来源设计定义，人员尚未指定。

## 3. 背景

当前项目有精确金额、项目预算、预留结算和积分预估，但充值/会员尚未开放。现有0.12元显示预计2整数积分容易被误读；商业钱包需要精确扣费、来源追踪与现金支付证据。竞品做法支持分来源积分与统一估价，但不能证明其远端账本适合直接复用。

## 4. 目标与衡量

| 目标       | 衡量方式                                                                 |
| ---------- | ------------------------------------------------------------------------ |
| 费用可理解 | CASE-CREDIT-01/02中金额、精确积分与确认上限可互相复算                    |
| 钱不丢不重 | CASE-CREDIT-03/04/06/07中重复、乱序、并发及退款仅产生一次有效事件        |
| 额度可控   | CASE-CREDIT-05/08/09中项目、账户、批次范围与Agent总上限都不能绕过        |
| 商业可测   | 每模型可关联实际采购、销售实扣、发行来源及补贴，不能把面值消费当现金收入 |
| 账务可靠   | CASE-CREDIT-13～18中写命令幂等、CAS、SAGA、消息重试、账本重建与缓存版本一致 |
| 接口可控   | CASE-CREDIT-19中越权、重放、超限请求被拒并可审计；压力结果按已评审SLO判断 |

上线后观测付费转化、复购、各模型贡献利润、冻结时长、支付差异率、失败补偿率及用户账单争议。当前没有真实基线，不承诺具体转化/毛利结果。

## 5. 使用场景与范围

纳入：单次/批量费用预览、精确积分、通用钱包、授权调用方的账户/流水查询与积分授予、扣减、冻结、核销、解冻命令、接入方幂等、事件投递、SAGA补偿、Redis余额只读缓存、月分区流水、接口限流与防滥用、支付入账、赠送批次、消费与现金退款区分、组织付款及项目预算、Agent子消费上限、对账核查。积分基础能力先用合成账务数据验收，不绑定特定供应商业务载荷；会员周期数据按来源设计承接，作为后续单月权益切片。

首版不纳入：转赠/提现、跨账户拼付、模型卡、自定义扣款顺序、自动充值、自动续费、无限生成、未经定义的会员自动退款折算。个人BYOK接入由模型接入专项拥有，本PRD仅约束平台不重复收模型成本。

套餐数字是设计36的候选，不是已确认需求。具体并发、存储及工具权益须产品能力验收后才能在购买页承诺。

共同接受：正常流程简洁，费用/返还明细可展开；320px、键盘和读屏可用；未入账不显示退款完成；无凭据或私有账单泄露。任务失败返还定义、最高支出风险及商业数字先通过评审再公开承诺。

## 8. 实施与验收

执行与验证环境见Plan32，调度见BACKLOG。CASE-CREDIT-13～19使用用户确认已启动的本机PostgreSQL、Redis、Kafka及合成账务数据，并为PostgreSQL创建本任务独立临时数据库；不得启动额外容器或连接/改写Glowloom业务数据库。无需真实支付或模型供应商；工程测试、模拟渠道、真实支付、真实供应商、产品接受与发布分别留证。性能阈值和限流策略数值须在执行前评审。文档评审不代表上述场景已执行。
