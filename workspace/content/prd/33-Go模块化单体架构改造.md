# Go 模块化单体架构改造

唯一来源设计：[设计47：Go模块化单体架构与RPC集成设计](../design/47-Go模块化单体架构与RPC集成设计.md)。原始需求经来源设计追溯至 [需求32 SRC-GO-MONO-01](../requirement/32-Go模块化单体架构改造需求.md#src-go-mono-01)。本文定义架构改造的接受范围与验收标准，不新增或削减既有产品功能。

## 1. 目标与边界

将当前处于半拆分状态的 Go 微服务后端回收并重构为**遵循 Google Go 规范的模块化单体**，消除不必要的网关、独立计算微服务、多角色容器与分布式围栏；同时保留独立 Node.js 运行时（`canvas/`、`agent/`），将 Go 与二者之间的内部通信升级为基于 **Buf + Protobuf + gRPC** 的强类型 RPC，并采用开源稳定组件库替代自研基础设施与已归档工具。

本 PRD 替代原 Go 微服务拆分 PRD（已清理删除，历史见 Git）作为 Go 后端架构的当前接受合同；并纳入 `SRC-GO-MONO-02` 确认的 **gRPC 方案 A** 与 **保留 Kafka 异步解耦** 边界。

## 2. 使用者与价值

- **终端创作者**：继续使用既有网页端、画布协作、AI 生成与 Agent 对话，公共 `/api`、SSE、WebSocket 与数据一致性不受破坏，且减少内部网络跳数带来的延迟与故障点。
- **后端与全栈维护者**：仅维护单一 Go 二进制与清晰的领域模块，不再承受跨服务分布式围栏、17 份内部微服务 proto 与 6 个 Go 容器的研发运维负担；Go 与 Node 运行时共享唯一 `.proto` 契约源。
- **部署与数据库维护者**：Compose 应用容器由 10 个精简为 5 个，数据库保持 `backend/db/schema.sql` 唯一结构规范与本地 ACID 事务。

## 4. 排除范围与接受边界

- 不将 `canvas/`、`agent/`、`workspace/` 重写为 Go。
- 文档评审与本轮知识库检查通过，不代表代码改造、数据库变更或生产部署已完成。
- 涉及存量生产数据库的任何 schema 清理，仍须由管理员依据 `schema.sql` diff 离线受控执行，严禁应用运行时 DDL。
