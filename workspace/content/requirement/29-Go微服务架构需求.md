<a id="src-go-ms-01"></a>

### SRC-GO-MS-01（2026-11-14）

用户原文：

> 我认为我们当前的服务需要改造成一个 go 的微服务项目，你有什么好的技术的选型以及对应的文档的设计，遵循 Google Go 的设计规范，先对我们的微服务结构进行设计

来源：本项目架构讨论。技术方案见[设计44](../design/44-Go微服务架构与技术选型设计.md)，实施调度见[BACKLOG](../../../BACKLOG.md#go-microservices-20261114)。

<a id="src-go-ms-02"></a>

### SRC-GO-MS-02（2026-11-14）

用户确认：

> 确认“四个业务服务＋轻量 Gateway”的划分 并开始执行拆分

确认 Identity、Creation、Media、Execution 四个 Go 业务边界及轻量 Gateway，并授权按设计门禁分阶段实施代码、测试与必要工程配置。Operation、Catalog、Billing 归 Execution；不把本次确认扩大为生产发布、存量数据库变更、真实付费调用、Git 提交或全部 Node 服务改写授权。首个可运行切片和后续任务见 [PRD30](../prd/30-Go微服务拆分.md)、[Plan39](../plan/39-Go微服务拆分执行计划.md)。

## 3. 需求边界

四个业务服务与轻量 Gateway 的边界已由 SRC-GO-MS-02 确认；仍需辨明、不能一揽子视为已确认的事项：

- 各业务服务何时获得独立写入权、首个业务域的物理拆分门禁及何时继续拆分。
- 是否将已有 Agent、Canvas 和已确认方案中的研发 Workspace 一并改写为 Go；不能仅凭本次 Go 方向静默推翻各自既有确认。
- 采用哪个 Go 框架、内部通信协议及数据库隔离级别。
- 团队规模、生产容量、可用性指标、部署平台和成本预算。

原有模型调用、账务、项目与协作语义仍由各领域来源持有；本需求不新增模型、支付、工作流或知识库产品范围。
