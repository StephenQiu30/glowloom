<a id="src-go-ms-06"></a>

### SRC-GO-MS-06（2026-11-15）

用户确认（归纳，非逐字引文）：参照 Google 官方微服务示例，先规范目录，不要过度包装。借鉴 [microservices-demo 的 checkoutservice](https://github.com/GoogleCloudPlatform/microservices-demo/tree/main/src/checkoutservice) 直接放置 `main.go`、实现和 `Dockerfile` 的服务内聚方式，不宣称这是 Google 唯一官方模板，也不照搬多 module 或部署体系。

该来源确认“服务内聚、先规范目录、不过度包装”的要求，不把特定 `main.go`、`cmd` 或包路径当作用户逐项指定的唯一标准。根单 Go module、集中测试、入口与组合根的具体布局属于[设计44 §7.5](../design/44-Go微服务架构与技术选型设计.md#75-go-项目结构)的工程选择，须说明与 Go 官方建议的取舍。已经执行的目录归位及其证据保留，不据此推定完整服务已经独立；后续布局调整不得复制业务实现、降低授权/事务合同或扩大部署授权。

<a id="src-go-ms-08"></a>

### SRC-GO-MS-08（2026-11-15）

用户确认（归纳）：依据需求分析及详细设计，完整实施全部微服务拆分，并在实现与测试后使用 `code-review` 对代码进行最终验收、修复发现的问题。该来源接续 SRC-GO-MS-07 的文档阶段，授权进入真实实现，不再把“本次仅文档”用作停止实施的理由。

完成须有四域业务写入权、真实入口、任务/事件/密钥责任、跨域授权与回执及 Gateway 唯一路由的接受证据；目录、端口、孤立技术 RPC 或局部测试通过均不能替代完整接受。最终审查针对实际实现及其依赖/故障边界，开工基线审查不计作最终验收，不保证静态检查可以证明绝无缺陷。仍保留并行修改、既有业务合同和 SQL 唯一规范；本次不自动授权追加 Git 提交推送、生产部署、存量业务库操作或真实付费调用。

## 3. 需求边界

四个业务服务与轻量 Gateway 的边界已由 SRC-GO-MS-02 确认；仍需辨明、不能一揽子视为已确认的事项：

- 各业务服务何时获得独立写入权、首个业务域的物理拆分门禁及何时继续拆分。
- 是否将已有 Agent、Canvas 和已确认方案中的研发 Workspace 一并改写为 Go；不能仅凭本次 Go 方向静默推翻各自既有确认。
- 采用哪个 Go 框架、内部通信协议及数据库隔离级别。
- 团队规模、生产容量、可用性指标、部署平台和成本预算。

原有模型调用、账务、项目与协作语义仍由各领域来源持有；本需求不新增模型、支付、工作流或知识库产品范围。
