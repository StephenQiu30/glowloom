# Go 模块化单体架构改造需求

## 1. 来源

<a id="src-go-mono-01"></a>

### SRC-GO-MONO-01（2026-11-25）

用户原文：

> 我们当前的项目是一个单体的项目，我认为这是一个冗余的部分设计，在我们当前的需求下是不需要通过微服务的，所以我们需要遵循 Google Go 的设计规范， 将我们的微服务项目改造成单体项目，并且需要先对我们的workspace下的文档进行改造优化，包括我们和画布以及agent服务之前可以使用 RPC 进行远程调用，以及不要重复造轮子，使用开源稳定的组件库和工具集来实现

来源：本项目架构重构决策。本需求明确替代原 Go 微服务拆分需求（已清理删除，历史见 Git）。对应技术方案见 [设计47](../design/47-Go模块化单体架构与RPC集成设计.md)，验收范围见 [PRD33](../prd/33-Go模块化单体架构改造.md)，实施计划见 [Plan42](../plan/42-Go模块化单体架构改造执行计划.md)。

<a id="src-go-mono-02"></a>

### SRC-GO-MONO-02（2026-11-25）

用户确认：

> 于此同时我们当前的文档部分内容也需要删除和重新整理，内容过于冗余，历史文档可以放入到对应的归档文件中，不要造成上下文的干扰
>
> 我们使用方案A 这种标准的组织形式，以及我们需要保留kafka作为我们的异步解耦的能力

确认结论：
1. **文档归档与清理**：将已替代的历史架构文档及一次性验收/核对记录从 `workspace/content/` 删除清理（历史通过 Git 追溯），避免污染知识库与 AI 上下文。
2. **RPC 选型已确认**：Go 单体与 `canvas/`、`agent/` 之间采用 **方案 A（标准 gRPC + Protobuf + Buf）**。
3. **Kafka 保留已确认**：保留 **Kafka** 作为异步事件解耦能力（单体进程内直接承载事件投递与消费，不再维护独立 `relay` 微服务容器）。

## 2. 明确要求

| ID          | 要求                                                                     | 确认边界                                                                                       |
| ----------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| FR-GOMO-01  | 将当前 Go 后端从多服务/微服务拆分形态改造回模块化单体（Modular Monolith） | 回收 `gateway`、独立 `creation`、`media`、`worker`/`relay` 等冗余拆分，保留清晰业务模块边界   |
| FR-GOMO-02  | Go 单体与独立 `canvas`、`agent` 服务之间支持通过 RPC 进行远程调用        | 保留 `canvas`（Yjs）与 `agent`（Pi Durable）两个独立 Node.js 运行时，升级跨语言内部通信为 RPC  |
| FR-GOMO-03  | 不重复造轮子，采用开源稳定的组件库和工具集替代自研基础设施与冗余胶水层   | 替换归档依赖、过度自研的任务/转发/代理/双向内部 HTTP 胶水，优先成熟稳定的开源方案              |
| FR-GOMO-04  | 先对 `workspace/` 下的架构与计划文档进行改造优化，再进入源码改造         | 本轮先行完成需求、设计、PRD、执行计划及导航同步，不越权直接修改业务源码、SQL 或部署配置        |
| NFR-GOMO-01 | 严格遵循 Google Go 设计与编码规范                                        | 遵守 Google Go Style Guide / Decisions / Best Practices 与仓库既有 `adapter → application → domain`、唯一 `schema.sql` 规范 |
| BR-GOMO-01  | 保留既有已验证的产品功能、前端公共 `/api` 合同与数据一致性语义           | 架构收敛不削弱认证、权限、幂等、计费、画布协作与 Agent 能力；不含生产发布、存量库变更或真实付费 |

## 3. 需求边界

已确认方向：

- Go 业务后端不再按四个业务微服务 + 独立 Gateway 拆分，统一收口为遵循 Google Go 规范的模块化单体。
- `canvas/` 与 `agent/` 仍作为独立 Node.js 运行时存在，与 Go 单体之间采用 **方案 A（标准 gRPC + Protobuf + Buf）** 通信（`SRC-GO-MONO-02` 已确认）。
- 保留 **Kafka** 作为异步事件解耦能力，在单体内部直接集成并回收独立 `relay` 容器（`SRC-GO-MONO-02` 已确认）。
- 先完成 `workspace/` 文档改造与历史归档（历史通过 Git 追溯），待确认代码改造启动时机后再按执行计划分阶段改造源码。

待确认事项（须在对应代码阶段前明确）：

- 是否在保留 Kafka 异步事件解耦的同时，引入 **River**（基于 `pgx/v5`）替换自研 `taskruntime` 后台任务调度器。
- 代码改造的启动时机及是否按阶段分批提交。
