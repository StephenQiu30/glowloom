# BeefTV 模型接入与计费调研

调研日期：2026-11-03（Asia/Shanghai）。调研对象：[glanderness/BeefTV](https://github.com/glanderness/BeefTV)。

外部源码固定版本：[`87b4be14bc1b`](https://github.com/glanderness/BeefTV/commit/87b4be14bc1bdeae7b1ffc2b7176b3d433fdd37e)，即本次 GitHub 连接器读取到的 `main`。结论针对这一版本，不追溯断言其他历史版本的实现状态。

当前版本适用说明：2026-11-05核验的`18a672fb09c62bd21c325370eb3e1255669f1004`已新增后端统一图片/视频/音频及批量估价，见[最新研究](2026-11-05-模型计费与积分竞品研究.md#2-beeftv统一估价可借鉴钱包不可直接照搬)。本文关于前端视频估价覆盖面的判断仅限上述11-03固定版本，不代表最新能力。

本文为调研文档，不构成已确认需求、技术设计或实施计划。本轮仅整理文档，不修改业务代码，不运行 BeefTV 客户端，不注册或充值，不调用付费模型。

## 1. 核心结论

**BeefTV 当前公开仓库最值得参考的是模型渠道与能力合同、价格展示、付费提交去重和结算异常恢复；它没有在当前桌面主线中公开一套可以直接搬用的完整充值、钱包及商业计费服务端。**

1. **当前产品是本地优先桌面工作台。** React/Wails/Go/SQLite 管理工作区；模型推理仍可访问外部 API。本地架构明确排除登录、支付、财务等 SaaS 路由；本地数据库迁移会清理旧钱包、充值及价格 SKU 等托管表。[B01]、[B02]
2. **模型接入有官方账号与自带 Key 两条路径。** 官方账号通过设备授权取得受管理的 BeefAPI 凭据，再拉取模型目录；自定义渠道保存 Base URL、凭据、协议、模型及参数能力，调用对应供应商。实际推理费用分别由官方远端服务或自带 Key 所属渠道收取。[B03]、[B04]、[B05]、[B06]
3. **公开价格合同主要围绕视频。** `video_pricing` 支持按秒、按百万视频 Token 的单价，以及部分参考生成按上游美元账单换汇加价后结算。不是所有文本、图片、音频都拥有统一完整的公开价格公式。[B07]、[B08]、[B09]
4. **不能把价格预览当成锁价或硬预算。** 当前目录价格经过校验、保存再展示，但可能缺失或变化；文档明确说明它不是实时计费保证，也不自动执行人民币预算上限。授权执行哪些素材，与允许消费多少金额，是两个不同合同。[B10]
5. **它较有价值的计费保护是避免重复购买。** 提交前保存身份和原请求；结果不明时先查询原任务；待结算时阻止直接重新生成；已扣费但结果丢失时先取回，确实取不回才提示再次消费。[B11]、[B12]、[B13]、[B14]
6. **Glowloom 已有更适合自身 SaaS 形态的计费基础。** 本地源码已包含不可变价格版本、精确金额计算、报价确认、预算预留、结算/释放流水及未知费用保护。建议复用这些基础，参考 BeefTV 补充价格解释、恢复交互与供应商证据表达，不另起一套重复账务系统。[G01]、[G02]、[G03]、[G04]、[G05]、[G06]

这里的“没有公开完整商业计费服务端”，具体指：在本次固定版本中，没有找到并验证官方钱包扣款、支付回调、真实上游账单对账和退款落账的完整服务端实现。它不等于“官方服务不收费”，也不等于“历史版本一定没有这些功能”。

## 3. 模型接入如何实现

### 3.1 两条接入路径

| 维度 | 官方受管理渠道 | 自定义渠道 / BYOK |
| --- | --- | --- |
| 配置入口 | 连接 BeefTV 官方账号 | 配置自己的模型服务 |
| 凭据来源 | 设备授权后远端颁发 API Key | 用户提供 API Key 或协议所需凭据 |
| 运行时身份 | `credentialRef=beefapi-enterprise`、`channelId=beefapi` | 本地渠道 ID、模型配置与秘密 |
| 模型目录 | 带凭据访问官方 `/v1/models` | 标准目录拉取、显式配置及插件补充 |
| 请求协议 | 按目录能力和官方协议执行；新图片使用托管媒体协议 | 按所选协议适配器执行 |
| 钱包与结算 | 官方远端账号体系；桌面端打开充值页并消费远端结果 | 上游渠道自己的账号与账单 |
| 桌面端本地账务 | 不建立自身商业钱包扣款 | 不把自带 Key 的上游费用自动转换成自己的钱包扣款 |

来源：[官方授权客户端][B04]、[官方连接服务][B03]、[本地模型配置][B06]、[模型目录解析][B15]。最后两行反映本地工作区与上游收费责任的边界，不构成对第三方供应商收费规则的承诺。

### 3.2 官方账号：设备授权、凭据保存、目录同步

主要流程：

1. 桌面端请求 `POST /api/oauth/device/code`，携带客户端身份与 inference scope。
2. 获取设备码、用户码、验证页面和有效期，打开受信任的浏览器确认页。
3. 轮询 `POST /api/oauth/device/token`，处理待授权、降速、过期、拒绝等状态。
4. 返回 API Key 后，校验服务源、账号 ID、token ID，以及 `market/group=enterprise` 等合同。
5. 加密保存凭据，再通过 `POST /api/oauth/device/complete` 完成确认；目录同步和确认完成情况也会保存，以便重启恢复。
6. 使用授权凭据访问 `GET /v1/models`，将模型、端点类型、图片/视频能力版本、视频价格等同步到本地渠道。
7. 前端使用安全摘要和凭据引用；运行时在 Go 边界解析真实凭据。连接状态和目录同步失败分开处理，不把“已拿到凭据”直接当成“所有模型已可用”。[B03]、[B04]、[B05]

官方生产源在该版本为 `https://beeftv.app`，兼容旧源 `https://enterprise.beefapi.com`。充值入口是受信任源的 `/console/topup`。这些是源码中声明的地址；本轮没有打开账号、支付或充值流程。[B16]

这套机制可参考之处是：**把账号授权、秘密存储、目录可用性和具体模型可用性分开表达**。它并不能证明任一已连接模型已完成真实调用验证。

### 3.3 自定义渠道：把服务、模型、协议、规格拆开

源码中至少有以下独立概念：

| 对象 | 核心职责 |
| --- | --- |
| `ModelChannel` | 渠道名、Base URL、秘密、Header、协议族、并发限制与启停 |
| `ChannelModel` | 渠道中的模型键、上游模型键、能力、具体调用协议、能力版本 |
| `ChannelModelVariant` | 将 operation、清晰度、时长等规格组合映射到实际上游 SKU |
| `LogicalModel` / Revision | 面向创作者的模型入口，以及冻结的能力与默认参数 |
| `LogicalModelRoute` | 将逻辑模型关联到具体渠道模型，包含优先级、权重和启停 |
| `RouteAttempt` | 记录某次任务实际使用的渠道、模型版本、派发状态、上游任务号及失败事实 |

例如，用户选择一个“视频模型”，不必同时理解所有供应商的模型 SKU。内部可将 `image_to_video + 720p + 10秒` 解析成某个渠道的实际模型键。**模型能力和规格必须与真实执行协议匹配，不能只靠模型名字猜测。**[B17]、[B18]

需要区分两条实际代码路径：当前桌面模型配置还会直接从本地文件生成渠道/模型快照；仓库中存在逻辑模型路由结构，不代表桌面所有请求都会经过多渠道路由，也不代表已验证生产故障转移。[B19]

### 3.4 协议适配与目录发现

内置协议覆盖 OpenAI Chat Completions、Responses、Claude、图片、音频及若干视频接口；不同视频协议的创建路径、轮询路径和载荷并不相同。插件合同还可声明鉴权、参数、校验、请求构造、响应提取和工作流。[B20]、[B21]

模型目录拉取与生成调用也被分开：

- 目录读取归一化模型 ID、默认值、选项和能力声明，不直接执行付费生成。
- 标准目录以外的供应商模型可由专门的发现插件补充。
- 通用 `/models` 返回了模型名字，不意味着该模型有合适的生成协议、参考素材能力或价格。
- 普通渠道目录不能任意发明宿主协议 ID；官方目录只对明确端点合同进行协议映射。[B15]、[B22]

自定义模型配置在磁盘使用加密封装，秘密读取结果会脱敏，并有配置 revision 和原子文件替换。此实现适合本地单用户桌面；Glowloom 的多用户服务端应继续使用已有服务端凭据管理边界。[B06]、[G07]

### 3.5 核心接入机制：声明式协议插件（`beeftv.plugin/v3`）与 JSON 表达式引擎

在考察 BeefTV 接入 40 余种第三方模型（如 MiniMax H3、火山 Seedream/Seedance、通义万相、Kling、Runway、Fal.ai 等）的实现时，发现其最核心的架构决策是：**将异构 API 的适配从 Go 业务逻辑中完全剥离，收敛为声明式的 JSON 插件包（`plugin-packages/*`）**。[B36]、[B37]

1. **Manifest 清单结构与全生命周期声明**：
   每个插件包包含一个 `manifest.json`，在 `contributes.providers[]` 中声明：
   - 基础元数据：`id`、`capabilities`（image/video/text/audio）、`baseUrl`、`auth`（Bearer/Header/AK-SK）；
   - 统一参数列表与白名单映射：`parameters`；
   - 客户端事前校验断言：`validations[]`，在发起请求前由宿主就地拦截非法参数并提示用户（如“MiniMax H3 首尾帧模式不能混入普通角色参考图”、“Seedream 图层拆分必须有且仅有一张参考图”），避免无效网络往返与上游计费拒绝；
   - 任务端点与执行：`create`（POST 路径与 Payload 构建）、`poll`（GET 轮询路径模板 `{{taskId}}`）、`cancel`、`response`（从上游 JSON/SSE 提取状态、任务号、媒体 URL、错误码的映射路径）。
2. **纯函数式表达式引擎（Variables & JSON Expression DSL）**：
   为抹平厂商间千差万别的报文格式，插件系统设计了一套求值表达式 DSL：
   - 支持逻辑与变换操作符：`$ref`、`$coalesce`、`$if`、`$switch`、`$map`、`$filter`、`$sortByOrder`、`$concat`、`$split`、`$omitEmpty`；
   - 支持按数组顺序声明的中间变量（`variables[]`），例如通过 `$split` 模型名判断是否为 `modern` 架构，动态计算出上游接受的 `ratio` 或尺寸规格；
   - 报文完全由声明生成，例如将参考图按 `role` 自动组装为特定嵌套数组。
3. **对比 Glowloom 的多设计模式纯 Go 方案**：
   - Glowloom 在[设计33](../design/33-多设计模式驱动的模型与供应商接入扩展体系设计.md)中设计了 8 种 Go 策略类族（`ProtocolStrategy`、`BaseProtocolDriver` 等），虽然类型安全，但每接入一个新协议或上游调整参数命名，都需要重新编写 Go 结构体、发布新后端版本并重启容器；
   - **参考价值**：Glowloom 应当保留 Go 基础驱动的骨架，但对于异构视频/生图模型的报文转换与参数白名单，应吸纳 BeefTV 声明式 Manifest 的思路，将参数映射与错误映射下沉为可配置的模板规则，降低后期的工程维护代价。

## 4. 模型计费到底如何做

### 4.1 先区分四件事

| 层次 | BeefTV 当前公开代码能确认什么 | 不能据此确认什么 |
| --- | --- | --- |
| 价格目录 | 从模型目录接收 `video_pricing`，校验并保存 | 远端如何采购模型、设置全量售价和折扣 |
| 费用预览 | 按参数展示单价或预估总额；不明时明确显示未知 | 锁价、价格有效期和硬消费封顶已被执行 |
| 结算观察 | 读取 reserved、charged、adjustment quota 与结算状态等响应字段 | 这些额度如何换算成人民币、内部如何落账 |
| 商业账务 | 打开远端充值页；本地结构排除并清理商业账务表 | 支付验签、钱包原子扣款、退款流水和财务对账已公开 |

依据：[B02]、[B07]、[B08]、[B10]、[B11]、[B16]。

**因此，它不是“在桌面端按模型次数直接扣积分”。公开源码展示的是价格消费端和结算观察端，最终财务权威位于远端。**

### 4.2 价格来自模型目录，不是前端固定价表

核心链路：

```text
GET /v1/models
  → 模型 video_pricing
  → 校验币种、计费方式、清晰度和费率
  → 保存到本地 model profile.videoPricing
  → 提供给模型选择器、生成方案和费用预览
  → 远端任务返回实际 usage / billing 状态
```

`NormalizeCatalogVideoPricing` 在该版本只接受 CNY，以及 `tokens` / `seconds` 两种模式；对允许的清晰度键、正数费率、参考图费用和参考账单字段作约束，再输出白名单字段。[B07]

目录刷新时，当前模型不再返回价格就会清理旧报价，避免继续显示过期价格；对应测试还覆盖模型下架后的可用性与报价清理。**离线或拉取失败时保留最后有效目录，与成功刷新但价格字段被撤回，是不同情况。**[B08]、[B23]

这属于“数据驱动的展示价格合同”。未看到桌面端为每笔消费签发可强制执行的价格锁定票据，不能把配置 revision 视为完整金融锁价机制。[B10]

### 4.3 按秒计费：可以算出参数级预估

前端 `estimateVideoTargetPrice` 对 `mode=seconds` 的普通生成计算：

```text
预估总额 =
  (所选清晰度的每秒单价 × 单个视频秒数
   + 超出免费张数的参考图数量 × 每张参考图费用)
  × 生成数量
```

其中，参考图附加费用只有目录声明时才参与计算；缺少有效时长或费率时退回参考单价，不伪造完整总额。展示计算最终保留四位小数。[B09]

**仅用于解释公式的假设示例，不是 BeefTV 当前售价：**

- 每秒 ¥0.20，5 秒；
- 3 张参考图，前 1 张免费，超出后每张 ¥0.01；
- 生成 2 个结果。

则预估为 `(0.20 × 5 + (3−1) × 0.01) × 2 = ¥2.04`。这只是前端预估算法示意，不代表上游账单、计费取整或退款规则。

### 4.4 按视频 Token 计费：当前主要展示单价

`mode=tokens` 的展示区分：

- 无视频输入：`rates[resolution].output`，单位为元 / 百万视频 Token。
- 含视频输入：`rates[resolution].reference_video`，同样以百万视频 Token 展示。[B09]

这里的 `reference_video` 在界面中表示“含视频输入时的费率”，不能擅自解释成一定要与 `output` 相加的另一笔费用。它也不是文本聊天的普通输入/输出 Token 价。

当前前端在这一模式下返回 `amount=null`，展示参考单价，不凭视频秒数臆造完整金额。仓库没有在这段算法中公开“画面尺寸、帧率、视频时长如何转换成最终可计费视频 Token”的完整供应商结算公式。[B09]

相关测试使用的 ¥69 / ¥42 是测试输入，不应当作为线上现价写入产品或销售说明。[B23]

### 4.5 参考生成：上游账单 × 汇率 × 加价系数

当按秒价格合同还带有 `reference_invoice`，且实际存在参考图时，前端不再给出确定总额，而显示：

```text
说明中的最终费用 = 实际美元账单 × usd_cny × 1.5
显示的预留额     = reserve_usd × usd_cny × 1.5 × 生成数量
```

实际美元账单尚未出现时，`amount=null`，同时展示预留金额和出账后结算的说明。[B09]

这是源码中能直接确认的商业加价表达，但必须限定：

1. `1.5` 在这一参考账单展示/预估分支中写定；不是所有模型统一加价 50% 的证据。
2. `usd_cny` 与 `reserve_usd` 来自目录，客户端只校验及展示；不是客户端实时查询外汇市场。
3. 预留额不是最终扣费，也不自动证明它是用户消费上限。
4. 源码中的说明不能证明远端已正确执行预留、补差、释放及退款账务；该部分需远端实现或真实对账证据。

对于 Glowloom，可参考“把成本来源、换汇、加价和预留原因讲清楚”；**不建议把固定 `1.5` 或 JavaScript 四位小数展示计算直接作为服务端账务真相。**

### 4.6 文本、图片、音频与积分兑换：哪些不能确定

已看到调用日志模型包含输入/输出/缓存 Token、用量可用性、估算成本微单位和币种等字段。**存在字段不等于当前所有协议都已填充完整费用，更不等于有一个完整计费引擎。**[B17]

当前公开目录解析和价格规范化重点支持视频报价。对于其他能力，本轮没有验证统一的文本缓存折扣价、图片质量阶梯价、音频字符/秒费率以及全模型价格发布后台。

托管媒体响应接收：

`quota`、`reserved_quota`、`charged_quota`、`adjustment_quota`、`usage`、`usage_state`、`billing_state`、`reconcile_deadline`。[B11]

但仅凭字段名，不能推断：

- 1 元等于多少 quota 或积分；
- 赠送余额、充值余额的扣减顺序；
- 分组倍率、用户折扣、成本价、销售价的全量关系；
- quota 的取整精度、跨币种结算及退款顺序；
- 充值是否使用某个支付机构，是否采用某个开源网关的账务实现。

仓库出现 NewAPI 协议适配器，只能证明它能调用相应接口，**不能据此断言官方钱包后端就是 NewAPI**。[B20]

## 5. 计费状态、失败和恢复怎样关联

### 5.1 任务状态、交付状态、结算状态分别保存

一个任务可能“上游已经成功和扣费，但结果下载尚未完成”；也可能“界面显示失败，但远端仍在核对账单”。BeefTV 没有只用一个 success/failed 来回答这些问题，而是从持久化事实计算 `Outcome`：[B12]

- `phase`：运行、取回、交付或最终失败等用户可见阶段。
- `regenerate`：`blocked`、`confirm` 或 `allowed`。
- `reason`：例如 `settlement_pending`、`charged_result_unrecoverable`。
- `reconcileDeadline`：上游给出的核对期限。

`Outcome` 在源码中明确是**只读投影，不持有状态，也不授权提交**。不能认为所有付费写入口只要使用这个字段，就已经有统一服务端消费守门。[B12]、[B24]

### 5.2 结算映射

以下为失败/恢复路径中的主要判断。运行中和成功交付等更早分支也会参与计算，不应将表格脱离整个函数单独实现。

| 已持久化的证据 | 当前投影/动作倾向 | 对计费的含义 |
| --- | --- | --- |
| `usage_state=pending/reserved` | 阻止直接重新生成 | 远端结算未完成 |
| 明确出现 `billing_state="" / reserved / precharged` | 阻止直接重新生成 | 已有待核对结算信号 |
| `usage_state=completed` 或 `billing_state=settled`，结果仍可能取回 | 先取回原结果 | 避免已付费任务被再次购买 |
| 上述已结算状态，但结果确定无法取回 | `confirm`，提示再次消费 | 已付费不代表本地产物一定交付成功 |
| `billing_state=refunded` | 允许按其他业务规则重新生成 | 客户端拿到明确退款结论 |
| `usage_state=failed` | 按官方合同映射为可重新生成 | 这是 BeefAPI 的使用状态语义，不是通用“任务失败即退款” |
| 只有第三方失败，缺少明确结算字段 | 通常要求再次确认；有恢复证据时先恢复 | 不猜测已经退款 |
| 证据读取失败 | 阻止直接重新生成，继续取证 | 数据缺失不能当成“没有消费” |

来源：[B12]、[B13]；对应已有测试覆盖待结算、已扣费无法取回、明确退款、缺失结算键等情况。[B25]

**字段缺失与显式空字符串必须区分。** 图片结算解析使用指针和 `HasBillingState`，明确出现空字符串表示待核对；完全没有该字段不能按相同方式处理。视频旧协议主要读取 `usage_state`，图片旧协议主要读取 `billing_state`，新媒体协议同时容纳多种字段。[B26]、[B27]、[B11]

`reconcile_deadline` 不是客户端自行推算的“到时间就退款/免费重跑”。本轮读取的待结算判断不会单纯因为本地时钟超过期限就解除阻止。[B12]、[B13]

### 5.3 内容审核失败、取消、下载失败都不能自动代表退款

- 内容审核失败会影响后续输入，但客户端不能仅从错误文案判断费用为零；结构化审核错误也有需要重新确认的分支。[B12]
- 取消先改变本地等待/任务状态，再尝试取消上游任务；上游不一定已取消，更不能据本地 cancelled 就认定退款。[B24]
- 下载/入库失败应继续原任务交付；已经生成的结果没有必要再次购买。[B12]、[B14]

对 Glowloom 的直接参考：**“执行失败”“产物未交付”“费用未知”“已退款”分别表达，保留各自证据。** 若供应商没有结算能力，应明确显示未知，并进入对账/人工处理，不虚构退款承诺。

## 6. 如何避免重复调用与重复扣费

### 6.1 本地与上游是两个幂等边界

本地 `clientOperationId` / `operationId` 用于防止重复创建本地任务与重复执行同一个业务提交。官方新图片链路还将稳定 `task_ref` 作为上游 `Idempotency-Key`。[B10]、[B11]

这两个保证不能互相替代：

- 本地任务没有重复创建，不证明上游网络重试没有重复购买。
- 上游支持幂等，也不代表可以更换模型、参考图、凭据或请求体后沿用同一键。
- 相同键但不同内容需要冲突处理，而不是悄悄生成第二个结果。

### 6.2 发出前记录，未知后查询

路由尝试由 `not_sent` 在实际发送前切为 `submission_unknown`，通过持久化状态取得发送所有权；随后依据响应区分 `accepted` 或 `rejected_no_job` 等状态。[B28]

因此，超时或进程重启不会被简单当成“肯定没发出去”。已受理但缺上游任务号、或者提交状态未知时，代码明确停止可能重复建单的自动重发。[B28]

官方托管媒体协议还保存冻结的请求和查询身份，用原任务号查询结果。API 目录声明媒体协议后，新图片请求进入 `/v1/media/tasks`；上传参考图与创建生成任务分离，客户端不自行按模型名称选择供应商传输。[B10]、[B11]

### 6.3 “继续取回”不应被概括为绝对不会产生费用

当前 `RecoverTask` 与 `Retry` 是不同代码路径。恢复不会创建新的本地任务，也不调用本地重试入口。[B14]

但有一个重要例外：

> 当用户主动选择继续取回、远端查不到原编号、原请求仍可恢复且没有已有结算记录时，客户端可以使用原 Key、原编号、原 Header 和原请求体补交。上游若先前没收到，这次可能成为原任务的首次实际生成和首次收费；若先前收到，则依赖上游同键去重返回原任务。

后台恢复只查询，不主动走这个补交分支，避免数小时后意外开始生成和收费。[B14]、[B29]

因此，准确表述应是**“恢复原消费身份，避免第二次购买”**。它不是远端恰好一次执行的独立证明，也不意味着所有恢复网络请求绝对没有费用。

### 6.4 故障转移不能绕过消费身份

源码中的逻辑模型路由支持最高优先级候选中的权重选择，并按能力、规格和健康阻止状态过滤。[B30]

但是失败后切换路由有限制：

- 必须有逻辑模型和明确 `rejected_no_job` 证据；
- 图片路径不在这个通用失败切路由分支中；
- 已取消请求不会继续切换；
- 已受理或未知提交不能当成普通失败换渠道重买。[B28]

值得参考的是这些限制，而不只是“多渠道自动重试”。对于用户按某个价格和渠道批准的任务，换路由还需要另行校验价格与授权范围；当前代码存在路由结构并不证明所有费用上限都已约束到最终派发。

## 7. Agent 费用预览与消费授权

BeefTV 会把生成目标、模型、参数、参考素材、数量及可获得的价格组织为生成方案；能计算的按秒视频可汇总，未知价格明确说明按所选渠道实际标准计费。[B31]

`canvas.generation.submit` 当前支持稳定操作身份、画布版本及模型配置版本校验；代码还区分外部调用者的 `ask`、`caller`、`auto` 授权模式。[B32]

这意味着：

1. 不能把它概括为“任何调用每次都必需人工点确认”；实际行为受调用者权限和授权模式控制。
2. 版本和目标快照可以防止批准后模型、输入或计划被悄悄替换。
3. “批准生成这些素材”不自动等于“消费金额不得超过 ¥X”。官方 API 文档对人民币硬预算缺口已有明确说明。[B10]
4. 文档不同段落存在分阶段叙述，例如前段写某些新恢复入口尚未接入、后段已说明 `/recover`。本文涉及恢复行为以固定版本的 `RecoverTask` 和 `managed_resubmit.go` 实际分支为准，不将旧阶段说明视为当前实现结论。[B10]、[B14]、[B29]

对 Glowloom，可参考方案级价格说明和目标冻结；人民币上限仍应交给现有服务端报价、预留和最终派发规则执行。

### 7.1 生成方案的 CAS 乐观锁防重扣机制（expectedRevision 与 expectedModelConfigRevision）

在深入追踪 `operations/generation_submit.go` 的执行链路时，发现 BeefTV 对人机协同中的并发修改与重扣风险有非常严格的防线：[B32]

1. **审批与执行的时间窗口风险**：
   Agent 在画布上完成剧本分镜并提出生成单提议（Proposal）后，会挂起等待人类审核（Ask 模式）。在人类看方案、喝咖啡或与团队讨论的几分钟内，可能发生两类并发改动：
   - 画布被协作者或用户手动修改：如调高了视频分辨率（从 720p 改为 4K）、删改了镜头提示词、移动或替换了角色参考图；
   - 系统价格发生变动：如渠道配置被更新、模型降价或调高了倍率。
2. **BeefTV 的 CAS 强版本校验**：
   调用 `canvas.generation.submit` 提交执行时，必须显式传入提议生成时所见到的两个版本快照：
   - `expectedRevision`：生成提议时的画布版本号；
   - `expectedModelConfigRevision`：生成提议时的模型与价格配置版本号。
   Go 后端在提交时严格比对当前实际数据：
   - 若当前画布版本不一致，直接拒绝并报错 `Conflict("revision_conflict", "画布已变化，请重新读取并确认生成内容")`；
   - 若模型配置版本不一致，直接拒绝并报错 `Conflict("generation_config_changed", "模型配置已变化，请重新读取生成提议")`；
   - 若画布节点参数与生成单中的目标不匹配，报错 `Conflict("generation_targets_changed", "画布上的生成参数已变化，请重新读取生成提议")`。
3. **对照 Glowloom 的实施缺口**：
   Glowloom 目前在 `backend/internal/agent/application/proposal_interrupt.go` 中实现了基于 LangGraph 的中断审批流（`ProposalHarness.HandleApprove`），检查了 `proposalID`、状态和 `approvedMaxMicros` 预算限制，**但目前尚未在 Proposal 中存储并校验 `ExpectedCanvasRevision` 和 `ExpectedPriceRevision`**。[G10]
   一旦用户在审批间隙手动改动了画布参数或管理员更新了模型倍率，系统会以旧预算盲目恢复图执行，极易引发后续生成与账务的不一致冲突。该机制必须直接吸收落地。

## 8. 与 Glowloom 的现有实现对照

本节只描述静态源码事实，不声称已经运行真实供应商、支付或结算流程。

| 主题 | Glowloom 当前可见基础 | 参考 BeefTV 的方向 | 存在的技术缺口或隐患 |
| --- | --- | --- | --- |
| 价格版本 | `PriceRuleVersion`；报价与实际用量沿用冻结的发布规则和汇率 | 将价格来源、更新时间和失效原因展示得更明确 | 基础扎实，需补齐展示端字段解释 |
| 计费细则落地 | 代码 `pricing.go` 中仅有时长、Token、分辨率计算 | 支持按秒、视频 Token 双轨、参考图免额（`free_reference_images`） | `PricingInput` 缺失 `ReferenceImageCount`，代码抛出 `ErrUnsupportedPriceCoefficient` |
| 异步结算门禁 | `billing/domain/reservation.go` 有 `held/settled/released` | 结算未决（`settlement_pending`）时强行锁定重新生成（`Regenerate: blocked`） | 缺少前端重试阻断，网络超时后用户重复点击存在二次扣费风险 |
| 提案审批防并发 | `agent/application/proposal_interrupt.go` 支持中断挂起与人类审批 | 提交必须带 `expectedRevision` 与 `expectedModelConfigRevision` 强校验 | `HandleApprove` 未校验画布与价格版本快照，审批间隙改画布会导致账实不符 |
| 协议接入架构 | 规划了 `ProtocolStrategy` 等 8 种 Go 策略设计模式 | 声明式 JSON Manifest + 表达式 DSL（`beeftv.plugin/v3`） | 纯 Go 硬编码扩展新渠道与非标参数成本高，建议混合引入声明式配置 |
| Agent 成本治理 | 单轮 40 步硬熔断（`turn_budget.go`）与流式看门狗 | 支持单轮预算，但缺少工程级预算天花板与 Prompt Caching 折扣 | 多 Agent 级联调用（短剧全流程）缺乏上下文缓存优化与项目总预算熔断 |
| 多种计费单位 | 图片、秒、请求、千 Token、千字符 | 补充说明不同计费单位能否提前精确估价 | 保持服务端高精度计算与前端预留说明 |
| 金额精度 | 微单位金额、`big.Rat` 精确中间计算、最后统一向上取整 | 保留服务端实现；前端只负责展示 | 已对齐，继续坚持微元原子记账 |
| 预算与账本 | 预算锁、reservation、reserve/settle/release 流水 | 不另建客户端钱包；补充用户可理解的预留/实扣/释放视图 | 已具备 SaaS 完整流水能力 |
| 实际金额不确定 | `ErrProviderCostUnknown` 及持久化调用事实 | 借鉴 settlement pending 与恢复状态的明确说明 | 需强化错误归类（`FailureCategory`） |
| 提交身份 | 绑定 operation、attempt、request key 的 `ProviderDispatchIdentity` | 与供应商幂等能力、查询身份和恢复入口逐项对应 | 需严格落地“不确定提交严禁自动重发” |

来源：[G01]、[G02]、[G03]、[G04]、[G05]、[G06]、[G08]、[G09]、[G10]。

本地 `CalculateActualCost` 按供应商可信计量和冻结规则计算金额，其中可能包含销售加价；因此名称里的 actual cost 不能不加区分地展示成“纯供应商采购成本”。若需要利润分析，应另行确认采购成本与客户销售价的记录合同，不能只凭函数名认定已经分账。[G01]

### 8.1 可以直接参考的设计原则

以下都是建议，不代表已经新增产品需求或实施承诺：

- **能力和价格来自可验证合同。** 为报价注明模型版本、服务渠道、适用参数和来源，不只展示一个模型名与单价。
- **未知价格明确显示未知。** 只知道单价时不承诺总额；参考账单型模型应说明预留和后结算。
- **将恢复与再次消费区分。** 原结果下载、原上游查询、同键补交、重新生成应有各自语义。
- **不从一般失败推断退款。** 明确未派发、上游失败、已退款、待对账分别保存，错误文案只辅助理解。
- **冻结用户批准的具体目标。** 任务、模型、参数、参考素材、数量和报价版本在确认后保持对应关系。
- **只在明确未建单时考虑备用渠道。** 未知受理时继续查询；切换模型或价格超出原授权范围应停止并重新报价。

### 8.2 需要补证后才能采用的能力

| 候选参考点 | 仍需确认的事实 |
| --- | --- |
| 按秒 + 参考图附加费 | 对应供应商是否真实按此收费；计费时长如何取整；批量是否按实际成功数结算 |
| 视频 Token 单价 | 供应商可计费 Token 的定义、参考视频计量、能否获得可信 usage |
| 按上游实际美元账单结算 | 账单唯一身份、币种精度、税费、汇率版本、延迟出账、最终证据及失败退款规则 |
| 预留与后结算 | 预留不足时谁承担差额、何时补扣、是否允许透支、账单迟到的最长等待及人工处理 |
| 同键补交 | 上游是否正式承诺幂等、幂等键保留期、同键异体冲突、跨账号/换 Key 的作用域 |
| 渠道自动切换 | 原渠道是否确定未执行、原报价是否覆盖新渠道成本、批准是否仍有效 |
| BYOK 模式 | 用户上游费用与 Glowloom 平台服务费如何分开；不应由竞品路径直接决定本项目收费策略 |

### 8.3 不适合直接照搬的实现

- 桌面端本地单用户 SQLite、文件凭据和无 SaaS 钱包形态，不适合作为 Glowloom 的多租户财务边界。
- 只展示当前目录价格，不能替代 Glowloom 已有的价格发布、冻结报价和确认时重检。
- 参考账单展示里的固定 `1.5` 不宜成为全模型通用政策；应由价格规则解释和发布。
- JavaScript 浮点与 `toFixed(4)` 用于预览，不能替代服务端精确账务。
- `Outcome.regenerate` 是读投影，不能直接当成写权限、消费授权或防重复提交凭证。
- 上游返回 `quota` 不能直接当作平台积分；需要明确币种与兑换合同。
- 不把单个测试、历史费用记录或成功案例视为整个计费系统已验收。

## 9. 公开实现缺口与许可范围

### 9.1 本轮无法从该仓库确认的财务实现

本轮没有获得或验证下列官方远端实现：

- 模型采购成本与销售价发布后台；
- 充值产品、支付创建、回调验签、支付幂等；
- 钱包并发扣款、赠送余额和有效期；
- 官方 quota 与人民币的准确转换；
- 实际美元账单如何对齐到一次生成及其原始账单凭证；
- 预留补差、退款和财务对账的完整流水；
- 统一人民币消费上限在所有调用入口及最终派发的强制执行。

当前本地数据库明确清理 `model_pricings`、`credit_accounts`、`credit_ledger_entries`、`billing_orders`、支付通知、对账表和旧价格 SKU 表，是“当前本地端不负责托管商业账务”的正面证据；**不证明这些服务完全不存在，也不证明曾在本仓库完整公开。**[B02]

### 9.2 对“参考代码”的许可事实

该版本 README 和许可说明明确表示采用分范围的 Source Available 许可，历史 MIT 材料保留原许可；不能将整个当前仓库当成标准 MIT 项目。[B33]、[B34]

本轮将其作为架构与交互调研来源，没有复制业务实现。若以后需要复制具体代码或以其代码提供商业/托管服务，应按所选文件和提交核对适用许可范围；本研究没有做逐文件许可归属鉴定。
