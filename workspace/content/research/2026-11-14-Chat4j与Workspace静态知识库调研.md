## 2. 对信息架构的启发

下表是结合现场观察形成的设计判断，不是 Chat4j 对外承诺：

| 参考观察                           | Workspace 采用建议                                                  |
| ---------------------------------- | ------------------------------------------------------------------- |
| 目录树按主题分组，条目标识内容类型 | 保留完整文档目录，增加领域入口与需求主链视图，三种入口指向同一正文  |
| 专文、课程和项目文档分别有入口     | 知识正文、Skill、工作流定义与执行记录分别组织，避免混在文章列表里   |
| 图库、知识图谱与原文共同存在       | 架构图、主链和引用关系从已有内容派生，点击能返回原文                |
| 关联工程与角色工作约定             | 给研发 Agent 提供版本化工程地图与任务上下文，角色筛选不冒充系统授权 |

不采用课程订阅、社交、学习时长、营销横幅、私有仓库分发等与当前研发 Workspace 无关的功能。没有证据说明 Chat4j 使用哪一种静态站框架，不能把候选选型标注为“Chat4j 同款”。

## 3. 静态展示技术比较

| 方案与一手来源                                                        | 已核验能力                                                                      | 对本项目的判断                                                                                                     |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| [Next.js 静态导出](https://nextjs.org/docs/app/guides/static-exports) | 可构建 HTML/CSS/JS；依赖请求、Cookie、Server Actions 等动态能力不属于纯静态导出 | 推荐作为评审方案：复用现有 React/Next/shadcn，后续在线协作可继续使用相同内容与界面模块；需自行补文档目录和渲染管线 |
| [VitePress](https://vitepress.dev/guide/what-is-vitepress)            | 面向 Markdown 的静态站生成器，具有文档主题和 Vue 扩展能力                       | 若目标只有文档站，初始投入更小；当前还要编辑、任务和工作流，需承担另一套 Vue 界面与集成边界                        |
| [Astro Starlight](https://starlight.astro.build/getting-started/)     | 基于 Astro 的文档主题，提供内容、侧栏及搜索等文档能力                           | 适合阅读站；引入 Astro 工程约定及后续协作页面集成成本，需要单独权衡                                                |
| [Pagefind](https://pagefind.app/)                                     | 对构建后的 HTML 生成静态搜索文件，可通过浏览器 JS API 查询                      | 建议与静态阅读版组合；中文召回、业务 ID、过滤与产物大小必须用实际语料验收，不承诺未测性能                          |

Next 官方页面本次显示最新文档版本为 16.4.6；仓库 `frontend/package.json` 实际为 Next 16.3.6、React 19.2.8，Node 主版本 24。这里只采用静态／动态能力边界，不自动升级依赖；实施时按选定安装版本验证。本轮未安装或构建上述候选工具。

推荐原因是完整 Workspace 的长期界面复用，属于项目设计取舍；不能从官方文档推导其开发成本一定最低。VitePress/Starlight 作为真正可行的阅读优先替代保留，用户尚未选定具体框架。

## 4. Skill 与工作流的公开依据

[Agent Skills 规范](https://agentskills.io/specification)规定 `SKILL.md` 及必要的名称、描述，允许引用资源；正文在选用后读取，其他材料按需加载。Workspace 可以保存标准 Skill 原文并生成目录、依赖和验证视图，不需要另造 Skill 文本格式。不同主机的发现、安装和工具授权仍需各自核验，元数据中的工具声明不等于运行沙箱已经强制执行。

工作流定义是本项目研发合同：输入、阶段、产物、验收及交接。是否让某个 Agent 执行、如何获取认证与恢复句柄，不由文档站框架或 Skill 规范代为保证；沿设计43单独定义。

## 7. 文档朗读、语音时序与阅读跟随

新增[短链接](https://v.douyin.com/GG1VSyb6gE8/)实际指向[王七七的53秒作品](https://www.douyin.com/video/7688056263297627577)。浏览器已打开，画面可见知识正文与黄色高亮；页面作品说明与用户分享文案一致，描述了自有声音复刻、TTS切片和时序驱动的跟随。未取得完整音轨转录，不把分享文案当口播逐字稿，也未下载视频或音频。

作者公开评论解释：前端利用合成后的时序识别当前句子；另明确说明黄色背景跟随自动化，页面滚动由自己操作。因此能支持“朗读＋时序高亮”的参考判断，不能据此认定视频演示了自动滚动、逐字精确同步或完整无障碍能力。作者自述的开发耗时不是Glowloom交付估算。

读取[MiniMax官方T2A文档](https://platform.minimaxi.com/document/T2A%20V2?key=66719005a427f0c8a5701643)：页面提供 `subtitle_enable` 与 `subtitle_file`，字幕为句级JSON、时间单位毫秒，且有适用模型限制；非流式URL结果有有效期。这说明音频与时序可作为阅读定位依据，但不证明任意当前模型或账户都支持逐字时序。本次仅核对文档，没有调用模型、申请音色或上传声音。

设计判断：以文档块／句段映射生成朗读文本，音频、时序、文档修订和音色参数共同版本化；预生成产物可以在静态站播放，合成仍由受控在线能力或获授权的生成任务完成。自动滚动应为可关闭的扩展，用户手动阅读时让出控制。默认建议使用系统音色，复刻本人或其他获授权音色作为可选能力，不将某供应商或声音克隆升级为已确认要求。详见[设计43 §7.15](../design/43-Workspace知识库与研发工作流服务设计.md#715-文档朗读与语音时序跟随)。
