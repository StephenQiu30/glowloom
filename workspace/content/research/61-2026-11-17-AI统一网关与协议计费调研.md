## 1. 结论与研究范围

**建议在既有 Execution 内完善统一 AI 网关业务边界，首选官方 Go SDK 承担同协议上游调用；跨协议转换按真实需求选用成熟组件。**
这条路线复用现有任务、号池、报价、冻结、结算和恢复能力，不另建一套网关用户、钱包或商业定价后台。
SDK 不是完整网关服务器；仍需薄协议入口、鉴权及业务合同整合，不能把“使用 SDK”写成“兼容入口已完成”。

本轮用户已经确认的产品方向：

- 所有 AI 服务调用、调度和模型计费统一经过业务网关治理。
- 同一模型规格按固定销售价向用户计费，实际供应商采购价独立核算。
- AgentScope 是可接入技术栈的例子，不是指定必须替换现有 Agent 的框架；具体复用方案由研究决定。
- 明确支持范围，先验收实际支持的协议子集，验证后再扩展转换，不要求任意协议无损互转。
- 遵循 MVP，复用成熟组件，关键业务歧义通过文档评审与 Grill Me 明确。

研究建议与产品确认分开：

- OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 分别声明兼容范围。
- 首期优先同协议直通；只有确有业务需要且能通过协议测试时才加入转换。
- Bifrost Go Core 是跨协议候选，但本次快照要求 Go 1.27.3，高于项目基线，不能直接定为可安装依赖。
- LiteLLM 是独立代理备选；采用它需要重新明确部署与路由权威，不能静默叠加。
- 媒体生成仍保留供应商异步任务适配，统一授权、派发、计量与结算不等于强制全部转成文本协议。

本页回答组件与协议如何复用，不替代 PRD 验收、真实供应商账单核对或商业发布批准。

## 2. 本仓库已有基础与差距

以下为基于本仓库 `4e9fd572e671c64367e4eb400166d4db31079e29` 的源码观察，路径以仓库根目录为基准；没有将静态存在等同于运行验收。

| 范围 | 已有事实 | 与统一网关目标的差距 |
| --- | --- | --- |
| API Gateway | `backend/gateway/proxy/routes.go:15` 将业务 API 分发给各服务 | 是服务路由入口，不能据此认定已提供三类 AI 标准协议 |
| 普通生成 | `backend/execution/operation/adapter/providerhttp/strategy_openai_standard.go:27` 区分 GPT-6 Responses 与其他 Chat Completions；文本为非流式 | 已有适配资产可复用，标准协议入站和完整流式语义尚需补齐 |
| Agent 模型调用 | `backend/internal/agent/adapter/modelgateway/chat.go:200` 固定调用 Chat Completions、`stream:false` | 与普通生成是两条实现路径；本轮检查未发现 Anthropic 模型协议支持 |
| Agent 前端框架 | `agent/src/pi-durable/model-provider.ts:86` 使用 Glowloom provider，经 BusinessClient 进入 Go | 不能把内部桥接理解为已向任意标准 SDK 提供兼容 API |
| Agent 账务 | `backend/internal/agent/adapter/modelgateway/gateway.go:184` 已创建操作、报价并冻结；`:392` 按原用量计价并结算，受冻结上限约束 | 应保留资金链；统一改造需证明所有入口仍遵守同一报价与账本合同 |
| Agent 号池 | 同一 `gateway.go:231` 写入 `provider_binding` | 未见对应 `route_pool_binding`，普通生成的号池证据不能覆盖 Agent |
| 普通生成号池 | `backend/execution/catalog/application/route_pool.go:11` 有版本化发布；`backend/execution/operation/adapter/postgres/route_pool.go:14` 按优先级及容量选择并冻结采购价格身份 | 已有主备路由基础，不等于已实现实时最低价或全部 AI 入口路由 |
| 安全补尝试 | 上述 Postgres 号池文件 `:60` 只放行 TCP 建连前失败后的唯一补尝试 | 新 SDK/框架不能绕过该边界隐式再次发送 |
| 积分精度 | `backend/execution/billing/domain/credits.go:20` 已有人民币微元与整积分向上取整 | 不应再引入网关自带 token 配额作为另一种可扣款余额 |

[既有验收研究50](50-2026-11-13-模型号池与销售计费验收.md)报告单线路 DeepSeek/方舟实单及双线路隔离测试。
它未提供真实同规格双供应商切换与供应商账单核对的完整证据；本轮没有重跑这些实单。

因此，主要工作是收敛已有入口与合同、复用协议组件并补证据，而非从零设计新号池、新账本和新 Agent 服务。

## 3. 市场方案与复用边界

候选按实际角色比较：SDK、可嵌入网关、完整代理、桌面配置工具和 Agent 框架不是同一类产品。
Magpie 与 CC Switch 的项目身份沿[研究49](49-2026-11-13-模型号池与多供应商路由调研.md)并经本次 GitHub 核验，分别是 `yetone/magpie` 和 `farion1231/cc-switch`。

| 候选 | 已核验能力与许可范围 | 对 Glowloom 的取舍 |
| --- | --- | --- |
| 官方 OpenAI Go / Anthropic Go SDK | 官方协议类型、请求和流式客户端；可配置上游地址与重试；两库为 Apache-2.0 | 首选同协议调用组件；复用现有 Execution 和账本，薄入口自行接业务合同；SDK 不提供号池或商业钱包 |
| Bifrost | Go Core 可嵌入，HTTP transport 有 Chat、Responses、Messages；供应商适配、Key 权重、重试和 fallback；根许可 Apache-2.0 | 跨协议优先候选；当前快照 Go 1.27.3 不匹配项目 Go 1.26.0/toolchain 1.26.11，先核定兼容版本与行为，不能直接引入 |
| LiteLLM | Python SDK/代理提供多类文本、图像与音频入口，支持模型组、限额和成本观测；MIT 不覆盖 enterprise 目录 | 独立服务备选；会增加进程、配置与运维边界，必须避免与 Execution 重复选路、重试和扣款 |
| New API / RelayKit | 完整 Go 网关、渠道权重与多 Key；RelayKit 提供协议转换；根项目与 RelayKit 标明 AGPLv3 | 参考号池与协议设计；完整用户/配额/数据库能力与现有业务重叠，许可适用须单独核定，不能直接视作替换底座 |
| Magpie | Go 本地网关及 Docker，支持多文本协议、逐 Key 协议/套餐/权重、路由组和会话亲和；MIT | 借鉴凭据能力目录、原任务身份与运营界面；核心位于 internal，不等于提供可直接嵌入的公共 SDK |
| CC Switch | Rust/Tauri 桌面配置与代理，区分直连、路由、聚合；支持多协议转换和故障转移；MIT | 借鉴配置可用性与命中诊断；其安全文档定位本地单用户，不能承担平台多用户隔离与资金事实源 |
| AgentScope | Python Agent 框架，适配 OpenAI Chat/Responses、Anthropic；凭据可配置 base_url；Apache-2.0 | 作为标准网关客户端样例；无需替换既有 Pi Harness，不能把框架重试当成平台路由策略 |

### 3.1 为什么首选现有业务网关加官方 SDK

项目已有大部分商业合同，新增独立完整网关会带来重复账号、预算、配置发布及失败状态。
官方 SDK 覆盖原厂协议类型与流事件，适合先接入同协议供应商；具体第三方供应商仍需单独兼容验收。
这既满足不重写协议客户端，也保留了 Glowloom 对授权、实际发送和资金变动的唯一控制。
该建议不意味着 SDK 已通过本仓库构建，也不意味着任意第三方 `base_url` 都与原厂完全一致。

两库均可注入 BaseURL、HTTPClient 和重试配置。OpenAI 当次快照要求 Go 1.26.0，Anthropic 要求 Go 1.25；在声明层面可适配项目当前基线，合并依赖图仍待构建。
SDK 的环境默认值不能决定付款线路：每个 attempt 显式注入已选端点、凭据版本与禁用重试配置。
本项目自定义供应商的 DNS 固定、公共 IP 和 Host 等校验位于 `backend/execution/operation/adapter/providerhttp/gateway.go` 的 `Client.do`，不全在底层 Transport。
因此，仅把现有 `http.Client` 传给 SDK 不能证明安全策略已复用；适配必须覆盖完整地址准入、重定向、超时、取消与发送证据路径。

### 3.2 Bifrost 的能力与边界

[官方 Go SDK 示例](https://github.com/maximhq/bifrost/blob/3836b75029eff8082a863b1876ee90780c95b384/docs/quickstart/go-sdk/setting-up.mdx)允许宿主通过 Account 提供供应商配置和 Key，无需采用其完整管理数据库。
[Core API](https://github.com/maximhq/bifrost/blob/3836b75029eff8082a863b1876ee90780c95b384/core/bifrost.go#L1073)包含 Chat/Responses 非流及流调用；[Anthropic 转换器](https://github.com/maximhq/bifrost/blob/3836b75029eff8082a863b1876ee90780c95b384/core/providers/anthropic/responses.go#L4598)有导出的请求、响应与流转换能力。
但[HTTP integration](https://github.com/maximhq/bifrost/blob/3836b75029eff8082a863b1876ee90780c95b384/transports/bifrost-http/integrations/router.go#L48)依赖 transport/framework 等模块，安装 Core 不会自动得到完整兼容服务器。
[Core go.mod](https://github.com/maximhq/bifrost/blob/3836b75029eff8082a863b1876ee90780c95b384/core/go.mod)要求 Go 1.27.3；本轮未找到并构建一个满足项目基线的锁定版本。

### 3.3 Magpie 与 CC Switch 可以借鉴什么

## 4. 协议、路由与计量合同

### 4.1 三类文本入口分别验收

| 协议 | 数据与工具结构 | 流式及用量注意点 |
| --- | --- | --- |
| OpenAI Chat Completions | `/v1/chat/completions`，messages → choices/message；tool_calls 与 tool message 关联 | 请求 `stream_options.include_usage` 后，末尾可能是 choices 为空的 usage chunk；中断可能拿不到最终用量 |
| OpenAI Responses | `/v1/responses`，input/output items；function_call 与 function_call_output 独立 | 使用 typed events，不能简单转成 Chat chunks；终态与错误需保留，缓存/推理 token 是总量细分 |
| Anthropic Messages | `/v1/messages`，system + content blocks；tool_use/tool_result 关联 | message_start、content_block、message_delta、message_stop 各有语义；累计 usage 不能逐事件求和 |

[OpenAI 迁移指南](https://developers.openai.com/api/docs/guides/migrate-to-responses)说明 Responses 与 Chat 的 Items、函数调用和状态管理不同；[流式指南](https://developers.openai.com/api/docs/guides/streaming-responses)说明事件差异。
[Anthropic 流式指南](https://platform.claude.com/docs/en/build-with-claude/streaming)覆盖工具参数增量和流内错误。
MVP 仅承诺经过验证的文本、工具、流式、终态和用量子集；Files、Conversations、托管工具、thinking 和多模态按模型能力单独开放。
必需字段无法映射时明确拒绝，不能静默丢弃后仍声称兼容。

### 4.2 一次逻辑调用与真实发送分开

调用方幂等键对应一个逻辑业务调用，每次真实上游发送对应一个 attempt，并记录已绑定线路及凭据版本。
一个 attempt 只能交给 SDK/组件一条已授权线路与一把凭据；路由、框架或 SDK 不得自行扩展为多次潜在收费发送。
[Bifrost 重试说明](https://github.com/maximhq/bifrost/blob/3836b75029eff8082a863b1876ee90780c95b384/docs/features/retries-and-fallbacks.mdx#L22)明确 Key 轮换不消耗 max_retries，设成 0 仍不等于池内只尝试一次。
[AgentScope OpenAI 模型](https://github.com/agentscope-ai/agentscope/blob/a9f0677013b2bfe2d8862b1ac9026064f4cc25bf/src/agentscope/model/_openai_chat/_model.py#L131)和[Anthropic 模型](https://github.com/agentscope-ai/agentscope/blob/a9f0677013b2bfe2d8862b1ac9026064f4cc25bf/src/agentscope/model/_anthropic/_model.py#L129)自身默认重试 3 次，还会传入独立 SDK 配置。
[OpenAI Python](https://github.com/openai/openai-python#retries)与[Anthropic Python](https://github.com/anthropics/anthropic-sdk-python#retries)默认另有 2 次重试，说明只关闭网关一层不足以约束发送次数。
对已发出但受理未知、已出现流内容或已取得任务号的请求，保留原身份查证；不因超时或 HTTP 5xx 自动切线路重新生成。

### 4.3 DeepSeek 多供应商不能只按名称聚合

准入至少核对精确模型版本、协议、上下文/输出上限、工具与结构化输出、计量口径及凭据所属额度。
同一账号的多把 Key 可能共用额度，应沿实际账号或额度组约束容量，不能把 Key 数量直接当作独立配额。
MVP 使用管理员审核的同模型同规格候选与优先级；跨模型自动降级和实时竞价路由不属于必要闭环。

[DeepSeek Anthropic 兼容页](https://api-docs.deepseek.com/guides/anthropic_api)在观察日明确：

- 原生提供 Anthropic 格式，但 `anthropic-version`、部分 thinking/parallel-tool 参数存在忽略或特殊处理。
- 部分不支持的 Claude 名称会映射到 DeepSeek 模型；因此请求 model 字符串不能证明实际使用了 Claude。
- 某些 Claude Code/OpenCode 场景会提高有效 max_tokens；不能未经验证就把参数视为采购费用硬上限。
- 最终 message_delta.usage 是累计值，不能再加上 message_start；输入总量需含缓存读取与创建桶。

上述是官方该端点的事实，不能推广为所有第三方 DeepSeek 供应商都支持相同功能或价格。

### 4.4 采购、销售与积分分账

采购成本绑定实际供应商、模型映射、线路、合同价格版本、币种、计价单位和实际用量。
销售价绑定用户选择的模型规格及销售版本；报价时冻结，供应商切换不改变已确认销售规则。
同一 token 模型的固定销售价指固定单价/规则，实际账单仍按合同规定的用量计算，不等于所有文本请求固定扣同一数额。
积分钱包沿既有合同冻结、核销、释放与调整；网关的虚拟 Key 限额和成本估算不能成为第二个可扣款余额。

用量归一化必须保留原协议与脱敏原始计量证据：

- OpenAI/DeepSeek Chat 的缓存输入是输入总量细分，不能在总量外重复加收。
- Anthropic 的 input_tokens 是未缓存输入；cache read/write 是另外的输入桶，缓存写入 TTL 也可能影响采购单价。
- reasoning_tokens 通常是输出总量细分，不能未经供应商合同核实就另行重复计费。
- 图像数、视频秒数、音频时长和工具次数按实际合同记录，不强行折成 token。
- 流中断、回调迟到或 usage 缺失是待核验状态；不能用“0 token”或客户端估算冒充实际采购结算。

[DeepSeek 定价页](https://api-docs.deepseek.com/quick_start/pricing)显示缓存命中/未命中、输出、峰谷时段及按次工具等维度；[缓存文档](https://api-docs.deepseek.com/guides/kv_cache)解释 hit/miss 字段。
[Anthropic 缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)说明非缓存、读取、创建及 TTL 计价差异。
这些证据支持价格版本与有限计量单位的设计，不要求 MVP 同时上线所有模型、工具和任意计价脚本。
取消、部分输出、未知用量的用户扣费与处理期限必须沿设计41的确认合同执行，本研究不另定资金规则。

## 6. 最小取舍与验收限制

最小设计取舍是一个业务网关边界、一套已存在的资金账本、明确版本的供应商映射及按需复用的协议客户端。
各 SDK 或候选组件只承担适配能力，不替业务层决定用户余额、采购合同或跨模型降级。
暂不加入独立开发者平台、个人订阅账号共享、第二钱包、自动最低价竞价、任意插件 DSL 或新的 Agent 运行时。

下列为需要进入对应 PRD 的验收维度，本次没有执行：

| 场景 | 需要取得的证据 |
| --- | --- |
| 三协议调用 | 锁定 SDK 版本，分别完成非流、流、工具往返、错误与终态；不支持字段明确失败 |
| 实际发送次数 | 模拟上游统计 POST，覆盖 SDK/框架重试、超时、5xx、半途断流，证明没有隐式收费补发 |
| 同规格双供应商 | 相同销售报价下命中不同供应商，采购价格与用量归属准确；真实验收需有授权和真实回执 |
| 用量完整性 | Chat 空 choices 的 usage 不丢；Anthropic 累计值不重复加；Responses 工具与终态可追踪 |
| 账本幂等 | 并发重放、重复回调、乱序恢复只产生合同允许的冻结和结算；未知费用可追踪处理 |
| 媒体原单恢复 | 保留原供应商、凭据版本和上游任务号，取消/超时后不重新创建收费任务 |
| 框架接入 | 标准 SDK 客户端能使用网关地址和平台凭据；AgentScope 可作样例，但不作为唯一验收对象 |
| 依赖与工具链 | 官方 SDK 在本仓库构建；如引入 Bifrost，取得兼容版本或经确认的 Go 升级依据 |
| SDK 出站策略 | 自定义地址、重定向、DNS 指向私网、代理、TLS 和发送后超时均经过原有完整策略，不绕过 Client.do 的校验 |
| 供应商对账 | 将实际采购回执与供应商账单核对，不以网关估算成本、README 或隔离测试代替 |

本次交付的是有来源的设计建议与差距核对。依赖构建、协议集成、真实双供应商路由、收费恢复及采购对账均不能据本研究标记为通过。
