### 3.1 保存链路

1. **主保存路径是节点、连线的增量批处理。** Canvas store 的 add/update/delete 入口调用 SyncQueue.enqueue；队列合并待发送操作，经 convertNode/convertEdge 生成 `nodes.{create,update,delete}`、`connections.{create,update,delete}`；POST `/api/canvas/nodes/batch`，附项目 ID 与版本。不是仅靠定期提交整张图 JSON。
2. **持久化 DTO 与交互运行时节点分离。** Node DTO 包含 nodeKey、projectUuid、type、name、tag、position（X/Y 字符串）、measured（宽高字符串）、parentKey、JSON.stringify(data)、workflowUuid；edge DTO 含 connectionId、source/target、handles、type、deletable/selectable。会清除 blob/data 临时资源 URL。它保存的是稳定节点身份、布局、分组、业务 data 与边关系，未将整个 React Flow 运行时对象原样提交。
3. **保存触发来自编辑操作，队列合并后调度。** 默认 RAF 调度；`NEXT_PUBLIC_COLLAB_RAF` 为 false/off/0/no 时才采用 500ms fallback。部分节点更新有独立 300ms 聚合路径。不要把 500ms 说成实际固定自动保存频率。增删改会按节点/边身份合并，带初始存在/不存在基线及“可能已落库”标记，处理删除后重建等情况。
4. **本地恢复确实接入保存队列。** module 349233 的 IndexedDB `liblibtv-sync/pending-ops` 被 034 的 SyncQueue 引用；按 projectUuid 聚合 operation，记录 createdAt、logicVersion=1。串行写入、按项目读取/清除，默认开启，可用 localStorage 开关关闭；TTL 配置 24h，并在构造时触发 purgeStale。离线、暂停、特定失败及退出路径会写 recovery journal，恢复网络/切项目等路径启动 replay。不能将 TTL 直接等同“保证离线保存24小时”。
5. **有恢复重放门控及发送边界。** 保留 projectGeneration，避免旧项目异步响应污染新项目；replay readiness gate 默认 30 秒；可注入 collab filter、offline transformer、upload gate。普通 flush 单飞，在途期间新增操作排队；大于200条操作时分块，413有额外处理。不能据此前端代码证明服务端事务原子性。
6. **保存状态和错误恢复是一等状态。** saved/pending/syncing/error/conflict 及失败消息进入 store；一般错误最多三次指数退避（1/2/4秒），业务错误、会话过期、413等分支另行处理。成功后才有正常 ack/清理路径；requestId 由 API 包装器生成或沿用，但未证实跨重试稳定，也未证实服务端幂等表。
7. **并发控制有明确客户端接口，但最终语义未知。** payload 含 version；本地有 serverVersion/localVersion；成功时本地版本自增；识别 HTTP409 或 VERSION_CONFLICT，调用可注入 conflict resolver。API 包装器可加 sessionId/timestamp，10101 表示项目在别处打开而暂停/处理。可见协同过滤和编辑锁接入。没有服务端证据，不能定性为严格 CAS、OT 或 CRDT，也不能断言每个冲突错误一定进入该分支。
8. **退出补发与恢复日志并存。** flushSync 对剩余操作保留恢复记录，使用 fetch keepalive，并有 sendBeacon fallback；61,440字节阈值影响发送路径。这是尽力提交；该分支 notifyOpSettled(ok:true) 不能证明服务端确认，因此不能算强持久化承诺。
9. **另有 draft、用户状态、payload、版本快照 API。** 015 中有 draftJson/canvasConfigJson/viewport 参数的 draft-update 包装器，021 中列出 user-state、node payload save/get、artifact-version、project version snapshot 等。已采集脚本中没有确认 draft-update 的具体编辑器调用点，不能把整图草稿与增量主路径的当前分工、触发频率或兼容历史解释成定论。

### 4.1 状态链条

1. **编辑器内存**：canvas store保存nodes、edges、viewport及workflowMeta。节点新增调用`enqueueOperation`；节点字段改动以`{type:"update",target:"node",targetId,data:{data:...}}`入队；位置变动以`{type:"move",target:"node",targetId,data:{position}}`入队。R2/R6/R7/R20。
2. **批次与合并**：拖动更新先以nodeId为key放入Map，100ms的gC包装触发一次提交，后续有flush路径。协作队列50ms触发一次批次，用文档`transact`应用操作；也提供立即操作。队列容量100，满时shift丢最旧操作，历史操作仅内存保留最多1000。静态可见这些边界，不代表已实际触发数据丢失。R5/R7/R12。
3. **共享数据结构**：store名为`yjs`，创建文档`new WUe`；`getMap("canvas")`，其`canvas_content`为Map，包含`type:"canvas"`、`nodes` Array、`edges` Array；每个节点/边递归转换为Map/Array；画布id/name/description位于外层Map。对单节点data按字段增量更新；数组部分会delete+push；setRemoteData支持按id增量合并或fullReplace。R2/R4/R6。
4. **网络同步**：使用自带`THe` provider，URL由`wss://${host}/canvas/ws`加`/roomname`及参数构成。参数名有roomId、userId、token、type、yjsClientId、version；version常量1.0.1属于此客户端协议参数，不能称为文档修订号。WebSocket为arraybuffer，文档update编码为同步消息send；连接时同步握手，另有awareness与同浏览器BroadcastChannel通信。R3/R17。
5. **重连与恢复**：provider配置base delay 3000ms、max backoff 30000ms、最多30次、指数退避加随机抖动；每小时resync。收到sync后绑定nodes/edges；初始化优先读取远端图，远端空而本地有节点时有initData保护分支。无登录凭据即跳过连接。没有验证离线关闭页面后能恢复未同步编辑。R18/R19。
6. **共享字段选择**：默认过滤客户端传入的running状态、output、finished状态；allowFields可显式允许output/finished，running仍被拒绝。说明编辑状态与任务结果有不同更新约束，但不能仅凭过滤认定所有结果均由服务器写入。上传临时blob/data URL、uploading/upload_error、composeRunning及部分UI属性有清洗处理。R8/R10/R20。
7. **视口**：`updateViewport`经1000ms包装调用`jr()`，按canvasId存到localStorage键`rh_canvas_viewport`。团队presence也可发送viewport awareness；与主nodes/edges文档和手动导出快照的viewport应区分。R11。
8. **撤销/重做**：独立内存快照栈，最多50步，保存nodes/edges/meta/timestamp；undo/redo可向Yjs增量setRemoteData。恢复时保留当前status/output/sourceObjects（某些节点类型有例外），不能将撤销栈称作服务端版本历史。R13。

### 4.2 模板保存

`SaveWorkflowDialog`调用store.exportWorkflow，得到`{nodes,edges,viewport}`；导出剔除computedPosition、handleBounds、selected、dimensions、isParent、resizing、dragging、events、initialized等UI运行时字段，并过滤悬空边。所选编组可单独导出。对nodes/edges的序列化大小设80MiB前端限制。R9/R10/R14。

HTTP调用payload形状：`{id:"",name,description,workflowContent:{...exportedGraph},thumbnail?}`，经`saveWorkflow` POST `/canvas/workflow/save`。发送前建立localStorage `workflow_backup_<timestamp>`，内容{name,data,savedAt}，最多保留3个；成功删除对应备份；失败携带backupKey到error事件。这是手动保存模板对话框的备份行为，不能推及所有节点自动保存。R14/R15/R16。

### 5.2 静态协议证据

#### 5.2.1 基线读取与历史版本

core 的 readSource/getProjectDraftAndResources 请求 `need_draft_json`，指定历史版本时带 `draft_version` 与 `exact_draft_version`；返回的 draft_json、draft_version、data_version 经 keyframe baseline decoder 校验。缺 draft_json、外部 dataVersion 不可读或精确版本不一致均会拒绝。

main 的历史列表检查每个 revision 的 draft_version、base_draft_version、update_id、actor_kind/id、edit_source、operation_id、data_version、committed_at_ms，并要求版本连续。恢复历史版本响应校验 `head_draft_version === expected_head_draft_version + 1` 及 `idempotent_replay`。这说明客户端历史恢复协议以创建一个新 head 为预期；不能只凭客户端验证证明服务器保证。

定位：core [75000,75700)、[343000,345200)；main [1114900,1117200)。

#### 5.2.2 保存单元是带身份与版本的操作，不是每次整图

协同 runtime 的 commit 为本地编辑建立 updateId（默认 crypto.randomUUID），产生 requestType、operateType、mutations，加入 network local operation 队列。出站 `revision` 载荷包含 projectId/draftId、updateId、baseDraftVersion、dataVersion、operation bytes、canonicalCommand；可带 inverseOfUpdateId/requestLogId。canonicalCommand 还描述命令类型、目标和受影响对象/边、changed paths。

协议支持 revision_batch，经协商后最多16个候选 revision 打包；支持 protobuf 二进制与协商的压缩。Frontier transport 对 Uint8Array 设置 application/x-protobuf，并区分 collaboration 与 presence channel。该代码支持增量协议；运行时是否每次使用batch/压缩应以消息证据为准。

定位：494 [7600,8500)、[121300,124600)、[130000,132000)；3817 [70000,72000)；transport [3200,4500)、[9500,10400)。

#### 5.2.3 authority ACK 是待确认操作的确认边界

服务器消息分支包含 joinAck、sync_complete、ac、broadcast、reject、submit_failed、resync_required、permission_changed、backpressure、heartbeatAck。`ac` 进入 `_receiveAcknowledgement`：必须能匹配 consuming/pending updateId，再检查 ACK 的 dataVersion 与对应本地提交一致并可解码 operation；不满足时进入恢复，而非直接显示成功。

`_commitAuthorityAcknowledgement` 清理 pending 和重试信息、设置 appliedDraftVersion、settleUpdateAcceptance(accepted:true)。若该更新有本地 durability record，随后 **后台** finalize journal 为 accepted，再调度剩余pending快照。不能将“收到ACK”和“本地终态已落盘”合成一个同步动作，更不能把客户端所谓 authority ACK 等同已独立验证服务器磁盘持久化。

定位：494 [132600,135700)、[139500,140200)、[181900,183000)。

#### 5.2.4 保存状态不是仅看网络连通

getSaveState 优先返回 blocked、unsaved、unknown_timeout，否则有 pending 返回 pending，没有则 saved。状态快照还包括 appliedDraftVersion、recoveryState、operationPending、localEditingAvailable。离线journal终态写失败时有降级/unsaved分支。

因此页面显示 Room connected 与显示“已保存”分别描述连接和本地状态机判断；读到现有项目时“已保存”并不构成新编辑持久化测试。

定位：494 [95000,95800)、[97600,98500)、[105700,106700)。

#### 5.2.5 并发存在实际双向变换路径

runtime 的 `_followNetworkOperation` 明确只接收 local × authority 或 authority × local；`_transformLocalAndAuthority` 对双方 mutations 分别调用 SDK.followMutationBatch，并在离线重放恢复中使用同类变换。可称为 **客户端 OT 式操作变换路径**，不只是凭依赖名推测。没有充分依据把整个平台断言为某特定成熟 OT 库，或推断服务器是否也运行相同变换。

基线恢复还会先拉 authority revision、校验已接受操作，再重建 pending。缺版本、不可证明ACK、schema/dataVersion不兼容可转入 needs_refresh/blocked 等恢复状态，避免静默把不可信操作当成已保存。

定位：494 [68000,70100)、[77900,78500)、[94500,95000)、[132000,133300)；core [250300,254000)。

#### 5.2.6 真正业务 IndexedDB journal 已定位

core 懒加载 `createDraftEditIdbPersistence`，传入 accountId/projectId/draftId/readAccountId；不是只发现“indexedDB”字符串。loader 经公开 webpack runtime 映射到 `static/js/async/async-canvas-draft-edit-persistence.b85a363570.js`。

数据库命名为 `octo-draft-edits:<encoded accountId>:<encoded draftId>:1`；条目 scope 仍校验 ownerAccountId/projectId/draftId。stores 为 draft-edits 与 quarantined-draft-edits，updateId unique index。Web Locks 以 databaseName 独占、ifAvailable获取，其他标签页为 follower；账户切换后 scope invalidation 会阻止继续写旧账户数据。

durable条目包含 schemaVersion、scope、updateId、dataVersion、revisionBytes、baseDraftVersion、createdAt、可选inverseOfUpdateId。terminal条目为 accepted/rejected/quarantined + finalizedAt。reconcile 在 IndexedDB transaction 中核对pending与终态；无法解码、dataVersion不一致、scope不一致不会盲目重放。journal预算为1000条、32 MiB，超预算abort并触发容量错误处理；quarantine有单独裁剪路径。这里没有证明固定TTL。

定位：core [241096,241420)、[249035,250300)；main [1271380,1271900)、[1280376,1281900)；persistence [240,1600)、[1500,4700)、[7300,8200)、[12000,12900)、[16900,17500)、[22900,23201)。

**重要反例：** main字符约979k 的 IndexedDB 是 `canvas-agent-wire-log`，约453k 是 `octo-observability-evidence`，两者是日志/观测存储，不能当作画布节点持久化证据。

#### 5.2.7 本地耐久与远程提交并非一律串行

普通 persist() 创建 `outboundPolicy:"parallel"`，因此不能说每个网络保存之前都等待IndexedDB写完。恢复加载的durable条目设置 after_durable；isOutboundSubmittable 依据该策略和durability状态进行门控。存在本地存储不可用/配额错误后的降级路径，以及用户本地数据恢复决策回调。

这也说明“离线支持”应拆成：允许本地编辑、是否可写journal、是否有独占owner、数据是否可恢复、何时允许发回服务器。不同分支不是同一个开关。

定位：494 [58500,59500)、[60100,61500)、[64800,66700)、[70900,73300)。

## 6. 对本工程的设计输入

以下是分析推导，具体方案只在design维护，不以竞品采用作为产品确认。

- 分开定义本地反馈、网络同步、持久接受与恢复。使用Yjs不免除业务验证；浏览器不使用业务IDB也不妨碍在线Yjs协作。
- 节点/边/正文应有稳定身份和明确共享粒度；不要整图JSON替换覆盖并发修改。素材二进制和短效URL不进入共享正文作为唯一身份。
- 自动保存的业务单元应是完整编辑事务。拖动预览、文本事务、任务结果和模板导出具有不同提交语义，不照抄竞品计时参数。
- 只有已接受变更可广播为正式内容。需要单独解决拒绝后依赖更新、幂等回执、提交后广播失败、多端撤销和迁移。
- 本轮只读运行观察及静态逆向不能给三个平台作可靠性排名；服务器提交时序、权限撤销和崩溃恢复仍需独立测试。
