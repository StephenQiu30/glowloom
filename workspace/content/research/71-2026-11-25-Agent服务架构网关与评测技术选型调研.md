# Agent 服务架构、网关与评测技术选型调研（2026-11-25）

观察日期：2026-11-25。用途：为 [需求33](../requirement/33-Agent服务架构重构与技术选型需求.md) 与 [设计48](../design/48-Agent服务Mastra架构与技术选型设计.md) 的架构与技术选型提供外部市场事实与同赛道对照依据。本调研仅记录公开事实、对比与适用限制，不替代用户确认，不作为工程实现或验收证明。

## 1. 生产级 AI Agent 服务语言与编排框架格局

基于 2025–2026 公开工程实践与主流框架文档观察，生产级 Agent 服务呈现 **TypeScript 与 Python 双主流**，Go 极少用于上层 Agent 编排而主要用于下层业务网关、计费与高并发基础设施：

| 维度           | TypeScript 阵营（SaaS / Web 产品内置 Agent 主流）                   | Python 阵营（复杂图编排 / 数据与 ML 主流）               |
| -------------- | ------------------------------------------------------------------- | -------------------------------------------------------- |
| **代表框架**   | Vercel AI SDK、Mastra、LangGraph.js、官方 TS SDK + 轻量自研 Harness | LangGraph、PydanticAI、Google ADK、OpenAI/Claude SDK     |
| **服务壳趋势** | 趋向轻量化（Hono / Fastify / 纯内核库 + gRPC），重型 NestJS 较少见  | FastAPI 为绝对主流                                       |
| **持久化恢复** | Postgres Checkpoint（如 `@mastra/pg`）、自建租约表、Restate/Temporal | LangGraph Postgres Checkpointer、Temporal + PydanticAI   |
| **核心优势**   | 与 Next.js/React 前端同语言、端到端类型安全、流式与 MCP 生态一线    | 模型与数据科学包最全、复杂有状态图编排与研究工具首发地   |

**选型匹配结论（Glowloom 场景）**：Glowloom 的 `frontend/` 与 `canvas/` 均为 Node 24 + TypeScript，`backend/` 为 Go 模块化单体。选用 **Node 24 + TypeScript + Mastra（基于 Vercel AI SDK）** 既避免在仓库引入第三种编程语言栈，又能直接获得 Mastra 原生的 Agent、Workflow（`suspend/resume`）、Memory（`@mastra/pg` + `PgVector`）、MCP（`@mastra/mcp`）与 Scorers 评测能力。

## 2. AI 网关选型与同赛道开源项目对照

### 2.1 通用开源与托管 AI 网关对比

| 方案           | 核心技术栈 / 许可       | 优势                                                           | 主要局限与风险                                                 |
| -------------- | ----------------------- | -------------------------------------------------------------- | -------------------------------------------------------------- |
| **Bifrost**    | Go 单二进制 / Apache 2.0 | 微秒级低延迟、Go 栈友好、内置重试/降级/语义缓存与 MCP 网关     | 高级 RBAC 与自适应路由在企业版；仍需对接自有业务计费账本       |
| **LiteLLM**    | Python / MIT 核心       | 100+ 厂商与新模型适配最快，支持虚拟 Key 与基础预算             | 需独立 Python 运行时，高并发流式开销偏高，协议转译偶吞厂商特性 |
| **Portkey**    | TS / MIT 核心           | 强 Guardrails、Fallback 与请求治理                             | 管控面与企业合规能力绑定商业版                                 |
| **New-API**    | Go / **AGPLv3**         | 开箱即用多租户渠道与额度后台                                   | **AGPLv3** 存在商用合规传染风险                                |
| **托管聚合**   | OpenRouter / Vercel AI Gateway / Cloudflare | 零运维、多厂商 Fallback；Vercel AI Gateway 支持 BYOK 与零加价 | 不适合私有化部署；国内多模态/视频生成厂商覆盖弱                |

### 2.2 AI 影视/漫剧同赛道开源项目对照（BeefTV & Toonflow）

查阅同赛道开源 AI 视频/短剧工作台 **BeefTV**（`glanderness/BeefTV`）与 **Toonflow**（`HBAI-Ltd/Toonflow-app`）的公开仓库架构：

| 项目         | 架构定位           | 文本 LLM 调度方式                                                           | 图/视/音多模态调度方式                               |
| ------------ | ------------------ | --------------------------------------------------------------------------- | ---------------------------------------------------- |
| **BeefTV**   | Go + Wails 本地优先 | 不部署独立外部网关；Go 后端内置轻量 **Model Channels**，支持官方与自定义中转 | Go 后端按模态路由异步生成、首尾帧/参考图轮询与落盘   |
| **Toonflow** | Node + TS 桌面/自托管 | 不部署独立外部网关；配置中心动态切换渠道，由 **Vercel AI SDK** 直接调用     | 独立图像/视频适配器与 ComfyUI 工作流节点             |

**核心洞察**：

1. 通用开源 LLM 网关只擅长文本 Chat/Messages 协议，无法覆盖影视创作平台核心的**异步多模态生成**（首尾帧、角色一致性、任务轮询与资产入库），该部分必然留在 Go `execution/gateway` + `operation`。
2. Glowloom 与 BeefTV/Toonflow 的主要差异在于**云端多租户计费账本与统一 Key 治理**。演进现有 Go `execution/gateway` 为统一渠道网关（文本原生协议透传 + 图/视/音异步生成 + 多租户账本），并允许上游渠道 `Base URL` 灵活指向直连厂商、OpenRouter 或自托管 Bifrost，是兼顾低复杂度与未来扩展性的最优平衡点。

## 3. 生产级 Agent Evals 与可观测性方案对比

现代生产 Agent 评测已从单一“终态文本打分”转向**终态质量 + 轨迹评测（Trajectory：工具调用顺序/参数/防死循环）+ 成本/步数约束**，并普遍将**离线 CI 门禁**与**线上观测回流**分层解耦：

| 工具 / 平台               | 定位与许可                  | 擅长场景                                                           | 局限性                                                 |
| ------------------------- | --------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------ |
| **Mastra Scorers + Vitest** | TS 原生框架内置 / MIT       | 代码级轨迹断言 + LLM-as-a-Judge，零额外设施直接融入 CI PR 门禁     | 不替代生产级海量 Trace 存储与跨角色线上标注 UI         |
| **自托管 Langfuse**       | 开源 LLM 工程平台 / MIT 核心 | OTel 全链路 Tracing、Prompt 版本管理、线上坏 Case 沉淀 Dataset、在线采样 | 若离线 CI 强依赖远程 Langfuse 实例，会增加 CI 脆弱性   |
| **Promptfoo**             | CLI 评测与红队工具 / MIT    | 多模型矩阵横向对比、Prompt 注入安全红队、YAML 驱动 CI 拦截         | 偏向 Prompt/端点级黑盒矩阵，对内部代码态轨迹断言弱于框架内置 |
| **Braintrust**            | 商业托管平台                | 实验对比与 PM/研发协作标注体验极佳                                 | 闭源云托管，不符合自托管数据主权要求                   |

**选型匹配结论**：采用**分层双轨**——离线开发与 CI 门禁使用 **Mastra 原生 Scorers + Vitest**（无外部服务强依赖），线上生产观测、Prompt 版本管理与 Bad Case 沉淀使用**自托管 Langfuse**（配本地 Prompt 缓存兜底）。

## 4. 调研限制

- 本调研基于 2026-11-25 公开资料、框架文档与开源项目公开架构信息，未在本地实际压测 Bifrost、LiteLLM 或 Langfuse 的资源占用。
- `@mastra/pg` 禁用运行时自动建表（`disableInit`）与静态 DDL 抽取需在 P1/P3 锁定精确依赖版本后，以隔离 PostgreSQL 实测验证为准。
