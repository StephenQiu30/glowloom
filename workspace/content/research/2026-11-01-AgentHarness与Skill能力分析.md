# Agent Harness 与 Skill 能力分析

日期：2026-11-01；2026-11-04 按用户最新确认纠正技术结论。能力来源与有效确认见[需求19](../requirement/19-完整创作Agent与Skill多Agent需求.md)；正式架构唯一见[设计32](../design/32-完整创作AgentHarness与Skill多Agent架构设计.md)，不以本调研作为实现或验收证明。

## 1. 当前结论

采用同仓库独立 `agent/` 服务，使用 TypeScript、官方 Pi Durable 与 PostgreSQL，统一 Docker Compose 启动。此前“Go 原生 LangGraph/StateGraph 可直接替代官方 Pi Durable”“独立 Node 必然过度设计/脑裂”“所有测试只在 Go 内完成”的结论缺少依据，且与用户 SRC-AGH-10～15 的确认冲突，予以撤销。不得以自建 Go 状态图冒充官方 Harness。

Agent 拥有会话、执行段、计划、owned children、上下文与恢复。Go 保留身份、项目授权、审批、预算、模型出口、业务命令和业务回执。跨进程代价是显式 HTTP 合同、稳定调用身份、业务回执查询与所有权围栏；这些需要故障验证，不能仅靠服务数量判断设计好坏。

## 2. 能力与执行边界

| 能力          | 所需行为                                        | 当前架构责任                                                        |
| ------------- | ----------------------------------------------- | ------------------------------------------------------------------- |
| 持久会话      | 输入、配置、任务、采用来源和产物引用可恢复      | 官方 Harness/Storage；PostgreSQL 单 session 分区与 owner epoch      |
| 模型/工具循环 | 根据结果继续决策、控制重试与上下文容量          | Pi 官方运行时；模型与业务工具出口转 Go，冻结 manifest               |
| 提案审批      | 等待用户期间整树禁止新增业务动作                | Go 提案/控制 outbox；官方 abort 收束、quiesced 回执、新执行段 grant |
| 工程写入      | 并发冲突可检测，不能覆盖协作者的版本            | Go 正式应用命令/画布 revision CAS 和幂等回执                        |
| 现场感知      | 下一次决策采用已核验的当前工程快照              | Go 当前快照；Agent 固定该请求上下文与内容哈希                       |
| 计划管理      | 依赖、来源、完成条件与采用状态可追踪            | Agent 应用 doc 与 plan_update；不构造第二调度引擎                   |
| 多 Agent      | 专业子会话、独立上下文、等待回收与父级取消      | 官方 owned conversation/task；精确角色工具名单、共享根预算          |
| Skill 包      | 内容/资源哈希、版本冻结、本人范围、启停和撤销   | Go 包/授权权威；skill_load 按需读取已固定资源                       |
| 扩展          | 复用官方 SDK 的可信资源加载                     | 只允许镜像内已审阅入口；禁用用户目录自动发现与运行时下载            |
| 隔离脚本      | 第三方代码有实际隔离与资源上限                  | 独立隔离执行设施；未配置时明确拒绝，不运行宿主 shell                |
| 媒体验证      | 区分实际字节检查、模型评估与人工审阅            | Go 受限对象读取与检查回执；Pi 多模态正文保留实际媒体内容            |
| 创作交付      | 剧本→主体→分镜→镜头/声音→时间线→可编辑工程/成片 | 各领域正式命令与产物回执；模型文字“完成”不等于业务成功              |

## 3. 与参考实现的关系

[BeefTV](https://github.com/glanderness/BeefTV) 的已核验文件、提交基线与技术对照见设计32 §3.2。它的应用级提案收束、写版本链、现场摘要和步数上限可提供实现参考；官方 Pi Durable 的任务、提交、所有权和恢复语义应直接复用，不能照着应用名重写内核。

本项目是多用户服务，选择 Fastify/TypeBox、受限 PostgreSQL 角色、Go 业务出口、方向不同的内部凭据和 Compose 服务边界；参考应用的本地存储/桌面权限模式不自动适用。45 秒空闲与 180 秒总请求上限作用于真实上游网络；持久 SSE 的最终文本事件不能宣称为已经接受真实供应商逐 token 流。

## 4. 专业角色与交接

制作统筹显式委派 script、art、storyboard、shot、voice、edit、qa 专业角色。每个 child 在第一次 submit 前收窄工具、扩展和预算，默认不能再次委派或脱离父任务后台运行。计划采用必须引用已完成子会话的原始来源；重做创建新委派并保留原结果，不静默改写已采用稿。

子会话与根共享业务 grant、owner epoch 和总预算。子预算从根的可用额度分配，压缩、规划与工具都计入根限制；独立上下文不等于独立权限。

## 5. 验证边界

分别验收官方 Storage 一致性、真实 PostgreSQL 所有权/COMMIT 故障、真实进程 SIGKILL、审批整树收束、Go/Node HTTP、受限角色与普通业务任务替代。确定性模型/工具夹具不代表真实供应商；本地镜像健康不代表业务完成；专业角色能够委派不代表完整剧本到成片的产品接受。当前状态和实际证据仅维护于 [BACKLOG](../../../BACKLOG.md#pi-durable-migration)。
