# LiteLLM 复评与 AI 服务接入调研

观察日期为 2026-11-19，Glowloom 基线为 main 的 `08ff5e071f3c21e79c7ad8c3aaca7e33929882c2`。外部证据使用 GitHub 连接器读取，源码引用固定提交。决策见 [SRC-AI-54](../requirement/04-AI平台接入与预设管理需求.md#src-ai-54)。

## 结论

**继续使用重建后的 Go 网关，当前无需部署 LiteLLM。** 现有网关已把授权、选路、积分冻结与结算、异步任务恢复合在一条业务链路里。同协议文本复用原生 SDK，媒体复用已有任务驱动。接入眼下的明确缺口是先验证、再生效。

| 方案 | 可复用能力 | Glowloom 的取舍 |
| --- | --- | --- |
| Go 网关 + 官方 SDK / 原生媒体驱动 | Chat Completions、Responses、Messages 独立出站，媒体沿用原任务协议 | 现行方案。只有新增协议、任务生命周期或计量语义才扩展驱动 |
| 在 Go 下游使用 LiteLLM | 兼容客户端、跨协议适配、自定义处理器和异步视频接口 | 保留为特定组合的候选。专有媒体仍可能需要 Python 适配，需要衡量跨进程、凭据同步和升级成本 |
| 用 LiteLLM 承担平台主网关 | 模型与凭据管理、路由、重试、限额、费用观测 | 会重新划分资格、预算、账务和任务恢复的职责。现有业务合同需要重做接受，当前缺少足以抵消成本的需求 |

## Glowloom 代码核查

- Go 从尝试快照绑定上游模型和 Key，SDK 禁用隐式重试，并校验实际 HTTPS 主机与地址。内网 LiteLLM 若进入试验，要走单独的可信服务连接，现有公共供应商地址规则仍适用。[网关入口](https://github.com/StephenQiu30/glowloom/blob/08ff5e071f3c21e79c7ad8c3aaca7e33929882c2/backend/execution/gateway/adapter/http/handler.go#L45) [出站客户端](https://github.com/StephenQiu30/glowloom/blob/08ff5e071f3c21e79c7ad8c3aaca7e33929882c2/backend/execution/gateway/adapter/provider/client.go#L73)
- 管理页分开发布销售模型和采购路由。模型发布先停用同名同协议的旧版本，路由只接受已启用模型。两次操作之间可能缺少合格路由。路由发布会立即启用，提交载荷没有验证证据。重新提交历史模型的同一 ID 不会恢复其当前版本指针。[管理接口](https://github.com/StephenQiu30/glowloom/blob/08ff5e071f3c21e79c7ad8c3aaca7e33929882c2/backend/execution/gateway/adapter/http/handler.go#L295) [发布存储](https://github.com/StephenQiu30/glowloom/blob/08ff5e071f3c21e79c7ad8c3aaca7e33929882c2/backend/execution/gateway/adapter/postgres/catalog.go#L19)
- 媒体当前采用单产物、固定按次购销。新增动态用量、复合交付或回调语义需要定向适配。任务查询从原尝试读取任务号、路由和凭据。[媒体驱动](https://github.com/StephenQiu30/glowloom/blob/08ff5e071f3c21e79c7ad8c3aaca7e33929882c2/backend/execution/gateway/adapter/provider/media.go#L140) [原单查询](https://github.com/StephenQiu30/glowloom/blob/08ff5e071f3c21e79c7ad8c3aaca7e33929882c2/backend/execution/gateway/adapter/postgres/pending.go#L62)
- SDK 授权绑定模型版本 UUID。换版后历史调用仍依原授权合同重放，新版调用需核对授权范围。[授权储存](https://github.com/StephenQiu30/glowloom/blob/08ff5e071f3c21e79c7ad8c3aaca7e33929882c2/backend/execution/gateway/adapter/postgres/grants.go#L26) [版本切换测试](https://github.com/StephenQiu30/glowloom/blob/08ff5e071f3c21e79c7ad8c3aaca7e33929882c2/backend/tests/aigateway/entrypoints_test.go#L249)
- [重建验收记录](62-2026-11-17-AI网关重建验收.md#7-未验证或未执行)已有隔离业务证据。真实付费供应商、采购凭证、管理员实站浏览器操作和生产切换仍需各自验收。

## 重新评估 LiteLLM 的条件

1. 考察对象是明确的供应商、精确上游型号、地区、协议和模式，现有 SDK 或媒体驱动确实无法满足。记录直连适配的变更与维护成本。
2. 锁定源版本和镜像摘要，核对功能许可、镜像来源和升级影响。MIT 条款对 enterprise 目录另有说明。优先试验无业务数据库连接的单线路代理。涉及数据库的功能需另行评估，因为官方部署支持迁移作业，serving 实例需显式禁用 schema updates。[源码许可](https://github.com/BerriAI/litellm/blob/6c5aec07b49da18435ec19ba0879552f1951cc8a/LICENSE) [数据库说明](https://github.com/BerriAI/litellm-docs/blob/127412cfca27ee9ff5cd35c4557bae59f2c1bd7f/docs/proxy/database_migrations.md) [发布来源](https://github.com/BerriAI/litellm-docs/blob/main/blog/security_update_march_2026/index.md)
3. 用 Go 直连作对照。核对必需字段、流终态、原始用量、上限、故障状态和延迟。固定唯一 deployment 和精确型号，禁用代理内部选路、重试及 fallback，用接收端计数证明每个尝试最多一次生成提交。受理未知、流已开始或已有任务号时，沿原尝试恢复。[LiteLLM 重试语义](https://docs.litellm.ai/docs/router/learn/reliability)
4. 模拟合约通过后再用明确预算验证真实渠道，每次付费探针保存单独收据。仅当覆盖收益或维护节省明确，且业务账本、恢复和回退通过，才考虑让新请求走该适配器。

本轮为资料及源码复核。LiteLLM 运行基准、真实模型调用和采购账单对账均未执行。
