# 通知中心与公告管理设计

状态：2026-11-16用户已确认按本版Figma落实，后端遵循现有Go规范。唯一需求来源：[需求31 / SRC-NOT-01](../requirement/31-通知中心与公告管理需求.md#src-not-01-原始需求)。事实依据：[研究57](../research/57-2026-11-16-即梦通知中心拆解与设计核对.md)。调度见 [BACKLOG](../../../BACKLOG.md#notifications-20261116)。

## 1. 摘要

管理员在现有工作台创建、预览、发布和启停通知，用户通过顶部公告、消息弹窗与Header收件箱查看，在同一通知中心筛选历史和一键已读。不另建通知微服务。

[Figma 34区](https://www.figma.com/design/uLqmeRWuQuzfrp9xOYg6FT?node-id=4060-127005)为已确认的页面基线。原生可编辑图层和原型表达设计；工程验收由[PRD32](../prd/32-通知中心与公告管理.md)与[Plan41](../plan/41-通知中心与公告管理执行计划.md)承接。

## 2. 参与者

- 普通用户：读取本人通知、筛选、查看详情、标记已读。
- 具有通知管理权限的管理员：创建、编辑、预览、发布、启停和查看操作记录。
- Identity：作为账号收件箱、公告展示和回执的业务所有者。
- Creation / Execution：保持任务、协作和积分等源业务权威，发布必要事件。

## 3. 背景

设计前的 `frontend/src/components/layout/product-account-actions.tsx` 铃铛调用占位功能；`basic-layout.tsx` 显示“消息中心暂未开放”。当前 `src/app` 无 `/notifications` 路由。

旧 `canvas/runtime/components/notifications` 保留 Bell、Provider、Inbox 及 `/notification/*` 客户端声明，但没有挂入当前布局，也未查到对应 Go 站内接口及数据库表。旧组件的水位、版本和账号缓存隔离可作合同参考，不能当作已接入能力。`identity.mail_delivery` 是邮件队列，团队通知也是邮件入队，不代表站内收件箱、已读或实际送达。

设计前根级Sonner普通4秒、错误6秒，含操作和进行中持续。本次用户要求默认5秒，是新的设计要求。遵循[设计44](44-Go微服务架构与技术选型设计.md)的四个业务服务和轻量 Gateway，以及 [DESIGN](../../../DESIGN.md) 的统一样式，不因通知增加第五个业务服务。

## 4. 目标

1. 全局公告位于整个应用 Header 之上，出现和关闭不遮挡公共工具栏及输入。
2. Header 支持最近通知、一键已读及完整中心入口。
3. 管理入口具有独立权限，支持发布、筛选和启停。
4. 自动关闭、展示、已读、业务处理互不混淆，并发到达不误清未读。
5. 复用组件和 Go 边界，结构仅在 `schema.sql` 维护。

## 6. 价值

用户从一个入口查找并处理通知；管理员控制内容、受众和有效时间。通知保留来源与版本，减少重复弹出、误清未读和无法解释的发布状态。

## 7. 方案

### 7.1 页面与组件

深色桌面1460×1040、手机390×844，沿Geist、Neutral语义变量和现有shadcn组件实例。侧栏240、共享透明顶栏，桌面正文32、手机16；长列表在ScrollArea内滚动。普通页面与画布外壳使用同一公告和通知状态来源，公告高度纳入布局；无公告不预留空行。

| 表面         | 组件与关键交互                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 顶部公告     | Alert + Button；桌面40、手机56，位于Header上方；最多一条，不轮播；按优先级、发布时间和稳定ID排序                         |
| Header收件箱 | 桌面Popover、手机Sheet；最近5条，标题、摘要、时间、未读、一键已读和查看全部；打开不自动清空未读                          |
| 通知中心     | Tabs、Select、Item、ScrollArea、Pagination；全部/系统/任务/协作/账户，未读和日期；默认每页20条游标分页，不虚构总数或末页 |
| 消息详情     | Dialog；标题、时间、正文及必要动作；手动关闭，Escape和焦点返回触发点                                                     |
| 自动消息弹窗 | Dialog；默认5000ms，显示倒计时和关闭；悬停、焦点、键盘或辅助技术交互暂停，离开后继续；长正文仅摘要                       |
| 操作反馈     | 复用根级Sonner；普通短时消息5000ms，进行中、未知结果、错误恢复持续保留                                                   |
| 管理编辑     | FieldGroup + Field、Input、Textarea、Select、Switch；可见标签、就地校验；首次发布使用Button，后续启停用带标签Switch      |

自动弹窗每账号、公告版本只自动展示一次。关闭、超时不写已读；详情成功读取后幂等标记已读，不能用前端“打开了弹窗”代替服务端确认。顶部关闭只抑制当前公告版本，不清收件箱。游客抑制在本页内存，登录用户回执在服务端，不新增浏览器业务存储。

自动弹窗最多一个；已有Dialog、支付确认、编辑或输入焦点时延后，普通通知不打断输入。同一事件不同时使用Sonner和自动Dialog；必要决策与错误恢复不放入限时弹窗。手机按钮触控44px，图标具有可访问名称，减少动态时取消位移。

### 7.2 一键已读

沿用旧合同的水位语义：摘要返回 `dataEpoch / mailboxVersion / maxInboxSeq / unreadCount`，客户端提交点击时快照的 `throughSeq`、数据世代和稳定命令ID。服务端只处理本人、同世代、该水位以前的消息；新到通知序号更大，仍未读。相同命令重复执行幂等，低版本响应不能覆盖新摘要。

请求中禁用按钮并保留原计数；成功使用服务端摘要更新；失败保持列表和计数并允许重试。摘要失败不显示虚构0；账号切换清除对应缓存；没有未读时禁用一键已读。

系统公告按公告版本和账号唯一投影到收件箱：发布时事务捕获既有合格受众，首次登录补齐当前仍有效公告，唯一约束防并发重复。定时版本预置待开放行，生效前不分配inbox_seq且不计列表、摘要或已读；到期首次读取再在邮箱锁内分配序号，既有离线用户过期后仍可看到历史。生效前停用或换版取消待开放行，恢复同版复用原行；团队受众开放时保守复验资格。游客仅查看公开公告。任务和协作通知根据源业务受众创建，客户端不能任意指定收件人。

### 7.3 管理与筛选

复用AdminWorkspace，在管理导航增加“通知管理”；路由 `/platform/notifications`，个人中心 `/notifications`。管理权限采用现有 `platform_admin`，不预建独立权限系统，服务端验证；隐藏入口不代替授权。

列表字段为标题、展示位置、接收范围、状态、生效时间及操作。关键词通过当前页搜索范围输入，其余条件集中在筛选面板：关键词、展示位置、接收范围、发布状态、生效起止日期。所有条件在服务端分页前生效，与游标绑定；条件改变重置游标。默认20条，不先增加昂贵总数查询。

表单为标题、正文、主要展示位置、接收范围、生效/失效时间，可同时保存到消息中心。位置是顶部公告、自动弹窗、仅消息中心；受众首版为全部用户、登录用户、指定团队。指定团队必须来自管理员可管理范围，公开公告不包含私人业务内容，不预建复杂人群平台。

高级设置收纳优先级、自动关闭时长、可选站内动作。时长默认5秒，服务端限定有限范围。正文使用安全文本、受控链接，动作走站内白名单，不接受脚本或任意HTML。预览使用实际展示组件，发布前可核对受众、位置和有效期，不暴露内部技术字段。

### 7.4 发布、启停和修订

发布状态为草稿 → 待生效 → 发布中 → 已结束，由发布时间和有效期计算。启用是独立布尔值，关闭后呈现“已停用”。首次发布用Button；已发布且未结束的内容用“启用”Switch。提交时保持原开关值并禁用，服务端成功后切换；失败保持原值并反馈。草稿不出现启停，已结束内容须调整时间再发布。

编辑已发布内容生成新草稿修订，发布后替换当前版本；命令携带expectedVersion，避免并发覆盖。停用撤下公告、停止新弹出及投影；已投递历史保留，详情标记已停用。恢复不清展示回执、不重复群发历史消息。新版本不改写旧收件箱快照。

### 7.5 服务与数据

在Identity内增设实际通知领域能力，按 `adapter → application → domain` 和显式构造注入。Creation、Execution只提供安全摘要、源事件ID、受众和受控动作引用，业务事实仍归原服务。可靠投影复用现有Outbox/Inbox，不另起消息代理。任务由既有生命周期管理，包含取消、租约和有界重试。

| 持久模型   | 必要字段与约束                                                                           |
| ---------- | ---------------------------------------------------------------------------------------- |
| 公告/修订  | 标题、正文、位置、受众、有效期、优先级、时长、发布/启用状态、创建人/更新人、修订号；CAS  |
| 本人收件箱 | 账号、单调序号、源事件/公告及版本、分类、内容快照、发生/已读时间；账号+来源+来源版本唯一 |
| 展示回执   | 账号、公告版本、展示/关闭时间；唯一约束抑制重复自动弹出，与已读独立                      |
| 投影幂等   | 公告版本与账号唯一；源事件ID与账号唯一；锁与事务保证读写水位及发布围栏                   |

索引服务本人时间倒序、未读、分类和有效公告，管理索引按真实查询计划补充，不预建全文搜索系统。发布/启停、审计与投影同事务。投影前复验版本及启用状态；重试不重新发布或重复生成通知。任务链接仍由原服务复验权限，不能凭通知获得业务访问权。

所有结构只在 `backend/db/schema.sql` 完整声明，公共权限预设按需维护 `data.sql`，通过schema_source_test。严禁增量SQL、migrations和启动DDL；存量数据库离线核验与变更单独受控。本轮直接维护唯一schema.sql完整结构，已有库部署前仍须离线受控比对。

### 7.6 API合同

沿当前REST风格实现，下表为生效合同；旧runtime声明不形成兼容接口。前端从Swagger生成，不手工修改生成客户端。

| 操作               | 生效合同                                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| 本人摘要/列表/详情 | `GET /api/notifications/summary`、`GET /api/notifications`、`GET /api/notifications/{id}`；身份、过滤、版本和游标绑定               |
| 单条/全部已读      | `POST /api/notifications/{id}/read`、`POST /api/notifications/read-all`；命令幂等、快照水位、权威摘要                               |
| 有效展示/回执      | `GET /api/notifications/display`、`POST /api/notifications/display/ack`；受众和版本校验，回执幂等，公共接口不泄漏私人数据           |
| 管理列表/详情      | `GET /api/platform/notifications`、`GET /api/platform/notifications/{id}`；管理权限、服务端过滤与分页                               |
| 保存/发布/启停     | `POST/PUT /api/platform/notifications[/{id}]`、`POST .../{id}/publish`、`PATCH .../{id}/enabled`；稳定命令ID、expectedVersion、审计 |

在边界统一校验字段、有效期、权限和状态，避免每层重复空判断。并发冲突可重新读取，未知结果先查询原命令而不是盲目重发。源对象删除或失权时安全摘要和动作可用性分别处理，不暴露内部表名或堆栈。

### 7.7 Figma画板与实施裁定

2026-11-16实施采用已有能力：管理身份为platform_admin，版本和序号以十进制字符串传输；用户不能指定收件人。发布当前用户投影与审计在同一数据库事务内，账号读取补齐合格公告，不增加独立公告队列或后台调度服务。定时公告必须保留既有合格用户离线期间的历史，尚未生效的内容不得提前暴露或提前消耗一键已读水位。

任务来源接入Execution现有status_changed.v1 Outbox与realtime消费组：源owner从confirmed_by给出recipient_id，Identity只处理安全终态摘要和受众，不读取Execution业务表。event_id+recipient去重与processed标记同事务；动作指向既有生成历史页面，由原服务再次鉴权。协作/账户分类可筛选，本轮不增加这两类自动源事件。

接入复用的infra Inbox为技术去重设施，Identity event适配器依赖internal/infra/inbox/application、PG适配器依赖internal/infra/inbox/adapter/postgres；两条依赖经本轮适配器边界核对后显式登记service_dependencies.json。应用层不引入infra或Execution模型；不为此放宽其他owner边界或声明服务已完全独立。

自动弹窗领取成功后仍须在真正打开前通过GET /api/notifications/display/{id}/{revision}复核，打开期间每5秒复核，停用/换版/过期立即或下次复核关闭；该校验不依赖是否保存到收件箱。首次请求因范围切换取消或临时失败时会自动恢复，领取的临时失败保留候选重试。有效公告独立于已读，自动消失与顶部关闭不标记已读。

- N01–N05：顶部公告、通知中心、Header浮层、一键已读反馈、手动详情、桌面限时弹窗。
- A01–A05：管理列表、新建和预览、启用/停用、完整筛选。
- M01–M07：手机中心、Sheet、限时弹窗、管理列表、详情、筛选和已读成功反馈。
- S01/S02：交互与服务合同，加载、空、无筛选结果、读取失败、已读/启停提交中和失败、冲突、已结束。

受众、频控、5秒暂停规则和生命周期由当前实现及对应测试落实。首版不包括邮件/短信平台、营销编排和通用模板引擎。
