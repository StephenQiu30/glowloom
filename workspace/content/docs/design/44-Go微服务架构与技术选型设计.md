# Go 微服务架构与技术选型设计

确认边界：用户于 2026-11-14 通过 [SRC-GO-MS-02](../requirement/29-Go微服务架构需求.md#src-go-ms-02) 确认“四个业务服务＋轻量 Gateway”，并授权开始分阶段拆分；不表示全部服务已经独立，也不扩大为生产发布或存量数据库变更授权。原始来源：[SRC-GO-MS-01](../requirement/29-Go微服务架构需求.md#src-go-ms-01)。实施状态、顺序与未决事项统一见[BACKLOG](../../../BACKLOG.md#go-microservices-20261114)。

[SRC-GO-MS-03](../requirement/29-Go微服务架构需求.md#src-go-ms-03) 进一步要求先提交 main 并推送已有切片，再继续拆分，并重申目录遵循 Google Go；不改变业务域独立门禁或生产边界。[SRC-GO-MS-07](../requirement/29-Go微服务架构需求.md#src-go-ms-07) 将本次目录优化限定为先修订设计文档，暂不执行源码或构建配置调整；目标结构和过渡条件见 §7.5。

## 1. 摘要

建议采用 **同仓、单 Go module、按业务边界拆分、渐进独立部署** 的方案：

- 目标为 **Gateway + Identity + Creation + Media + Execution**，即一个轻量入口、四个 Go 业务服务；这是目标责任图，不要求一次启动五套新服务。
- **Operation、Catalog、Billing 同属 Execution**。先保留报价确认、额度预占、派发和结算的本地事务，不为追求服务数量强拆钱包。
- 继续使用 Gin、GORM/PostgreSQL、Redis、Kafka、数据库任务记录和现有观测基础；新增 Go 内部强类型 RPC 时采用 gRPC-Go/Protobuf。不同时引入另一套微服务框架和基础设施体系。
- 保留已接受的 Agent/Pi Durable 和 Canvas/Yjs 独立运行时；研发 Workspace 继续遵循[设计43](43-Workspace知识库与研发工作流服务设计.md)。这些非 Go 边界是否改写，须单独确认，不能由本设计替代既有决定。
- 先建立契约和数据所有权，再拆进程。**分离 API、worker、relay 只是运行角色隔离，不等于已经完成微服务拆分。**

Google Go 指南约束清晰性、包设计、接口、错误和并发等工程质量，不指定唯一微服务框架或目录模板。以下服务划分属于结合本仓库事务与职责的架构判断，不冠以“Google 官方微服务架构”。

据此，当前更准确的描述是“**Go 模块化业务后端 + 独立专用运行时**”，而非四个 Go 业务微服务已经存在。尚未取得生产容量、调用链基线、故障统计及团队独立发布需求，不能断言微服务必然更快、更省或更高可用。

### 3.2 不可绕过的约束

1. [AGENTS](../../../AGENTS.md) 中 Google Go 与 `adapter → application → domain` 规则继续有效。
2. `backend/db/schema.sql` 是唯一结构规范，`backend/db/data.sql` 是唯一公共种子来源；不新增其他 SQL 文件、`migrations/`、自动迁移框架或运行时 DDL。
3. 现有业务与安全语义不因网络拆分而降低；幂等、权限撤销、原请求恢复、预算与真实费用均按所属领域合同执行。
4. 前端继续通过同站代理访问当前 `/api` 合同；沿用 Handler/DTO 注解 → swag → 前端生成客户端链路，不手改生成文件。
5. Agent 的会话和运行状态仍由 Agent 单独拥有；Go 不镜像其执行状态、不监督其 Node 进程，不重新引入 Temporal。

### 3.3 需要在拆分前处理的现状差距

- **普通维护必须只有 DML 能力。** 初始调研发现 flow 分区维护可达动态 DDL；对应约束是[应用服务](../../../backend/internal/infra/maintenance/application/service.go)只能消费 PrunePublished / PruneExpired 端口，[历史分区任务](../../../backend/internal/infra/maintenance/adapter/task/maintenance.go)只允许完成收束，不能再执行 DDL 或重排。管理员显式操作使用的 [PartitionStore](../../../backend/internal/infra/outbox/adapter/postgres/partitions.go)仍含分区 DDL，不得重新接回普通生命周期；分区预建、保留与存量库角色变更须由管理员受控执行，不能换成常驻自动 DDL 进程。代码门禁不等于存量库权限已经核验。
- **身份与项目创建也有强事务耦合。** [请求作用域适配](../../../backend/internal/app/scope/scope_access.go)在消费者事务中保留身份/成员锁；[项目创建](../../../backend/creation/workspace/adapter/postgres/create_project.go)会一并创建画布、预算并确保钱包。Identity 并不是因为名称清晰就能立即物理拆出的低风险服务。
- **已有 Saga 不等于已分库。** credit saga 仍受 schema 中跨 operation/workspace/billing/infra 的约束与事务保护；是否启用某开关不改变必须清点这些依赖的要求。
- **测试布局与门禁须区分规范和现状。** PROJECT 要求测试集中 backend/tests，但源码中仍存在生产目录内的测试；CI 的 race 套件也不代表完整 lint/vuln 门禁均已执行。本设计描述目标规则，不声明当前工作区已经全面合规。

## 4. 目标

### 4.1 本设计的目标

- 为每个业务服务定义职责、权威数据、依赖方向、通信方式和可独立发布条件。
- 将现有模块映射到服务，而非照表、照队列或照页面一对一拆服务。
- 明确事务、任务、事件、权限与文件交接的边界，防止形成“多个进程共同读写一套业务表”的分布式单体。
- 给出尽量复用现有能力的技术选型和 Go 工程结构。
- 为 [PRD30](../prd/30-Go微服务拆分.md) / [Plan39](../plan/39-Go微服务拆分执行计划.md) 提供可验证的技术接受条件；不扩展未获确认的产品范围。

### 4.2 非目标

- 不以预建四个空进程代替业务拆分；实施限于 SRC-GO-MS-02 和验收合同，不包含生产发布、存量业务库变更或未经确认的业务重写。
- 不因拆分统一改写所有语言、HTTP 框架、ORM 或公共 API。
- 不把组织、团队、画布、剧本、主体、通知、搜索、计费分别预建成独立服务。
- 不承诺未经测量的 QPS、延迟、SLO、副本数、分片方案或灾备目标。

## 5. 使用场景

| 场景                  | 角色及触发                    | 必须保持的结果                                                         |
| --------------------- | ----------------------------- | ---------------------------------------------------------------------- |
| 登录后访问创作项目    | 用户经同站入口请求项目或画布  | 身份验证与项目授权分离，失效身份不能因内部调用绕过限制                 |
| 确认报价并执行生成    | 用户或获授权 Agent 确认原报价 | 一次预占、一次业务受理；未知回执查询原请求，不另建收费请求             |
| 上传、处理并采用素材  | 用户上传或 Execution 交付输出 | 对象归档与资产发布有明确回执，未发布资产不被当作可用结果               |
| 关闭项目或撤销权限    | 项目管理员或账号所有者操作    | 禁止新准入，可靠收束在途工作，不能在删除后重新落入有效作品             |
| 重启 worker、重放事件 | 部署或故障恢复                | 原任务及资金身份不变，过期 worker 不能覆盖新 owner，事件重放不重复结算 |

故事对应需求29的 FR-GOMS-01/02 与 NFR-GOMS-01；这些是架构场景，不新增各领域产品范围。

## 6. 价值

- 保留已经建立的业务一致性，把拆分成本集中到确实需要独立扩缩、隔离故障或独立发布的边界。
- 将媒体重任务、生成出站和账户入口的资源与权限隔离，减少共享超级数据库角色及组合根耦合。
- 用契约、权限和故障验证证明可独立运行，而不是以目录或容器数量作为完成指标。

代价是增加网络故障、事件延迟、部署版本、凭据和运维成本；只有相应隔离收益成立时才继续物理拆分。

## 7. 方案

### 7.1 边界原则

1. **业务不变量优先于模块名。** 必须同事务成立的规则，默认留在同一部署和数据库事务内。
2. **一个事实只有一个写入权威。** 其他服务使用 API、命令或带来源版本的只读投影。
3. **服务内部调用不绕远路。** 同一 Execution 内的 operation/catalog/billing 使用消费方接口和本地事务，不经 Gateway 或自调用 RPC。
4. **独立服务不共享应用层与 ORM 模型。** 可共享生成协议与无业务的基础设施能力，不共享领域实体和业务仓储。
5. **无可靠边界，不拆进程。** 暂时无法替代跨领域 JOIN、外键或事务时，保留相应组合部署；不能以“最终一致”掩盖语义缺口。

### 7.2 目标责任图

```text
浏览器
  │ 同站 HTTP / SSE / WebSocket
前端同站代理
  │
Go Gateway ───────────── Identity
  ├──────────────────── Creation ─── Canvas / Yjs（既有 Node 运行时）
  ├──────────────────── Media
  └──────────────────── Execution
                          ├─ Operation：报价、确认、原请求与执行
                          ├─ Catalog：模型、供应商、凭据与路由
                          └─ Billing：预占、账本、结算与补偿

Agent / Pi Durable（既有独立服务）
  └─ 经受限 Go 业务入口调用 Creation / Execution / Media

业务服务之间：必要的同步 RPC + Kafka 事件
每个服务内部：API / worker / relay 按实际任务分开运行
PostgreSQL 同集群起步：按所有权分 schema / role / 任务与事件记录
```

这是调用与权威示意，**不表示每对服务都要建立双向 RPC，也不表示每个服务都必须有三类进程**。Gateway 不承接 Agent 的内部业务权威，外部模型供应商凭据仅进入所属服务。

### 7.3 服务职责与现有模块映射

| 建议服务  | 权威职责及现有模块                                                                                                              | 数据归属与对外能力                                                                      | 明确不承担                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Gateway   | 公共路由、请求标识、入口限流、粗粒度身份验证、流式代理                                                                          | 无业务数据库；按路由转发既有 HTTP 合同，必要时做明确的只读聚合                          | 钱包、报价、项目授权决策、跨服务数据库事务、全局业务编排   |
| Identity  | `identity`：账号、认证、会话、平台身份、账号安全与邮件任务                                                                      | 拥有身份数据；提供验证、会话和撤权合同                                                  | 项目/团队成员与资源级权限、直接删除他域业务表              |
| Creation  | `workspace` 的组织/创作空间/项目与团队，`canvas`、`script`、`bible`、`subject`、创作编辑侧 `prompt`；承接相应 Go Agent 业务适配 | 拥有项目生命周期、协作接受、剧本/主体和编辑草稿；提供资源授权、版本快照、采用与项目命令 | 模型供应商出站、媒体物理对象权威、资金结算、Agent 执行状态 |
| Media     | `media`、`mediatool`：上传、资产/版本、对象位置、归档、转移、清理及媒体处理任务                                                 | 拥有媒体表与对象生命周期；提供资产发布/读取/处理及精确版本引用                          | 项目编辑权威、报价、模型路由、按媒体处理结果自行退款       |
| Execution | `operation`、`catalog`、`billing` 及相应任务：冻结报价、准入、供应商路由/提交/查询、原请求恢复、预占和结算                      | 拥有执行、目录与账本数据；提供报价、确认、取消意图、查询和实际费用事实                  | 项目文档、Yjs 权威、媒体物理清理、Agent 会话与规划状态     |

补充边界：

- Creation 中的现有 `workspace` 是创作空间业务模块，**不是**根目录拟建的研发知识库 `workspace/` 服务，两者不能合并数据所有权。
- `prompt` 当前部分表位于 `workspace` schema，操作确认又使用事务绑定的编译/草稿适配。目标区分“编辑草稿”与“Execution 冻结快照”，但不能仅改包名或表前缀就认定分离完成。
- `agent_business` 及 Go `internal/agent` 业务边界须按工具实际修改的权威分配；审批、项目、资金分别调用所属端口，不另建一个拥有全部业务库权限的“Agent 万能服务”。
- 通知邮件先归 Identity；分析/观测先沿现有领域事实与投影，不预建通用通知、报表或日志微服务。
- 账务保持独立模块和访问控制，但**不作为本轮独立进程目标**。确有独立合规、隔离或组织责任需求时再评估 Billing 服务及跨服务资金协议。

### 7.4 技术选型与取舍

下表是建议基线。已安装版本以 [go.mod](../../../backend/go.mod) 和各锁文件为准；新增依赖在获准实施时核对支持期、安全公告和许可并固定版本，不把调研日期当作永久版本承诺。

| 能力               | 建议                                                             | 选择理由与限制                                                                                                     |
| ------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Go 版本            | 沿用当前 Go 工具链基线并通过安全门                               | 当前 `go.mod` 声明 Go 1.26.0 / toolchain go1.26.11；构建镜像与 CI 必须实际一致，不能仅凭文件声明认定运行环境已升级 |
| HTTP               | 继续 Gin，使用标准 `net/http.Server` 生命周期                    | 已有 Handler、鉴权和生成合同；Gin 仅存在于 adapter，不泄漏到 application/domain                                    |
| 微服务组织         | 普通 Go 包 + 显式装配，不新增综合框架                            | 现有平台能力已覆盖连接、任务和事件；Kratos/go-zero 并非不可用，但本轮无法证明换框架收益足以覆盖合同和接线重写成本  |
| Go 内部 RPC        | 新增契约采用 gRPC-Go + Protobuf，实际拆边界时引入                | 强类型、取消和 deadline 传播；只生成确有消费者的协议，不先给所有内部函数套 RPC                                     |
| 浏览器与 Node 通信 | 保留 HTTP/JSON、SSE、WebSocket；Node 内部合同继续现有 HTTP/SSE   | 不强制将 Yjs 或 Agent 流式边界改成 gRPC；公共 `/api` 与前端生成链继续有效                                          |
| 数据访问           | 继续 GORM/PostgreSQL；锁、队列及关键 SQL 显式表达                | 保留已有事务语义，不在拆服务同时改 ORM；新热点如需 pgx/sqlc，另以测量和具体查询评估，不全量双栈                    |
| 缓存/短期协调      | Redis                                                            | 不作为钱包、任务和授权的唯一持久权威；缓存包含租户/资源范围、版本、TTL 与失效策略                                  |
| 异步事件           | Kafka + Transactional Outbox + Inbox/业务幂等                    | 复用已有依赖；采用至少一次投递，Kafka 自身的幂等生产不等于外部数据库业务只执行一次                                 |
| 长任务             | PostgreSQL 工作记录 + Go worker，保留 lease / owner / epoch 围栏 | API 与长任务解耦，保留持久身份与恢复；不重新引入 Temporal、Redis 队列或第二套调度中心                              |
| 依赖注入           | 新服务手写构造函数及显式装配；存量 Wire 接线受控维护             | Wire 官方已于 2025-08-25 归档且说明不再维护；不为本次设计全量替换存量，也不作为新服务基础扩展                      |
| 配置与密钥         | 显式服务配置结构，继续 `GLOWLOOM_*`；部署注入密钥                | 启动校验各自必须依赖，按服务分配 DB/MQ/对象存储权限；不新增一套配置中心或记录真实凭据                              |

#### 7.5.3 目标布局与入口数量

保留服务优先的根目录。一个真实可执行程序时，直接使用 `<owner>/main.go` 与 `<owner>/app`；`main` 只处理进程入口、退出和调用装配，不承载业务规则。API、worker、relay 只有实际任务与权限需求才启用，运行角色不自动等于多个二进制。

**有两个需要不同依赖闭包的真实程序时才使用 `<owner>/cmd/<process>`。** Creation 的有状态 API 与无状态 document，Media 的有状态 API 与无状态 normalize 属于这一情形。只有完整 owner 入口实现并经过切换评审后，才一次性迁移该 owner 的真实入口及装配；不为目标对称提前建立 `cmd/api`，也不让其转发 legacy 全量根。

目标形态如下，`identity/main.go`、`execution/main.go` 和两个 `cmd/api` 都是后续有真实实现才产生的路径：

```text
backend/
  go.mod / go.sum
  gateway/
    main.go
    app/                         # 一个真实进程的配置、装配与生命周期
    proxy/
    Dockerfile
  identity/
    main.go                      # 完整 owner 具备运行能力后再建立
    app/
    domain/ application/ adapter/
    Dockerfile
  creation/
    cmd/
      api/main.go                # 完整有状态 owner
      document/main.go           # 保留独立、无数据库的文档计算闭包
    app/

      document/                  # 计算入口的实际装配，不能互导

      api/
      normalize/
```

目标树中不再有永久的 `internal/app`、`cmd/glowloom` 或无 owner 业务桶。它们在过渡期保留，满足 §7.5.6 的逐项退出条件后才删除；本次文档工作不执行任何迁移。

#### 7.5.4 包职责与依赖方向

- **先按业务，再按必要层次。** `execution/operation`、`catalog`、`billing` 和 Creation 既有业务模块保持内聚；不同域不为树形对称复制相同子目录。已有领域/用例/适配职责遵守 `adapter → application → domain`，纯转换或计算包没有实际职责时不补空层。
- **组合根只做装配。** `app` 可以导入本 owner 的具体 adapter 并注入消费方小接口；业务包不得反向导入 `app`。配置读取、连接、server/worker 所有权、cancel/wait 和探针归各自进程组合根；规则、SQL 和逐用例流程归实际业务包，不能沉入总 wiring 文件。
- **同域使用本地端口。** Operation/Catalog/Billing 可在 Execution 内按用例和本地事务协作，不改为自调用 RPC，不为“隔离”复制其模型。跨业务模块也须避免循环和不必要的应用耦合。
- **跨域只经已定义合同。** 消费方 adapter 转换生成 RPC/HTTP 合同与自己的用例类型，不能直接导入他域 application、ORM 或领域实体。protobuf 不进 domain，不能以一套跨域通用 Principal/Entity/Repository 绕过职责。
- **门禁检查完整闭包。** 现有跨 owner 直接边逐条登记、只允许经设计减少或调整，不将基线当作最终合法依赖。最终禁止跨域业务包导入；Go `internal` 可见性与这条项目规则分开验证。
- **测试与资源随真实责任核对。** 集中 `backend/tests` 为项目选择，不是 Google 强制；保留行为断言和既有必要白盒测试，不为搬测试导出生产内部状态。业务 JSON、字体和媒体资源仍只保留一份，许可与生成协议不因搬路径重写。

#### 7.5.5 共享能力的准入与放置

只有同时满足以下条件的机制才进入 `internal/platform`：不决定某个领域政策、不拥有多域业务表或密钥、无反向业务/组合根依赖；依赖由真实消费者注入，错误、Context 和并发所有权明确。两个使用者不是充分理由；能保留在实际 owner 的小实现，不先抽象成全局接口。

| 能力                                         | 允许的位置与限制                                                                                                                              |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| DB/Redis/Kafka 连接、日志、追踪、服务身份    | `internal/platform` 的具体技术包；不得默认读取全量服务配置或获取所有域权限                                                                    |
| 任务租约、Outbox/Inbox 的通用存储机制        | 通过准入后可复用机制；owner、记录隔离、业务＋消息事务由所属服务保证，不内置全域 handler registry                                              |
| 授权围栏机制                                 | 共享技术状态及原命令协议；账号、成员、项目准入政策和成功决定仍归 Identity/Creation 等 owner                                                   |
| RPC/HTTP schema 与生成物                     | 唯一协议源和生成链；不是共享业务 domain、ORM 或手写第二套公共 DTO 的地方                                                                      |
| 对象存储技术访问                             | 可复用无业务的连接/传输；对象生命周期与密钥权限归 Media，不把全量对象凭据注入所有消费者                                                       |
| Agent、Skill、审计、分析、业务事件及实时投递 | 按具体权威拆分：Creation 项目/工具接受、Execution 供应商/费用、Media 引用与对象；技术观测与 owner 无关部分才可评审下沉，不能整体搬到 platform |

禁止新建无明确责任的 `common/shared/utils/pkg`，也不预建接口层、facade、统一服务基类或另一套配置/调度中心。根 `internal` 保持中性不等于存量 `infra`、`audit` 等代码已经满足准入。

### 7.6 Google Go 规范的具体落点

| 规则                 | 在本项目中的落点                                                                                      | 检查方式                                 |
| -------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 清晰、简单、最少机制 | 按领域职责组织包，保留必要层，不为每个实体生成一套接口和空实现                                        | 设计评审与依赖图，不以目录数量验收       |
| 消费方定义小接口     | application 按用例需要声明端口；adapter 返回可直接使用的具体类型；只为真实边界或替换需求定义接口      | 禁止通用大 Repository、`Ixxx`、`Impl`    |
| 单向依赖（项目约束） | `adapter → application → domain`；跨模块通过小端口并在 app 装配                                       | AST/import 门禁及编译                    |
| 明确错误链           | 仅增加语义时用 `%w` 包装，应用错误在边界映射 HTTP/gRPC 码；使用 `errors.Is/As` 判定，不比较文案       | 重复、冲突、拒绝、依赖超时场景测试       |
| Context 首参         | 从 `c.Request.Context()` 进入应用，传给 SQL/RPC；不把 `*gin.Context` 作为业务参数，不长期存储 Context | 代码评审、取消/超时测试                  |
| 受控并发             | 后台任务明确 owner、cancel、退出和 wait；队列与并发有界                                               | race、停机和泄漏检查                     |
| 命名与包职责         | 短而清晰的小写包名，避免 `utils/common` 和反复重复包名的 API；不复制 Java 全局分层                    | gofmt/goimports、lint 与人工评审         |
| 可测试               | 领域规则纯粹、构造注入；测试通过项目约定的 `backend/tests` 入口验证                                   | 单元测试、真实隔离 PostgreSQL 与协议测试 |

**规范依据和验收口径：** [Style Guide](https://google.github.io/styleguide/go/guide) 与 [Style Decisions](https://google.github.io/styleguide/go/decisions) 为本仓库编码规则的依据；[Best Practices](https://google.github.io/styleguide/go/best-practices) 的建议结合实际场景评审，不把示例目录或建议冒充无条件 must。全量 `golangci-lint run ./...`、vet、build 和已有 race/故障接受共同执行，不能只用增量过滤结果代替整体检查；工具通过仍不能证明所有设计判断正确。项目的领域依赖门禁检查全部生产包，domain 不导入 application、adapter 或生成 RPC 合同，application 不反向导入 adapter；领域 Scope 到外部 Principal 的转换由实际消费层完成，不为转换新增公共 DTO 或工具包。仅被 OpenAPI 生成注解引用的类型，须保留外部生成合同名并就该引用精确说明静态检查例外，禁止用基线豁免掩盖真实问题。

**请求生命周期与任务生命周期必须分开：** HTTP 取消应停止本次等待，但已经在事务中受理的持久任务由服务生命周期管理。任务使用带有持久授权、截止与幂等身份的工作记录，不能仅把请求 Context 换成 `context.Background()` 后裸起 goroutine。

### 7.7 API 与通信合同

**外部入口：** 同站代理继续转发 `/api` 到 Gateway，再由其路由到对应业务 HTTP adapter。Gateway 以路由转发为主，避免同时维护第二份公共 DTO。现有授权、Cookie、CSRF/Origin 和 SSE/WebSocket 合同逐项保持；若公共接口确需变更，应沿所属产品主链单独批准。

**内部同步：** Go 服务新增 RPC 仅按领域分包，目录、Go 包名和 gRPC 服务标识不带业务版本后缀；同一功能只保留一份当前合同，避免源码、生成物与调用方形成多套不一致路径。proto 为这类 RPC 的单一来源，使用固定版本的 `protoc`/Go 插件生成并核对差异。删除字段号不得复用，破坏性变化必须先评审兼容性与发布顺序，再同步更新服务端和全部消费方，不保留重复业务实现或双权威。已有 Node HTTP 合同按自身生成链维护，不再手写一份同名 RPC。

**调用规则：**

- 每次调用有显式 deadline，并传播剩余预算；gRPC 默认没有 deadline，不能依赖默认值。建立连接、单次调用、队列等待和长期流式连接分开限制。
- 读请求或明确幂等命令才允许有界重试；只由一层负责，退避加抖动，服从整体 deadline。超时不代表对端未写入。
- 有副作用命令携带稳定 `command_id`、资源范围、请求内容摘要及调用者/授权来源；同身份同内容返回原回执，同身份不同内容拒绝冲突。
- 未知回执先按原 ID 查询；没有供应商原请求幂等或确定未发送证据，不得重发收费提交。
- 应用错误区分未认证、无权限、不存在、状态冲突、额度不足、依赖不可用和超时；不可全部变成 HTTP 500 或 gRPC Internal。
- 不把 SSE/WebSocket 当作可靠任务事实库；重连以有序游标/版本和持久回执补齐，限制慢消费者并支持停机收束。

**同步依赖收敛：** Gateway 可依赖领域服务，Creation/Execution/Media 通过有目的的端口交接；禁止任意循环调用和逐资产串行 RPC。列表使用批量查询或有版本只读投影；写入授权与资金判断不能仅依赖可陈旧投影。

#### 7.7.1 Media 无状态规范化计算边界

`backend/media/main.go` 与 `media/app`、`media/processing` 承接原上传 WebM→H264 MP4 规范化计算，是可独立部署的 Media 计算切片，不取得资产发布权，也不代替 §7.9 的持久准入与排空协议。生产上传通过消费者 `UploadNormalizer` 的 gRPC adapter 调用；资产最终授权、审阅、对象路由、原子提交与未知回执核对继续由原 owner 执行。服务及依赖闭包不得引入业务组合根、GORM、数据库、Redis、Kafka 或对象存储驱动，不加载业务 `.env`。

- 协议唯一源为 `backend/api/proto/glowloom/media/normalization.proto`，生成到 `backend/internal/contract/gen/media/`；固定 protoc 35.1、protoc-gen-go v1.36.12、protoc-gen-go-grpc v1.6.1。调用 `Normalization.Normalize` 双向流，但严格先上传、半关闭，再下载；不接受路径、任意 URL、对象密钥或用户身份。
- 首帧只包含源大小、SHA-256、MIME；后续为每帧至多 256KiB 的字节块。源及产物各至多 500MiB，实收大小、摘要、magic、真实探测与完整解码均须一致。仅接收单 VP8/VP9 视频轨、无音轨的 WebM；产物为单 H264、无音轨的 MP4。时长不超过 60 秒、帧率不超过 60 FPS，边长不超过 8192、总像素不超过 4000 万；不能靠截断时间或字节数制造成功。
- 两端各自创建并拥有临时文件，不共享挂载或传递本机路径。接收器在短流、额外帧、摘要不符、取消及失败时清理；客户端即使收到全部字节，也必须等到最终 gRPC 成功状态才交给原上传流程。调用方输入仍由调用方关闭。没有持久写入命令、应用重试或本地转码回退。
- API 单次总预算 150 秒，原生计算上限 120 秒，服从上游更短 deadline。服务拒绝缺 deadline 或大于 180 秒的调用；全局有界在途名额覆盖接收、计算、发送全部阶段，不设置无界队列。身份/准入、格式/大小、过载、取消/超时、依赖不可用分别映射明确 gRPC 状态，诊断不泄露 FFmpeg 输出或本机路径。
- 每次调用使用独立 API→Media 令牌，32～4096 字节可见 ASCII 且无空白，三处配置与协议构造一致校验。非 local 两端必须完整 TLS 1.3 mTLS，仍须令牌；local 明文只适用于隔离私有网络。仅传递服务自身认证及 W3C trace 关联，不转发任意调用者元数据、用户认证或 baggage；服务完成日志关联 trace ID、方法、状态和时长，不记录媒体内容或令牌。
- 运行时仅私有 RPC/健康监听与所需原生工具，启动核验依赖和可写临时盘，停机先撤 readiness，再有界排空，超时取消 RPC/子进程并等待退出。Compose 默认并发 2、CPU 2、内存 3GiB、只读根、有界 2100MiB 的不可执行临时盘，端口不发布到宿主；提高并发须重新核算临时盘、原生内存与实例容量。Media 不等待业务基础设施，其他 worker/relay 不因该切片增加启动依赖。

无地址且无令牌的非 Compose API 明确禁用 WebM 规范化，其他上传类型不变；配置一半则启动失败，不静默退回单体。此约定不代表独立数据角色、跨域授权屏障、分布式提交、完整采集器观测或四个业务域已完成。

#### 7.7.2 Identity 权威读取与准入端口

协议唯一源 `api/proto/glowloom/identity/authority.proto`，服务 `glowloom.identity.Authority`，生成于 `internal/contract/gen/identity`，不增加数字版本或共享业务 Principal。`Verify` 校验真实 legacy/access 凭据，只返回 account/session UUID 与 credential epoch；它不是写许可、scope/project 授权或平台资格证明。`AdmitSessionCommand` 在验证 CSRF 后，以认证得到的精确账号/会话调用 Identity 原政策事务，绑定完整协调 Command、原内容摘要、动作、authority 集合与目标 writer，登记持久准入。

- 私有请求以 oneof 区分 legacy/access，不接受调用方 Principal 或 actor UUID；原始凭据只在受认证的 Identity 调用中传输，不回显、记录或持久化。只读 Verify 可不携带 CSRF，以保留首次读取的原公共合同；提供时仍必须正确。access 无 CSRF 仅使用显式 `ReadAccessIdentity`，返回三个标识且不更新活动；既有 `CurrentAccess` 仍强制 CSRF。Admit 两端必须为原规范非空证明，不能借只读路径登记写命令。
- 四个 caller 使用互不相同的专用令牌，caller 与目标 writer 必须一致；Creation 不能借自己令牌任意替 Execution/Media 申请写入。后续若需要受控转授，须另有明确能力与接受，不泛化执行入口。
- 准入在原 account/session 锁及当前 credential epoch 下复核；未开放、关闭中、旧 epoch 都失败关闭。不自动创建/重新开放 authority，也不把一次 `Verify` 的成功缓存为后续事务授权。完整其他 owner 最终写仍须本地围栏，治理成功点仍须持久 ACK/排空。
- 每次有期限、有界消息、闭合错误与精确回执；无透明重放、无本地认证回退，只传播服务认证及 W3C 关联，不转发用户头或 baggage。传输凭据由组合根显式注入，非 local 完整 mTLS 约束不变。
- 此私有端口固定 `NoActivity`，不能用于静默替换正常公共操作的活跃计时。真实用户活动与后台读取应在相应公共端点迁移时分别保持原 session idle 合同；真实 JWT/SQL/准入与拒绝用例单独接受。

`ResolveAdmission` 只允许经过服务认证的 Creation 读取已存在的 Identity 原准入，绑定完整 command 和原目标 writer，不传用户凭据或接受请求方 Principal。Identity 在原政策事务登记时，以只读追加的 `identity.session_command_admission` 保存 `(command_id,target_writer)`、原账号/精确会话/credential epoch、请求摘要及 authority-set 摘要；与技术准入账本同事务写入，碰撞全值不一致回滚。读取须与原技术账本及当前资格/精确 head 交叉核对，不登记、重开或补造历史证明，缺证据失败关闭；不能把 authority epoch 或当前用户值当原 credential epoch。Creation 取得证明后仍须本地成员/项目/动作政策事务和自己的准入，效果 owner 最终围栏负责网络查询后的撤权竞态，读取期间不跨 RPC 持锁。

### 7.8 数据所有权与数据库隔离

建议先**同 PostgreSQL 集群、按服务 schema/受限角色隔离**，不立即多实例。Execution 可以在本服务拥有的 operation/catalog/billing 数据之间使用单事务；Creation 可在其项目/文档领域内维持事务。

| 数据类别                               | 目标所有者           | 拆分要求                                                                       |
| -------------------------------------- | -------------------- | ------------------------------------------------------------------------------ |
| 身份、会话、认证安全                   | Identity             | 外部服务不能 JOIN 身份表或自行更新会话；账号删除通过权威撤权与生命周期合同传播 |
| 项目、团队、文档、剧本、主体及编辑草稿 | Creation             | 将跨服务身份/资产引用改为显式 ID/版本及验证合同，不保留跨所有者级联删除        |
| 资产、对象位置、上传和媒体工具工作     | Media                | 使用受控资产发布回执及引用版本，不把私有对象 URL 当授权依据                    |
| 报价、执行、目录、钱包与账本           | Execution            | operation 与 billing 本地一致；外部服务不能写 ledger 或修改执行状态            |
| Agent 执行状态                         | 既有 Agent           | 保持受限 `agent` schema；Go 业务回执与 Agent 恢复状态不混存为两个权威          |
| Outbox、Inbox、任务记录                | 各写入所属业务的服务 | 技术机制可复用，记录必须有明确归属、权限与唯一性范围                           |

具体规则：

1. 当前 `infra.outbox`、`infra.processed_event`、`infra.task_work` 等共享记录是演进对象，**不能给所有新服务继续分配全表写入权限并宣称数据已独立**。物理拆分时在唯一 `schema.sql` 内为所属服务声明自有记录/约束，或证明等效的数据库强制隔离；未满足前仍属过渡组合部署。
2. 拆服务前清点所有跨所有者 JOIN、外键、触发器、事务与删除路径。保留同一服务内的外键；跨服务引用改由权威 API、发布回执、版本校验和对账维护，不能简单删除约束而不补语义。
3. 业务更新与所属 Outbox/任务入队使用同一本地事务。Inbox 去重与业务效果同事务提交，成功后再确认消费；幂等保留期须覆盖业务与重放窗口。
4. 事件至少含 `event_id`、类型/版本、聚合 ID、聚合版本、发生时间、资源范围和 trace 关联。分区键按聚合选取，只承诺所需范围的顺序；不假定跨 topic/分区全局有序。
5. 消费者处理重复、乱序、版本缺口、毒消息与 DLQ；授权撤销和资金不以“稍后投递成功”代替安全合同。过大事件只携带受控引用，不复制凭据、整段私有文档或二进制。
6. Redis、分析投影和前端缓存不是权威；投影必须可定位来源版本、显示延迟并能受控重建。
7. 新库只从 `schema.sql` 初始化。已有库由管理员基于实际结构与该文件的 diff 离线核验、备份及受控变更，验证后才启动服务；禁止重放空库 SQL 或由应用执行 DDL。

[Schema 来源测试](../../../backend/tests/db/schema_source_test.go)约束 SQL 文件来源，但不自动证明结构语义、角色隔离、跨库恢复或无动态 DDL；这些需要另外的测试和评审。

### 7.9 关键业务链与不能直接拆开的事务

**生成确认与结算：**

```text
Creation 给出当前可用的项目授权、输入版本与采用上下文
    → Execution 生成冻结报价及输入快照
    → 用户确认稳定 quote_id / command_id
    → Execution 本地事务：验证报价 + 预占额度 + 写 operation + 入队 + Outbox
    → worker 以原身份领取、准备派发、提交或查询原供应商请求
    → Media 幂等归档并返回精确资产发布回执
    → Execution 按真实费用证据本地更新账务与操作状态
    → Creation 幂等采用资产版本；前端按回执和事件刷新
```

该图表达目标交接，不把现有项目锁和草稿事务自动替换成一次“授权查询”。必须满足：

- Creation 的输入/草稿版本及授权必须冻结为可验证的交接事实；Execution 不再在确认事务里 JOIN Creation 的表。校验与使用之间的撤权、项目关闭和输入变化须有明确围栏。
- 资金预占、operation 受理、任务入队和事件写入继续在 Execution 本地事务内原子成立；结算与操作资金状态亦如此。
- 供应商提交可能已发生而回执丢失时，保留原供应商请求身份及未知责任，不创建新请求；有真实成本也不能因下游归档失败而虚构零费用。
- Media 归档和 Creation 采用各自有持久命令/结果回执。未归档、不可读、未采用、未审阅与完成分别表达，不能因供应商返回成功就宣告作品交付成功。
- 资产发布与资金结算跨服务时以显式状态和恢复协调，不假装一个 PostgreSQL 事务覆盖三者。若既有产品不变量要求共同原子提交，相关职责必须继续组合部署，直到等价合同被接受和验证。

**项目关闭/删除：** Creation 必须先以持久状态关闭新准入并推进生命周期版本，再可靠通知相关执行和媒体所有者建立禁止旧版本写入的围栏；收集在途任务、费用责任和清理回执后才能完成删除。迟到命令、重复关闭、消费者中断和关闭中重启都必须可恢复。

关闭过程中不得向用户报告“已全部删除”却仍允许新收费/发布。同步返回、等待状态、在途动作能否继续及取消责任须沿项目主链明确；**仅靠一条异步 ProjectDeleted 事件或短 TTL 缓存不足以替代当前项目锁语义**。不能证明等价时，不拆 Creation 与 Execution 的该条事务边界。

**项目创建、复制与媒体清除：** 当前项目创建把初始画布、预算/钱包一并准备，复制及素材清除也检查多个领域引用。拆分后必须由各 owner 幂等准备并交回持久回执，只有所需权威均确认后才能向用户报告“创建可用”或“清除完成”；失败、超时、半成品可见性与补偿沿项目/资产主链明确。不得把超时当作对象不存在，也不得漏查他域引用就物理删除仍在使用的素材。若接受新的 preparing 状态，应明确作为产品语义变更确认，而非偷偷替换原原子创建。

主体媒体绑定、批量采用等同理：先明确权威、不可变输入和命令回执，再设计跨服务协调；不用通用 Saga 框架替代业务状态与补偿规则。

### 7.10 身份、授权与跨服务安全

- 延续现有登录/会话体系，不因微服务直接更换 Keycloak 或将所有会话改成长期 JWT。
- Gateway 只做入口身份检查和明显非法请求拒绝；Creation/Media/Execution 必须各自校验服务身份、用户/团队/项目范围与当前操作权限，不能信任可伪造的 `X-User-ID`。
- 生产跨进程使用 TLS 及受限服务身份/短期凭证；选用 mTLS 还是部署平台身份由环境决定，不在文档记录密钥。内部端口不发布为匿名公共 API。
- 权限授予与撤销涉及权威版本、截止和明确失效策略。高风险写入无法确认授权时拒绝，不以陈旧缓存继续收费、删除或采用；账号“即时软删除并撤权”的既有规则不能被降级为仅异步最终生效。
- 一次远程 `CheckActive` 后继续本地写入，并不等价于当前身份/成员锁。跨服务准入与撤权须在共同权威上形成可串行化的顺序，并在撤权成功回执前确认所需写入围栏与在途责任；否则仍保留相关事务组合部署。短期 JWT、异步失效事件和 fail-closed 声明本身都不能消除检查后写入的竞态。
- Identity 不可用时是否允许已验证的低风险读取，由会话与权限合同决定；不笼统规定所有请求依赖一次远程认证，也不默认失效后仍开放。
- 服务分别获得 DB role、Kafka topic/group ACL、对象存储前缀和供应商出口权限；Gateway 无业务 DB，Creation 无供应商密钥，Agent 无资金账本写权限。
- 当前 local/loopback 保护变为服务间网络准入前，需要专项威胁评审、监听/Origin/代理头配置及鉴权测试；不能简单删除限制后对外监听。

### 7.11 运行、恢复与可观测性

- **角色隔离：** 先按现有 API/worker/relay 拆容器和资源；`all` 可用于受控本地场景，但多副本任务正确性仍由数据库 claim/fence 和幂等保证，不由“只启动一份”保证。
- **任务恢复：** 保留 `owner + lease + epoch` 等围栏，业务发布在验证有效 owner 的事务窗口执行；过期 worker 即使恢复也不得写入。数据库围栏不能撤回已经发往供应商的请求，外部提交仍依赖原请求身份和恢复合同。
- **健康：** liveness 只看进程是否可继续；readiness 核对本角色必要依赖。下游降级不应触发所有服务相互健康等待与循环重启。
- **优雅停机：** 停新流量/claim，给在途调用与流式连接有界收束，等待已拥有 goroutine，安全交还或等待租约，最后刷新观测并关闭连接。停机期限由真实任务和部署窗口核定。
- **过载：** 每个队列、租户和供应商有并发、速率与等待上限，重试不突破总体预算；CPU/内存型媒体任务与网络型供应商任务分别配置资源。
- **发现与发布：** Compose 服务名提供发现，显式服务地址注入。上线前验证新旧依赖的契约可配合；每个时点只有一个业务写入 owner，不以长期双写实现切换。
- **回退：** 代码回退须确认与现有数据/事件版本兼容；数据所有权转移后不能直接启动旧进程恢复写入。所有权切换需要停写/排空、围栏和审计，可由管理员受控转交，禁止两个 owner 同时活跃。
- **观测：** HTTP/RPC/Kafka/worker 传播 trace 关联，日志记录 service/role/version、原命令/operation 与资源范围。用户/项目/operation 等高基数 ID 留在受控日志或 trace，不作为无界指标标签。
- **最小指标：** 请求错误与延迟、RPC deadline、队列深度与最长等待、租约过期、Outbox lag、Inbox 重复/DLQ、供应商未知回执、资金预占超龄、结算差异、资产发布与采用失败。指标阈值根据基线另定。

### 7.14 首个独立入口切片的技术合同

- 独立入口为 `backend/gateway/main.go`，配置与生命周期在 `backend/gateway/app`，协议转发在 `backend/gateway/proxy`，镜像定义在 `backend/gateway/Dockerfile`；不导入 `internal/app` legacy 全量组合根，不创建数据库、Redis、Kafka 或对象存储连接。仅有入口职责，不预建领域/仓储空层；目录归位遵循 §7.5。
- 本地 Compose 的公开链路为 frontend → gateway:8080 → backend:18080；宿主 1123 仅发布 Gateway，业务后端不发布宿主端口。现有业务后端继续 local、loopback API 与 socat 内网桥接；Agent 的 `/internal` 调用直接使用业务后端，Gateway 不开放该路径。此合同不是跨主机或生产放行。
- Gateway 只转发 `/api` 及其子路径；保留方法、有效路径/查询原始编码、请求体、Cookie、Authorization、Origin、Host、幂等身份与上游状态/响应，不替代业务鉴权。不调用路径清理后把含 `..`、重复分隔符或非法查询的请求改送其他端点。
- 使用标准库 ReverseProxy 的 Rewrite；不信任客户端 Forwarded、X-Forwarded-*、X-Real-IP 或伪造身份头，不自行声明用户/项目权威。普通请求不设置总体写超时截断上传/流；连接和响应头等待有界。SSE 立即刷新、WebSocket 保持原升级协议。
- 无应用级自动重试。非安全方法使用不复用连接的 Transport，避免标准 Transport 因 `Idempotency-Key` 在复用连接故障时自动重放未知写入；原回执查询与恢复仍归业务 owner。此折中可能增加连接开销，不能无证据宣称容量改善。
- `/healthz` 是 Gateway 进程存活，`/readyz` 有界探测业务后端就绪，不回显下游诊断或地址。网关自身 4xx/502/504 沿用公共 Problem 形状及 request ID、no-store，不改写后端已返回的业务错误。
- SIGTERM 停止接入，取消请求生命期使 SSE/WebSocket 一并关闭，等待所拥有的服务协程和代理 handler 后关闭空闲连接；Docker 宽限期覆盖进程收束窗口。Compose 声明与纯协议测试不等于容器部署、真实登录或供应商接受。

### 7.15 API、任务与中继的运行角色隔离合同

这是运行隔离，不是业务域独立：

| Compose 服务 | 业务命令                               | 单角色健康端口                 | 所有权说明                                       |
| ------------ | -------------------------------------- | ------------------------------ | ------------------------------------------------ |
| backend      | `glowloom --role=api`                  | 18080，经内网桥接 loopback API | 仍承载现有全部业务 HTTP 适配器及 API 自有维护    |
| worker       | `glowloom --role=worker --queues=auto` | 8081                           | 持久任务仍在原队列与数据库中，租约/幂等身份不变  |
| relay        | `glowloom --role=relay`                | 8082                           | 原 Outbox/Inbox 与 Kafka consumer group 保持不变 |

- 三者共用业务镜像、配置和数据库角色；编译依赖也未隔离，不能据此声称四个数据 owner、最小权限或故障完全独立。业务表/基础设施故障仍可能同时影响多个角色。
- 各自健康探针只检查本角色；不将 API/worker/relay 互设为启动健康依赖。Gateway 只调用 API；完整 Compose 启动用 `--wait` 检查全部角色，API 就绪不代表异步任务已经完成。
- `auto` 与原 `--role=all` 的选择相同：默认 flow、media，配置凭据私钥后加入 provider；agent.codex 仍须显式选择。保留独立 worker 空参数默认 flow 与显式队列校验。`all` 仅保留为明确选择的组合运行方式，不再是镜像或 Compose 默认。
- 选中的任务队列先放在同一 worker，避免未经验证改变本机临时产物/原生工具交接。只有 API 开启 loopback 的公开业务桥；worker/relay 不开该桥、不发布宿主端口。开发 overlay 对三个角色应用同一源码重建规则。

目录以 §7.5 为准，不为三个角色复制三套空模块：`backend/cmd/glowloom/main.go` 保留业务角色/显式管理员薄入口，`backend/internal/app/queues.go` 仍是 all/worker 共用的队列能力选择；Gateway 的真实入口、配置生命周期、代理和镜像分别在 `backend/gateway/{main.go,app,proxy,Dockerfile}`，不再装入 legacy `internal/app`。`backend/tests/app`、`tests/deployment` 保留队列与部署合同测试。

Google Go 规范落实为包内聚、小接口、显式注入、错误链和可收束并发，而非把 `cmd`/`internal` 惯例套成服务必需层级，或机械增加 `services/`、多 module、Java 式全局分层。未切断的跨域接线仍在唯一 legacy 组合根，不因目录归位宣称业务角色或四个 owner 已独立。

### 7.16 Media 两个候选用例的事务阻塞事实

限定核对项目本地上传与视频深度处理，不据此外推整个 Media 域：

- [上传提交](../../../backend/media/adapter/postgres/upload.go)在最终事务重新校验操作者、锁定项目，再写资产/派生、存储接受、幂等回执和审计；未知提交后的对象清理也受同一项目锁约束。
- [ScopeAccess 装配](../../../backend/internal/app/media/media_scope_access.go)把同一事务交给 Identity 会话/活动校验和 Creation 项目内容授权；不是可以直接替换成普通 HTTP 预检的独立授权端口。
- [深度命令](../../../backend/media/mediatool/adapter/postgres/depth_commands.go)与[控制权威](../../../backend/media/mediatool/adapter/postgres/depth_control_authority.go)还涉及 Canvas 来源、任务/事件、控制人、复核和 Media 发布；原生处理停止事实不等于撤权后的业务发布授权。

物理拆分须先证明等价的持久提交授权栅栏：关闭/撤权关闭新准入，已准入提交及未知结果得到排空/核实后才能确认完成，旧授权不可继续发布。该协议仍待具体设计与并发测试，不在此直接实现或放行；RPC 检查一次、JWT/TTL 缓存和异步失效不等价。原同库事务在门禁通过前保留。

### 7.17 项目上传的 Creation owner 端口合同

项目上传将业务表查询收回 owner，不改变事务边界、HTTP DTO 或现有权限语义：

- Media application 定义消费方小接口 [`UploadProjectAccess`](../../../backend/media/application/upload_project_access.go)，只表达 `AuthorizeUploadProject` 与 `AwaitUploadProjectCommit` 两种不同责任；不导入 Creation 领域类型，也不把所有 Media ScopeAccess 实现强迫扩成通用接口。
- [`Creation owner`](../../../backend/creation/workspace/adapter/postgres/upload_access.go)在调用方真实事务内复用项目内容授权：身份/Scope 后取项目 UPDATE 锁、锁后检查 active，再读上传所需 aspect。沿用旧锁顺序与写入准入，不经包含封面/模型检查的完整项目快照扩展失败条件。
- [`组合适配器`](../../../backend/internal/app/media/upload_project_access.go)显式使用同一事务：请求端保留 CheckSession，worker 端保留 CheckActive；错误沿既有映射传播。Media 缺少该能力、owner 缺少真实事务或项目事实时失败关闭，不回退为 Media 自行查询 Creation 表。
- 未知提交核对不等于新的上传授权。owner 仅用项目 UPDATE 锁等待先前提交结果，不要求当前会话有效或项目 active，也不滤掉 archived/软删项目；随后 Media 只查询自己的资产事实。若无法锁定或项目不存在，返回未知错误，不能把“查不到项目”解释成允许删除对象。
- 原上传流水线仍在最终事务重新授权；准入后、对象创建后撤权/关闭都不能靠旧 Principal 获得发布权。提交响应丢失时，独立、有界的结果核对上下文不随原请求取消；资产已经存在或结果未明时保留对象，不重发写命令。

按 §7.5 归位的文件路径为 `media/{application,adapter/postgres}`、`creation/workspace/adapter/postgres`，跨域组合适配仍在 legacy `internal/app/media`；测试继续在 `tests/{media,workspace,boundaries}`。接口留给消费方、SQL 留给数据 owner、跨模块映射留给组合适配器，符合 Google Go 的职责内聚与显式依赖，不增加空服务目录、远端伪事务或公共 utils。

这只是本地 owner 责任收敛：Media 上传路径不再包含跨域表查询，但组合进程、事务连接、数据库角色与 Identity/Creation 锁仍共享。并未实现 §7.16 的分布式持久授权屏障，也不证明整个 Media 域已独立；正式物理拆分仍受 §8.1 门禁约束。

### 7.18 Creation 原文提取的独立计算服务合同

- `backend/creation/main.go` 与 `creation/app` 只承载 TXT/DOCX → 富文本、编码、来源映射和警告的真实提取，不导入旧全量组合根、Media application、Identity、任务、数据库、Redis 或对象存储。纯计算留在 `creation/document`，可复用 Creation 自有 `creation/script/domain`；旧提取适配器仅做类型/错误映射，不保留两份解析实现。HTML 编辑器转换仍是原本地领域适配能力，不属于本切片；目录归位遵循 §7.5。
- 唯一内部协议源为 `api/proto/glowloom/creation/extraction.proto`，生成包 `internal/contract/gen/creation`，服务 `glowloom.creation.Extraction`；统一领域命名，不添加数字版本目录、包或服务名。双向流先接收唯一的 size/SHA/MIME 头与字节，half-close 后才返回完整结果 JSON 字节流；不接受路径、URL、对象 key、用户凭据或持久发布命令。
- 源文件上限 20MiB，单帧 256KiB；真实 size/hash 验证后才解析。富文本沿既有闭合 schema（8MiB、150 万 Unicode scalar 等限制）校验，结果 JSON 上限 32MiB，消费方验最终 RPC OK 后才解码与再校验，不接受截断成功、替代文本或隐式重试。RPC 全程 60 秒预算且不得无 deadline，取消沿解析传递，源文件仍由调用方关闭；全局并发槽覆盖接收、解析、响应，不能靠每连接 stream 上限替代全局有界量。
- 使用独立专用服务令牌（32～4096 可见 ASCII、无空白），非 local 必须双向 TLS1.3；仅传 W3C traceparent/tracestate，不能继承任意用户身份 metadata。无本地回退。独立配置只读 Creation 字段，不加载业务 `.env`；健康与停止各自有界，不泄漏原文、临时文件名或认证材料。
- 生产文档导入 worker 注入远端 `SourceExtractor`；文件读取、任务认领、顺序/幂等、最终发布授权和未知结果恢复保持原 owner。远端返回内容只代表提取事实，不是发布权，失败/取消不得继续持久发布。无新表、无 DDL。本合同不宣称整个 Creation 域或其数据已经迁出。

### 7.19 完整业务 owner 的持久交接合同

本节承接需求29 SRC-GO-MS-05；目标仍是四域＋Gateway，不把规范化/提取计算切片外推为完整拆分。完整 Identity 拥有身份与精确会话；Creation 拥有组织/scope/团队/项目、Canvas/Script/Bible/Subject 及 Go Agent 创作授权；Execution 拥有 Operation/Catalog/Billing、所有供应商与 Codex 出站；Media 拥有资产、媒体工具和全部物理对象。注册、账号注销、团队治理、项目准备、Agent 调用、生成归档、引用/删除均须纳入交接，不遗漏头像/Logo、subject voice、trial、Script 私有对象与分析查询。

#### 7.19.1 数据及技术记录

- 普通运行角色分别为 `glowloom_identity`、`glowloom_creation`、`glowloom_media`、`glowloom_execution`，不是 schema owner，不继承全库 `glowloom_app`；由管理员离线预建。Gateway 不连接业务数据库。实际 login 只能获得单一 owner 角色，不能通过会话自报 owner 或自设 GUC 改变权限。
- 各 owner 拥有自己的任务、Outbox/Inbox、DLQ、重放审计与幂等记录。可以物理分表，或在现有技术表使用数据库强制且不能由应用绕过的 owner 记录隔离；后者须覆盖 RLS、唯一键/冲突、插入归属、角色继承、分区直访及后台 maintenance。仅在 SQL 加 WHERE、按 kind/topic 命名或传 context 都不算隔离。
- 保留现有租约/claim token、业务＋任务＋Outbox 原子性与 Inbox 去重＋本地效果原子性；不复制四套调度机制。共享全库角色仅是尚未切换的旧 owner，不能被新服务继承或作为回退。最终切换后撤除其业务写权。
- 跨 owner FK、视图、触发器及 SECURITY DEFINER 都须消除跨域权威依赖，尤其钱包绑定/预占、Media scope 校验与清理引用；同 owner 的强约束保留。不能仅删 FK 或授予 definer 后门就宣布完成。唯一结构仍为 schema.sql，无运行 DDL。

#### 7.19.2 持久准入与最终写入围栏

准入记录至少绑定原 command/幂等键、输入摘要、目标 writer、账号/精确 session、scope/project、动作资源、各权威 epoch 及精确回执。控制记录保存 authority key、单调 epoch、新准入开关、原协调 ID、封闭的 writer 集合与逐 writer 确认；新 writer 同步围栏后才能接入。worker 的 owner/attempt/lease epoch 与授权 epoch 分开保存。

Identity → Creation → 效果 owner 按固定顺序在各自本地事务登记，全部准入后才能执行；不跨 RPC 保持 SQL 锁。各 issuer 的登记必须绑定同一个原效果 command、摘要、动作、完整 authority 集合及同一个目标 writer；不能将 Identity 的 targetCreation 记录与 Creation 的 targetExecution 记录拼成 Execution 许可。Creation 的输入冻结等源侧效果若需独立 writer 回执，使用另一个稳定 SourceCommand 身份并完整绑定原 consumer 意图、选择和资源；源命令不能冒充 consumer 准入或反向扩大权限。效果 owner 在最终业务写＋回执＋Outbox 的同一事务中锁定并核验本地围栏，缺失或旧 epoch 拒绝。issuer 身份必须由私网服务认证及操作级权限确定，不能信任任意客户端自报 issuer、actor 或 epoch；普通服务身份不能伪造 Identity/Creation 控制指令。

撤权先禁止新准入，再安装更高围栏。业务提交先取得锁则围栏等待其提交并核清回执；围栏先持久则旧命令拒绝，包括迟到消息。逐 owner 的围栏及旧业务效果结论持久后才 ACK，协调者集齐证据才记录成功；崩溃/丢 ACK 只查询原命令与协调 ID，不以 TTL、超时、取消或暂时查无记录推断未提交。

未知供应商结果不要求永远阻塞账号禁用：若命令已经持久冻结为不可新增/发布业务效果，可只允许原身份补记退出、真实费用及封存/恢复事实。预占与未知责任保留，不能退款重送，恢复账号也不自动解冻旧发布。普通读仍保留当前会话与 scope 隐私，不用陈旧成员投影授权。

围栏安装和原命令核对使用唯一技术合同 `glowloom.coordination.WriterFence`（源 `api/proto/glowloom/coordination/writer.proto`），不形成新的业务服务或通用命令执行器。四个 writer 各用自己的受限连接安装本地控制；控制 adapter 在安装和核对前以数据库实际角色能力核验固定 writer audience，不以配置标签代替。每个目标分别绑定 Identity/Creation 的专用令牌及 mTLS 身份，禁止透传用户身份、跨 issuer 安装和重放到错误 writer。安装回执精确回显 writer、authority、epoch、blocked 与协调 ID，客户端只在最终成功且完全匹配时确认。命令核对绑定原 ID、输入摘要、动作与完整 authority 集合，只供拥有该命令责任的权威恢复使用，不因核对重新授予写权；单次 RPC 有期限，无自动重试，结果未知按原协调身份继续。

持久效果回执只接受完整 JSON object，规范化后的线级上限为 1MiB；精确数字使用十进制字符串变换，不能经 float64 损失事实。先受限展开指数并核验 PostgreSQL numeric 范围、总长度及最大 256 层嵌套，避免短输入在 JSONB 中放大、提交后不能恢复。数据库 JSONB 文本因空白允许最多 2MiB，读取后仍须重新规范化并满足 1MiB；不能因存储显示格式或大整数改变原结果。该技术回执不替代各业务 owner 的闭合结果 schema。

#### 7.19.3 成功点与原有公共语义

- 项目有在途任务仍返回原冲突，不自动取消或新增公共 closing。Creation 持久协调闸短暂阻止新准入，核对全部 owner 及已登记未送达工作；busy 则可靠恢复准入，未知不当 idle，确认无阻塞后才改变项目状态与围栏。恢复必须区分失败后重开与已经关闭，不能因进程退出永久封死 active 项目。
- 注册由 Identity 协调：Creation 幂等准备组织/个人 scope，Identity 持久激活决定；必需参与方 ready 后才报成功，列表/直读/登录授权不暴露半成品。团队事实归 Creation，账号资格闸归 Identity；最后管理员、邀请/提案、成员转交与账号禁用/注销须共享持久资格顺序，不能用一次远程计数或异步投影。
- 项目创建由 Creation 协调：本地项目/初始 Canvas 与 Execution wallet/budget 准备完成后发布唯一可用决定。未准备完成不能公开项目或授权支出；内部恢复态不引入公开 preparing。
- Agent 调用由 Creation 先原子保存 grant 围栏、call 授权与 run 预算承诺，再发 owner 幂等命令。Execution 本地保存原执行/预占/费用与回执；未知不能退承诺、换请求重送。Node 仍单 origin 连接 Creation 私有入口，静态工具名→owner 的协议 adapter 代替跨域 import；不镜像 Node 执行状态。
- 生成交付由 Execution 持久 output 命令驱动 Media 幂等归档/审核，回执绑定 operation/output 序号、内容 hash、资产与审阅版本；Execution 本地绑定并按真实费用结算，Creation 采用另有回执。必需产物未可用不能报 completed，归档失败不抹零已发生成本。

注册准备在 Identity 自域独立责任中固定邮箱、原 operation/输入证明、账号/组织/scope 稳定身份与待激活用户快照；未激活快照不进入公开账号表，不保存明文密码或向其他 owner 传递凭据。Creation 的组织/个人 scope 准备和 Execution 的 wallet 准备各在本域保存不可变、全值匹配的原回执；wallet 准备绑定已完成的 Creation 回执，不由异步投影或布尔值猜测资源已就绪。只在所有必需准备和账号初始 open 协调完成后，在 Identity 本地原政策事务发布账号与一次审计。旧跨域外键或 definer 只在真实受限角色替代链路通过后按完整 schema 离线替换，不能给新 role 补他域权限维持旧机制。

已接受注册的原证明匹配优先于新的条款/密码/邮件准入政策重验：恢复只完成原已接受意图，不改变其原条款或重新消费 grant；未受理请求仍严格执行当前政策。初始账号、精确会话、scope/project 的 authority open 必须由各自真实创建政策持久协调并收齐 writer 确认，不在任意查询/Admit 自动创建；历史已关闭或非原协调不能借登录/重试重开。会话的原成功凭据回执须可恢复，不能在丢 ACK 后另建会话或把不可用 cookie 当已完成。

账号资格变更先在原政策锁下持久关闭 account 新准入与原操作责任，再安装并核实固定 writer 围栏；密码、禁用/删除、角色、会话及平台授权变化各保留自己的政策与成功点。Creation 团队职责冲突不能用远程管理员计数替代：候选资格只以 Identity 的专用 LastTeamAdministrator 准入证明绑定原治理 request/team/candidate/command/目标 Creation/current qualification epoch；Creation 再在本地团队/成员锁与最终候选围栏下判定角色。未知候选不是不合格，候选集及原命令不可替换。拒绝职责变更的恢复须持久更高 epoch 重开并收齐 ACK 后才返回原冲突，已冻结旧业务命令不复活。

#### 7.19.4 会话撤权源侧

Identity 的单会话撤权由自身受限数据库身份执行：在原账号→请求会话→目标会话锁下校验当前资格和归属，在同一个本地事务内保存不可变目标/请求者会话、原协调 ID 和预期 epoch，同时撤销目标会话及 refresh 链、关闭该 session 的持久准入。事务提交后才调用四个 writer；完整 ACK 与源侧完成事实核实并持久化后，业务方法才可返回成功。源侧撤销已提交但 ACK 未齐时保持 pending，不回滚撤销、不另起协调、不重新开放。

会话准入必须在同样的原账号/会话政策锁内重新核验当前身份与 credential epoch，并将命令绑定到该账号及精确会话的两个 authority 世代；缺少任一 authority、夹带其他账号/会话或 Identity authority 均拒绝。Identity 仅证明账号/会话存活，不替代 Creation 的 scope/project 或效果 owner 的业务权限；源侧政策锁与准入账本提交后才能调用远端，不用一次 Principal 查询或原会话仍在缓存中替代。

credential epoch、account authority epoch 与 session authority epoch 是独立事实，scope/project 的修订号也不能代替各自围栏 epoch。内部消费者需要组装命令时，由 Identity 在真实账号／session 锁内读取当前 complete/open 的精确 head；缺失或已关闭就拒绝，不在读取中初始化或重开。该只读回执仍不授写、不替代完整命令准入及 Creation 资源政策，Verify、原准入证明与 authority 读取保持 NoActivity。

前台活动由各 owner 的公共 HTTP 注册代码按固定白名单分类，仅在既有成功状态之后发送有限、受 caller 约束的活动目的；用户 header、轮询、流、预览、状态请求或任意 UserActivity 布尔值不能扩展它。Identity 重新核验真实凭据和精确 session 后才更新活动，不能信任 caller Principal，不放宽原 CSRF 或延长绝对过期时间。业务响应已经提交后，活动补记失败只记录独立失败，不改变原结果或要求客户端重放已提交写入；Gateway 继续只承接路由与传输。

恢复入口只消费已持久化的原撤权身份，不接受新的 actor、目标或权限，不复活已失效会话；它属于 Identity 内部责任恢复，不能公开为免登录会话目录。新的撤销其他设备请求仍须核验请求者当前身份；已经接受的同一公共请求只能凭原证明恢复固定责任，不能改选目标或获得会话目录权限。重复自退出也须通过原凭据及 CSRF 绑定的专用恢复路径，不能把 revoked/暂时未找到当作分布式撤权已完成。源侧完成记录与安全审计同事务保存，重复完成不重复记成功事件。回执时间戳使用数据库实际可表示的微秒精度，不能以内存纳秒值与重读结果冲突；完成审计先取原账号的外键所需锁，再取责任记录锁，与政策路径统一锁序。令牌和会话清理不删除原撤权责任，账号已清理时仍可凭原记录完成审计。

公共请求以既有 `Idempotency-Key` UUID 固定原操作、动作和目标集合；`revoke-others` 的第一次接受在同一政策事务内固定全部目标，重试既不漏掉已本地撤销的 pending 目标，也不纳入随后新建的会话。请求责任与各目标的原撤权责任分开保存，凭据和会话清理不删除它们。首次正常授权后，在该事务内保存实际接受凭据的种类/摘要与原 CSRFHash；只保留摘要，不保存令牌或 CSRF 原文。access 指纹对原 token 字符串做 SHA-256，legacy/refresh 沿用解码后的 32 字节摘要；同一会话实际验证通过且未撤销的 refresh 证明可以与 access 一并保留；已撤销 refresh 不能被补登记为原证明。已失效凭据只能通过这些不可变证据、同一 key/动作/目标核对恢复原请求，不能补建证据或准入新命令。公共 Origin、Cookie 协议消歧及 CSRF 传输校验保持；错误不清 Cookie，全部目标持久完成后才可返回成功。

首次接受请求时，Identity 在同一事务内登记只含原 request ID 的 owner 恢复任务；任务入队失败则撤销、准入关闭和请求记录一同回滚。私有恢复 worker 沿用现有持久任务、租约及事务尾部 fence，只读取已接受请求的固定目标，不依赖浏览器仍在线、令牌仍存在或重新认证；完成依旧核实所有 writer。重建 worker 复用同一 request/task/协调身份，失去租约者不得提交源侧完成或完成队列；恢复故障保留原责任，失败任务按现有机制显式保留给核查，不按 TTL 删除。启用前的既有 pending 请求通过受限 owner 的有界 DML 对账补齐缺失任务，既有 completed/failed 任务不能被重开。

浏览器对同一活跃身份、同一后端和精确撤权目标保留原操作键；未知结果只允许用户显式重试，不自动重放写入。操作键只存内存，不把凭据或 CSRF 写入浏览器存储；Creation scope 改变不丢弃身份撤权责任，身份改变则清除旧键。只有收到当前原操作的 204 才释放该键，迟到的旧响应不能释放下一次操作的新键。其他写请求和调用方显式提供的键保持既有语义。页面重载或丢失原证明不意味着可以重新授权；客户端内存不代替服务端持久请求和内部恢复责任。

公共组合根显式注入完整 request、source closure、writer coordinator 三个依赖；任何部分缺失必须拒绝启动，不受 V2 签发是否可用影响。全部未配置只表示仍处于原单体迁移前模式，不代表已完成 owner 切换；切换后必须由独立运行入口强制提供，不能删除配置或在远端失败时回退原 handler。公共启用前必须同时覆盖 legacy Logout、refresh 自退出、有效 access/legacy Cookie 所走的目录撤权、revoke-others，并证明 pending 自退出可恢复、批量重试不遗漏已本地撤销的目标。未覆盖全部入口前保留原事务保护，不仅替换某个 Logout 或在写 Cookie 后异步等待；Redis negative hint 仍只是持久完成后的 best-effort，不是围栏或必要成功条件。

#### 7.19.5 对象保留、接线与切换

Media 持久保存 pin/object/引用 owner/command/关闭 epoch/状态及回执。其他 owner 先取得稳定 pin，再本地提交采用；只有确定未提交或解除引用证明才能释放。提交后丢 ACK、pin 后崩溃都查询原命令，未知不按 TTL 清除。删除先在 Media 本地关闭新引用，再核清全部既有引用/未决承诺，最后物理删除；不能把同事务 referenceguard 换成一次远程无引用查询。

原 Acquire 回执与当前保管状态分开读取：前者永久保留原 held 结果及真实资产种类、版本、字节／审核事实，后者可为 held、bound 或 released。读取必须匹配原 pin、Acquire command、消费 owner／command／摘要、消费资源、scope/project，并核实原 Acquire 已持久提交及不可变事实摘要；不能为历史账本补造缺失事实，也不因读取登记新许可。Creation 冻结采用仅接受精确匹配且仍受保管的 pin，绑定自身独立 SourceCommand，不拿 Execution consumer 命令替代。原冻结已提交后的精确重放不依赖当时的 Media 连接。保管证明不替代后续业务读／执行所需的当前权限和 Media 访问许可。

消费证明由真实 owner 自域账本给出。Creation 的 adopted 证明须同时匹配原已提交 SourceCommand 回执、原不可变输入快照和精确 pin；取消或阻断该快照不删除其中的历史引用。not_adopted_frozen 只允许原 SourceCommand 已永久冻结、没有效果回执且没有提交快照，不能由缺行、未决命令、超时或取消推断。永久冻结与最终采用 Guard 锁定同一原命令，二者只可能一方先完成；被冻结的命令不得迟到采用已释放 pin。没有独立、持久的精确移除事实时，不返回 removed。

采用及未采用证明使用双向独立受众与已验证 mTLS；读取只返回闭合事实和摘要，不返回对象 key、凭据或任意 actor 状态。Media bind/release 在网络核对之后，以本域 pin 锁、资源围栏、完整原证明和独立效果回执同事务提交。账号撤权后的纯保管收尾可以完成已有永久责任，但不得重开账号／session head、恢复旧命令或授予新的业务读写；项目／scope 关闭仍须遵循原排空顺序。旧引用、原输出归档回执及未决承诺没有全部核清前，新 pin 表为空也不是物理删除许可。

物理对象路由/密钥只归 Media，包含 Script 私有对象、供应商 artifact/manifest、trial 和项目复制。其他 owner 仅持受限对象工作身份/精确回执，不接受任意 URL、路径或 key。Node Canvas 仍是由 Creation 专用身份调用的纯候选 HTTP runtime，不增加回调或重写。

供应商原结果的保全早于对象归档：Execution 在取得响应后先按原 provider_call 身份、原 action/attempt/request key、接收时间和原定价上下文持久保存已知 usage／费用事实，再进行下载、FF 处理、摘要计算与 Media 交接；暂不能定价保留 unknown 和原事实，不能写成零。artifact 身份还须区分真实调用及序号，分区 provider_call 使用原 id 与 create_time，不能将同 operation 的不同步骤或供应商调用误并为一个序号。Media 只接收字节及受限 artifact 事实，不能收到供应商凭据、任意源 URL 或 raw usage，也不能在交接时绕过原已冻结对象工作重新选择路线。

为承接已完整取得的原结果，Execution 可保存有界的临时交接 payload；其作用止于 Media 原 Stage 回执，不能成为另一套对象路由或资产权威。大对象采用不超过 256KiB 的不可变块及完整原身份、总大小、摘要和封闭状态，沿既有各类输入上限与并发预算处理，不能把整个最大视频塞入单个内存消息或反复拼接大 bytea。缺块、截断、摘要不符、未得到最终成功状态都不是 present；只有 Media 原完整回执在本域核实并持久化后，才在同事务中清理临时字节。未知交接不按 TTL 丢弃，重建只核对原 Stage／Resolve 或原完整交接身份，不能重发收费生成。首次完整 payload 持久化之前崩溃仍可能只有已知成本及未知结果；仅能查询原供应商结果的只读能力才能恢复该窗口，不能虚称字节已经保全。

完整入口不得导入旧全量 app 或其他 owner application/domain/ORM；现有跨域 Principal 以消费方最小值对象和协议 adapter 替换。完整 Media/Creation 按 §7.5.3 分开有状态 owner 与纯计算程序的组合根和依赖门禁：前者只使用本域权限，后者继续验证整个可执行程序的无 DB 闭包，不能只检查计算子包或放宽原入口白名单。Gateway 固定 method/path 唯一分发，保持 Cookie/Origin/CSRF、SSE/WS、防伪头与写入不透明重放；`/internal` 不公开，无单体 catch-all。

公共路由归属按稳定 method/path 固定，不能按当前混合源码目录推断：团队及 `/platform/teams/:id/*` 的成员、邀请、转让、统计、导出和审计归 Creation；平台账号邀请和 admin-grants 归 Identity。统一 `/invitations/{preview,accept,decline}` 与 `/me/authority-proposals` 仍由 Identity 承接原公共合同，其中团队事实/效果必须经 Creation 合同，不能继续跨表操作，也不让 Gateway 解析 token/body 选 owner。`/analytics/{creation,business}` 的权威事实是执行/账务，公共处理归 Execution，项目可见性经 Creation 合同；三个 `/platform/diagnostics/{overview,logs,logs/:id}` 只读路由归 Identity 的受控平台查询，不把 legacy 进程内 Buffer 当作四域诊断汇总。

Gateway 完整模式要求四个明确且不同的 origin，和显式 legacy 单上游迁移前模式互斥，任何半配、混配或自环启动失败。完整模式不得存在未知路径 catch-all 或单体 fallback；升级连接与普通请求都受有界停机管理。合同库存应从实际 HTTP Register 提取并经真实四上游验证，覆盖精确 method、参数路径、特殊静态段和编码歧义；配置/路由测试通过不代表下游已经独立，也不授权在缺失完整 owner 时启用该拓扑。

切换须停旧准入、排空/围栏旧 worker、核对命令/供应商/对象/资金、管理员离线核验结构角色，再切唯一 writer/路由；旧进程重启不能复活权限。回退同样转移唯一 owner，不双写、不恢复万能 all。实现及隔离验收不等于授权实际生产/存量切换。统一命名不重算既有幂等/派发/事件身份。

## 8. 实施与验收

### 8.1 允许物理拆分的门禁

不以新目录、容器启动或 HTTP 200 作为服务完成证明。每个候选服务至少满足：

| 门禁             | 必须证明的条件                                                                    | 对应需求接受条件 |
| ---------------- | --------------------------------------------------------------------------------- | ---------------- |
| G-GOMS-01 所有权 | 拥有的模块/表/任务/事件/密钥可枚举；没有越权 JOIN、外键、应用导入或隐式全库写权限 | AC-GOMS-01/02    |
| G-GOMS-02 事务   | 原本同事务的不变量有本地保留或已接受的等价交接协议，未知回执有查询与恢复路径      | AC-GOMS-03       |
| G-GOMS-03 合同   | 公共生成客户端一致，内部协议兼容；错误、deadline、幂等及流式重连经过验证          | AC-GOMS-04       |
| G-GOMS-04 故障   | 重试、崩溃、重复/乱序事件、lease 过期、关闭及撤权不造成越权、重复收费或丢失责任   | AC-GOMS-05       |
| G-GOMS-05 运行   | 独立构建、配置、角色权限、健康、观测、停机和受控回退都有对应验证                  | AC-GOMS-05       |

### 8.2 最小技术场景

| ID           | 前置与动作                                            | 可观察接受结果                                                          |
| ------------ | ----------------------------------------------------- | ----------------------------------------------------------------------- |
| CASE-GOMS-01 | 同一确认命令并发重放，包含回执丢失后重试              | 返回同一 operation/预占，不多建任务、不重复收费；同 ID 异内容冲突       |
| CASE-GOMS-02 | operation 写入后、事件发布前杀死进程                  | 业务与 Outbox 同在或同无；恢复后能投递且 Inbox/业务去重                 |
| CASE-GOMS-03 | 供应商已接收但响应丢失，重建 worker                   | 保留未知责任并查询原请求，不再提交一个新收费请求                        |
| CASE-GOMS-04 | 原 worker 租约过期，新 owner 接管，原 worker 恢复写入 | 旧 epoch 的业务发布被拒绝，最终结果与结算保持一份                       |
| CASE-GOMS-05 | 归档延迟或失败、供应商已产生费用                      | 成本事实仍保留；未发布资产不被报告成品，恢复不重复归档/采用             |
| CASE-GOMS-06 | 项目关闭同时存在确认、派发、媒体发布和迟到消息        | 关闭围栏生效，状态真实反映在途责任；完成删除后无新有效写入              |
| CASE-GOMS-07 | 账号软删除/撤权后复用缓存、旧令牌与内部请求           | 高风险命令及应撤销访问按原安全合同拒绝，不依赖异步投递最终成功          |
| CASE-GOMS-08 | 用服务 A 的角色访问 B 的业务表/队列，或伪造用户头     | 数据库/消息权限与服务端鉴权均拒绝，不能绕过网关获得业务权限             |
| CASE-GOMS-09 | RPC deadline、依赖不可用与流式断开/重连               | 重试有界，任务不因断开重复启动，状态可查询且流式可补齐                  |
| CASE-GOMS-10 | API/worker/relay 独立启动和收束                       | 无相互健康依赖死锁、无失控 goroutine，持久任务可恢复                    |
| CASE-GOMS-11 | 项目创建/复制中断，或清除时他域仍持有素材引用         | 不报告半成品可用；不误删被引用对象，重试沿原命令恢复                    |
| CASE-GOMS-12 | 普通服务启动并执行维护任务，数据库角色禁止 DDL        | 任务不尝试创建/挂接/删除分区等 DDL，业务角色无 DDL 权限且必要业务可运行 |

后续实现遵循 Red → Green → Refactor，使用隔离 PostgreSQL、受控对象存储/供应商与真实协议验证。修改 Go 时执行适用的格式、vet、lint、race、govulncheck 及生成/边界检查；涉及结构时额外执行 schema 来源、角色与结构语义测试。
