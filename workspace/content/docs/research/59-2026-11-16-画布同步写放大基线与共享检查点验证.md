# 画布同步写放大基线与共享检查点验证

来源：[需求10 SRC-SAVE-09](../requirement/10-画布协作编辑需求.md) → [设计17](../design/17-画布Yjs协作编辑设计.md) → [PRD09](../prd/09-画布协作编辑.md) → [计划19](../plan/19-画布Yjs协作编辑实施计划.md)。执行状态见 BACKLOG。前序 SQLite 适配评估见[调研58](58-2026-11-16-画布存储压力与SQLite适配评估.md)。

## 1. 结论

串行隔离负载中，共享完整二进制检查点使接受窗口的 PostgreSQL WAL 减少 **30.0%～36.9%**；2000 节点的 12 次编辑平均从约 **32.1 MB 降到 20.3 MB**。每组仍有初始版本和 12 个内容修订，共 13 个完整历史版本；历史 JSON、二进制内容与原始 epoch/sequence/hash 绑定保留。

可以确认写放大下降。延迟存在明显宿主机波动，不能据此承诺稳定的端到端加速、多人吞吐或生产容量。当前完整状态仍每次持久化一次，历史 JSON 仍逐内容修订保存；本轮没有改变快照粒度或引入增量回放恢复。

## 2. 环境与负载

- 2026-11-16，Mac17,2，10 CPU、24 GiB 内存；本机原生 PostgreSQL 18.4、Node 24.19.0、Go 模块实际工具链 1.26.11。Docker 无响应时使用新的独立 PG 数据目录与监听端口，没有重启或改动现有服务。
- 基线源为 `841d2617765ad58674afa270924de90199b58083` 中的接受适配器和规范性 schema；优化源为本次未提交改动。三个生产文件的前后 SHA-256 已随[机器数据](59-canvas-sync-performance-metrics.json)记录。前序编辑器迁移和其他并行未提交工作保留。
- 基线库、优化库分别从对应完整 `schema.sql` 与 `data.sql` 初始化；测试专用启用 `pg_stat_statements`。`synchronous_commit=on`、`full_page_writes=on`、`wal_compression=off`、`shared_buffers=128MB`；观测期间 `autovacuum=off`、`checkpoint_timeout=1h`、`max_wal_size=4GB`，用于减少后台波动，不能直接照搬为生产调优结论。
- 50/200/2000 个文字节点，每节点 288 个确定性、非均匀 ASCII 字符；单节点插入一个中文字符或位置 x 增加 1。每类重复 3 次，每次 12 个独立更新，共 **432 次前后对照接受**。固定客户端 ID 生成增量，初始化的 Yjs ID 编码长度仍可能影响完整状态与 delta 的少量字节。
- 客户端更新通过同一个真实 Yjs 文档连续生成，生成进程不在测量窗口内。接受路径是正式 `YjsService.Submit → 私有 HTTP runtime → CommitYjs → PostgreSQL`；不包含浏览器渲染、WS 网络广播、外部模型或对象存储请求。

接受时间包含回执查证、基线加载、候选计算和原子提交。WAL 由接受前后 `pg_current_wal_insert_lsn()` 差值得到；重字段 SQL 使用 `pg_stat_statements` 的 calls、wal_bytes、total_exec_time 前后差值。历史字节为 JSON 与二进制的**逻辑大小**，引用共享后仍按版本计数，不能当作磁盘占用，也不能用 WAL 降幅推算历史磁盘降幅。SQL 分组只观测重字段写入，未统计全部 SQL 或锁等待。

## 3. 实测与定位

WAL 为每 12 次提交的 3 轮平均值，MB 使用 10⁶ 字节；延迟为各类 36 次提交的合并样本，p95 取 nearest rank。

| 节点 | 操作 | WAL 前 → 后（MB） | 降幅 | p50 前 → 后（ms） | p95 前 → 后（ms） |
| --- | --- | --- | --- | --- | --- |
| 50 | 文字 | 0.966 → 0.676 | 30.0% | 76.2 → 54.8 | 105.3 → 136.4 |
| 50 | 拖动 | 0.915 → 0.619 | 32.4% | 66.8 → 54.3 | 90.8 → 83.8 |
| 200 | 文字 | 3.363 → 2.177 | 35.3% | 167.8 → 121.8 | 199.3 → 153.8 |
| 200 | 拖动 | 3.317 → 2.128 | 35.9% | 175.8 → 124.7 | 217.5 → 160.5 |
| 2000 | 文字 | 32.100 → 20.260 | 36.9% | 1694.3 → 1084.9 | 3812.4 → 1452.0 |
| 2000 | 拖动 | 32.106 → 20.256 | 36.9% | 1041.0 → 1861.3 | 1167.4 → 2539.4 |

2000 节点文字增量每 12 次仅约 233～246 字节，完整状态却约 1.69～1.74 MB。基线重字段写入中，历史 INSERT 约 20.0 MB WAL，当前完整状态 UPDATE 约 11.8 MB WAL；优化后历史 JSON 与引用写入约 8.6 MB，唯一完整二进制及 head 引用更新约 11.5 MB。主要收益来自避免跨表复制相同的完整二进制。

原路径每次接受前后都调用历史记录函数，已有修订也序列化整个文档并尝试 INSERT。额外 `EXPLAIN (ANALYZE,WAL,BUFFERS)` 冲突样本未观察到 WAL，因此不能把这些冲突尝试当作主要物理写放大。本轮存在性检查跳过重复序列化和重字段发送；每组历史 INSERT 从 24 次尝试变为 12 次，另有轻量存在性查询和检查点引用检查，**不宣称总 SQL 数下降**。

### 延迟异常的交替复核

首轮 2000 节点拖动出现明显反向结果，因此另编译两个隔离测试二进制，按基线 A → 优化 B → 优化 B → 基线 A 连续执行相同的 12 次拖动负载，共 48 次接受，并拆分 runtime/commit 时间。没有在这段测量中并行运行本任务的编译、Race 或 Node 测试；宿主机仍与其他工作共享。

| 轮次 | 版本 | p50 接受（ms） | p50 runtime（ms） | p50 commit（ms） | WAL（MB） |
| --- | --- | --- | --- | --- | --- |
| 1 | 基线 | 1268.5 | 756.1 | 475.6 | 32.100 |
| 2 | 优化 | 1331.9 | 793.3 | 506.2 | 20.258 |
| 3 | 优化 | 1246.8 | 751.7 | 464.1 | 20.249 |
| 4 | 基线 | 1415.1 | 830.8 | 521.0 | 32.123 |

合并每版本 24 次接受后，p50 为 1303.8 → 1273.5 ms，runtime 为 783.4 → 764.4 ms，commit 为 480.8 → 470.2 ms。首轮的明显退化未稳定复现，而 WAL 减少约 36.9% 在四轮均保留。样本量与环境不足以证明稳定延迟收益；后续应在固定资源、并发和 RTT 下继续测量候选全量重建及数据库加载成本。

## 4. 实现及行为约束

- `canvas.collab_checkpoint` 每份完整状态只写一次。head 与历史分别保存 `state_id`，使用同文档复合外键；跨文档引用受约束，应用角色没有 checkpoint UPDATE 权限。
- 初始化、正常接受和新 epoch 历史恢复都在原事务中创建检查点并切换引用。接受事务仍联合保存领域投影、增量日志、回执与 Outbox，确认时点和 writer fencing 不变。
- 每个内容修订仍保存完整 JSON 和原始二进制绑定。已存在历史不被后续纯因果状态覆盖；纯因果更新仍推进 commitSeq、保存完整当前二进制及增量，清理其被替换且无历史引用的旧检查点。
- 清理只针对同文档刚被替换的旧状态；当前引用、历史引用与外键共同保护保留数据。失败回滚同时撤回新检查点、引用切换及清理；无变化更新和幂等重放不新增完整状态。
- Go PostgreSQL 适配器沿用现有 GORM/事务 SQL。NestJS Canvas 仍只计算候选，无数据库连接、CRUD 或手写 SQL。用户要求已补入仓库 AGENTS：NestJS CRUD 使用 ORM，禁止 ORM 自动结构同步/运行时迁移。

## 6. 部署边界与剩余成本

只验证了规范性 schema 初始化的新隔离库，**未执行存量业务库转换或部署**。结构变更集中在 `backend/db/schema.sql`；仓库没有新增 SQL 文件、迁移目录、自动迁移框架或服务 DDL。

存量上线前由管理员停写、备份并基于实际结构与规范性 schema 离线受控转换：为旧 head/version 的完整二进制建立 checkpoint 引用；只有**同文档、字节完全相同**的状态才可共享，不能仅按 revision、graph hash 或 commitSeq 合并。纯因果变化下 head 和同内容 revision 的历史二进制可能不同，必须分别保留。核对每条原历史的 JSON、二进制与所有元数据，检查非空引用、外键、权限及回读结果后，再移除旧 state 字段并启动新版。本报告的性能阶段未执行转换；后续合成存量副本演练与上线核验步骤见[调研60](60-2026-11-16-画布存量检查点离线转换演练与上线核验.md)，仍未执行现有业务库变更，不得将隔离结果称为生产存量升级验收。

未测量磁盘稳态、锁等待、网络广播及多人并发吞吐；当前大图的候选全量重建、完整投影加载和逐版本 JSON 仍有成本。SQLite 不作为此次替换方案。进一步优化须继续保留原恢复合同并另建同负载证据，不能凭本次 WAL 结果直接降低历史频率。
