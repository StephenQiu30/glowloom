# 画布存储压力与 SQLite 适配评估

日期：2026-11-16。来源：SRC-CAN-17；GitHub 固定提交源码、Firecrawl 检索及 SQLite 官方文档（通过 Context7/Firecrawl 核对）。本文区分源码事实、建议与未验证项；不把上游单用户存储当成织光多人协作的验收。

## 1. 结论

当前建议保留 PostgreSQL 作为团队画布的持久接受权威，先测量并减少写放大。SQLite 可以作为未来桌面单用户工作区的候选，或可重建的本地读缓存；本轮不新增 SQLite、不切换数据库或客户端保存成功语义。用户明确 SQLite 放置位置“先根据调研确定”，不等于已要求采用某个位置。

画布编辑器源码集中到 `canvas/editor/`；应用页面、当前身份/空间、业务 API 与会话装配留在 frontend。源码集中不要求把整个 frontend 服务并入协作进程。工程边界见[设计10 §7.1.1](../design/10-画布交互设计.md#711-编辑器源码归属src-can-162026-11-16-已确认)。

## 3. SQLite 应放在哪里

| 位置 | 可获得的收益 | 当前判断 |
| --- | --- | --- |
| 浏览器 SQLite/WASM + OPFS | 可支持复杂本地查询、读取缓存或桌面式离线数据管理 | 不会自动减少仍须服务端持久确认的编辑写入，也不提供跨用户同步。Worker/VFS、多标签页锁、配额、清理及部分VFS的COOP/COEP需独立验证；会与现有跨域媒体加载共同影响部署。当前仅存少量个人视图或有界未决日志，不足以证明新增SQL引擎值得。 |
| Canvas 服务端单个 SQLite 文件 | 嵌入式部署简单；按画布拆文件可研究不同画布的写入隔离 | SQLite 每个数据库文件同时只有一个写者；WAL 的读写并行有用，但不是多写者能力。可经同机应用服务向远程用户提供访问，并非不能做多人应用；然而我们的多实例路由、权限撤回、提交回执、Outbox与素材任务关联需要重做持久事务边界，不能以换驱动代替。 |
| 独立桌面单用户工作区 | 与 BeefTV 的部署和数据所有权相近 | 是更匹配的 SQLite 场景；当前织光尚未把桌面离线工作区确定为此次交付范围，不预建这套运行模式。 |

SQLite 官方说明：WAL访问者须位于数据库文件所在同一主机；不要把 WAL 数据库放在网络共享文件系统供多个服务主机直接写。浏览器 OPFS VFS 的限制不同于原生 SQLite WAL，不能混用结论。不能把本地落盘称为已完成团队保存。

## 4. 当前写入链路的真实观察

以下为源码事实，尚无线上负载指标或优化收益百分比：

- `frontend/src/components/canvas/yjs-live-session.ts` 的 `change(state, stable)` 在手势预览阶段只更新本页状态，稳定事务才进入后续处理；不是每条 pointermove 都写数据库。共享内容与个人视图已有分离。
- `canvas/src/runtime/candidate.ts` 从基线重建隔离文档，计算候选并返回完整编码状态与规范投影；该路径的文档解码/投影/传输成本会随内容增长。
- `backend/creation/canvas/adapter/postgres/yjs.go` 的 `CommitYjs` 将接受后的完整二进制写入 `collab_document.state`，另写增量 `collab_update`、原提交回执及 Outbox。不能删掉这些语义来伪造“性能提升”。
- `yjs_history.go` 的 `recordYjsVersion` 序列化文档，并按 revision 保存文档 JSON 和对应二进制状态；`CommitYjs` 在接受前后均尝试记录，唯一约束防止同 revision 重复行，但不免除序列化与冲突检查成本。历史空间和写放大值得测量。
- `store.go` 的 `saveGraphWithRestoration` 已比较节点/边并跳过未修改项，不能描述为每次重写所有节点。其删除检测仍逐个扫描新数组，`persistYjsProjection` 也会处理完整图和引用；大图 CPU/校验成本与数据库I/O应分别测量。

## 5. 建议的优化顺序与接受条件

1. 使用隔离数据库和合成画布建立50/200/2000节点的基线，分别覆盖拖动、正文持续输入、多人同画布和不同画布。记录每动作接受次数、入站增量/候选全状态字节、SQL次数/耗时、锁等待、WAL及历史增长、浏览器帧耗时与长任务。禁止用空图渲染或单机磁盘速度代替多人接受测试。
2. 在现有接受事务内减少重复序列化、全图扫描和可证明冗余的读取；先保持原回执、历史恢复和引用规则。变化必须有真实负载前后对照及原行为回归。
3. 若完整状态和历史确为主要成本，再设计“每次持久化已接受增量 + 有界检查点 + 可验证重建”。checkpoint之前的增量、原提交身份、回执、删除事实与恢复所需历史不能提前清理；崩溃、拒绝及切epoch均需证明。此项是后续设计建议，本轮未实现或降低历史能力。
4. 只有在明确需要复杂本地查询/离线工作区且有收益证据时，再考虑SQLite。任何第二存储都必须声明能否丢弃、如何重建和谁能宣告保存成功。
