# 画布WebSocket实时同步需求

## 1. 原始需求与问题

用户要求“画布数据更新使用WebSocket建立连接，为后续多用户协同工作建立基础”。画布编辑提交、确认与权威变更推送使用唯一WebSocket通道，不以HTTP兜底或另设定时保存器。心跳负责保活、版本及权限核对，不代替数据库回执。Go连接层采用已确认的`coder/websocket`。本需求回答：**变化怎样到达其他客户端，连接中断后怎样恢复，用户如何知道当前同步状态。**

“本地连接”暂按浏览器与当前部署的画布后端建立长连接理解，本地开发连接本地服务；不推定为设备间P2P或独立桌面服务。

本需求依赖[数据需求08](08-画布数据库持久化与DAG需求.md)的版本、持久回执、授权与可恢复状态。并发编辑自动合并由[协作需求10](10-画布协作编辑需求.md)负责，接通WebSocket不能作为协作合并验收。

来源承接：本轮SRC-SAVE-01～03见[需求08来源表](08-画布数据库持久化与DAG需求.md#11-保存需求来源与归属)，竞品证据见[研究03](../research/03-画布节点保存与协作机制竞品研究.md)。FR-SYNC-01的自动提交与BR-SYNC-01的独立持久确认仍是需要；当前实现出现手动保存按钮不能反向改写需求。完整编辑事务的边界由设计定义，不把竞品的50ms、100ms或RAF值写成产品要求。

## 2. 范围

纳入：建立连接、授权订阅、初始化与增量衔接、操作传输、服务端确认、远端推送、状态呈现、断线检测、重连补齐及撤权。

数据库表设计与DAG语义归需求08；Yjs合并、个人撤销、在线成员与光标归需求10。评论、邀请和演示跟随不由本需求新增。初始化、上传等可沿用适合的HTTP接口，但不能留下绕过权威提交规则的写入入口。

## 3. 产品策略与成功标准

| 维度       | 本需求策略                                                   |
| ---------- | ------------------------------------------------------------ |
| 愿景       | 已保存的修改及时到达有权访问的客户端                         |
| 用户与任务 | 优先同账号双标签页与跨设备观察，继而验证双账号接收变化       |
| 成本       | 复用应用服务边界；测量连接数、广播、补齐传输与恢复成本       |
| 价值       | 不必手动刷新，也能知道连接与保存是否成功                     |
| 取舍       | 通信与恢复独立验收，并与Yjs合并及持久化联合验证              |
| 指标       | 已提交变更的远端可见延迟、重连补齐成功率与重复业务效果数     |
| 增长       | 实时连续体验为后续协作提供基础，当前不新增邀请增长或付费承诺 |
| 能力       | 长连接、授权生命周期、初始化竞态、确认重试、背压与运维观测   |
| 可持续优势 | 稳定可解释的恢复体验；通信协议本身不是独占优势               |

最小验证：一端编辑、另一端观察，注入ACK丢失与重连，比较两端已确认版本；不以双方同时编辑来混淆通信与协作合并的独立接受。

## 5. 同步、权限与状态合同

- **BR-SYNC-01：连接、编辑权限与保存状态分开。** 临时断线不等同于失权；完整编辑事务无论是否在线都立即进入同一有界内存队列，在可发送时自动提交，心跳仅核对状态并查证未决回执，不替代业务确认。 连接成功不等于保存成功；“已保存”的唯一规则引用需求08的BR-DATA-07，本需求负责准确呈现。
- **BR-SYNC-02：初始状态与后续变更连续。** 初始化期间发生的提交不能遗漏；重复、迟到或缺失消息有明确检测与恢复行为。每文档的持久接受顺序由权威提交路径提供，不能由消息到达顺序臆造。
- **BR-SYNC-03：重试沿用同一操作身份。** 本需求负责识别未提交、已提交未确认与被拒绝结果，并使用需求08的持久幂等能力；不得把重连变为重复编辑、生成或计费。
- **BR-SYNC-04：历史不足可重建。** 读取需求08提供的一致状态和恢复资料；页面中未确认的操作不得直接覆盖新状态。按需求10处理Yjs差量同步、被拒更新及本页输入恢复；无本地持久草稿的取舍引用需求08的BR-DATA-08。
- **BR-SYNC-05：权限覆盖整个连接生命周期。** 连接、订阅、每次提交及新消息投递须符合当前账号和资源权限；失效、切换账号、撤权及归档按已有身份合同处理，撤权生效窗口待设计。已建立连接不得永久绕过权限检查。
- **BR-SYNC-06：被拒绝结果可理解。** 服务端拒绝写入时，不广播为成功变更；前端显示原因并恢复或保留未确认内存状态，不能误报已保存。

BR-SYNC-01～06的恢复细化：

- 自动保存覆盖正文、参数、布局、节点/连线/分组和素材引用等已完成业务编辑；不依赖点击保存、失焦、离页或停止输入。手势预览与尚未完成的IME组合不冒充已提交事务；素材上传与图绑定分别确认。
- 连接中断、鉴权待恢复、已撤权、只读、队列满和确定拒绝必须有不同处置。只读/暂停写入不锁死仍获授权的平移、缩放和浏览；明确失去访问权限后停止私有内容展示和接收。
- 回执为accepted时补齐对应权威版本；确定rejected时保留输入进入恢复；结果unknown时只查证原请求。权威服务明确未找到原回执后才沿原身份/载荷重试，不能因超时换ID。恢复、重发、切账号/项目须隔离会话，迟到回执不能修改新会话。
- 断线恢复成功不要求自动覆盖他人的新内容。安全兼容意图可恢复；同字段、删除、引用失效等不能安全重建的内容须显示差异和处理选择；用户未处理前保留未解决状态。

IR-SYNC-01：设计需要覆盖连接鉴权、订阅、初始状态与实时增量之间的无缝衔接、提交、确认、拒绝、重连补齐和历史不足时重建。消息字段、心跳、限流、背压和协议版本属于设计，不在本稿预先定死。

IR-SYNC-02：本地开发与生产部署采用相同业务语义；生产使用安全连接，并核验来源与授权。断线、身份过期、权限撤销、旧协议客户端与服务重启必须有可观察结果。

WebSocket的双向通信职责参考[RFC 6455](https://www.rfc-editor.org/info/rfc6455/)，业务消息、确认与恢复合同仍需后续设计。传输成功不代表协作合并或数据库持久化完成。

## 6. 质量目标与独立验收

| 编号        | 目标与口径             | 验证方法与待决                                                                                             |
| ----------- | ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| NFR-SYNC-01 | 同步体验可测量         | 分别采集本地反馈、持久化ACK、远端可见延迟的p50/p95/p99；节点/边数、人数、RTT、持续时长及目标值在设计前确定 |
| NFR-SYNC-02 | 长连接维持授权隔离     | 未授权订阅、越权写入、撤权后消息推送均验证；撤权生效窗口需定义，不能只检查连接建立时的权限                 |
| NFR-SYNC-03 | 出错可诊断、恢复不误导 | 区分连接失败、提交拒绝、确认不明、同步中与已保存；观测操作ID、文档版本和失败类型，不记录凭据或完整私有内容 |

测量必须给出节点/边规模、连接数、网络RTT、持续时长和部署方式；p50/p95/p99阈值、撤权窗口和重连恢复目标尚未确定，不以一次本地演示代替容量接受。补充检查慢客户端、限流/背压、连接泄漏与旧协议客户端。

**独立验收入口：** 依赖真实数据存储，使用双客户端单写者或顺序编辑测试消息与恢复；并发合并结果另按需求10验收。服务器重启与跨实例恢复须在实际部署条件下补证。

| 编号       | 前置与操作                                        | 通过条件                                                                                                                                                                          | 所需证据                      |
| ---------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| AC-SYNC-01 | 两客户端打开同一画布，A修改节点                   | A不点击保存，已完成编辑自动通过WebSocket提交，权威确认和B的变更均通过WebSocket返回，无需刷新；数据库读回一致；不能仅用HTTP写入加WebSocket通知冒充完成；初始化期间发生的操作不遗漏 | 双客户端和服务端版本/消息记录 |
| AC-SYNC-02 | 发送前、提交中、提交后ACK前分别断线，随后重连     | 正确区分未提交/待确认/已接受；断线途中及随后连续拖动可结束，后继落点保留；原操作查证一次效果，健康连接丢ACK也由心跳恢复；补齐并刷新核对已确认位置                                 | 可控断网、事务结果和操作回执  |
| AC-SYNC-03 | 服务重启、消息重复/迟到、历史不足或长时间断线     | 不重复执行；能补齐或安全重建；未确认内存操作不盲目覆盖新状态                                                                                                                      | 故障注入、快照/历史边界测试   |
| AC-SYNC-04 | 未授权连接/订阅、账号切换、撤权、归档期间继续提交 | 隔离数据，拒绝无权操作；按定义窗口停止新私有消息；只读不被长连接绕过                                                                                                              | 权限集成测试和真实会话        |

AC-SYNC-01/02还覆盖持续输入、素材上传未完成/失败、旧ACK晚于新编辑、队列满前的事务接纳和应用内离页。AC-SYNC-03/04覆盖unknown与未找到回执的区别、账号/项目切换后的迟到回调，以及暂停写入时仍有权限的浏览操作。

通信与协作分别验收；三专项联合接受见需求10的AC-COL-06。执行证据见计划18、19，容量、生产与多实例接受按实际环境单列。
