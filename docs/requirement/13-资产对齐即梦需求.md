# 资产对齐即梦需求

## 1. 原始要求与确认

来源：2026-10-28 用户请求。

> 对即梦中的资产进行检查以及完整的需求的分析，并整理到我们当前的项目中的一些功能进行检查和整理，这一步不需要查看我们当前的功能实现，先进行完整的分析，第二步对照我们的当前的实现，更正和补齐，保持和即梦的一致性，同时我们的命名方式也需要更新，对设计稿进行彻底更改，然后在落实我们的代码实现。

已确认：按竞品独立分析 → 实现差异核查 → 更新需求和设计稿 → 代码实施的顺序执行；资产信息架构、功能及用户可见命名对齐即梦。该要求替代需求11中“素材库优先”作为资产总入口的旧顺序；原上传素材、文件夹、回收与恢复的业务能力保留为参考素材管理，不能因改名删除用户数据。

竞品事实见[调研08](../research/08-即梦资产完整需求分析.md)，织光方案由[设计26](../design/26-资产信息架构与即梦对齐设计.md)唯一持有。

## 3. 补充确认与待明确合同

已确认（2026-10-28用户补充）：用户进一步要求“我们需要全量对其，保证功能和设计完全一致”，因此本次包括全部资产交互闭环，不以只读核心完成替代全量交付。生成历史仅显示“本人发起的生成记录”；处理方式保持与即梦一致。现有字段不能无证据地将确认者等同创建者，缺少可靠发起人事实的历史数据不可冒充本人的记录。

已补证与验证边界：

- 共享发行代码已证明历史画布为旧画布/旧草稿工作流；织光使用显式来源，不映射协议版本、归档或回收。
- 短剧采用显式分类，但既有对象如何归类需独立规则；不得按视频或剧本节点猜测，不自动改写已有项目。
- 已取得结果级操作、PDF/Markdown格式、批量上限与部分失败客户端证据；即梦当前账号非空运行样本仍缺少，织光真实SQL与合成UI夹具分别验收。

这些待明确事项不影响先完成观察报告、差异表与设计结构；不得据此声称完整一致性或真实生命周期验收完成。进度与下一步仅在[BACKLOG](../../BACKLOG.md)维护。
