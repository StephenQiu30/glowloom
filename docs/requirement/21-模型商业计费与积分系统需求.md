## SRC-CREDIT-02 实施与结算确认

用户要求「完整落实我们的积分的计费以及模型的计入的方案落地」。后续明确采用1元=10积分、生成实扣以确认价为上限、超出由平台承担、费用未知继续冻结。支付选择「暂不接真实渠道，只做隔离验收」。上述授权用于实现和隔离验证。商品价格、正式渠道、周期会员与售后补偿政策仍按各自合同审核。

## SRC-CREDIT-03 余额准入

用户要求「我们当前的项目中应该预估积分不足就拒绝执行，积分不可以为负」。所有新确认的正价项目任务必须在派发前冻结足额可用积分。项目未绑定钱包时可用积分按零处理。并发确认以事务中的冻结结果为准，零价结果复用不冻结积分。

## SRC-CREDIT-04 创作空间钱包、可选项目与整数积分

日期：2026-11-06。用户确认直接生图、生视频和创建画布，项目可选。模型按供应商官方 API 的实际计量与采购价计算，BeefTV 作为接入参考。销售价独立审核，以官方实际消耗对应金额乘可调倍率，默认 1。每 ¥1 换 10 积分，整次消耗向上取整。生成确认价封顶、足额才执行、积分不可负、费用未知保留冻结沿 SRC-CREDIT-02/03。独立创作和项目内创作见[需求07 SRC-PC-08](07-项目与画布创建原始需求.md#src-pc-08)。

### 账户、付款方和项目

| ID | 规则 | 验收 |
| --- | --- | --- |
| FR-CREDIT-07 | 在个人空间使用个人钱包，在有授权的团队空间使用团队钱包。服务端按经授权的当前空间解析付款方，个人与团队余额分别展示。没有显式团队上下文时，默认个人空间。 | 无项目时能读取余额和报价；切换空间时重读余额和报价，不从另一空间自动补扣。 |

| FR-CREDIT-10 | 确认时冻结付款账户、空间、可选项目、消费模式、价目和上限。历史消费继续归原付款方。 | 报价后切换空间、失去权限或项目迁移使原报价不可用。已确认任务按原付款方对账。成品后来加入项目只改变组织位置。 |

### 报价、扣费和恢复

| ID | 规则 | 验收 |
| --- | --- | --- |
| FR-CREDIT-11 | 费用旁显示预计整数积分。明细按需展示，区分单位、数量、费率与可变价上限。修改影响费用的模型、参数、引用或付款方后更新服务端报价。 | 首页、独立画布和项目内以同一组输入得到同价。费率或用量不完整时显示「费用待确认」，禁止以零价提交。 |
| FR-CREDIT-12 | 采购按官方费率、原币和实际用量记录；销售按审核版本及冻结倍率计算，使用审核汇率换算。整次调用按人民币销售金额乘 10 后向上取整，先聚合本次各计费项再取整。 | ¥0.12 对应 2 积分，采购金额仍为 ¥0.12。单次请求两张同价图按 ¥0.24 计 3 积分；两次独立调用各扣 2 积分。已确认报价、冻结和实扣使用同一整数口径。零金额结果复用为 0 积分。 |
| FR-CREDIT-13 | 确认时原子检查钱包余额、适用积分批次及已配置预算，足额才冻结和派发。实际用量可信时按确认上限内结算并释放剩余。部分成功按供应商可核验用量计价。 | 可用 1 积分无法确认 2 积分；并发请求总冻结不超过可用额。预估 3、最终 2 时扣 2 并释放 1；费用超确认上限的部分记为平台成本。 |
| FR-CREDIT-14 | 请求未派发或有明确零费用证据时释放冻结。供应商结果或费用未知时保留原冻结并进入核查。重试、重放、恢复及回执查询沿原请求标识。 | 重复提交、超时刷新和重复供应商回执只有一次收费；退款或补偿采用可追溯的反向流水。 |
| FR-CREDIT-15 | 钱包展示可用、冻结、近期到期及收支明细。积分来自核验支付、已批准的会员权益或可追溯赠送批次，按批次的有效期、用途和付款空间使用。 | 查流水可定位原任务、价目及消费/返还；余额不足与项目额度不足提示不同。一次性本机 100 积分试点额度独立受控，项目限额不能发行积分。 |

### 迁移与待评审

- 既有项目数据和付款事实保留。先验证存量库钱包增量结构和历史回执回放，再开放独立创作的付款入口。历史金额、冻结和已结算积分不追溯重算，新规则由新报价版本承载。
- 账本仍需保存供应商原币、换算后的采购成本、销售金额、用户实际扣除的整数积分和冻结差额。整数积分不可通过重定义采购费率来实现。
- 会员商品、正式支付渠道、赠送期限、团队项目预算配置权限、默认团队付款策略及多项目报告仍须单独评审。页面可见的竞品活动价和会员限制不作为本项目销售规则。

## SRC-CREDIT-05 积分服务基础一致性、性能与防滥用要求

日期：2026-11-08。状态：用户明确提出。先以本地合成积分命令验证基础能力，不依赖具体模型供应商业务载荷，不调用真实支付或供应商，不触碰生产库。

| ID | 要求 | 验收要点 |
| --- | --- | --- |
| FR-CREDIT-16 | 积分服务至少支持账户、余额与流水查询、积分授予、直接扣减、预冻结、正式核销和解冻；调用方不能决定未授权账户或绕过模型报价创建模型消费。 | 使用合成调用方及账户完成全生命周期；模型业务继续由 operation 报价与准入承载。 |
| FR-CREDIT-17 | 所有写命令使用接入方提供的幂等键；同键同请求重放原结果，同键不同请求内容拒绝，幂等凭据覆盖命令待处理与重试期。 | 并发重放只生成一次积分效果与一组流水；改金额、账户、动作或来源复用同键时冲突。 |
| FR-CREDIT-18 | 积分并发扣减使用乐观锁；服务端计算新余额并以版本条件提交，禁止 SQL 对余额执行扣减算术。高并发写入由消息队列异步解耦和削峰。 | 竞争扣减不造成负余额或双花；CAS 冲突可重试，重试耗尽转入明确的失败/核查路径。 |
| FR-CREDIT-19 | 每笔积分发放、扣减、冻结、核销、解冻、过期和补偿都生成不可逆、可关联来源的积分流水；更正通过反向流水完成。 | 从流水重建余额投影后与权威版本一致；应用角色不能改写或删除财务事实。 |
| FR-CREDIT-20 | 跨业务核销按 SAGA 处理：先预冻结，成功后核销；明确失败自动解冻并写补偿流水。上游结果未知时保留原冻结并查证，不能将未知当失败。 | 成功、明确失败、重复回执、超时未知、服务重启均沿原命令和冻结身份推进，积分效果最多一次。 |
| FR-CREDIT-21 | 消息通过 Outbox/事务消息保证与账务事实一致，至少一次投递；失败按策略重试，耗尽后进入死信队列，消费端幂等，死信可受权重放。 | 注入数据库提交失败、Broker不可用、重复/乱序消息、消费者崩溃及死信重放，均无丢账、重账或静默释放。 |
| FR-CREDIT-22 | 热点余额可用 Redis 缓存，缓存需可证明版本及失效/更新顺序；Redis 不一致或不可用时，不得错误放行消费。 | 缓存版本不得倒退；失效、冷启动和Redis故障回源权威账本；写入准入仍以一致性事务结果为准。 |
| FR-CREDIT-23 | 积分不可变流水按月分区，支持跨月查询、并发写入、分区预建及受控历史归档；全局幂等不能依赖分区内唯一键。 | 月界写入和游标分页结果完整；分区维护重复运行安全；请求键与业务来源在跨月后仍全局唯一。 |
| FR-CREDIT-24 | 积分接口需要按接入方、账户及请求来源限流，并具备防盗刷措施，包括调用身份校验、重放防护、额度上限、异常频率识别和可追溯审计。 | 越权账户、伪造/过期签名、nonce重放、超限发放/扣减和超频请求被拒并留下脱敏审计；阈值由上线策略评审设定。 |
