## 2. 使用者与目标

创作者需要在同一画布组织素材和生成草稿，保留引用关系并继续创作。已有保存与生成合同在画布实现中保持有效。产品确认人与实施责任人不补造姓名。

## 4. 数据与业务规则

| 编号      | 规则                                                                                                 |
| --------- | ---------------------------------------------------------------------------------------------------- |
| BR-CAN-01 | 服务端图与回执是保存事实；浏览器本地缓存不成为第二套业务持久化                                       |
| BR-CAN-02 | 节点 UUID、媒体 `ref_id`、归属、权限与输入版本沿用现有合同；预览 URL、Blob、播放器状态不作为媒体身份 |
| BR-CAN-03 | 保存中的请求体与幂等键固定；结果未知重试原请求，冲突保留本地草稿，撤权后停止私有访问                 |
| BR-CAN-04 | 本轮不放开已保存生成草稿删除，也不以撤销新增为由绕过删除限制；已保存资源删除需先完成引用与回执设计   |
| BR-CAN-05 | 布局边、生成引用与业务投影分别定义；框选、定位、复制、拖动和视口操作不得触发付费生成                 |
| BR-CAN-06 | 当前图容量为 2000 节点、4000 边；它是协议上限，不是已实测流畅容量                                    |
| BR-CAN-07 | 模型凭据、供应商执行器、桌面后端和远程插件运行时不属于画布实现；需要这些能力时另按所属领域设计       |

## 13. 页面与组件按产品职责重建

SRC-CAN-09：2026-10-20 用户指出当前组件命名不能作为画布服务的结构，要求重建需求以及组件页面实现。本节为该要求的需求合同，状态待评审。第 1～12 节已经接受的业务规则继续有效；本节替换的是页面与组件的组织方式。

当前 `frontend/src/app/canvas/_components/` 把视口、节点、分组、历史、图像处理和页面控件平铺在同一目录，并用 `canvas-` 前缀和 `beeftv` 等上游产品名命名。目录本身已经是画布，文件名再重复画布，职责被抹平；测试和 `data-canvas-engine` 也把上游引擎名写进了产品标识。这使后续接入只能对着来源文件名说话，不能对着创作者打开的页面说话。

重建后的画布仍是一张编辑页。创作者从「我的画布」打开项目主画布，页面读取项目与画布身份后进入编辑。保存、素材和生成继续使用现有服务，不另建图存储或第二套编辑器。
