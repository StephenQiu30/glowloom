## 解释边界

- 一致性包括信息架构、入口、布局关系、操作方式、状态反馈、可用性限制和结果去向，不能只复制暗色外观。
- 本次研究中的 `JC-*` 是观察与候选验收编号；标为待验证或建议的内容不自动成为用户已确认的即梦事实。
- 模型名称、价格、会员标记等是观察当日、当前账号和当前参数组合的界面事实，不是 Glowloom 必须固定写死的服务合同。
- 用户没有要求在此阶段消费积分、开通会员、公开画布、邀请团队、上传个人文件、提交或推送 Git。
- 不以观察到的 UI 推断即梦的框架、后端协议、存储算法或模型实际可调用性。
- 实施状态和后续安排统一记入 BACKLOG，不在本文件宣称完成设计、代码或产品验收。

## 验收原则

1. 每项结论有来源、观察条件、证据类型和覆盖边界。
2. 需求必须覆盖正常、空、禁用、失败及恢复条件；没有观察到的行为显式列入未解决问题。
3. 后续差异核对逐条引用需求 ID，不能仅以存在组件或通过构建判断一致。
4. 设计稿须覆盖完整状态集合并关联需求；实现验收区分界面、模拟数据、真实服务和多人操作。
