# 短剧制作平台源码与发行包对照调研

调查日期：2026-11-12（Asia/Shanghai）。Glowloom 源码基线：`695c779dd8d4a74713d29b575cc188a26b7e997d`，另有并行工作区修改；本文列出的本地路径为本次只读检查所见，不代表当前部署状态。用户明确要求先形成完整需求，不编写产品代码。本次没有安装或运行参考产品、调用收费模型、修改连接配置或部署。

## 1. 结论与证据口径

可复用的核心是制作合同与执行机制：把剧本、制作资产、叙事镜头、模型生成单元、候选素材、采用版本、剪辑片段和交付任务连起来。主 Agent 负责目标、方法与分工，专业子 Agent 负责限定范围的提案和审查；收费准入、正式写入、任务恢复和产物归档必须由确定性的业务操作负责。Skill 的制作方法、框架的持久化 API 与实际端到端成片是三类证据。

本次使用用户指定的 GitHub 插件核对固定提交源码与发行元数据，Firecrawl 搜索并读取项目官网、README 和官方案例，Context7 核对 Pi、FFmpeg、Mastra 文档；按本地技能 `reverse-engineer-anything`（`~/.agents/skills/reverse-engineer-anything/SKILL.md`）的适用边界，对实际发行 ZIP 及其中交付的 JavaScript 做 REA 静态分析。普通源码树直接阅读，没有把 REA 当作源码分析的必要包装。

| 证据类型 | 可以支持 | 不能据此推定 |
| --- | --- | --- |
| 固定 SHA 的源码调用链 | 注册、入参、状态写入、恢复分支及生产方法的存在 | 当前部署已启用、所有分支运行正确、真实模型质量 |
| 官方说明和案例 | 作者声明与案例明确列出的制作结果、人工操作和失败项 | 隐藏实现、全自动成片、当前版本完整接受 |
| REA 发行物静态证据 | ZIP 内容身份、选定宿主代码及有限函数关系 | 程序已运行、网络端点已调用、后端及依赖全量行为 |
| 上游框架文档 | 正式 API 语义、媒体处理约束与框架边界 | 参考项目锁定版本已具备最新功能、本项目已验证兼容 |

本文“未找到”仅限所列源码和定向检索范围，不证明整个产品永远不存在该能力。完整制作、真实供应商恢复、计费、音画质量、目标剪辑器导入均未在本次运行验证。

## 3. BeefTV：从业务操作到确定性交付

### 3.1 实际调用链与主子能力边界

`用户目标 → Pi Durable 会话/Skill → operation bridge → Go 正式 operation → 业务任务 → 媒体入库和画布绑定 → 交付操作`。

[宿主包与会话创建][beef-owner] 使用 Pi Durable 1.5、SQLite Storage，显式设置 `maxRetries: 0` 和工具顺序执行。[operation bridge][beef-bridge] 把正式操作描述映射成工具；稳定操作 ID 与首次参数身份共同防止同名请求被换参。持久化框架负责执行历史，Go 负责实际业务回执，不能据“Durable”推定外部副作用恰好发生一次。

在 `agent-host`、Go 后端及插件目录的定向检索中，没有建立产品已注册并使用 owned child conversation 的完整调用证据。SDK 支持子会话、界面有助手或工具顺序执行，都不能充当主子 Agent 并行生产证明。Glowloom 的真实子会话、预算与停止合同继续归设计32，而不是照搬此处的单助手形态。

### 3.2 Skill、MCP 与任务等待

- [Skill 加载与上下文恢复][beef-skill] 有实际 `skill_load` 及运行[恢复后的 Skill/计划/现场上下文重建][beef-context]。方法资源应随运行固定版本，不能只在首次消息拼入一段提示词。
- [MCP 入口][beef-mcp] 是将本地正式 operation 提供给外部 Claude/Codex 等客户端的 **MCP Server**，写操作要求 `operationId`。所读范围没有建立站内 Agent 作为客户端调用任意外部 MCP 服务的证据。Glowloom 本次要求的是后者，也可另外提供受权服务端入口，两者不可混淆。
- [任务等待][beef-await] 检查任务、真实 `resourceId`、错误与目标节点绑定，避免将“供应商返回成功”直接等同为“画布已有可用素材”。观察失败返回原任务身份，不重新提交生成。其进程内延时和本次执行的约20分钟截止，并不等于跨重启保留的绝对截止/`next_wakeup_at`，不能直接作为多实例后台等待方案。
- [Skill 脚本执行器][beef-script] 包含哈希/路径、临时目录、清理环境、超时、输出上限和进程组取消。这是宿主进程约束，所读代码不足以证明容器、网络或文件系统强隔离；不满足 Glowloom 开放第三方脚本所需隔离接受条件。

### 3.3 分镜和生成准入

[故事板写入][beef-storyboard] 将时长、故事/台词、意图、视点、表演、景别、情绪、光线、音效、镜头运动、动作节拍、必需内容和连续性出口存为结构字段，并关联图/视频节点。这里值得借鉴的是可校验数据，而不是要求所有镜头都填写冗长提示词。

[准备操作][beef-prepare] 只建立故事板行和待制作节点，不偷偷收费生成。[依赖检查][beef-deps] 拒绝将尚未完成的参考与依赖它的目标在同批次一起付费提交；[订单准入][beef-order] 检查版本、模型配置与已确认目标。方法上必须先准备、审阅、固定引用，再受理实际生成。

### 3.4 交付与自动续跑的可复用机制

[确定性交付工具][beef-delivery] 按 `timeline.update → render → nodes.create → task.bind → project.export` 执行，嵌套 `api.executeTool` 使用稳定 key。每一阶段保留回执；节点绑定或工程导出失败时，只补未完成阶段，不重复已完成的本地渲染（该工具回执标注 `local: true, charged: false`）。可借鉴的不是新增一个“交付 Agent”名字，而是多步交付工具具有恢复位置、原结果身份和完整性检查。

[continuation 身份][beef-continuation]、[待续跑扫描][beef-pending] 和 [后台续跑处理][beef-background] 展示了业务层登记后续工作、通过相同宿主入口准入并在观察流断开后继续核对的路径。生产后台不能仅依赖用户页面收到一条 SSE 后再发下一条消息。

### 3.5 官方案例提供了什么证据

[官方案例页][beef-examples] 标注的《最后一瓶水》基于 2.0.1：计划8镜头、约59秒，完成5张首帧、3段视频（第4/5/6镜）和2段旁白，仍有3张首帧失败、5段视频缺失，未完成全片时间线、字幕、最终导出及完整音画接受。该案例明确不是完整成片，不能据此写“已证明一键自动短剧”。

20.34秒换角色案例包含人工/本地修补、时间线和音频回填，超出单次模板执行。三个文本 Skill 案例也不证明视频生成或市场安装成功。案例可用来设计逐项交付清单和部分失败表达，不能代替端到端接受。

## 4. Toonflow：真实协作与 MCP 客户端，但持久生产须另验

### 4.1 多 Agent 是实际调用，不是角色提示词

[主运行时][toon-runtime] 使用 Pi Coding Agent 的 SessionManager、会话文件与工作区文件锁；这不是 Pi Durable Storage。[subAgent 工具][toon-sub] 在一个工具内部用 `Promise.all(tasks.map(...))` 同时执行子任务，顶层工具设为顺序执行也不妨碍这一内部并发。[delegation][toon-delegation] 建立独立子会话文件、父子和任务信息，传播 AbortSignal、事件及 usage；还区分临时任务、本地 Team 和远端 A2A。

[storyboardTeam][toon-team] 有 director 对 writer/reviewer 的分工及连续性知识，这是具体协作材料；其结果是分镜文本，不等于已经生成全部图片、视频和音轨。Glowloom 应借鉴任务书、独立上下文、汇总采用与审查，不照搬无限并发、无限轮次或把每个镜头都拆成独立 Agent。

### 4.2 Skill 与外部 MCP 的实际边界

[Skill 管理][toon-skills] 使用 SDK 加载、frontmatter、工作区/全局目录优先级与文件锁。它证明有方法装载和编辑能力，不证明活动任务固定不可变数据库版本。

[外部 MCP 客户端][toon-mcp] 进行服务发现、连接 ID/哈希命名空间、调用前启用和配置修订复查、取消传播，并把 `isError` 作为错误处理。这些可以帮助 Glowloom 确定连接隔离、重名与失败归一合同；代码本身不能证明跨主子根预算、远程写入未知后的去重或全部外部取消已生效。

### 4.3 制作方法与后台稳定性分开评价

[工作流 Skill][toon-workflow] 及其 [assets][toon-assets]、[stateAndDelivery][toon-state] 资源给出来源→资产身份→导演提示→参考图→生成→采用→连续性/交付的方法。`state` 文档是操作方法，不是数据库任务状态机。

[canvasExecution][toon-canvas] 明确原生节点返回 `generating` 后，缺少状态/等待工具时应结束本轮并让用户回来确认，且页面关闭可能因节点卸载中断。不能将这种制作方法宣称为无需页面的自动后台生产。

[媒体任务][toon-media] 有任务 UUID、原请求/供应商/资产/文件检查点、同 ID 换参拒绝和收费前意图记录，明显优于只有一个 loading 状态；但 JSON 文件和进程内 Map 不能直接充当 Glowloom 多实例 PostgreSQL 租约与资金权威。

[FFmpeg 工具][toon-ffmpeg]、[视频处理][toon-video] 可实际执行拼接、滤镜、抽帧、裁切与探测。所读范围不能据此签收持久多轨时间线、字幕及可编辑工程完整交付。原生宿主/任意 FFmpeg 参数也不应直接开放成公网执行接口。

## 5. waoowaoo：阶段输出、活动轮次权威与终态续跑

### 5.1 当前源码与旧宣传有差异

当前基线是 [Codex App Server 管理][waoo-runtime] 与创作画布助手；不能用历史“小说一键视频”的架构介绍概括本次版本。它与 Glowloom 的 Pi 服务路线不同，本轮借鉴业务语义，不建议替换运行时。

[creative-skills registry][waoo-skills] 注册核心、剧本、美术方向、资产、视频方向、音乐方向等制作方法；[output registry][waoo-output] 另行声明 screenplay、creative direction、资产/视频/音频生成批次的严格 schema、对应 Skill、持久文档与媒体 operation。**Skill、阶段产物和实际执行工具分别注册**，让助手可以继续读取、审查和采用结构结果，避免把最终聊天文本当唯一生产记录。

[视频导演方法][waoo-director] 先完整故事时间线，再组织模型可生成的分段，记录入口/出口状态、人物方位、道具、动作及连续声音，引用确切资源 ID/内容版本。其15秒或180秒等示例不应变成所有供应商的通用上限。

### 5.2 受权操作和自动接续

[MCP Server][waoo-mcp] 基于 canonical operation registry；[capability turn][waoo-turn] 校验当前活动轮次及 owner/runtime turn。历史聊天记录和工具描述不是正式执行权限。

[任务工作流][waoo-task] 在终态回执和释放槽后找出 ready follow-up batch 并通知；[助手服务][waoo-followup] 校验 follow-up、会话归属，按幂等身份准入，重放返回原轮次，随后准备和启动投影。活动轮次与用户新输入冲突要由业务准入决定，不能盲目追加第二个根任务。

该项目采用 Temporal Activity 重试复用 attempt ID、新业务尝试另定的机制。Glowloom 已明确移除 Temporal：借鉴“同次恢复复用原 attempt、终态事实唤醒后续”的不变量，落实到现有 Go 任务权威、持久投递、Pi 和 PostgreSQL，不引入另一个调度系统。

### 5.3 合成不是简单拼 URL

[合并合同][waoo-merge] 固定素材 ID/内容版本、起始帧/帧数与输出策略；[视频管线][waoo-ffmpeg] 统一 fps、缩放补边及编码；[音频管线][waoo-audio] 处理无音轨、裁切/补齐、响度、配乐 cue、淡入淡出与 ducking。可借鉴的是统一时基、显式长度和声音策略，不能仅把若干播放地址顺序拼接作为完整制作交付。

## 6. 火宝：业务实体明确、工具能写入，生产恢复仍有边界

[Agent registry][huobao-agents] 包含剧本改写、要素提取、分镜拆解和提示生成四类角色；[路由][huobao-route] 以 `mastra.getAgent(type).generate(..., {maxSteps: 20, requestContext})` 执行并返回工具结果。多个角色注册与单请求内自动工具循环，不能证明主 Agent 调度整套子 Agent、崩溃后恢复全部步骤。[Mastra 装配][huobao-mastra] 所读文件只注册 agents，没有建立持久 workflow/recovery 的完整证据。[Skill][huobao-skills] 是工作区文件加载和角色范围管理，不是不可变运行 manifest。

[分镜工具][huobao-storyboard] 读取分集、角色/场景/道具及已有分镜上下文，schema 包含镜号、景别、角度、运动、画面、气氛、提示、时长和实体 ID，写入前核对剧和集的归属。批量保存分镜而非只回一段 Markdown，是值得采用的业务能力。其首次批次 `replace_existing` 清空再逐批写的策略，不能直接照搬为正式替换：Glowloom 应先保存完整候选版本，再原子采用，失败不能留下半份新故事板或抹掉已采用镜头。

方法提示把8–15秒生成段落分成多个子镜头，说明**叙事镜头不一定等于一次模型请求**。实际时长须由具体模型目录与报价约束，不应把提示词里的时长建议做成数据库统一限制。

[任务路由][huobao-tasks] 对原视频处理中、失败后恢复/强制新建作区分；[generation service][huobao-generation] 的 `recoverVideoTask` 优先下载已有结果 URL、处理过期链接并查询原供应商任务，缺少原任务身份时不盲目重新生成；`resumeInterruptedTasks` 有扫描处理中记录的代码，但本次没有完整验证其启动调用和多实例恢复，因此只报告恢复函数存在。进程内 `activeTasks` 也不是跨节点租约。

[单集合并][huobao-merge] 按分镜顺序选择已有视频、检查文件与 FFmpeg、记录合并任务，再异步拼接和探测；允许跳过未就绪分镜意味着可以产出部分合成。正式产品必须显式区分“预览/部分导出”与“整集完整交付”，不能因为得到一个 MP4 就算整集成功。

## 7. 从创意到短剧的可执行生产合同

以下是跨项目归纳后对 Glowloom 的建议，不是即梦或任何参考产品的内部架构事实。阶段允许往返修订；对已采用版本的修改先计算影响，不清空全部结果。

| 制作阶段 | 输入与正式输出 | Agent/Skill 工作 | 确定性业务与接受条件 |
| --- | --- | --- | --- |
| 来源与创意 | 原文/文件/视觉参考 → 来源版本、创作要求、权利确认 | 长文本理解、来源定位、改编方向建议 | 真实字节与完整范围；不静默截断；保留人工修订 |
| 剧本与分集 | 已采用来源 → 剧本候选、分集候选/采用版本 | 编剧、审稿；检查情节/对白及遗漏 | 候选与采用分离；版本 CAS、范围和变更回执 |
| 制作资产 | 已采用剧本 → 角色/场景/道具、分集造型、音色及参考采用 | 美术/资产提取、制作建议、独立审查 | 引用现有 Bible；别名与实体身份明确；参考图生成/选用有版本 |
| 叙事分镜 | 单集剧本/Bible → 镜头候选和采用版本 | 导演、分镜、连续性审查 | 景别/机位/动作/对白/时长/入口出口、来源与实体引用可校验 |
| 生成规划 | 采用镜头 → 一个或多个模型生成单元/覆盖关系 | 按模型能力组织首尾帧、参考、段落和声音策略 | 不能把剧本行、导演台镜头、供应商请求强行视为同一实体；明确覆盖与剪辑区间 |
| 参考与关键帧 | 固定资产/镜头 → 已归档并采用的图片/预演参考 | 构图、姿态、光线与一致性检查 | 依赖素材未 ready 或未采用不得提交下游收费；改变后重报价 |
| 视频与声音 | 已就绪依赖 → 原 operation/attempt → 候选 take/音频/字幕 cue | 视频、配音、音乐与质量审查可在允许范围内分工 | 根预算/逐项报价；有界并发；提交未知查原请求，不自动新付费 |
| 采用与局部重做 | 候选素材 → 指定镜头/区间的采用关系 | 说明质量差异、失败原因与影响建议 | 生成成功不等于采用；重拍不覆盖原 take；重新采用只失效真实下游 |
| 时间线与预览 | 已采用素材/对白/cue → 时间线版本 | 剪辑、节奏、衔接和声音建议 | 使用现有时间线/渲染器；明确 fps/画幅/时间单位/缺失项/音轨策略 |
| 交付 | 固定时间线 → 可解码成片、工程包与交付报告 | 核对任务书，报告缺镜/黑帧/音画/字幕问题 | 分阶段回执；归档、绑定、导出失败只补该阶段；部分成片显式标明，不虚报完成 |

建议的稳定关联：`sourceRevision → episodeRevision → productionShotRevision → generationUnit → operation/attempt → take/assetVersion → adoptedTake → timelineClip/version → exportTask/artifact`。一段生成可覆盖多个叙事镜头，一个镜头也可经多次生成形成多 take；覆盖、裁剪和采用由显式关联表达，不复制一份并行任务引擎。

连续性至少表达角色/造型、场景/时间/光线、道具持有、站位/视线、动作入口出口和声音延续。审查结果保留依据、严重度和人工采用决定；不能以 LLM 自评替代可解码、音轨和时长检查，也不能将抽帧结果宣称完整看过整片。

### 制作场景示例：一集六镜头的对话短剧

以下只说明目标行为，不是已执行结果。用户提交剧本与角色参考，指定“一集六个叙事镜头，先审阅分镜和预算”。主Agent读取完整授权范围，编剧整理来源/分集候选，美术与分镜子Agent在独立上下文准备资产和镜头，连续性审查提出可定位的问题。用户采用剧本、资产与分镜版本后，再按实际模型能力将六镜头组织为若干生成单元；不预设六次视频调用，也不未经同意自动付费。

参考图就绪并采用后，正式batch受理允许的生成。某个单元提交后网络断开，系统查询原供应商任务；另一个单元明确失败，只重做该项。用户离开页面，已受理任务继续核对和归档；主Agent按持久等待点收集结果，展示候选take，采用范围依事先授权或人工决定。任何新权限、追加预算或人工冲突进入原批准合同。

采用素材与配音/cue进入时间线候选；用户调整一次剪辑后，自动装配不得覆盖该修订。真实渲染成功、工程包导出失败时保留成片，只恢复导出阶段。若仍缺一个必需镜头或字幕未完成，交付报告列缺项，预览明确为部分输出，不能显示“全集完成”。停止任务后保留已完成素材，不启动迟到的新生成或导出。

### 10.2 GitHub、Firecrawl、Context7 的用途与限制

GitHub 读取四个仓库的固定提交、树、相关文件和 BeefTV release 元数据。Firecrawl 读取 [官网][beef-site]、固定 README 与 [案例][beef-examples]，搜索定位另外三个项目；官网的“完全开源”宣传不能覆盖实际 LICENSE。

Context7 分别查询 `/earendil-works/pi`、`/websites/ffmpeg_documentation`、`/mastra-ai/mastra` 的官方材料：

- [Pi Durable 文档](https://github.com/earendil-works/pi/tree/main/packages/durable)区分提交意图、执行和重放；稳定工具 key/子会话请求身份不提供外部世界 exactly-once。嵌套并发取决于实际 awaits/委派，仍须业务幂等。本次索引列出的版本不足以直接证明固定1.5安装版本兼容最新文档，实施原型必须单独锁定核验。
- [FFmpeg 文档](https://ffmpeg.org/ffmpeg-all.html)要求 concat 时间戳、流布局和分辨率归一；xfade 对 fps/尺寸/像素格式/时基有约束，amix 需要明确持续时长和混音策略。真实 concat 调用不自动等于完整时间线。
- [Mastra 官方源码与文档](https://github.com/mastra-ai/mastra)区分普通 `agent.generate/stream` 与具有持久执行/恢复的 workflow。最新能力不反向证明火宝固定依赖 `^1.17.0` 已接入该能力，也不是要求 Glowloom 更换框架。

尚未验证：四项目真实模型/账户/计费和部署；多实例崩溃恢复；BeefTV 其他发行资源与后端的版本一致性；目标剪辑器实际导入、长片逐镜连续性、对白/字幕同步与完整成片质量。后续工程接受必须保留这些条件，不能以本次调研或历史 fixture 替代。
