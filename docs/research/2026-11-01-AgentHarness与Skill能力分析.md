# Agent Harness 与 Skill 能力分析

日期：2026-11-01（Asia/Shanghai）。本文分析完整创作 Agent 的功能、模块职责与集成条件，为[设计32](../design/32-完整创作AgentHarness与Skill多Agent架构设计.md)提供能力依据，不作为实现或验收证明。

## 1. 核心能力

| 能力       | 功能要求                                                             | 服务边界                                                |
| ---------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| 持久会话   | 保存输入、运行配置、模型轮次、工具任务及产物引用，重启后恢复同一运行 | Harness 负责执行序列；业务服务保存授权与实际操作回执    |
| 模型循环   | 根据目标和工具结果继续决策，处理拒绝、错误、上下文容量与费用         | 使用固定 SDK，所有物理请求经过模型网关                  |
| 计划管理   | 查看和修订步骤、依赖、预期产物与完成条件                             | 计划版本变化使受影响的批准失效                          |
| 业务工具   | 以封闭 schema 调用剧本、主体、分镜、生成、媒体与后期能力             | Go 重新校验权限、版本、参数和预算，不信任模型提供的身份 |
| 多 Agent   | 创建独立专业会话，委派、并行、等待、回收和取消                       | 子任务继承父任务的权限与预算上限，不能扩大作用域        |
| Skill 包   | 安装、版本固定、启停、资源读取、更新、回退、私人改写和受控发布       | 包与安装状态归 Skill 服务，运行持有明确版本与内容摘要   |
| 上下文管理 | 按需加载 Skill、引用授权素材，压缩后保留有效约束                     | 摘要不替代原始业务事实、权限或固定版本                  |
| 隔离脚本   | 执行明确声明的加工脚本，限制资源、网络、输入与输出                   | 专用沙箱执行，宿主进程不直接执行包内代码                |
| 创作交付   | 从剧本到分镜、镜头、声音、时间线和成片，并保留编辑工程               | 生成、归档、采用、渲染与检查分别取得正式回执            |

## 2. 运行时与业务服务

采用独立 `agent-runtime/` 承担 SDK 生命周期、会话存储、模型循环、工具调度、Skill 扩展和专业子会话。现有 Go 服务继续掌握身份、凭据、权限、预算、项目修订及媒体事实；运行时只持有必要的短期能力与业务引用。

工具调用先保存稳定身份和参数摘要，再通过业务操作桥执行。业务已经提交而运行时确认丢失时，恢复必须读取原回执，不能重新创建任务。Temporal 继续处理生成、媒体和脚本业务任务，不同时执行另一份模型循环。

规划阶段先做确定性预检，用户批准有限规划预算后才调用模型。规划只读授权上下文；专业解析、提案写入、媒体生成和脚本执行使用另行批准的执行计划。Go 接受停止命令时即关闭新副作用准入，不等待运行时收到通知。

## 3. Skill 生命周期与上下文

Skill 使用 `SKILL.md` 入口及机器可校验的 manifest，包内资源以规范路径和内容哈希定位，依赖固定到明确版本。安装、启用、会话激活和公开发布分别管理；更新安装指针不改变已有运行的版本。

加载前核对能力、依赖和权限；目录展示摘要，正文及辅助文件按需读取。压缩或重启后重新核验活跃版本并恢复必要规则。普通禁用影响未来激活，紧急撤销立即阻止新增动作；缓存和子会话不能绕过撤销。

脚本执行需要专用 Linux Docker＋gVisor 服务、锁定镜像、幂等 Job 回执及真实隔离测试。没有执行后端时阻止依赖步骤并说明原因，不能把包可安装视为脚本能力完成。

## 4. 专业 Agent 与业务交接

制作协调 Agent 负责目标、计划和结果汇总；专业 Agent 分别处理剧本解析、编剧、美术、分镜、镜头、声音、剪辑与质量检查。每次委派有稳定身份、独立上下文、输入版本、可用工具、产物 schema、预算和取消关系。

剧本解析应产生带原文定位的分集、场景、人物、道具和台词提案；长文本分片合并须处理重复、边界和歧义。用户正式采用后，下游才消费对应版本。子 Agent 回复、模型评分和供应商 taskID 都不能单独作为业务完成证明。

## 5. SDK 集成条件

集成基线为 Pi `1.3.0`，固定提交 `71023aec1546d6d677a65669c5665c0927ce0dd0`。具体能力以[官方耐久 Harness 文档](https://github.com/earendil-works/pi/blob/71023aec1546d6d677a65669c5665c0927ce0dd0/packages/durable/README.md)及[SDK 接口定位清单](evidence/2026-11-01-agent-harness/pi-source-manifest.json)为依据。该版本仍将 Durable API 标记为 experimental，因此必须通过版本锁定、故障恢复、接口兼容和升级演练后才能开放真实运行。

模型交换使用持久 taskId 与 memo 固定逻辑调用身份；压缩也经过费用网关。相同输入的不同任务不能误合并，原请求未知时不能通过新尝试绕过对账。

会话存储要求单写者；进程重启恢复不等同于跨主机高可用。SDK watch 从当前快照续接，慢消费者可丢弃中间增量，因此界面必须支持权威快照恢复。业务事件与已发生副作用仍由 Go 回执核验。

## 6. 验收边界

功能接受应分别覆盖 SDK、Go 控制/模型/工具桥、Skill 生命周期与脚本、实际多 Agent、版本化工程、成片交付和恢复。安装依赖、聊天回复成功或单图生成都不能替代完整创作接受。

本轮仅调整与完善文档，没有安装 SDK、创建运行服务、执行产品测试、迁移数据库或进行真实收费。正式方案归设计32，范围与验收归PRD19，执行步骤归Plan28，当前状态只在BACKLOG维护。
