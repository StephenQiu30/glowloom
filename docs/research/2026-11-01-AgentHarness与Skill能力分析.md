# Agent Harness 与 Skill 能力分析

日期：2026-11-01（2026-11-03 架构纠偏更新）。本文分析完整创作 Agent 的功能、模块职责与集成条件，为[设计32](../design/32-完整创作AgentHarness与Skill多Agent架构设计.md)提供能力依据，不作为实现或验收证明。

## 1. 核心能力

| 能力       | 功能要求                                                             | 服务边界                                                |
| ---------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| 持久会话   | 保存输入、运行配置、模型轮次、工具任务及产物引用，重启后恢复同一运行 | Go 进程内 LangGraph 状态图与关系型 Checkpointer 持久化  |
| 循环调度   | 根据目标和工具结果继续决策，处理拒绝、错误、上下文容量与费用         | Go 状态图有向循环，直连统一模型网关，单轮最大 40 步熔断 |
| 提案中断   | 模型发起生成、修改或重要动作时，主动截断后续输出并挂起等待审批       | 借鉴 BeefTV `Proposal Yield`，由 LangGraph Interrupt 挂起|
| 连续写链   | 单轮多次写工具调用版本自动顺延，兼顾批量流畅执行与并发防冲突         | 借鉴 BeefTV `WriteChain`，本地维护递增 CAS 版本链头     |
| 现场自愈   | 协同编辑发生时，模型在下一次决策前感知最新实体差异并自动调整         | 借鉴 BeefTV `StudioDigest`，比对差异注入 `<canvas_changes>`|
| 计划管理   | 查看和修订步骤、依赖、预期产物与完成条件                             | 计划版本变化使受影响的批准失效，通过 `plan_update` 维护 |
| 业务工具   | 以封闭 schema 调用剧本、主体、分镜、生成、媒体与后期能力             | Go 业务操作层校验权限、版本、参数和预算                 |
| 多 Agent   | 创建独立专业会话，委派、并行、等待、回收和取消                       | Supervisor-Worker 模式，子任务继承受限范围与预算        |
| Skill 包   | 安装、版本固定、启停、资源读取、更新、回退、私人改写和受控发布       | 包与安装状态归 Skill 服务，运行持有明确版本与内容摘要   |
| 动态装载   | 按需通过 `skill_load` 加载技能正文，独立任务触发上下文重置           | 动态展开 `SKILL.md`，超预算降级说明原因                 |
| 隔离脚本   | 执行明确声明的加工脚本，限制资源、网络、输入与输出                   | 专用 Linux gVisor 沙箱执行，主进程不直接执行包内代码    |
| 创作交付   | 从剧本到分镜、镜头、声音、时间线和成片，并保留编辑工程               | 生成、归档、采用、渲染与检查分别取得正式回执            |

## 2. 架构演进与技术纠偏

### 2.1 为什么废弃 Node.js 独立宿主方案？
前期探索尝试引入独立 Node.js Host 运行外部 Pi Durable SDK，但暴露了严重的系统性缺陷：
1. **过度设计**：单机桌面端的设计硬搬到云端，为了对接 SDK 必须在底层手写 PostgreSQL bytea 二进制日志、Advisory Lock 锁竞争与 HMAC 签名；
2. **状态撕裂（分布式脑裂）**：Go 持有用户、权限、画布与计费，Node 持有记忆与会话，两端数据频繁往返同步，导致事务难以原子保证；
3. **违反工程原则**：破坏了项目一直坚持的单一二进制进程原则。

### 2.2 为什么选择 Go 原生 + LangGraph (StateGraph) 编排？
1. **状态图天然支持 Agent 循环**：无需手写 while 死循环，LangGraph 原生是有向循环图，节点（Nodes）和条件边（Conditional Edges）天然对应大模型与工具的交互模式；
2. **原生 Interrupt 机制完美承接人机协同**：当模型发出生成提议时，图执行器自动挂起，将 State 存入 PostgreSQL 关系型检查点，等待前端审批后再 resume；
3. **消除跨进程损耗**：所有业务调用直接以同进程 Go 函数/接口执行，GORM 事务强一致，性能与可靠性大幅提升。

## 3. 吸收开源 BeefTV 的工业级实践

通过深度逆向与分析开源创作引擎 [BeefTV](https://github.com/glanderness/BeefTV) 的成熟实践，将其四项经实战检验的状态机机制吸收到 Go 原生架构中：
1. **Proposal Yield**：提议生成时返回终止信号，协同 `plan_update` 截断后续推理，防止模型在未获审批前继续幻觉编造；
2. **Write Chain**：单轮执行内维护本地版本链头，后续操作以最新的 `expectedRevision` 递增提交，消除批处理自相冲突；
3. **Studio Digest**：模型请求前比对工程最新状态，生成 `<canvas_changes>` 差异文本注入上下文，实现被动冲突自愈；
4. **Turn Budget Watchdog**：单轮步数上限 40 步硬熔断，流式连接 45 秒空闲保活。

## 4. 专业多 Agent 与业务交接

采用业界标准的 Supervisor-Worker 模式：
- **Supervisor (制作统筹)**：负责意图理解、计划生成与专业分派；
- **Script Worker (剧本解析)**：负责长剧本拆解与原文定位；
- **Storyboard Worker (分镜编排)**：负责机位、时长与分镜排布；
- **Shot Worker (镜头导演)**：负责镜头提示词与生成提案；
- **Audio & Cut Worker (音频剪辑)**：负责配音对齐与时间线导出。

各 Worker 在 Go 内部共享状态图的 `AgentState`，但运行在独立的作用域、白名单工具集与系统提示词之下。

## 5. 验收边界

功能验收覆盖 Go 原生图引擎、Checkpointer 检查点恢复、Supervisor 委派、提案中断挂起、写链 CAS、现场自愈及成片交付。所有测试在 Go 内部闭环验证。
