## 编号与职责

各目录独立使用两位连续编号，`00`用于范围或总览，正文从`01`开始；编号代表阅读顺序，任务执行顺序仍以依赖为准。PRD统一进入`docs/prd/`；详细FR/BR/DR/IR/NFR保留在`docs/requirement/`；设计放`docs/design/`；可执行计划放`docs/plan/`。修改直接更新当前正文及引用，不保留旧路径副本和历史残留。根README/AGENTS/PROJECT/DESIGN/BACKLOG及工具约定文件保留标准文件名。

## 完整链路与职责

| 阶段        | 回答的问题                                 | 交接内容                                               |
| ----------- | ------------------------------------------ | ------------------------------------------------------ |
| requirement | 用户需要什么，规则和验收是什么？           | 需求编号、边界、行为规则、数据与质量要求、AC           |
| design      | 如何让需求在界面和系统中成立？             | 交互、状态、数据、接口、异常路径及方案取舍             |
| prd         | 基于需求与设计，这次交付为谁解决什么问题？ | 用户价值、目标、完整范围、首轮与后续边界、产品接受条件 |
| plan        | 按什么顺序实施，如何证明完成？             | 任务、依赖、代码落点、验证、退出条件及发布回退         |

| 模块               | requirement                                        | design                                                      | prd                                   | plan                                                  |

详细规则与 AC 的唯一来源是 requirement，交互及技术机制维护在 design；PRD 引用并汇总产品交付定义，plan 不自行扩大或缩小范围。行为变化先更新 requirement，再同步 design、prd、plan；纯技术调整从 design 向后同步。待确认、已确认、待实现和已验收状态分别标明，保存文档不等于接受或上线。
