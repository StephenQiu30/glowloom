# PRD：模型计价透明与结算恢复

唯一来源设计：[设计34](../design/34-积分消耗系统与模型真实计价体系设计.md)。状态：评审稿。需求：SRC-AI-35、FR-AI-35～39、AC-AI-35～37。执行：[Plan30](../plan/30-模型计价透明与结算恢复实施计划.md)；状态和调度只见[BACKLOG](../../BACKLOG.md#beeftv-adoption)。

## 1. 摘要

帮助创作者在确认前理解费用，在断线或失败后看清预留、实扣及核查状态，优先取回原结果。复用已有报价和项目预算，不新增充值钱包。

用户已授权按本方案实施（见需求04 SRC-AI-35）；该授权不替代新商业政策确认、真实收费授权或产品接受。

首个模型限定确认沿来源设计34与需求04 SRC-AI-36：Seedream 5.0 Flash按0.12元/输出张、无加价、1元=10积分报价，整数预估显示2积分，实际金额不改为0.2元。只在用户明确确认报价后预留并生成；本次最多3次供应商请求、总预算不超过1元，两模式真实验证通过后可启用。此项不开放个人钱包，也不替代其他模型的价格审核和真实验证。

## 2. 参与者

创作者确认具体消费；模型管理员审核价格；有授权的核查人员查证账单。维护者负责预算与执行一致性，具体人员及商业政策确认出处尚未指定。

## 3. 背景

研究发现BeefTV主要公开价格展示、任务结算观察和去重；Glowloom已有价格版本、精确金额、预留及账本。因此交付重点是完整解释和安全恢复，而非复制客户端扣积分方式。

旧文档中的“失败全退”“超时解锁”和未经核验的实时价格不作为本PRD接受依据。

## 4. 目标与衡量

| 目标         | 接受依据                                                                   |
| ------------ | -------------------------------------------------------------------------- |
| 消费前可解释 | CASE-BIL-01～04中显示金额性质、单价/数量、规则版本和费用明细               |
| 消费不重复   | CASE-BIL-05/06/11/12中并发或重连不增加原消费的生成次数/预留                |
| 结算不猜测   | CASE-BIL-07～10中缺失、取消、交付失败、迟到证据均不被错误显示为免费/已退款 |

仅按可观察事实接受，不承诺供应商完成时长或退款时效。

## 5. 用户与使用场景

创作者需要在创作中决定是否消费及能否继续取回；管理员需要审核规则来源并解释异常；核查人员需要定位原请求及原账单。普通成员不能读取其他项目或供应商原始账单。

## 6. 用户价值

| 六要素       | 创作者                             | 管理/核查人员                    |
| ------------ | ---------------------------------- | -------------------------------- |
| Who          | 个人/团队创作者                    | 模型管理员、授权核查人员         |
| Why          | 避免不明费用和重复购买             | 判断应结算、释放还是继续核查     |
| What before  | 看失败提示后再次点击               | 依赖分散回执与错误文字           |
| How          | 明细确认、独立费用状态、原任务恢复 | 价格版本、可信用量与稳定请求身份 |
| What after   | 理解本次批准内容及已付费结果去向   | 不凭失败清零，不改写历史账目     |
| Alternatives | 去供应商后台人工对账               | 手工核对任务与账单               |

价值主张：在已有项目预算内，让一次批准对应一次可追踪消费；需要新生成时重新确认，未知费用继续核查。

## 7. 产品方案与验收

### 7.1 纳入与不纳入

纳入来源化价格说明、精确预估与积分展示、参考图费用规则校验、结算读投影、服务器去重屏障、原结果取回和结构化错误解释。前端默认保留简洁摘要，明细按需展开。

不纳入支付充值、赠送余额、独立财务后台、个人BYOK、跨渠道自动补买、任意同键补交。缓存折扣、视频Token或延迟美元账单只有对应一手合同与政策关闭后才开放；缺条件时保留“不支持/需核查”，不填假价格。

SRC-AI-38补充接受：缓存命中不得按未命中重复收费；缺缓存证据不猜测。视频按实际输出Token结算，报价标明估算；参数和媒体不满足已实现估算合同则拒绝报价。Pro参考图首张免费、后续按审核来源收费。当前只完成待验证配置与工程接受，不发收费请求，不将保存成功显示为真实验证成功。

### 7.2 用户流程

选择模型及真实输入→服务端报价→显示预估/预留性质与明细→确认当前报价→原子预留→单次派发→分别查看生成、交付与费用→继续取回原结果或核查→明确需要新消费时重新报价。

价表/输入变化导致旧报价失效；关闭弹窗或刷新不取消已受理任务。未知与核对期限到达不提供绕过屏障的确认按钮。

只有单价/未知时展示目录费用说明，不创建可确认报价；正式报价必须有确定预留金额。同一未决节点改模型、提示词或请求键也不能绕过屏障。费用金额以平台账本为准，上游观察值单列；上游声称退款而平台尚未入账时显示待核查，不显示退款完成。

### 7.3 用户故事

**US-BIL-01 看懂费用**：作为创作者，希望看到基础单价、数量、参考附加项、汇率/倍率及金额性质，以决定是否消费。来源FR-AI-35～37、设计34 §7.2～7.4。讨论：1:10和零加价对外承诺待补来源；前端显示不改变微元账本。确认条件：已知金额可复算；未知不显示免费；不足1积分不误作0；明细键盘可达。追踪CASE-BIL-01～04。

**US-BIL-02 可靠确认**：作为创作者，希望重复确认和配置变更不会多扣，以保持预算可解释。来源AC-AI-35、设计34 §7.6。讨论：批准具体输入与报价，非任意同名模型。确认条件：并发确认仅一份预留/发送；旧价旧输入拒绝；预算不足无付费POST。追踪CASE-BIL-04/05。

**US-BIL-03 看清费用事实**：作为创作者，希望分别看到结果与结算状态，以免把失败误当退款。来源FR-AI-38、设计34 §7.5～7.6。讨论：预留释放不等于已扣款退款。确认条件：缺字段、pending、已扣费和真实退款分别展示；超时和审核不自动清零；不得回显原始账单。追踪CASE-BIL-06～10。

**US-BIL-04 继续取回原产物**：作为创作者，希望已经付费的结果可沿原任务恢复，以免再次购买。来源FR-AI-39、AC-AI-37、设计34 §7.7。讨论：服务器校验原身份；取回入口不负责新生成。确认条件：已有结果继续交付；unknown不重发；取不回且结算明确时新消费需新报价；恢复界面具备焦点和窄屏支持。追踪CASE-BIL-06/08/11。

**US-BIL-05 区分异常并核查**：作为管理员/授权核查人员，希望区分项目预算、上游欠费及速率等问题，以处理正确对象。来源FR-AI-38～39、设计34 §7.8。讨论：402/429不自动归类用户余额。确认条件：结构码与执行阶段决定说明；核查留审计；跨组织拒绝。追踪CASE-BIL-09～12。

### 7.4 测试场景

| CASE-BIL-02 参考图        | 管理员发布有依据规则      | 0/免费数/超1张、多个输出报价→按声明范围计费                                    | 重复引用/mask口径明确，缺定义拒绝                     |
| CASE-BIL-03 未知价格      | 创作者，只有单价/原币预留 | 查看→显示未知或预留，不显示免费/硬封顶                                         | 未认可规则禁止收费派发                                |

### 7.5 未决商业合同

积分兑换的对外政策、零加价承诺来源、分数积分显示、参考图计数、缓存折扣、视频Token口径、延迟账单超额承担和已扣款退款补偿需明确。未决事项不阻止文档交付，但相关能力不得声称已可上线。

### SRC-AI-37 报价体验验收补充

唯一来源仍为设计34。默认费用摘要与确认动作紧邻；未知金额不能显示免费，技术快照按需查看。正常报价无重复核对动作；过期更新先释放成功，确认未知只恢复原请求。普通单价以元编辑，Token单位只显示相应字段，切单位不丢输入；复杂规则、积分比例和倍率不得被基础表单静默覆盖。试运行由一次明确费用按钮授权，未确认不调用供应商。
