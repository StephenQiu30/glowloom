## 1. 摘要

为平台管理员提供可管理、可验证的 AI 平台配置，使火山方舟和 OpenRouter 能通过内置预设添加 Key、配置模型并开放给创作者。创作者使用已启用模型和明确的参数/费用，无须了解平台请求协议，也不能接触平台 Key。

平台预设、账号连接、模型版本和上线发布组合分别管理，让新增模型、调整价格、轮换 Key 与历史任务恢复有明确边界。

## 2. 背景

调研基线已有供应商、加密凭据、模型/价格版本和任务活动合同，管理页面当时尚未开放。本轮已实现管理页面和执行 worker；本地代码验证仍不能证明真实平台账号可用。来源和原始缺口见设计第4节。

本轮沿配置、发布和执行合同实施。低配置负担参考 CC Switch 的预设方式，但织光还需处理多用户权限、素材引用、长期视频任务和费用。市场比较保留在设计第2节，PRD 不重复竞品排名。

## 4. 目标用户

| 人群             | 需要完成的工作                                               | 约束                                                                       |
| ---------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 平台管理员       | 建立并维护共用 AI 服务，选择可用模型，追踪配置变化和费用异常 | 仅当前有效的平台管理员可配置；管理 Key 不自动授予全部私有项目素材读取权    |
| 个人与团队创作者 | 在自己的授权项目中选择模型、组织输入、知道费用、找回结果     | 不配置平台 Key；团队管理员也不能维护平台供应商；模型能力与素材权限同时生效 |

首轮聚焦维护共用能力的管理员与消费能力的创作者，两类角色共同完成配置到创作闭环；个人/团队BYOK人群不在首轮。

## 5. 价值主张

| 六项要素       | 平台管理员                                                   | 创作者                                         |
| -------------- | ------------------------------------------------------------ | ---------------------------------------------- |
| 谁             | 维护公共 AI 能力的人                                         | 使用图像、视频和文本能力创作的人               |
| 为什么         | 希望快速接入并能安全升级，避免不可解释的故障和费用           | 希望知道模型能做什么，提交后能找到真实结果     |
| 之前怎样做     | 可手动维护 URL、Key、模型 ID 和参数表，反复核对差异          | 可分别访问供应商工具，再下载重传结果           |
| 怎样改善       | 预设填充、分项检查、版本化模型配置与受控启用                 | 统一能力表单、费用确认、任务恢复与资产入库     |
| 之后的结果     | 能解释每次配置生效范围，定位账号、模型及协议问题             | 不学习多个平台协议，保留同一项目输入与产物关系 |
| 替代与选择理由 | 直接写配置或使用通用网关；选择织光以连通模型配置、创作和结算 | 使用平台控制台；选择织光以保持项目与素材上下文 |

“之前”描述可行替代方式，未进行用户访谈。价值主张：管理员配置一次并持续管理可用能力，创作者在同一工作流中获得可解释的参数、费用和结果。

## 6. 解决方案

### 6.1 体验与设计入口

主流程：管理员维护火山方舟/OpenRouter 预设及可复用模型配置 → 接入操作者选择预设并填 Key → 自动创建停用连接和模板中的待验证模型/价格 → 分项检查/模型发现 → 管理员明确确认试运行与启用 → 按能力设置默认 → 创作者使用。没有模型模板时明确提示管理员先维护，不让接入操作者重复填写 URL、协议或 JSON。

#### 6.1.1 2026-10-18 接入体验修正

主路径调整为：管理员维护预设（可选复用模型/价格模板）→ 接入操作者选预设、填 API Key → 自动命名并保存连接/模板实例 → 分项检查 → 管理员确认真实试运行及发布。普通创作者只选已启用模型，不学习接入协议。详见需求04第9节与设计07第11节。

“已保存连接”“Key 已写入”“鉴权已确认”“模型已发布”分别显示。只有连接配置的内置预设不能暗示已提供可用模型；管理员可在已配置模型上维护可重复使用的完整预设。模型模板复用减少后续账号重复录入，验证证据仍绑定新连接与新凭据，不自动付费或自动激活。任意第三方中转平台和个人 BYOK 未因此进入首轮范围。

### 6.3 技术与运营边界

范围内的技术约束：复用 catalog/operation/billing/media 与现有页面入口；平台差异通过适配器和小接口处理；不新增独立网关服务。UI 明细、状态机、字段及 API 见设计第6～8节。

## 7. 交付与发布

首轮包含上述完整管理闭环和四类执行链路；按计划 T-AI-01～T-AI-09 顺序推进，可分阶段演示，但不能以后台表单完成代替平台接入完成。建议先完成配置持久化，再执行协议，最后进行真实账号和浏览器综合接受；不设未经估算的工期。

BytePlus、第三平台、个人/团队 BYOK、自动跨平台路由、独立音频生成、提示词市场及新的聊天产品不在首轮。自定义预设仅配置已实现的两平台协议，不是可执行脚本或任意协议插件。

接受需逐项满足 AC-AI-01～AC-AI-20并出具真实链路证据。任何链路未通过则保持关闭并在接受记录列为未完成；不能静默删掉该链路来宣布首轮完成。发布按连接/模型组合灰度开放；回退停新任务并保留兼容 worker、历史配置、凭据引用与账单。保存本 PRD 不等于产品接受或发布授权。
