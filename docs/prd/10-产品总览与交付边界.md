## 1. 摘要

织光面向使用图片、视频和画布开展内容创作的个人及团队，连接灵感、输入、素材、生成、结果采用和继续创作。当前交付重点是把已深化的身份、项目/主画布、编辑器、AI接入和资产上传能力组成可靠闭环，再依据真实合同逐步开放候选能力。

本文件提供整套知识库缺少的产品总入口：说明各能力归谁、覆盖到哪里、什么条件才算交付。详细业务规则和AC仍由需求文档负责，技术机制仍由设计负责。

## 2. 背景与证据

产品范围已有CAP-GL-01～32完整候选目录，原有9份专项PRD分别深化部分能力，但缺少整体覆盖映射。共享工作台与Figma实施记录也缺产品层承接，现由[需求11](../requirement/11-统一工作台与创作入口需求.md)、设计09和PRD11补齐。

2026-10-20用户明确要求五类AI来源、通用模型预设，并修复缺少必要PRD的流程知识库。本文据已有需求、设计与计划整理；没有用户研究数据的目标保持待测，未形成合同的候选能力不以空壳文档宣称就绪。

## 5. 价值主张

| 六要素                   | 创作者                                                         | 平台管理与运行人员                                     |
| ------------------------ | -------------------------------------------------------------- | ------------------------------------------------------ |
| Who：谁                  | 围绕素材与项目创作的人                                         | 负责模型、存储及运行的人                               |
| Why：为什么              | 希望连续完成创作，减少输入丢失与结果分散                       | 希望接入可控并能解释故障和费用                         |
| What before：现在怎么做  | 在生成、文件和编辑工具间手动转移内容；项目内各入口尚有接受缺口 | 逐供应商维护模型ID、凭据、能力和价格                   |
| How：如何改善            | 统一项目/主画布、编辑引用、真实任务及素材关系                  | 预设与模型候选、分项验证、明确发布、原请求恢复         |
| What after：之后得到什么 | 可找回正确输入与产物，判断能否继续、是否收费                   | 可定位缺失条件，切换不破坏历史任务和素材               |
| Alternatives：替代方式   | 继续使用独立工具并手工归档                                     | 手动维护各供应商后台；本方案减少重复配置但保留显式验证 |

上述替代方式为产品分析，未进行用户访谈验证；实际收益用第3节指标建立基线。

## 6. 产品方案与覆盖矩阵

### 6.1 主旅程与分工

浏览灵感/打开近期项目 → 输入或新建主画布 → 登录及选择真实归属 → 引用素材/主体 → 选择可用模型和参数 → 确认费用并提交 → 观察真实状态 → 比较/采用 → 保存并继续。导出、分享等按能力开放，不将完整目录强行列为每次创作必经步骤。

共享入口见[PRD11](11-统一工作台与创作入口.md)及[设计09](../design/09-统一顶栏与阶段入口设计.md)；其余机制沿各专项设计。一个PRD可服务多份技术计划，研究、迁移和运行手册不需要各复制一份PRD。

### 6.3 跨模块接受

每个开放用户流程同时满足身份/归属、草稿与输入、模型和价格、任务状态、素材位置及恢复条件。任一环节未就绪则该模式不能作为可执行能力开放。采用结果须可追溯真实输入与模型；未知结果先查证，不能诱导重复生成或支付。

### 6.4 假设与未决

尚无全产品真实漏斗基线、整体发布日期和团队容量；具体负责人未指定。候选中的完整资产/主体管理、生成任务中心、图片/视频编辑、音频、导演台/成片、社区及钱包支付在选入开发前必须明确独立交付结果，补对应链路；不能仅从当前代码或UI推定产品合同。

工作台团队/邀请入口历史冲突由PRD11承接；AI价格政策、账号权限及Codex节点隔离由PRD03承接；法律发布材料仍按总索引的缺失说明处理。本次知识库整理不恢复或编造协议。

## 7. 交付与维护

已有专项持续按原计划完成剩余接受，不因新总览重新排期。相对依赖为身份/真实归属→项目与草稿/素材→已发布模型及真实生成→结果保存/继续；数据持久化、实时与OT依原设计分层交付，五类AI扩展依计划10。候选进入迭代前完成链路与就绪评审，数量和时间服从实际容量。

产品接受按具体来源、模式、角色和环境记录。出现越权、数据丢失、重复派发/收费或历史文件不可读时暂停受影响入口并按专项恢复；全局发布不从局部测试推导。需求变化先更新拥有规则的文档，再更新设计、PRD和计划；总览只同步覆盖边界，避免维护第二套AC和实时状态。

2026-10-20确认来源是用户要求补齐知识库；本次完成的是文档范围与交接修复，细化方案待评审，业务实现、真实接受与发布仍以原专项证据为准。
