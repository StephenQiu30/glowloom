# PRD28｜日志与创作经营分析

唯一来源设计：[设计42](../design/42-日志与创作经营分析设计.md)。执行计划：[Plan37](../plan/37-日志与创作经营分析执行计划.md)。2026-11-13 · 评审稿；完整创作与经营分析范围已确认，功能细分与验收阈值为建议。

## 1. 摘要

让值班能查清故障，让创作者能判断有效产出，让运营和经营核查者能解释创作转化、资金与成本。提供固定的日志查询与分析视图，复用现有项目能力，不建设通用日志平台或自助 BI。

## 2. 背景

当前已有服务日志、追踪基础、安全事件与业务审计，创作统计入口尚未开放。数据分别存在于请求、Agent、任务、素材、交付与计费领域；日志条数不能回答真实作品、付费和收益问题。当前事实与限制见设计42 §3。

## 3. 目标与成功标准

| ID        | 可检验结果                                                             | 首次接受方法                                                        |
| --------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------- |
| KR-LOG-01 | 一个请求/业务 ID 可定位有权查看的原任务与尝试，秘密和跨范围记录零泄露  | 正常、超时、重连、重试及越权固定样例全部满足 AC-LOG-01～04、08、09  |
| KR-LOG-02 | 创作、转化、成本与资金图表和权威样本一致；重复事件不多算，缺数据不补零 | 按设计42 MET字典手工核对固定样本，AC-LOG-05～07、10、11全部符合预期 |
| KR-LOG-03 | 采集/投影故障时业务结果不被改变，统计能说明缺口并安全恢复              | 故障、回补与权限演练满足 AC-LOG-08～12；实际容量边界单独测量        |

目前无真实定位耗时、转化、留存或利润基线，不承诺改善百分比。上述为功能接受条件，不是生产容量或商业效果已达标。

## 4. 用户与价值

| 价值要素   | 值班/研发                          | 创作者与团队管理者                  | 平台运营与经营核查者                |
| ---------- | ---------------------------------- | ----------------------------------- | ----------------------------------- |
| 谁         | 处理请求、后台任务和供应商故障的人 | 判断本人/本团队创作效果的人         | 评估用户增长、付费与成本的人        |
| 为什么     | 需要查清原请求和未知状态           | 需要知道投入是否变成采用及交付      | 需要分清现金、消费、成本和有效收益  |
| 当前方式   | 拼接容器日志及业务记录             | 查项目、素材和任务，缺汇总入口      | 查不同业务记录，尚缺统一分析视图    |
| 解决方式   | 有界查询、错误分类、原任务关联     | 创作漏斗、采用/交付、复用与用量趋势 | 用户/付款空间同期群、实收与费用明细 |
| 得到的结果 | 有证据定位，不因查日志重复派发     | 找到卡点，比较真正可用的产出        | 同口径核对转化与贡献，看到缺失依据  |
| 现有替代   | 容器日志加手工查单；保留作回退     | 手工逐项目核对；适合少量对象        | 受控导出手工核算；本方案减少拼接    |

三类人共用时间和范围筛选，但读取不同权限的数据。经营核查权与平台治理身份分别验证。

## 5. 方案与完整交付范围

1. **运行诊断：** 请求/错误/关键系统记录、按 ID 查询、脱敏链路、错误趋势、耗时、积压与采集完整性；保留原审计入口及其范围。
2. **创作分析：** 从入口/注册到首次创作、生成、采用和交付，覆盖手工路径、Agent/工作室阶段、素材复用、用户/团队活跃与留存。按模态、模型、项目和入口查看固定维度。
3. **经营分析：** 首付与复购、充值退款、积分批次和权益使用、销售消费、采购及失败重试成本、补贴和可核对贡献；模型/渠道比较不混淆用户业务单与采购尝试。
4. **共同体验：** 固定概览、趋势、同口径明细和受控 CSV；显示时间、范围、口径、更新时间与数据缺口。页内筛选复用现有组件，键盘可达，窄屏可读。

## 7. 假设与风险

用户要求完整分析，但历史访问、采用、支付分摊、会员和可变成本不保证已具备可重放来源；这些能力保持在完整范围内，按数据依赖逐项开放。没有可靠源时，报表不可用并说明缺项，不靠日志推算。容量、期限、口径细则和经营授权沿需求27 DEC-LOG-01～04评审。

## 8. 交付边界

先建立诊断与事实口径，再开放创作全流程，随后接入完整经营来源并完成联合验收。每批只开放已经通过来源、权限、数据质量验收的指标；不能只交运行面板就宣布本需求完成。执行依赖、状态和下一步见 [BACKLOG](../../BACKLOG.md#logs-analytics-20261113)。

范围外：公共日志服务、自助BI、任意SQL、跨站追踪、会话回放、第二套计费/账本、自动补发/退款/经营决策。未指定负责人和排期，不补造承诺。
