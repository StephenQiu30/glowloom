## 1. 设计目标、现状与约束

保留兼容并发修改，让客户端与数据库得到一致合法的图。OT（Operational Transformation，操作转换）调整基于旧状态的操作位置或含义；WebSocket只传消息，数据库版本检查只防止错误覆盖，两者都不能代替OT。

自拟示例：原文AB，甲在位置0插入X，乙删除位置1的B；甲先接受后，乙的删除位置须变成2，结果为XA。后续文本、对象、引用和撤销分别按本设计裁决，不把整个画布当字符串。

| 现状/约束                                                     | 依据与核对时间                                                                                                                                                 | 影响                                                                                  |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 现有提交拒绝expected_revision不匹配，配置多为整块更新         | [存储实现](../../backend/internal/canvas/adapter/postgres/store.go)、[命令模型](../../backend/internal/canvas/domain/document.go)，2026-10-20静态检查          | 此为实施前基线；2026-10-21已接入v1有限操作、转换及持久终态回执，执行证据见计划19第7节 |
| 当前提示词支持段落、文字、hardBreak与reference，没有通用marks | [前端extensions](../../frontend/src/components/generation/composer-session.ts)、[后端Draft](../../backend/internal/prompt/domain/draft.go)，2026-10-20静态检查 | 先覆盖真实受限富文本，不以纯字符串代替引用，也不凭空引入任意样式树                    |
| 节点及部分子对象已有稳定ID，某些槽位仍为数组                  | [批量表](../../backend/internal/canvas/domain/batch_table.go)、[导演配置](../../backend/internal/canvas/domain/director.go)                                    | 对象按ID定位；数组位置不能充当永久身份                                                |
| 用户选coder/websocket，要求免费、自部署、最小设计             | 本会话已确认选择                                                                                                                                               | 保持现有Go/PG；选库不等于选择或实现OT算法                                             |

本版明确受限富文本的序列表示、转换算法、编辑器接点及全部现行配置字段的操作映射；存量关系分类见设计14第5.3节。三个设计问题已有具体处理方案，不再以“实施时选算法/逐字段再盘点”代替设计。跨语言实现、三方因果和真实旧库样本仍须验证；这与设计决策是否明确分开记录。保持OT方向，在现有Go/TS内实现有边界的业务适配，不建立通用引擎或独立服务。

## 4. 模块职责与接口合同

### 4.1 参与方与操作模型

| 参与方                | 输入/输出及职责                                                             | 不负责                            |
| --------------------- | --------------------------------------------------------------------------- | --------------------------------- |
| 客户端操作适配        | 编辑器/图操作→受支持命令；维护基线、在途和缓冲；apply/transform用于乐观显示 | 不自行确认权限、保存或调用生成    |
| Go转换职责            | 原批次、基准后的连续日志→转换后的批次、noop或明确冲突                       | 不保存第二份图、不决定有权绕过DAG |
| 画布应用及PG事务      | 当前授权、版本、业务规则、规范效果、回执与必要撤销资料                      | 不在数据库事务内等待网络          |
| coder/websocket适配器 | 按设计15传递命令、终态和有序变化                                            | 不实现第二套转换规则              |

操作身份为(actor_id,op_id)；actor由会话取得。信封含document_id、base_revision、operation_version、commands，冻结在途信封不随重连修改。细粒度操作至少表达创建/删除对象、设置字段或属性组、插入/删除文本、增删或移动有序元素、Undo目标操作。当前命令名尽量沿用；不得开放任意JSON路径修改系统字段。

实施合同细化（v0.7）：新操作信封使用`operation_version=1`、`base_revision`、`operations`；协议2承载它，协议1维持旧CAS读取并在文档切换后禁止旧写入。操作类别为`create_node/delete_node/connect/disconnect/set/text/insert/remove/move/migrate_composer`及单独`undo_of`。字段以白名单`path`定位；集合元素路径使用`@稳定ID`，map键仅在明确的params/bone_overrides允许位置使用，不开放任意JSON Patch。属性组为命名路径（如`position`或`config.generation.model`），值包含该组成员；T使用类型化retain/insert/delete。C附`expected`与`expected_exists`；模型/来源相关操作附`context`，与原基准身份一致，不授予权限。派生字段与正式标签不在客户端白名单。旧四字段草稿通过一次性的`migrate_composer`转换：expected绑定完整旧草稿、服务器保留段落/提示词/负提示词/比例/数量生成composer，已有composer不能再被替换；并发旧提示词编辑使迁移前提失效。新日志包含实际字段前像/规范效果和媒体UUID引用索引，后者仅用于既有历史保留查询；单日志受现有1MiB媒体读取预算约束。

切换在首次新模型成功提交中原子记录，旧基准跨越无规范日志的历史一律持久拒绝`history_unavailable`；不在普通连接加入时静默改变写入模型。现有历史和旧成功回执保持可读。新模型确定拒绝在回执事务提交后才对外确认。历史窗口上限128个接受版本、4MiB日志，单日志1MiB；沿既有10秒数据库操作预算。另在进入转换前限制4096个操作对/重放单位和32MiB估算文档复制量，累计历史共同收费；Undo按重放、涉及文本字段谱系和逆操作×后来操作收费，不将整个输入批次无条件平方。超限持久拒绝history_unavailable并查证、重同步。这是有界保护，非生产吞吐承诺；本地2000节点/378188字节、一次历史/文本操作对实测约109ms，未做生产并发压力测试。

一个批次原子接受或拒绝，内部命令有明确先后顺序。已有命令数组仍可承载这些语义，不预建插件化操作注册平台。命令需声明稳定对象/字段身份及必要前提（例如参数所属modelVersion），前提不是由客户端授予的权限。

### 4.2 转换、业务裁决与顺序

服务器在文档锁内确定唯一接受顺序。base_revision之后的命令逐条参与转换；同一批次和本地缓冲的后继操作基于前序操作后的状态，必须更新转换上下文，不能都当成同一旧基准的独立操作。只读取日志而不保留因果关系不算完成转换。

对同基准的有效并发操作A、B，A先进入权威顺序，记B′为B跨A转换的结果、A′为A跨B转换的结果；必须验证“先A后B′”与“先B后A′”得到相同结果。客户端处理远端已接受操作时必须使用相同的先后优先级，不能每端都认为自己的操作更优先。这一性质只适用于能够共同接受的操作；业务非法组合由权威拒绝及客户端回滚处理，不虚构合法转换。

**先校验基准，再转换**：持锁读取当前图及base_revision之后的连续日志，对涉及的字段/容器按日志前像逆向还原到基准，按操作类型校验原目标存在性（已知删除身份的幂等删除仍可noop）、文本长度和UTF-16边界、集合身份与前提；同批后继步骤基于前序后的临时状态。随后按权威历史正向转换，当前权限和完整候选图约束最后复核。不能只验证转换后的操作，否则旧基准越界或切断代理对的输入可能被后来插入掩盖。旧日志缺前像、超过已测转换预算或还原不确定时返回持久化的history_unavailable拒绝，并要求重同步；不创建历史快照表，也不在锁内做无界历史扫描。base_revision超前同样终态拒绝，客户端不能篡改原信封后重试。

批次转换采用逐步上下文：将远端批次的每条规范操作与本地顺序批次成对转换，后一对使用前一对的输出；不是把每个Q或每个step对同一个未更新远端操作分别转换。S/G同字段赋值时，A先接受、B后接受，则B′保留B、A′不覆盖B；A的实际写入及Undo归属仍进入权威日志。C冲突或依赖失效没有伪造的可接受双路径，按拒绝/协调处理。第4.4的表只定义序列组件，整图还必须遵循这些对象裁决及第4.5的集合规则。

三种结果明确区分：兼容操作自动转换；互斥意图按下列产品规则裁决；不合法或无法解释的操作整批拒绝。noop只用于已经达到同一目标或已定义的幂等删除等情况，不能用noop偷偷吞掉不存在目标上的用户编辑。

### 4.3 对象、字段、关系的处理规则

| 并发组合                   | 明确规则及结果                                                                                                                   | 分类                 |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| 不同ID创建；同节点不同字段 | 均保留；共享身份不由数组下标决定                                                                                                 | 自动转换             |
| 不同操作用同ID创建         | 拒绝ID冲突，不把其内容合并；同op_id重试由回执返回                                                                                | 明确拒绝             |
| 同一普通字段赋值           | 服务器后接受者的值生效；不按客户端时钟；后者不能覆盖其他字段；同值赋值仍记录有效写入归属，不以空命令抹掉触碰证据                 | 权威顺序裁决         |
| 移动、缩放、三维变换       | x/y为位置组，width/height为尺寸组，三维transform为业务定义的完整变换组；同组后接受者生效，不把位移相加；不同组可合并，约束仍复核 | 属性组裁决           |
| 模型切换与参数编辑         | 模型＋模式及必须联动的参数切换作为原子意图；针对旧模型的参数编辑若前提已失效则拒绝，不能套到新模型；同模型不同参数键可合并       | 前提校验＋字段转换   |
| 节点删除与编辑/连线        | 删除先接受，则后续编辑/连线以target_deleted拒绝；编辑先接受且删除合法，最终删除，显示后续删除事实；受保护对象的删除仍拒绝        | 删除裁决，不自动复活 |
| 相同对象重复删除           | 仅已知同一身份确实被删除时noop；未知ID为target_not_found，不把拼错ID当成功                                                       | 幂等裁决             |
| 普通Connect/Disconnect     | 不同合法边保留；同ID不同端点拒绝；不同ID却构成同一语义关系则duplicate_relation拒绝，不创建隐式ID别名；已知边重复删除noop         | 转换＋关系唯一性     |
| 依赖并发成环               | 按接受顺序只提交仍无环的批次；另一批dag_cycle拒绝，不先广播再回滚数据库                                                          | 业务校验             |
| 分组归属与移动             | 同一子节点parent后接受者生效，最终必须无环；移动仅作用于意图中列明的成员ID；后加入成员不隐式跟移                                 | 转换＋业务校验       |
| 分组被删与并发移动/归属    | 删除只解除成员归属并保留世界坐标；已存在子节点的显式移动仍可接受；将节点加入已删分组则拒绝                                       | 明确裁决             |
| 节点删除与其引用           | 同批清理可编辑边和可清理引用，效果写入规范日志；任一受保护引用不能清理则拒绝整个删除批次                                         | 原子业务裁决         |
| 系统结果与用户输入         | 结果绑定原input_revision，仅更新所属结果字段；新输入保留，重放不新增任务或费用                                                   | 受保护业务写入       |

移动/删除等是本轮提出的明确设计规则，待产品评审；不伪造其已被用户逐项接受。普通Add不得复用墓碑ID；恢复同一引用绑定时保留官方编号并提升bindingGeneration，恢复节点内绑定同样提升代次，防止删除前的上传回调重新生效；专门的Undo恢复“同一历史对象”按第5.3节处理；跨过删除及恢复历史的旧编辑仍已失效，不能因ID重新存在就接受。消除前版“禁止复用却又允许恢复”的歧义。

### 4.4 纯文本与实际富文本规则

文本位置采用UTF-16代码单元；Go不得用字节长度或rune数量直接解释位置。字符操作不允许切断代理对，不做隐式Unicode归一化；用户删除动作按编辑器识别的可见字符范围产生，组合字符/emoji序列须保留其意图。删除范围采用左闭右开；插入/删除/替换的批次及同位置优先级固定。

| 文本并发组合                    | 预期结果                                                                                                                                        |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 同位置插入X与Y                  | 先接受的片段在前，后接受的在后；同批次内部次序保留，各客户端不能按到达顺序自行交换                                                              |
| 删除与之前位置的插入            | 调整删除位置，仍删除原来目标；如AB中先插X再删除原B，应得XA                                                                                      |
| 删除与删除区间内/边界的并发插入 | 删除仅作用于原基准被选中的内容，保留未见过的并发插入；必要时删除拆成多段，不连新插入一起吞掉                                                    |
| 重叠删除                        | 重叠的原内容只删一次，剩余片段合并/拆分后应用；全部已删可noop                                                                                   |
| 替换与替换/插入                 | 替换逻辑上删除原选区并插入新内容，编码统一为第4.4.1节的insert后delete，不当作整字段赋值；保留双方插入片段，原内容只删除一次；位置冲突按前述规则 |
| 后继编辑修改刚插入的内容        | 按因果链处理，不把它与自己依赖的创建/插入当作独立并发；前序被拒则后继阻断                                                                       |

#### 4.4.1 确定采用的表示与算法

2026-10-21实施现状补充：main的41c2f0ef已将资源文本编辑器升级为可包含标题、列表、marks和Markdown格式的DocumentEditor。它与下述创作提示词schema不同。保留其现有存储与格式；普通段落文字的真实PM步骤映射到`config.text`序列，复杂Markdown格式/复杂结构编辑用单字段组`config.text_source`（成员text）执行C替换，要求原source及历史无触碰，冲突保留原意图供明确重试，不将整config或全文diff当作字符贡献。复杂Markdown并发合并不在本轮受限序列保证中；已向用户异步提出该边界，当前按推荐假设实施，后续答复可调整。

采用**受限序列OT**：现有JSON仍是存储模型，转换时投影为文字段、paragraphBreak、hardBreak、reference(referenceId)组成的序列。后三类是不同的类型化原子，各占1个位置；文字长度按UTF-16。不得用某个Unicode字符充当原子哨兵，否则会与用户输入混淆。

- 相邻段落之间编码一个paragraphBreak，首尾不追加；空文档序列解码为一个空段落，单个paragraphBreak解码为两个空段落。连续分隔保留连续空段落；hardBreak始终留在本段内。
- reference只保存referenceId，名称与显示编号由绑定/labelState取得。重复出现的同一绑定是不同位置的原子，删一处不会删其他处。
- 相邻文字节点允许合并，空content与缺省content允许规范化；必须保持文字、段落、软换行、引用顺序与身份的语义往返，不要求JSON字节或文字分片方式相同。未知字段/marks/节点类型拒绝有损转换。
- 操作为retain(n)、insert(类型化片段)、delete(n)的顺序流；长度均为正整数，末尾未声明的基准内容视为retain。替换在选区起点表达insert新片段再delete旧片段，统一同位置优先级；同一意图内保持插入片段次序。不接受越界或切断代理对的组件，不把整段文本重新赋值作为普通输入。

transformPair的输入必须具有同一基准，A为服务端先接受者。以下A′表示A跨B，B′表示B跨A；双游标读取组件，retain/delete按较短剩余长度n拆分，insert不消费原基准。表中“空”是不输出组件，不代表丢弃撤销所需原始删除归属。

| 当前组件                         | 输出A′            | 输出B′            | 推进规则                                  |
| -------------------------------- | ----------------- | ----------------- | ----------------------------------------- |
| A insert（包括双方同位置insert） | 原A insert        | retain(A插入长度) | 仅推进A；保证先接受插入在前               |
| B insert，A非insert              | retain(B插入长度) | 原B insert        | 仅推进B；并发插入不被删除吞掉             |
| A retain / B retain              | retain(n)         | retain(n)         | 双方消费n个基准位置                       |
| A delete / B retain              | delete(n)         | 空                | 双方消费n个基准位置                       |
| A retain / B delete              | 空                | delete(n)         | 双方消费n个基准位置                       |
| A delete / B delete              | 空                | 空                | 双方消费n个基准位置，原始删除贡献仍留日志 |

apply、transformPair、位置映射在Go/TS使用同一规则和固定向量；纯文本字段使用同一算法的文字子集。每个编辑步骤保留顺序，首版不必实现跨步骤compose或通用树变换。服务端先转换再解码并执行现有Draft、资产、图约束校验；非法结果整批拒绝。引用绑定和跨字段的业务裁决仍走第4.3、4.6节，不能仅靠这张序列表保证整图合法。

#### 4.4.2 接入现有编辑器及后端的具体位置

接点为[composer-session](../../frontend/src/components/generation/composer-session.ts)的ProseMirror事务与intent，而不是onChange返回的整个Draft；[prompt-document](../../frontend/src/components/generation/prompt-document.ts)和[Go Draft](../../backend/internal/prompt/domain/draft.go)继续负责现有schema。ProseMirror的步骤及位置映射语义参考[StepMap源码](https://github.com/ProseMirror/prosemirror-transform/blob/master/src/map.ts)及[ReplaceStep源码](https://github.com/ProseMirror/prosemirror-transform/blob/master/src/replace_step.ts)；以下适配是本项目设计，不能当作该库已有的Go能力。

1. 对事务内每个step，使用其执行前后文档及StepMap的变化区间，转换成序列操作；后一步基于前一步结果。普通ReplaceStep映射选区和插入片段；ReplaceAroundStep保留gap对应内容，只转换实际被替换的区间。禁止拿事务前后整份JSON做一次大替换或按相同字符猜测删除位置。
2. 建立PM位置与序列边界映射：段落内容起点映射本段序列起点，段内文本/原子按上述长度计数，前段内容末尾到后段内容起点对应一个paragraphBreak；doc首尾映射0和序列长度。结构边界记录左右关联方向；拆段插入分隔，合段删除分隔，软换行插入hardBreak。使用步骤的原区间和保留区间确定映射，不能直接减一个固定偏移。应用生成操作后必须等于步骤后文档的规范化投影，否则unsupported_editor_step并停止该意图提交；不允许退回整块覆盖。现行Enter、Backspace合段、跨段选区、粘贴和引用操作都必须通过该门禁才可发布。
3. addReference、removeReference、replaceReference、reorderReference分别生成绑定新增＋可选原子插入、绑定删除＋全部原子清理、带代次前提的重绑、按ID移动；保留当前同一动作的原子事务。仅选区/光标改变不生成业务操作。上传完成仍核对contextKey、replicaId、referenceId、generation、attempt；过期回调不改变新绑定。
4. 服务端规范操作投影回编辑器事务，同时映射选区；标记为远端/权威协调，不能再次进入发送队列或本地历史。当前history函数用replaceWith恢复整文档，协同模式须改接第5.3节的操作Undo；未发送Q才可本地取消。重做使用新op_id重提仍合法的原意图，无法安全重建则不可用，不能恢复旧frame。当前snapshot/replaceDraft只用于初始化、经核实的重同步，不作为每次远端编辑的覆盖入口。
5. 现有本地label分配改成“权威labelState＋未确认绑定临时显示”；临时显示不写正式highWater/allocations，不复用replaceDraft中会拒绝重新编号的旧历史合并路径。服务端在锁内按接受顺序分配编号并返回规范效果；前端按referenceId协调编号，P原信封不变、Q不依赖临时编号。临时绑定显示“待确认引用”；为复用现有validatePromptDraft，可在内存候选上合成不冲突的临时标签表做结构检查，但该表不并入B、不进入操作payload或持久化快照，收到规范效果后重建。不能把缺少allocations的临时Draft直接送给现有严格校验器，也不能允许客户端自选正式编号。纯编号协调不触发生成或单独的新输入意图。
6. Go在现有canvas应用路径中完成字段定位、历史转换、候选配置重建，随后调用既有prompt校验和draft_sources来源核验，再交给设计14的统一事务。WebSocket不传ProseMirror私有Step JSON，不要求Go运行Tiptap，也不增加Node.js服务。

引用规则：

- reference按原子元素处理，按referenceId关联绑定；删除不能留下半个引用，文字移动不能改变绑定身份。
- 新增mention及所需绑定在同一原子批次；共享绑定可有多个mention，删除一个mention不隐式删除仍被使用的绑定。显式移除绑定须同批清理其所有mention，否则拒绝。
- 同一绑定的source（含sourceVersion）、mediaKind、role、bindingGeneration作为整体修改，使用基准绑定代次作前提；并发重绑先接受者使后者前提失效，后者明确冲突，不能混出半新半旧素材。不同referenceId的新增/编辑保留。
- 绑定移除先接受，则后续新增同绑定mention或重绑拒绝；mention先接受，后续合法的显式移除绑定须清理当前全部mention，效果记录并同步。
- labelState维持现有单调编号及墓碑约束；并发新绑定由服务端按接受顺序规范化分配可用显示编号，客户端先显示临时状态，再应用权威绑定/编号效果。不能整块最后写入labelState而复用他人已分配编号，也不能把标签渲染文本当引用身份。

本次核对的实际编辑器没有粗体/斜体等marks，故不预建通用格式化OT；粘贴按既有允许schema处理，不静默删除服务端已存在的未知格式。算法和适配范围已经选定；换行、空段落、中文输入法、emoji和引用的Go/TS配对实现及三方交错仍须按第7节验证。未来新增marks须另补模型与规则，不能宣称已覆盖任意富文本。

### 4.5 嵌套集合与数组规则

batch_table的行/列、director物体/镜头/关键帧等有ID的集合按ID编辑：不同元素字段保留，同元素同字段沿第4.3节，删除优先。批量表输入槽用(row_id,column_id)定位，持久数组按当前列顺序序列化；删列同时清理其槽位，重排列不改变输入归属。

有序集合插入表达“新元素ID＋before_id，空为末尾”，删除按ID。相同基准、同一锚点的两个新增按服务端接受顺序排列：A先接受、B后接受时，B′仍插在原锚点前，A′改插在B的新ID前，因而两条路径都是A、B、锚点；末尾锚点同理。不同锚点新增及不涉及锚点的删除可保留；锚点已删/跨集合、目标身份冲突明确拒绝，不能擅自追加到末尾。

**集合重排采用窄范围C裁决，不实现通用Move OT**：Move携带元素ID及目标before_id，但读取该集合的成员/顺序前提。自基准后有其他操作增删/移动该集合成员，则该Move以order_conflict拒绝；反向情况（基准之后已接受Move，旧基准的新增/删除）也拒绝。只影响同一集合的结构，不阻止不同元素字段、行提示词或(row_id,column_id)槽位编辑，不扩大到整个config；同批内显式顺序操作可基于前序合法结果继续。字段编辑与重排并发均保留。C依据日志中的结构触碰，不能只比较最终ID数组是否相等。

前版“同元素两次移动后接受者生效”与简单before_id执行不足以保证收敛，现删除该承诺。例如初始[a,b,c]，A将a移到c前、B将b移到c前，按两种直接应用顺序会得到不同结果；本版第二个并发重排明确拒绝。该小范围裁决符合BR-COL-03允许明确处理互斥意图的边界，不将所有集合编辑标为不支持。成员关系和子树约束在完整批次后校验。

没有稳定ID的集合优先使用现有唯一业务键（例如骨骼名称）；不存在可靠键、必须整块更新的配置作为单个原子字段组处理。相同组若在基准之后被改过则要求重新编辑，不能全量最后写入。此类集合在第4.6节明确列名，不把所有config都归为冲突块。代码中的timeline、director、generation、batch_table在editable门禁下均可编辑；受保护的是不满足门禁的节点及系统事实，不能把timeline整体误判为只读。

2026-10-20逐项对照canvas/domain的[document](../../backend/internal/canvas/domain/document.go)、[draft](../../backend/internal/canvas/domain/draft.go)、[generation](../../backend/internal/canvas/domain/generation.go)、[batch_table](../../backend/internal/canvas/domain/batch_table.go)、[timeline](../../backend/internal/canvas/domain/timeline.go)、[director](../../backend/internal/canvas/domain/director.go)、[director_outputs](../../backend/internal/canvas/domain/director_outputs.go)以及[prompt/domain/draft](../../backend/internal/prompt/domain/draft.go)。以下表按JSON字段命名，所有子类型继续展开；操作名称是协议语义，不在本轮增加接口代码。

## 5. 数据、状态与一致性

### 5.1 保存与终态

数据库、日志和回执完全引用设计14：接受图、规范效果、必要撤销资料、版本和回执一次提交；确定业务拒绝只提交rejected回执，不推进图revision。瞬时失败与提交未知无终态，原信封查证；同一op_id不允许先终态拒绝、后又接受。noop仍占一个接受版本并存回执，不更新生成输入、活动或触发副作用。

日志记录所有用户、HTTP残留和系统操作的规范效果，含服务端追加的引用清理/编号分配；原请求与规范结果不能混同。基准未来或历史断档在已认证、格式有效且版本受支持时写终态拒绝并停止转换；版本模型未知属于入口error。两者都要求客户端停止自动发送并按原因重同步/升级，不把history_unavailable当可盲重试的临时网络故障。不能把当前值相等当作没有他人写过，也不能从最新图推测不存在的历史。

### 5.2 客户端在途、缓冲与拒绝

客户端仅在内存保存权威基线B、一个在途批次P和有序缓冲Q。P的网络原文不可变，另有随权威历史转换的本地显示版本；Q建立在应用P及前序Q后的状态上。未发送的连续同节点拖拽可合并为最终位置，不跨已发送、文本或结构操作乱序合并。

- 远端变化按revision连续进入B；其规范命令与P的显示版本双向转换，再依次协调Q。只转换P、却把Q继续应用到旧状态，会破坏因果，必须禁止。
- 自己的ack先到只说明P已持久接受；等对应revision在B连续应用后才移除P，再确认Q已相对新B重定位，生成下一冻结信封。ack/changes重复不得二次执行；以(actor_id,op_id)识别本人，不按UUID猜测。
- 服务器规范结果若因业务裁决/追加效果与本地预测不同，客户端重建B＋待处理意图：标签按referenceId替换显示；清理/固定资产等效果显式列在canonical commands，逐一检查Q的读写前提；文本只用步骤映射，不做整文档diff。对有确定映射的Q重定位；依赖已删除目标、失效模型或无法解释文本位置的Q进入恢复对照，不能盲发或把所有Q静默丢掉。
- 在途P只有显示版本可转换，wire原文保持不变。若另一端删除使P显示版本失效，暂时停止呈现不合法效果并阻断依赖Q，但仍等待P的持久终态；客户端局部判断不能伪造reject。独立Q仅在P终态及连续基线明确后重新发送。
- P终态拒绝后去掉P乐观效果；依赖其创建、插入或结构结果的Q一并阻断。独立意图只有能证明其对象/位置仍有效才可重新基于B生成操作；否则保留恢复对照。重建操作使用新op_id，不能篡改原信封。
- 输入法组合输入期间继续接收并记录权威变化，但不强制覆盖正在组合的编辑区；组合结束后由组合起始基线产生操作并转换到当前B，目标已删或无历史则明确失败。

断线按设计15暂停新编辑。重连先确认P的accepted/rejected/not_found，再追赶历史；not_found时只允许原P重试。收到新快照也不能自动认定P已失败；不具备足够历史/映射时暂存意图供重新编辑，不把旧文本或整图全量覆盖。

### 5.3 协同撤销

Undo携带新op_id及target_op_id，目标必须是当前操作者已接受的操作。服务端从原日志取得其真实效果和必要前值，再按目标之后的规范历史转换逆操作；不相信客户端提供的“旧值”，不依赖一份旧整图。日志不足则明确undo_unavailable。

| 目标及后续变化     | 撤销规则                                                                                                                                                                                                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 普通字段或属性组   | 仅目标仍拥有该组最后有效写入时恢复前值；他人后来即使写入相同值也算触碰，不能仅比较值；不同字段的他人修改保留                                                                                                                                                                                 |
| 文本插入/删除      | 撤销只去除自己的插入贡献或恢复自己删除的原内容；跨后续操作转换，保留他人的新输入；他人也曾删除的重叠内容不能因自己的Undo复活，即使他人删除已转换为noop；靠日志原始目标/区间及归属判断；最小版发现后续删除与待恢复范围有重叠时整批undo_conflict，不实现部分复活或永久字符墓碑；无法证明时拒绝 |
| 新建节点/边/子对象 | 只有没有后来他人贡献或引用依赖时才可删除；已有他人使用/编辑则拒绝，不代删他人内容                                                                                                                                                                                                            |
| 删除节点/边        | 仅可按原删除日志恢复同一对象身份及当时实际移除的可恢复关系；此为Undo，不是Add复用ID。重新校验端点、权限、当前分组、DAG及资产；任何部分不能恢复则整批拒绝；已存在的独立删除墓碑不能被顺带复活                                                                                                 |
| 分组或集合移动     | 仅目标关系未被他人后续修改且原锚点/父节点仍合法时恢复；否则拒绝，不强行恢复旧成员集合                                                                                                                                                                                                        |
| noop或已撤销目标   | 无可撤销贡献；返回明确不可撤销，重复同一Undo信封则返回原回执，不重复效果                                                                                                                                                                                                                     |

撤销记录最少包括原操作身份/基准、字段或容器路径、规范前后值或插删片段、文本步骤位置映射和触碰集合；删除变成noop仍保留原删除区间及其基准。通过连续日志在临时工作区投影贡献，不给每个字符新增持久ID或独立撤销库。只有无重叠、无失效前提且可证明的逆操作才接受；拒绝是明确的用户结果，不能把所有文本Undo都关闭后宣称完成AC-COL-03。

是否已撤销可由带undo_of的规范日志查询，不新增撤销状态表。一个批次若任一逆操作会破坏他人贡献，整批Undo拒绝，不默默部分撤销。未发送的本地缓冲可本地取消；P结果未知时先核实，不能发送猜测性的逆操作。跨刷新撤销暂不作产品承诺，即使服务端留有必要验证资料也不自动增加历史浏览器功能。

## 8. 兼容、发布边界与评审

先固定并评审操作模型及本文语义，再用有限原型验证高风险反例；通过后交付正式Go/TS转换内核与数据调用合同，再完成字段/编辑器、客户端协调器及Undo接入，最后进行数据/通道联合接受。原型通过只允许继续实现，不能当成正式内核或全部AC已完成。规则未被算法支持的类型明确阻止危险并发，不静默降级为全量覆盖；这种保护只能用于阶段验证，不能据此取消富文本或宣称需求10完成。是否分批发布另由后续产品范围决定，本轮未授权。
