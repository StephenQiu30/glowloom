# 画布OT处理设计

## 1. 摘要

按稳定节点身份和有限编辑操作协调并发修改：保留不同对象、不同属性及文本中的兼容意图；对同字段、删除和关系冲突给出确定裁决。转换后的候选仍须经数据服务授权和图校验。

2026-10-22本设计重新从原始需求出发。它规定待验证的语义和算法边界，不认定已有转换代码正确；旧实现与旧测试不能替代以下性质和场景验收。

## 2. 参与者

同一画布的有权限编辑者、客户端协调器、服务端转换模块、事务提交服务。转换模块不访问数据库、不建立连接；历史和持久结果沿设计14、传输沿设计15。

## 3. 背景

[需求10](../requirement/10-画布OT协同一致性需求.md)明确要求OT、本人贡献撤销和结果版本绑定，特别规定不能把整图覆盖、仅最后写入或全部冲突拒绝称为OT完成。FR-COL-01～03、BR-COL-01～06及AC-COL-01～06是依据。

本轮前端范围仍为五类编辑节点。原有生成、富文本和引用的需求身份保留；凡未被当前组件支持的结构必须保护，不以“组件范围小”为由删除历史内容或声称完整OT已交付。

## 4. 目标

各端排空待确认操作后，确认版本与规范共享图一致；兼容编辑不静默丢失；撤销不抹掉别人的有效贡献。候选依赖遵守需求10保留的免费生产使用与自托管约束，许可证需在选型时核验，不沿用旧调研结论。无需引入通用树编辑引擎、永久字符墓碑、离线持久在线草稿或历史回滚产品。

## 5. 使用场景

一人移动节点、另一人改正文应同时保留；同一正文两端插入/删除应调整位置；删除与连线交错不能留下悬挂边；自己的撤销不能整图回退；迟到生成结果不能覆盖后来编辑的输入。

## 6. 价值

用户可以继续贡献编辑，能理解需要处理的冲突。算法正确性、业务裁决和传输恢复分别可验证，不以单个字符串例子或一次双端演示证明全图可靠。

## 7. 方案

### 7.1 操作与基准

使用[设计14操作合同](14-画布数据与接口设计.md#75-编辑操作合同)，不比较两份最终JSON生成“最后覆盖”。操作指向稳定节点/边ID，属性使用白名单字段，文本使用序列操作，素材替换带旧绑定比较，分组作为原子复合编辑。

每个批次有不可变op_id、client_id、base_revision、operation_version。base_revision只表示创建该批次时的确认基线，不能为了重试修改原body。后续依赖前一批次的意图放Q中，待协调完成后以新的基线形成下一次提交。

server_revision是唯一接受顺序。客户端时间戳不决定胜负；不能把客户端时钟偏差变成写入优先级。

### 7.2 服务端转换流程

在文档写入序列中读取base_revision到当前版本的连续规范历史。先证明原操作在其原基线上合法，再逐步沿历史转换到当前基线；转换双方必须处于同一上下文，不能把不同版本的原始操作直接两两组合。

转换得到候选后，由设计14执行最终权限、媒体和图校验，并原子写当前状态、规范操作、必要effects及回执。拒绝也有明确持久结果。历史不完整、语义版本不支持或转换预算超限时，返回明确恢复原因，不能跳过中间操作。

同批操作具有顺序与依赖，转换时保持批次原子性。一个对象被删除导致批次中的另一操作失效时，按业务语义明确拒绝整个批次或形成可解释的规范空操作；不得静默接受半批。

### 7.3 并发裁决矩阵

以下为本版设计选择，须通过性质及产品场景验证；不是既有实现事实。

| 并发组合                   | 处理语义                                                     | 必须验证                                     |
| -------------------------- | ------------------------------------------------------------ | -------------------------------------------- |
| 不同节点，或同节点不同字段 | 保留双方修改                                                 | 无整节点覆盖，应用顺序变换后收敛             |
| 同节点位置/尺寸同时修改    | position与size各为不可拆字段组；同组由服务端接受顺序裁决     | 不产生甲的x配乙的y；明确最后接受的规范值     |
| 同一普通字段赋值           | 确定接受顺序裁决；与文本转换区分                             | 重复、迟到消息不改变最终顺序                 |
| 同正文插入/删除            | 序列OT调整位置，重叠删除只删除一次                           | 同位置插入、交叉删除、emoji与IME不丢兼容字符 |
| 删除与编辑/连线            | 删除优先，不自动复活；失效意图有明确结果                     | 无悬挂边、无错误成功提示；可恢复本页输入     |
| 创建同ID                   | 仅原op_id重放可返回原结果，其他请求拒绝身份冲突              | 不能覆盖旧对象或别的文档对象                 |
| 同语义连线重复             | 显式拒绝重复；其他边按稳定ID独立转换                         | 拒绝不产生半批写入                           |
| 分组/取消分组/移动分组     | 保留成员世界坐标；原子处理成员；同成员归属冲突明确裁决或拒绝 | 组与子节点一致，无环；取消分组不丢节点       |
| 素材替换并发               | 比较旧media_ref；旧绑定已变时拒绝第二个替换                  | 不以最后写入悄悄覆盖别人素材                 |
| 合并后成环的依赖           | 转换后只接受满足DAG的提交                                    | 收敛不以保存非法图为代价                     |
| 后台结果与新输入           | 结果绑定原内容/输入版本，新输入保留                          | 不重新生成或扣费，不覆盖后来正文             |

对同位置/字段的权威顺序裁决只解决该类语义冲突，不代替文本OT、复合操作或客户端因果协调。首次上线必须明确每个实际可编辑操作属于自动转换、业务裁决、受保护或尚未支持，不能全标不支持后宣布完成。

### 7.4 文本与富文本

序列操作采用retain、insert、delete；位置单位为UTF-16代码单元，禁止拆开代理对，输入输出均校验Unicode有效性。同一位置的并发插入用一致、可重放的优先顺序；文本原子与引用原子分型，不能用特殊字符伪装媒体引用。

纯文本节点的正常输入提交序列操作，不能每次替换全部正文。中文组合输入在组合事务结束后形成明确操作；本页选择区随变更映射，不能把选区或光标存入共享图。

富文本必须先定义受支持的结构、格式操作和引用身份，再接入适配。不得把任意编辑器JSON序列化字符串后套普通文本算法并宣称结构正确。若采用受限文本/标记模型，要逐项说明段落、格式、嵌入引用与粘贴的可逆表示及结构验证；无法无损表示的历史正文只读保护。

当前五类组件中的普通正文可以先独立接受，但不能因此将需求10的富文本/引用接受标为通过；共享生成编辑器未接入期间，其正文和输入版本由原业务保护。富文本算法选择须以实际文档、Go/前端交叉向量和性质验证为依据，不因仓库已有某个库而默认采用。

### 7.5 客户端B/P/Q协调

B是已确认基线；P是唯一在途批次，保留原始网络body；Q是P之后尚未发送的本页意图。屏幕图由确认基线加协调后的P/Q和短暂手势预览推导，不另存一份可独立提交的整图。

收到他人连续规范变更时，先核对上下文，双向转换远端操作与本地P，继续协调Q，推进B后重算显示。网络上P的原body不可变，内存中可维护用于显示的转换副本，两者不得混淆。

收到自己的规范变化时，以op_id识别并应用服务器最终结果，P只消费一次；不再把自己的操作当他人操作转换第二遍。ACK先到只证明持久结果；仍须取得对应规范变化或包含它的可靠快照，再安全释放后续意图。changes先到也不能重复套用乐观效果。

拒绝P时，Q中依赖P创建对象的意图不能直接发出；重新求值并列出不可继续的部分。能独立保留的编辑可继续协调，不能清空所有Q掩盖丢数据。历史不足按设计15进入查证与快照重建，未确认意图不能整图覆盖新基线。

### 7.6 撤销与素材历史

undo_of指向本人已接受操作。服务端根据规范贡献和必要前像构造逆意图，并跨越其后有效历史转换；再次执行相同undo请求仍幂等。恢复节点、关系或旧素材须重新验证当前权限、对象状态与图合法性。

撤销自己的文本插入只删除自己的贡献，不删除其他人的后续插入；重叠删除、对象已删除、素材不可用或历史不足时允许明确不可撤销。不能把旧整图快照作为协同撤销。重做同样是受当前状态约束的新意图，不复用旧请求ID绕过校验。

操作历史中涉及的素材引用要由素材保留策略保护，不能仅保留临时URL。撤销不会新建生成任务或触发计费。

### 7.7 算法验收与资源约束

定义apply、transform、normalize及inverse的输入输出和上下文约束，Go与前端使用同一组序列化测试向量。对支持集合验证双路径收敛、至少三客户端多步交错、因果顺序、合法意图保留、拒绝回滚和逆操作边界；有意不支持的组合要有稳定错误和理由。

测试不能只比较最终revision或只验证“不崩溃”，应比较规范化内容、节点/边、分组、素材及输入版本。普通字段最后接受的结果正确，也不能证明文本序列转换正确。

历史条数、原子数、转换工作量、时间和内存必须有界；超过预算返回需要重同步或明确冲突，不持锁无限转换。具体预算按设计14容量场景测量后固定，不能删历史后盲目转换。首轮不为避开验证引入无限历史客户端缓存或另一个协同服务。
