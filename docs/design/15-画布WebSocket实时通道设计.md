# 画布WebSocket实时通道设计

## 1. 摘要

通过WebSocket传输Yjs同步、持久提交、回执和临时协作状态，支持连续编辑、断线恢复及权限变化。

## 2. 参与者

画布客户端、协作服务、Go授权与持久接受服务。

## 3. 背景

来源为[实时同步需求09](../requirement/09-画布WebSocket实时同步需求.md)。共享模型见[Yjs设计](17-画布Yjs协作编辑设计.md)，接受事务见[数据设计](14-画布数据与接口设计.md)。

## 4. 目标

有权限的客户端及时获得已接受变化，清楚了解连接与保存状态，在断线、重连和服务重启后恢复一致内容。

## 5. 使用场景

首次打开、同账号多标签页、多人并发、编辑期间断线、提交回执丢失、权限撤销和服务重启。

## 6. 价值

用户连续创作时能够确认哪些内容已经保存，并在网络恢复后继续同一编辑会话。

## 7. 方案

### 7.1 连接与授权

建议外部连接继续由Go的`coder/websocket`接入，内部JS运行时只处理已授权的房间合同，见[设计17工程边界](17-画布Yjs协作编辑设计.md#70-工程边界与部署建议)。每个画布会话维护一个有效连接，绑定用户、项目、文档、协议版本和epoch。握手检查会话、Origin、项目权限与文档状态；连接生命周期内持续检查授权。跨项目切换释放旧连接、监听和临时状态。

### 7.2 初始化与同步

先完成授权和版本协商，再同步已接受的二进制基线及缺失更新。用Yjs state vector协商差量；初始加载与实时订阅之间保证更新连续。获得可编辑基线后开放写入。

同步、持久提交、回执、拒绝、presence和心跳具有明确消息类型。协议编码与版本在客户端和服务端共用合同中维护。

#### 7.2.1 同步屏障与消息职责

初始化从同一持久读点取得epoch、commitSeq=s和二进制基线，同时安排读取s之后的接受日志；发送sync_complete(s)不遗漏读取期间发生的提交。可先订阅并缓存或从持久日志追赶至明确屏障，再转实时流；缓冲溢出需重建，不能静默跳过。只读客户端只接收已接受状态。

| 消息职责                        | 关键字段/语义                                                                               |
| ------------------------------- | ------------------------------------------------------------------------------------------- |
| hello / ready                   | 协议/schema、文档、epoch、权限与已接受版本；初次未得到基线前不可写                          |
| state vector / accepted diff    | 只交换已接受文档的同步差量；客户端带未确认内容的差量不得作为绕过submit的写入口              |
| submit                          | updateId、epoch、schema、不可变payloadHash、update bytes、依赖/用户动作元数据；身份取自会话 |
| receipt / resolve               | accepted/rejected/not_found/unknown，原ID/hash与commitSeq；resolve只查原操作，不创建新保存  |
| accepted update / sync_complete | 接受序号连续或明确补齐范围；重复可忽略，缺口先追赶再推进已确认基线                          |
| presence / heartbeat            | 临时交互与存活/版本核对；不写回执，不代表数据库接受                                         |
| denied / resync / backpressure  | 明确错误与恢复方向；不得以空图或成功回执代替                                                |

这是消息语义建议，具体名称与版本由共享协议统一；不得把现行Go operation_version=1载荷伪装成Yjs兼容协议。常规Yjs provider的双向同步或同浏览器BroadcastChannel会传播本地更新，不能直接接到要求接受前验证的权威房间；应限制客户端上传只能进入submit，跨标签页也不绕过Go接受。官方[y-websocket说明](https://docs.yjs.dev/ecosystem/connection-provider/y-websocket)只作为实现参考。

### 7.3 编辑与持久确认

提交信封包含文档、epoch、提交ID、载荷哈希及Yjs更新，发起身份取自认证上下文；同一封包记录其覆盖的用户动作身份，批量封包仍原子接受或拒绝，不逐条猜测成功。服务端接受并持久化后返回修订号及原提交回执，随后向有权限客户端广播。

客户端分离已接受基线B与含P/Q的乐观编辑文档；用于同步的state vector必须来自B，不能拿乐观文档掩盖尚未接受的结构。只把服务端已接受更新应用到B，并以受控来源合入编辑文档；回声和远端更新不能再次作为本地用户提交入队。客户端保留有界未确认更新。同步完成只表示内容同步；“已保存”由持久回执确定。心跳单独反映连接状态。

### 7.4 保存队列与状态

可形成共享事务的连续编辑即时进入本地共享模型；尚未获合法上传身份的选择沿设计14保留在独立内存意图中；已获授权的待上传占位可保存，但不得提前写入最终资产引用。未确认提交保留不可变身份和载荷。收到远端更新后合并兼容编辑。UI分别显示连接、未确认数量、保存结果和恢复动作；只读状态保留浏览操作。

临时断线时，最近已获写权限的会话允许本页有界内存编辑；首次未授权、撤权、epoch不符或队列达到上限时暂停新增写入。离开页面时提示未确认内容。画布业务持久存储禁用；个人偏好与其他非业务存储边界见[设计14](14-画布数据与接口设计.md#721-应用可控的客户端存储清单)。

#### 7.4.1 内存队列与“已保存”判定

建议每会话一个已封包在途提交P和有界后继队列Q。P身份/bytes不变；Q继续接收完整编辑事务，P被接受后再封包发送后继。不同会话在服务端按画布接受顺序协调；不以单在途为由冻结正常用户输入。队列上限同时按字节、事务数和编辑恢复工作量限制，满后明确暂停新增写入，绝不shift丢最旧编辑。

保存状态是独立状态机：本页尚未封包或发送为未保存；已发送未有终态为待确认；确定拒绝为被拒绝/需恢复。只有当前会话所有已完成且未撤回的业务编辑均有确定accepted结果、P/Q排空、已接受基线已应用到相关commitSeq、无未解决上传或恢复输入，才显示已保存。初次载入权威基线且无本页编辑也可显示已保存。仅取消本地预览不需服务器回执；已经进入Yjs因果链的撤回须作为新动作确认，不能丢弃字节制造缺失依赖。新输入在旧ACK到达前产生时仍显示未保存/待确认，不能由旧ACK把dirty整体清掉。素材上传成功只表示素材可引用，不代表图绑定已保存。

业务Y.Doc、待发bytes、富文本恢复输入和语义意图只在本页内存；不接入y-indexeddb、迁入的业务journal或localStorage消息备份。个人视图白名单继续允许。离线页面关闭/崩溃损失未送达输入的取舍沿需求08，并在离页时说明。

#### 7.4.2 自动接纳与页面存续

编辑器完成一次可保存事务就入同一队列；不等待点击保存、失焦或静默间隔。若界面保留“立即同步/重试”，它只唤醒或等待该队列；心跳、重连计时器和退避负责恢复，不是第二个整图保存器。草稿字段尚无合法值、IME仍在组合或素材尚未发布时须显示未完成状态，不能因P/Q为空宣称已保存；合法的参数变化也不能只等离页才提交。

接纳前检查事务/内存预算，为正在进行的单次手势或IME保留有界完成空间；达到上限时阻止开始下一次业务编辑并说明原因。单次粘贴/导入超限须在改变共享文档前明确拒绝，不能先在界面显示成功再丢弃。已有P/Q和恢复输入不被驱逐；异常期间只读浏览仍可用。具体上限在实施前明确并测试，不承诺无限离线输入。

编辑会话键包括账号、空间、项目、documentId、epoch和本次编辑会话身份；WS另带连接世代以隔离旧连接回调。正常重连不更换编辑会话、不清空P/Q或素材回执，也不把连接世代加入不可变提交身份。ACK/远端消息核对当前连接世代；上传结果核对原编辑会话及目标生命周期，再按当前权限接入，不因同一会话正常重连便丢弃已成功的素材回执。续期回调同样核对账号/会话是否仍有效。切项目/应用内路由离开前，有未决内容时提供留页继续恢复或明确放弃内存输入后离开的选择。主动退出账号或确认切账号时销毁旧私有状态；明确失去读权限时立即停止展示/接收并清理旧内容。仅失去写权限但仍可读可保留本页恢复输入供查看，不能再发送；同账号短暂凭据失效只冻结发送，不按普通断网继续扩张输入。

刷新/关闭可用beforeunload提示，但不能保证浏览器一定显示或等到ACK；不使用sendBeacon、keepalive HTTP或后台同步另开保存路径。页面隐藏不等于完成提交；页面重新显示或从浏览器页面缓存恢复时先验证会话/epoch再开放写入，不信任恢复出的旧权限。关闭后只能承诺读取服务器已有事实。

### 7.5 重连与拒绝恢复

采用有界退避重连。重连先验证授权与epoch，查证原提交结果，再补齐已接受状态与缺失更新。重复回执和更新幂等处理；未知提交沿原身份与载荷查证或重试。

访问凭据过期（`401/access_expired`）通过统一会话续期协调器恢复；HTTP Cookie续期不会更新已建立WebSocket的握手凭据，因此续期后须关闭旧连接并重新握手。每次授权恢复只自动续期一次，重新获得ready后恢复预算；连续过期、续期失败或明确撤权分别保持可见失败并支持适当重试。页面关闭或账号/空间切换取消等待，禁止旧续期完成后复活连接。未确认保存保留原client/op身份、基线和载荷，重连先resolve，不得当作新保存发送。

拒绝更新及依赖它的后续编辑转入恢复状态：重建已接受基线，保留可供用户恢复的本页内容；只有通过验证的后续意图才能重新提交。恢复过程由[设计17](17-画布Yjs协作编辑设计.md#73-合法接受与恢复)定义。

显式重新应用必须绑定用户刚查看的服务器版本。Go操作协议过渡阶段使用不可变提交字段`strict_base=true`：服务端先查既有回执，再在同一文档行锁事务内校验`base_revision`等于当前持久版本；不相等则持久记录`review_stale`拒绝，不转换成覆盖新版本的写入。该字段计入原请求身份，查证与重试不能移除或修改。用户重新查看后才可用新ID提交；客户端检查不能替代这个服务端约束。Yjs阶段仍须在epoch、writerTerm与候选接受边界内保证等价的审阅版本约束，不将此标量协议当作Yjs实现。

#### 7.5.1 确定与未知结果的恢复顺序

重连先恢复并核验同一账号/空间/文档的当前权限、协议和epoch；通过后暂停发送Q，查证原P并追赶已接受基线。下表区分查询结果和传输故障，不能都用“重新保存”处理。

| 情形                        | P与后继输入的处理                                                                                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 同epoch、accepted           | 保留原回执；B补齐到至少该commitSeq后才完成P，随后发送依赖完整的Q；重复或迟到ACK幂等处理                                                                      |
| 同epoch、rejected           | 原P为确定终态，进入设计17的依赖重建；不能改P字节再复用原ID                                                                                                   |
| 同epoch、权威查询not_found  | 在当前授权/版本有效时原ID、原hash、原bytes重试；与仍在执行的原请求竞争时由持久幂等保证同一效果                                                               |
| 查询超时、暂不可用或unknown | 保留原P及Q，不宣称拒绝/未提交，不生成新ID；有界退避查证，用户可留页重试                                                                                      |
| epoch已改变                 | 有当前读权限时查证旧epoch原P，保留曾经accepted的历史事实；加载新epoch基线，不发送旧P/Q，不把旧accepted当新epoch写入。未接受/后继意图仅在本页恢复区供显式处理 |
| 身份或访问范围改变          | 不向新账号/画布发送旧P/Q或回执；按7.4.2隔离与清理，禁止以恢复输入为由绕过授权                                                                                |

仅缺增量历史时从持久checkpoint和后续日志重建B；不因为采用全量同步就把epoch或提交ID换掉。若确需转换epoch，则执行上表的谱系隔离，不能悄悄把旧队列套入新文档。

健康连接也需按超时/心跳版本线索查证长期未决P，防止只在断线后resolve。这是同一队列的恢复动作，不是定时发整图保存器。查证必须校验当前权限；访问已撤销时不为了保留输入泄露已失权内容。

### 7.6 临时协作状态

presence承载在线成员、光标、选择与拖动预览，按文档授权隔离，设置频率、尺寸和过期时间。断线或超时后清理；个人视口由各端独立控制。服务端按认证连接绑定presence身份，不信任客户端冒充他人；只向仍有读权限的订阅者投递。光标使用画布坐标，文本选区使用协作绑定的相对位置。presence丢帧可覆盖旧值，业务提交与回执不可丢弃；二者采用独立背压策略。

### 7.7 资源与运行

限制报文、连接队列、未确认更新和恢复工作量；慢连接明确进入重连恢复。服务重启从持久基线恢复，旧实例通过writerTerm及持久版本门禁失去写权限；普通owner接管不改变文档epoch。慢客户端无法追上时断开并显式要求补齐，Outbox不能无限占用单连接内存。

前后端、worker、relay及协作应用服务通过Docker启动，复用现有基础依赖。健康检查覆盖应用依赖及协作可接受状态；日志记录文档、提交身份和终态，保护凭据与私有正文。

## 9. Yjs 协议4接线

协议3保留未转换画布的既有操作服务；协议4只通过同一Go WS入口接入私有Yjs计算。逐画布转换后旧协议收到 `collaboration_upgrade_required`，数据库门禁拒绝旧通道写入。消息字段、完整快照资源上限与部署开关见[设计17 §10](17-画布Yjs协作编辑设计.md#10-go-正式入口的第二阶段接线合同)。

完成事务触发 `yjs_submit`，心跳与重连触发不可变原请求的 `yjs_resolve`；客户端没有定时保存轮询。接受事务后先发送当前授权快照再发送原提交回执；广播/快照不替代原回执。显式恢复提交带 `reviewSeq`，在当前epoch/writerTerm围栏内检查审阅基线。旧epoch未决请求只在原身份下查证，已知终态后归档可读输入；不把重连当作重新执行旧更新的许可。只读但仍有读权的页面可以查证P，失读权则停止投递并释放内容。


### 9.1 历史与在线光标消息

协议4增加 `yjs_history`（按 revision 游标列出30条元数据）、`yjs_version`（读取授权只读版本）和 `yjs_restore`。恢复携带不可变命令 ID、页面 sessionId、目标版本 ID、审阅 epoch/commitSeq；当前基线变化返回 `review_stale`，客户端重新审阅后才能生成新命令。未知结果沿原命令在服务端心跳/重连时重试；已接受结果先按当前读权限查原回执。控制命令错误不得误拒绝同时等待的普通业务提交。

`yjs_presence` 与业务更新隔离，仅包含服务端认证 actorId、连接 clientId、画布世界坐标与更新时间，不进入业务状态、版本、回执或浏览器业务存储。客户端最多100ms发送一次末值，服务端最多80ms接受一次位置更新；5s服务端心跳保持活跃，15s无活跃会话不再展示，断开连接立即移除。每房间最多128连接、单实例最多1000房间；相同画布的重复活动 clientId 被拒绝。当前房间在单API实例内存中，跨实例在线状态不在本批验收范围，不能据此宣称分布式 presence 已完成。
