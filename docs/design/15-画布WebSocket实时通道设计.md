用户补充（2026-10-21）：画布只使用后端WebSocket长连接完成编辑提交、确认和权威变化推送；参照Lucky核对设计，从手势所有权、保存队列和权限状态根因修复拖动抖动、回弹及无法继续拖动。不得以HTTP保存兜底或另设定时保存器。

### 3.6 需求原文与规则：原始需求与问题

来源：原需求《09-画布WebSocket实时同步需求》第1节。

用户要求“画布数据更新使用WebSocket建立连接，为后续多用户协同工作建立基础”。本需求回答：**变化怎样到达其他客户端，连接中断后怎样恢复，用户如何知道当前同步状态。**

“本地连接”暂按浏览器与当前部署的画布后端建立长连接理解，本地开发连接本地服务；不推定为设备间P2P或独立桌面服务。

### 5.2 产品定义：体验与状态

来源：原PRD《08-画布WebSocket实时同步》第6.1节。

连接→授权→订阅、快照和增量追赶→ready→可编辑。ready仅代表追赶完成；有在途或缓冲内容时保持待确认。临时断线只暂停发送，保持已确认可写权限和页面内意图；首次未授权、明确失权或无法安全协调才暂停编辑；重连先查原终态、补齐基线再发送后继；撤权清除私有画面，归档维持授权只读。具体状态与错误按上游设计第3、6节，不另建原型或第二套业务规则。

| Why：为什么              | 无需刷新就能看到变化，并能判断自己的编辑是否已保存。                                    |
| What before：现在怎么做  | 现有画布尚无本专项的完整双向WS与恢复验收证据，不能把HTTP保存加通知当作目标已完成。      |
| How：如何改善            | 统一连接生命周期、连续版本补齐、持久回执查证和明确保存状态。                            |
| What after：之后得到什么 | 及时获得权威变化；断线不误报成功、不换ID重复提交；撤权后停止私有消息。                  |
| Alternatives：替代方式   | 手动刷新或轮询无法满足本次明确的双向WebSocket要求；使用已有Go进程避免增加独立网关服务。 |

## 7. 方案

### 7.1 现行保存与交互合同（2026-10-21）

来源：原设计《15-画布WebSocket实时通道设计》文首。

1. 打开画布后建立一个已鉴权的WebSocket；节点及创作输入编辑、持久回执与权威变更通过同一连接传递。HTTP只承担适用的初始/恢复读取、身份与素材等职责，不另设画布HTTP保存兜底或周期保存器。
2. 完整编辑事务立即入协调器；可发送且没有在途请求时立即提交。已有在途操作P时，后继意图Q只在页面内存排队；原P的编号和载荷冻结，确认后再按设计17转换、合并并发送Q。取消900ms静默等待，不在pointermove中发送位置；中文组合输入结束后提交完整事务。
3. 服务端持久化并推送确认与权威变更。心跳核对版本、权限及连接健康；有未决P时以原编号和原载荷查证，覆盖连接健康但应用层ACK丢失；没有未决操作时不空写。ready、heartbeat和快照均不能单独表示本地编辑已保存。
4. 传输在线状态与最近一次权威可写许可分离。首次授权前不可编辑；临时断线仍可在当前页面编辑，恢复后先核实P、补齐基线再发送Q。明确失权、身份切换、拒绝或不能安全重同步时停止新编辑。页面内后继队列按序列化字节数限制1MiB，超限保留已有意图并进入可见恢复处理；刷新、关闭与崩溃不承诺恢复未送达内容。
5. 节点只发起拖动，画布持有整次手势的pointermove/up/cancel；节点外松手同样结束，失焦、页面隐藏与卸载清理监听和预览。预览坐标与文档坐标分别持有，远端更新和迟到回执不能覆盖当前预览；松手消费最终坐标，形成一次编辑，结束后必须能再次拖动。视觉与创作栏细节见[设计10](10-画布组件实现调研与迁入设计.md#726-长连接保存与交互权限分离)。
6. 显式保存和生成前flush只等待同一队列的服务端确认；断线时不能将未确认草稿当作生成来源。默认全能参考、精简参数弹层与去掉“需要调整”的界面规则仍由设计10维护，不在连接状态中追加冗余说明。

协议2的操作、增量、终态回执及B/P/Q转换按[设计17](17-画布OT处理设计.md)；真实故障验证和工程门禁按[设计15第8.12节](15-画布WebSocket实时通道设计.md#812-唯一长连接保存与连续拖动修复2026-10-21)。单实例、本地真实项目证据不代表全站状态轮询已经改造。

### 7.2 方案比较与选择

来源：原设计《15-画布WebSocket实时通道设计》第2节。

| 方案                                  | 价值、成本及限制                                      | 结论                       |
| ------------------------------------- | ----------------------------------------------------- | -------------------------- |
| 现有Go＋coder/websocket，同站升级代理 | 复用业务授权及事务，满足双向通信；需补实际Upgrade路由 | 用户已选库，采用此接入建议 |
| 独立连接服务、跨实例广播框架          | 当前没有容量证据证明必须增加组件                      | 不预建；未来多实例须补证   |
| HTTP写入＋WebSocket只发通知           | 不能满足上行编辑也走WebSocket的原要求                 | 不作为需求完成方案         |

新增一个画布WebSocket入口，建议路径`/api/canvases/{id}/live`，连接绑定一个画布。生产使用同站wss，本地使用同一业务路径。现有Gin完成会话和来源检查，再用coder/websocket处理升级与收发；继续复用画布应用服务。

[coder/websocket官方API](https://pkg.go.dev/github.com/coder/websocket)提供Accept、Read/Write、SetReadLimit、Ping及关闭能力，采用[ISC许可](https://github.com/coder/websocket/blob/master/LICENSE.txt)。本轮锁定v1.8.15，已接入双向命令与数据库回执。它不提供画布房间、数据库保存或OT，这些由我们的少量业务代码负责。

现有[Next Route Handler](../../frontend/src/app/api/[...path]/route.ts)为fetch型HTTP代理，不能假设可透传Upgrade。部署入口须将该WebSocket路径转发到Go，保持同站Cookie和原始Origin，其他HTTP路径沿现有BFF；不为此引入新业务服务。[升级代理说明](https://nginx.org/en/docs/http/websocket.html)仅为配置参考，不代表选定或已有NGINX。此路由是实施必须补齐的一项部署工作。

最小运行范围为一个承接画布实时连接的Go实例；内存仅保存连接、订阅和发送队列，数据库仍负责权威顺序。不预建跨实例房间或Kafka广播；现有outbox继续其原职责。多实例同时承接画布连接不在本版接受范围，实际发布需要多实例时须先补通知分发验证，不能直接扩副本宣称已支持。

### 7.5 消息合同

来源：原设计《15-画布WebSocket实时通道设计》第4.2节。

采用JSON消息，固定一个操作模型版本；`op_id`为UUID，复用现有幂等键。初版revision保持当前数据库整数范围。只定义完成闭环所需消息，不引入多套schema协商或快照分片协议。

| 方向与消息                  | 最少内容与行为                                                                                                                                                               |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 客户端join                  | scope_id、operation_version、last_revision（初次为空）、pending_op_id（若有）；scope只是范围选择，不是授权凭据                                                               |
| 服务端ready                 | revision；初始化或恢复追赶已连续到该版本，允许进入实时订阅；编辑仍须快照/权限状态可写且无恢复阻断，并不确认其他pending                                                       |
| 服务端snapshot              | document及revision、当前可读/可写状态；节点边来自数据库一致性读取                                                                                                            |
| 客户端submit                | op_id、base_revision、operation_version、commands；原信封一经发送不可修改                                                                                                    |
| 服务端ack                   | actor_id、op_id、operation_version、接受revision、规范命令及必要结果；仅数据库提交后发送，不广播回执中的整图或内部前像                                                       |
| 服务端changes               | from_revision、to_revision、有序日志项（revision、actor_id、op_id、operation_version、commands），仅投递客户端需应用的规范效果，不广播内部撤销前值；客户端按revision连续应用 |
| 服务端reject / error        | reject为已持久化的业务拒绝（op_id、原因、observed_revision）；error为入口/连接错误或结果未知，不能让客户端把未知结果当终态                                                   |
| 客户端sync / 服务端同步响应 | 客户端提供last_revision及pending_op_id；服务端返回该用户回执结果（accepted/rejected/not_found）、changes，历史不足则返回snapshot及重同步原因                                 |

握手成功后须完成join授权才发送私有图。ack可与changes重复，客户端按revision和(actor_id,op_id)识别已处理结果；ack提前到达只确认保存，缺失的前序版本补齐后再推进本地权威基线。查回执返回not_found只表示当前未查到，不证明原提交不会随后完成；使用原请求再次提交，由数据库幂等锁裁定。

连接URL绑定document_id，join范围必须与其项目一致；submit无需重复传文档ID，服务端补入完整信封及请求hash，重复提供且不一致时拒绝。ack与changes使用同一操作身份和版本，不能依赖连接身份猜测别的标签页操作。

已有HTTP初始化读取、上传、登录刷新和项目管理继续存在；正式画布编辑上行、保存确认及其他客户端的增量均走WebSocket。HTTP残留写入必须沿数据设计14提交，不能保留另一套绕过权限或版本的保存路径。WebSocket消息仅包裹必要同步元数据并复用业务命令类型；不把它伪装成HTTP OpenAPI接口，也不在本轮预建通用协议生成框架。

回执状态由数据设计14唯一规定：accepted/rejected是持久终态；not_found不是拒绝。终态重复返回原结果，不能在拒绝响应丢失后又接受同一操作。已认证且操作版本可识别的base_future/history_unavailable/order_conflict均为持久reject；读取回执需当前读权限，归档只读用户仍可查自己此前已提交的结果，无读权限不返回私有结果。模型版本必须在join及submit检查，未知操作不跳过；重新修改命令使用新op_id。

### 7.6 数据、状态与一致性

来源：原设计《15-画布WebSocket实时通道设计》第5节。

1. 授权后先登记画布订阅，再读一致快照R。订阅期间的变更只记录“需要追赶”提示，在数据库取固定水位H，读完R到H的连续日志后发送ready(H)，再从H之后追赶；始终按revision排序。避免“有快照就可编辑”及初始化窗口漏更新。
2. 客户端在内存显示编辑，最多一个批次在途，其余编辑留在内存缓冲。服务端调用现有事务提交路径；成功后ack，并唤醒该画布所有授权连接按revision读取changes，不直接按提交回调先后乱序广播。
3. 所有服务端接受的画布变更在事务提交后通知本进程订阅者；正式页面编辑只经WebSocket提交，后台业务结果沿同一权威事务更新，不另设前端HTTP保存路径。为覆盖提交成功但通知丢失，连接心跳时核对数据库head；发现落后就补读日志。无须为这一兜底新增消息基础设施。
4. 临时断线后显示重连中与待确认，仅暂停发送、保留已确认可写权限和页面内意图；明确失权或无法安全重同步时暂停编辑。重连重新鉴权，先核实pending_op_id，再补缺失日志；未确认原请求只能原样重试。
5. 日志不连续、基准过旧或操作模型不兼容时读取snapshot。已接受的pending不得再次执行；其他意图按设计17重建或明确提示冲突，不用旧整图覆盖服务器。刷新后没有内存基线，直接读取数据库快照。重同步的ready只表示权威基线就绪，pending处理完成前仍禁止自动发送新批次。

连接状态为连接中/已连接/重连中/无权访问，保存状态为未保存/待确认/已保存/被拒绝，两者分别显示。有待发送内容时不能仅凭另一批ack显示“全部已保存”。断线、拒绝和历史不足均保留当前页面可查看的未确认内容；账号切换或撤权时清理旧账号私有内存。

每连接同一时间只有一个初始化/补齐任务；新的sync合并进当前追赶，不能并发发送两份不同基线。重复/较旧revision忽略，revision跳跃先缓冲并请求sync，缓冲达到上限则重同步。恢复时回执与快照/日志不能互相覆盖：即使快照版本更高，仍要用操作身份查清原提交。

submit/ack/changes沿[设计17第7.6节](17-画布OT处理设计.md#76-纯文本与实际富文本规则)的类型化序列及第4.6节字段操作传递，不发送Tiptap/ProseMirror Step或整份composer作为普通编辑。服务端生成的input_revision、新增引用的权威编号、删节点的槽清空/资产固定均包含在同一revision规范效果中；客户端按referenceId/子对象ID协调，临时标签不成为协议身份。快照继续使用现有JSON结构。设计14第7.8节识别的未知/损坏图在join时给出只读原因，ready只确认追赶完成，不将只读状态改成可编辑；只读订阅仍受权限控制，不能通过旧HTTP入口绕过写入限制。

新增持久字段及终态回执均引用设计14，不另定一套存储；单实例订阅只保留连接与版本游标。所有改变客户端可见状态的写入，包括归档/后台结果，必须可通知或被head/权限检查发现。没有规范日志的段落只允许安全快照恢复，不能作为OT转换历史。

### 7.7 异常、安全与恢复

来源：原设计《15-画布WebSocket实时通道设计》第6节。

- 会话沿现有Cookie认证，握手严格验证允许的Origin；不把token放URL。用户身份由服务器取得，客户端不能指定actor。归档仅允许读。
- 每次提交及每次实际发送私有数据前重新检查当前会话、范围和项目权限；撤权后清理队列并关闭。空闲连接按有界权限检查周期核对并处理撤权，该周期须在发布前结合身份合同确定；每次发送前的授权检查为投递判定点，已经写入网络的字节无法撤回。
- 会话过期关闭连接，沿既有HTTP续期后重连；socket心跳不自动延长账号活跃期限。只读权限改变必须更新编辑状态。
- 每连接一个读取循环和有界有序发送队列，受服务生命周期context管理，关闭时释放订阅、队列和goroutine。使用库的读限制、发送超时及Ping；不要把已结束的HTTP请求context当成长连接生命周期。
- 复用现有100命令批次边界，设置Ping周期、读写超时、最大消息字节和有界发送队列。前版30秒/10秒/1MiB/64条/8MiB没有本项目测量依据，移出设计承诺；实施前用真实合法节点样本和代理时限确定配置基线。
- 快照最大字节数单独按现有最大合法画布样本确定，不能将单操作消息上限误套为整图容量；超过已验证容量要明确返回容量错误，不截断。此容量未关闭前不能接受全部节点恢复。慢客户端队列满则关闭并重同步，不静默跳过增量；不预先做自定义分片。
- 重连采用有上限的退避和抖动，停止重复计时器。服务退出先停止新连接，有界等待在途事务并断开连接；未收到ack不代表未提交。

参数是设计建议，实际代理超时、Cookie路径、scope解析及身份模块当前改动须在接入时联合验证。记录连接数量、关闭原因、保存/远端可见延迟及补齐失败，不记录凭据和完整提示词。

| 失败分类                        | 结果与恢复                                    | 验证                                     |
| ------------------------------- | --------------------------------------------- | ---------------------------------------- |
| 输入格式/版本不支持             | error；不应用未知命令，提示升级或调整         | 旧客户端/恶意帧，AC-SYNC-03、04          |
| 图约束/受保护字段等确定业务拒绝 | reject与持久终态一致，整批不生效              | 拒绝响应丢失后重试，AC-SYNC-02           |
| 超时、断线、提交结果未知        | 保持pending，原op_id查证；不换ID重发          | 提交前后各断点，AC-SYNC-02               |
| 历史缺失、乱序或慢消费          | sync/快照；停止继续套用操作；队列满断开再恢复 | 不丢pending、不丢中间版本，AC-SYNC-03    |
| 撤权/过期/账号改变              | 停止新私有投递、清队列、关闭或只读            | 投递前授权判定和既定检测窗口，AC-SYNC-04 |

### 7.18 需求原文与规则：同步、权限与状态合同

来源：原需求《09-画布WebSocket实时同步需求》第5节。

- **BR-SYNC-01：连接、编辑权限与保存状态分开。** 临时断线不等同于失权；编辑事务在可发送时立即进入唯一写队列，心跳仅核对状态并查证未决回执，不替代业务确认。 连接成功不等于保存成功；“已保存”的唯一规则引用需求08的BR-DATA-07，本需求负责准确呈现。
- **BR-SYNC-02：初始状态与后续变更连续。** 初始化期间发生的提交不能遗漏；重复、迟到或缺失消息有明确检测与恢复行为。每文档的持久接受顺序由权威提交路径提供，不能由消息到达顺序臆造。
- **BR-SYNC-03：重试沿用同一操作身份。** 本需求负责识别未提交、已提交未确认与被拒绝结果，并使用需求08的持久幂等能力；不得把重连变为重复编辑、生成或计费。
- **BR-SYNC-04：历史不足可重建。** 读取需求08提供的一致状态和恢复资料；页面中未确认的操作不得直接覆盖新状态。没有OT时可保留内存并提示冲突，有OT时按需求10转换；无本地持久草稿的取舍引用需求08的BR-DATA-08。
- **BR-SYNC-05：权限覆盖整个连接生命周期。** 连接、订阅、每次提交及新消息投递须符合当前账号和资源权限；失效、切换账号、撤权及归档按已有身份合同处理，撤权生效窗口待设计。已建立连接不得永久绕过权限检查。
- **BR-SYNC-06：被拒绝结果可理解。** 服务端拒绝写入时，不广播为成功变更；前端显示原因并恢复或保留未确认内存状态，不能误报已保存。

IR-SYNC-01：设计需要覆盖连接鉴权、订阅、初始状态与实时增量之间的无缝衔接、提交、确认、拒绝、重连补齐和历史不足时重建。消息字段、心跳、限流、背压和协议版本属于设计，不在本稿预先定死。

IR-SYNC-02：本地开发与生产部署采用相同业务语义；生产使用安全连接，并核验来源与授权。断线、身份过期、权限撤销、旧协议客户端与服务重启必须有可观察结果。

WebSocket的双向通信职责参考[RFC 6455](https://www.rfc-editor.org/info/rfc6455/)，业务消息、确认与恢复合同仍需后续设计。它不承担OT操作转换。

## 8. 实施与验收

### 8.1 本轮实施边界（2026-10-20）

来源：原设计《15-画布WebSocket实时通道设计》文首。

历史记录：以下为2026-10-20协议1的实施边界，不再作为当前协议或断线编辑规则；当前合同见下节与设计17。用户当时授权闭合现有数据库命令协议：`coder/websocket v1.8.15`、同源 `/api/canvases/{id}/live`、一个 Go 实例、PostgreSQL 权威存储。上行 `submit {op_id,body:CommandsInput}` 真正执行数据库事务；提交后 `ack {op_id,revision,result}`。`join {protocol_version:1,scope_id,csrf_token}` 后先收到 `snapshot {revision,document,writable}` 再收到 `ready`。后续 `sync`、心跳和提交通知均重新授权并读取数据库；此阶段发送权威快照，不虚构规范增量日志。

断线仅保留页面内存中的原 key/body；重连 `resolve {op_id,body}` 查询同一 actor/document/hash 的持久成功回执，存在则返回原 ack，不存在返回 `not_found {op_id}` 后重发原请求。没有回执不代表失败；版本冲突返回 `error {op_id,status:409,code:revision_conflict}`，停止自动提交并保留对照内容。错误拒绝暂不落独立终态表。绝不将旧编辑自动改绑到新 revision，也不把心跳、ready 或快照当保存成功。

每5秒进行 Ping/Pong 与数据库版本/写权限核对，写入及 Ping 超时5秒、单次数据库操作超时10秒；客户端20秒无消息重连。入站帧最多1MiB；客户端先按完整信封UTF-8字节数校验，超限不发送、保留内容并暂停自动重试；快照最多16MiB，超限明确关闭而不截断。每个连接一个持续 reader、一个串行处理/writer、最多一个待处理业务消息；sync提示合并，业务队列满则断开并在重连后查原回执，reader不等待队列以免阻塞Pong；通知每连接至多一个合并信号，不缓存权威画布。参数为本地最小实现的可调整上限，不能作为生产容量承诺；大画布/多实例仍须测量。

同源 Cookie 和严格 Origin 在 Upgrade 时校验，join 的 CSRF/范围以及每次私有投递、命令和心跳重新验证；心跳与后台重连的授权探测不延长会话闲置期（探测复用现有GET画布接口，不调用会记录UserActivity的GET session）。归档转只读、丧失读权限断开并清除页面私有数据。连接中断仅暂停发送，已授权画布仍可编辑，草稿与原操作保留在当前页面内存；明确失权或身份变化才停止新编辑；干净页面应用新快照，有未确认请求先查原回执，有本地改动则进入显式冲突对照。

OT 继续独立：本轮沿用 CAS 拒绝过期版本，不能自动合并并发文字或字段编辑。原文中的 `changes`、类型化操作、拒绝终态与 OT/增量恢复仍是后续能力，未实现前不勾选设计15全部验收；本轮验证只覆盖上述 CAS＋快照闭环。Mock 预览继续仅页面内存，正式画布不引入浏览器持久存储。
