# 模型商业计费与积分钱包设计

日期：2026-11-05。状态：评审稿，商业数字与新规则均为建议，未发布。来源：[SRC-CREDIT-01、FR-CREDIT-01～06](../requirement/21-模型商业计费与积分系统需求.md)。外部依据：[竞品研究](../research/2026-11-05-模型计费与积分竞品研究.md)。

本设计是[PRD23](../prd/23-模型商业计费与积分系统.md)的唯一来源；执行由[Plan32](../plan/32-模型商业计费与积分系统实施计划.md)持有，状态与决策依赖仅见[BACKLOG](../../BACKLOG.md#commercial-credits)。[设计34](34-积分消耗系统与模型真实计价体系设计.md)继续拥有计量、报价冻结、结算证据与原消费恢复。

## 1. 摘要

推荐采用“统一积分标尺、逐模型销售定价、预付积分钱包、独立会员权益、项目预算双重准入”。先实现可追账的按量消费和购买积分，再开放周期会员。用户可以不买会员而购买通用积分；不以会员资格阻断已购通用积分使用。

建议继续1元=10积分，底层保留CNY微元，不把每次消费向上取整为整数积分。模型成本与销售价格分开记录；会员、赠送和充值按批次分开，不把项目管理员设置的预算限额当充值资金。模型充值、现金退款、消费返还、预留释放各有独立事实。

## 2. 参与者

| 角色           | 权限与价值                                                         |
| -------------- | ------------------------------------------------------------------ |
| 个人创作者     | 在自己的付款账户消费，查看原价、预留、实扣及积分来源               |
| 团队付款管理员 | 购买组织积分，设置项目/成员预算、查看组织订单；不能读取供应商秘密  |
| 团队成员       | 在授权项目限额内消费组织余额，不把组织积分转入个人账户             |
| 模型管理员     | 审核采购计量与销售价格版本；无权仅凭改预算给钱包充值               |
| 财务/核查人员  | 处理对账、退款与补偿；异常人工调整需理由和独立复核，不可删除流水   |
| Agent          | 在绑定账户、项目及批准上限内申请子消费；没有发行积分或自主充值权限 |

责任人姓名未指定；最小权限复用现有组织/项目授权，不另造一套身份系统。

## 4. 目标

1. 一次授权对应一组可复算、可限额、不可重复派发的消费。
2. 任一余额可追溯到支付、周期权益、赠送或补偿来源；资金与项目授权同时满足才消费。
3. 批量短剧与Agent可看到已知总额、未知项和最高批准支出，不把成片时长当生成成本。
4. 支付重放、并发、批次过期及迟到退款不导致重复入账或负可用余额。
5. 可按模型/渠道核算实际贡献利润，促销和免费模型必须有成本承担方。

## 5. 使用场景

- 首次试用：领取一次性试用积分，仅适用明确的低成本模型，耗尽后自主购买通用积分。
- 单次生成：改模型、数量、时长或参考后更新报价；确认看到的最高支出后执行。
- 制作一集：查看分镜图片、视频尝试、配音及Agent成本预算，批准总上限；执行中逐项冻结并累计。
- 团队协作：成员有余额却被项目限额拦截时，找团队管理员；上游欠费时不引导成员重复充值。
- 异常恢复：取回原结果；未知费用显示核查与冻结额；已实扣消费的返还显示独立补偿记录。
- 会员取消：关闭下期续费不立即撤销本期已购权益；历史订单和剩余通用积分可查询使用。

## 6. 价值

创作者能回答“为什么扣、扣了多少、用的是哪笔积分、失败是否返还”；团队能控制一集/项目/成员的投入；平台能区分销售收入、供应商成本与促销补贴，避免零加价同时承担无限赠分、重试和存储费用。

### 7.2 成本、销售与利润

每个可消费发布绑定：供应商模型/区域/渠道/模式、采购计量版本、销售规则版本、输入参数约束、冻结汇率、积分比例、有效期、审核来源、最高支出政策、用量证据和付款账户。新价格追加版本，在途任务不随目录变化重算。

采购成本C是供应商实际应付；销售金额P是用户按冻结销售规则承担的面值；充值实收R不是积分面值V。赠分不产生现金收入。会员价、赠分、支付渠道费用均影响有效回收率。采用以下测算口径，金额须统一税务口径后比较：

```text
r = 对该销售面值实际分配的净收入 / 已消耗积分面值
贡献利润 = r × P − C − 可变平台成本O
贡献利润率 = (r × P − C − O) / (r × P)
目标零售面值 P >= (C + O) / [r × (1 − 目标贡献利润率g)]
```

净收入扣除支付手续费、现金退款和相关税费；O包含归档/分发、审核、平台承担的失败重试等可变费用。固定研发、人力不在该贡献口径中，不能把它当公司净利润。销售计量仍沿唯一计价引擎，不为财务复算建第二套用户扣费算法；采购单独按原用量与冻结采购规则计算。

建议用30%作为试运行测算目标，比较20%/30%/40%的售价与竞品竞争力，再逐模型评审；不是已测得利润。赠分和折扣全部按100%兑换做压力测算，不依赖积分过期获利。模型未通过真实计量和成本验证，不因存在目录单价而启用。

**纯算术样例，非现行价表**：C=0.12元、O=0.02元、r=1，目标30%，P至少0.20元＝2积分。若只按成本乘1.3，P=0.156元，扣除O后贡献率约10.26%，不是30%。若充值满100赠10%的积分，r至多1/1.1，原P=0.20元的贡献率降为23%，尚未扣额外手续费；因此首版不做充值赠分叠加。

Flash历史报价0.12元＝1.2积分是既有限定实例；将其商业售价改为0.20元必须另发布并确认，不能修改历史价格或把本例自动上线。

| 类型                        | 采购与可信计量                                            | 对用户的销售表达                            | 准入与结算                                                               |

| 本地Codex/BYOK              | 用户自己的供应商费用不属于平台采购                        | 上游自付；若平台收托管/存储服务费需独立报价 | 默认不重复扣模型积分；个人BYOK仍须独立接入验收，本设计不宣称已支持       |

### 7.4 精度与报价体验

- 1元=1,000,000微元；1积分=100,000微元。金额存int64，中间计算big.Rat；API精确微元用十进制字符串，避免JavaScript安全整数问题。
- 1微元=0.00001积分。积分详情可显示最多5位小数、去尾零；默认2位，正数小于0.01显示“<0.01积分”并可展开精确值，绝不显示0。只在最终金额计算边界取整一次，不逐项向上取整成整数积分。
- 保留旧`EstimatedCredits`供既有消费者，新增精确投影字段消费后再迁移UI；不改变旧字段语义。新字段和API合同由设计/生成类型实施时统一确定。
- 默认生成按钮附近只显示“预计1.2积分”；展开显示模型、数量、实际扣费规则和“最多1.2积分”。估价未知显示“费用待确认”，不显示免费。
- 固定价生成一次明确确认；Agent已批准的预算内不每步弹窗，但每个子消费仍由服务端准入。修改输入、模型或超上限时重新报价确认。
- 余额区默认显示可用；展开分列冻结、近期到期及三类来源。缺模型权限、项目限额、平台上游欠费、速率限制与钱包不足使用不同提示；仅钱包不足指向充值。

### 7.5 积分来源、期限与扣款

| 积分类型              | 建议发放                                             | 有效期                         | 限制/返还                                        |
| --------------------- | ---------------------------------------------------- | ------------------------------ | ------------------------------------------------ |
| 购买积分 paid         | 支付成功并核验后，按冻结商品面值入账                 | 不设到期，不依赖会员续费       | 不转赠、不提现；现金退款走原支付订单及已审核条件 |
| 会员周期 subscription | 每个已付款权益周期发一批；年付也逐月发，不一次发全年 | 该月权益周期，采用显式起止时间 | 关闭续费保留本期；不把购买积分一起清零           |
| 赠送 promotional      | 首次试用、运营活动、明确的平台补偿                   | 每批公开到期时间；试用建议7天  | 来源、适用范围、总预算可追踪；不能合成付费余额   |

默认在**符合模型/项目范围**的批次里先到期先使用；同到期时间按赠送→会员→购买，再按批次ID稳定排序。购买积分无到期，自然最后消费。首版不提供用户自定义顺序，确认明细可查看分摊。任何限定额度必须显示适用范围，不能在通用可用余额中制造“有余额却不可用”。

确认事务锁定批次分摊。已预留部分即使跨过到期时间，也允许原任务按冻结分摊结算；到期仅销毁未被预留的可用部分。释放或补偿返还按原来源/原分摊回溯，不把赠送转换成购买积分：原批次未到期则回原批次；已到期则新增同范围、可追溯的补偿批次，仅恢复本次被占用/扣除金额。建议在该来源链首次到期返还时给一次7天宽限，持久化root_lot_id、grace_used和固定grace_deadline；所有后继批次继承，重放、再次占用/取消或再次返还不能延长。超过该期限不自动再发，平台责任延误交人工核查。不得用每次取消重新计算“当前时间＋7天”。

周期以商品冻结的`period_start/end`为准，按Asia/Shanghai日历月周年生成，月底取该月最后一天；同一订阅周期使用唯一键，重试不重发。显示具体日期，不混用30天、31天和自然月。补发按原周期权益身份去重，不能因重启重复发放。

| 团队       | 席位/协作费＋组织共享按量积分，单独报价      | 成员预算/审批/审计为核心；不把个人包强行转组织包                                          |

首版只开放评审通过的试用和通用包，会员先不启用自动续费；推出周期会员时优先单月购买，年付与续费另验。首版无模型折扣、无充值赠分、无零积分无限生成，减少隐藏叠加。未来折扣若引入必须冻结到报价，以最差回收率r重测利润；价格表不能运行时查即时会员倍率。

会员权益不承诺突破上游并发、无限算力或永远商用；去水印等仅限平台有权控制的品牌水印，模型许可/内容权利不由会员自动取得。账户到期后的存储保留与导出按存储领域另定规则，不能未提示就删除用户素材。

### 7.7 付款账户、项目与Agent预算

个人工作区绑定个人付款账户；团队项目明确绑定组织付款账户，成员本人的积分不自动补足团队余额。一个operation冻结一个付款账户，首版不支持混合付款。切换工作区清楚显示付款方。

确认同时满足：账户有效、可用积分充足、项目预算、成员预算（如启用）、Agent批准余额（如适用）、模型权限及原未决屏障。预算是额度约束，可由管理员调整；只有验证过的发行事件能增加钱包。钱包不能通过`ChangeBudgetCommand`充值。

短剧预算包含实际模型调用尝试，不按成片分钟一口价。**纯算术制作样例**：12个5秒镜头成片60秒，预计平均2.5次视频尝试，则生成150秒；假设销售0.5元/生成秒，视频750积分；24张分镜图假设0.2元/张为48积分；文本假设0.5元为5积分，总预算803积分。该单价、尝试率和文本额均为假设，不代表当前模型报价/质量保证。失败、弃用镜头及二次改稿会改变成本，预算应列出这些假设和剩余批准额度。

Agent批准记录冻结项目、付款账户、允许模型/用途、有效期、总上限、单调用上限及重试策略。每个真实模型调用对应子operation；预留计入总上限，结束后实扣＋仍冻结不得超过批准值。并发子调用在服务端同一锁序内原子占用额度，不能各读同一余额。LLM仅接收服务端报价与剩余额度，不决定价格或凭空报告扣费。

更换成价格更高模型、增加输出、超总上限或授权过期都暂停并要求新批准。系统恢复先查原operation；上游未知时不创建新的收费重试。同一计划的未决额度不因新的批准记录而自动清除。

### 7.8 账本与数据合同

扩展既有Go模块化单体与PostgreSQL，不新建支付/积分微服务。`operation/application/pricing.go`继续是唯一用户计价引擎；billing增加账户资金、权益发行和交易准入；catalog管理价格版本；支付供应商适配器只负责外部支付证据。

以下为建议新增的数据职责，名称为实施合同草案，不是已有表：

| 实体                                 | 必要内容及约束                                                                                            |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| wallet_account                       | 主体类型/ID、CNY面值币种、状态；同主体唯一，余额投影含version，不充当身份授权                             |
| credit_lot                           | 账户、来源类型/唯一来源ID、面值、到期、范围、商品/权益政策版本；发行来源唯一，禁止负剩余                  |
| wallet_journal / wallet_posting      | 业务事件ID、关联operation/order/refund、幂等键、金额、账户/批次、分录；不可更新金额或删除，修正用反向补偿 |
| wallet_hold / wallet_hold_allocation | 原operation及reservation、每批分摊、授权上限、未结额；同operation唯一持有身份，释放/消费上限受原分摊限制  |

钱包日记账采用平衡分录：一个业务事件内同币种有符号微元总和为0，在可用、冻结、已兑换、过期及发行对手账户之间移动；批次分摊和余额投影在同事务更新。此为积分使用权技术账本，不替代现金支付及法定会计账。充值发行需要独立来源证据，不允许通过“平衡分录”任意增发。

核心不变量：可用与冻结分别非负；发行额=可用＋冻结＋净已兑换＋已过期＋已撤销；消费返还减少净已兑换但不修改原实扣；跨批次补偿以原批次撤出/新批次发行关联，不能双算。供应商采购超额不会生成用户负余额。项目原结算保留，退款若恢复可用预算也写关联调整，不能改历史实扣。

现有`billing_ledger_entry`继续作为项目预算/消费事实；新钱包事件显式关联原reservation，资金账与预算账在一次数据库事务提交，同一个事件只发布一次Outbox。投影重建不生成新发行，不从网页余额反写账本。

### 7.9 确认、结算与异常

1. **估价**：读取已审核价格，计算销售金额/最高支出；未产生冻结。批量返回已知金额、未知项和可确认项，未知不能按0合并。
2. **确认**：重新鉴权、校验报价/输入与未决屏障。在既有确认事务写预算预留、钱包分摊、operation与Outbox。重复幂等键仅重放相同内容；同键不同内容冲突。不能仅在现有代码中插入“先锁账户”：当前确认先锁operation再目标屏障，结算先锁reservation再预算，恢复/撤销也有原锁；必须形成覆盖全部路径的锁序再实施。
3. **派发**：仅事务成功后沿原Outbox；派发前重检原授权与消费身份。钱包余额的后续变化不令已批准消费重复扣款。
4. **结算**：可信实际用量沿冻结销售规则计算。固定价依实际可计费输出；可变价用户实扣不超过批准最高支出。多余预留释放；平台成本超额单记，不向用户钱包透支。采购未决和销售未决分别标识。
5. **未知**：保留原冻结、查原任务和账单，超时仅升级核查。对长时间冻结，建议24小时转人工核查、72小时触发平台保障评估；这是建议的运营节点，非自动退款保证或上游最终性证据。若平台承担风险向用户返还，独立记录补贴并禁止原消费再次扣用户。
6. **恢复**：沿设计34查询原任务/交付原产物，不新建收费提交。新生成需要新报价；交付状态不覆盖费用事实。

拟定全路径锁序：业务幂等身份→归属账户/项目的财务准入事务锁（多键按规范化键排序）→项目/operation行（多operation按ID排序）→原项目/目标屏障→reservation/hold（按ID排序）→项目预算/成员/Agent额度→批次（稳定排序）。账户/项目映射先按不可变关系只读定位，取锁后重检，不接受客户端自报绑定。实施前列出确认、批量、结算、撤销、恢复、预算调整、支付发行、退款、过期及补发的实际持锁矩阵；任何路径不得持有后序锁再取前序锁。旧预算路径若与新路径共享项目/operation也须同步接入准入锁，不能只改新钱包入口。此为待实现合同，须用命令间竞争和故障注入证明无反向锁序，不能据本文声称现有锁序已经满足。

承诺“最多扣Y积分”之前，必须把现有仅Token封顶扩成显式销售政策，并验证非Token路径；只改前端文案不能获得封顶。

### 7.10 任务返还、现金退款与支付

| 场景                                               | 用户积分                                                                       | 供应商成本与账务                                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| 确认前取消、明确未派发且无费用                     | 无实扣；有预留则按原分摊释放                                                   | 不产生假退款                                                                        |
| 生成失败，上游明确零收费                           | 原预留释放                                                                     | 保存零收费证据                                                                      |
| 平台承诺的任务未成功交付                           | 建议全额返还该失败消费的用户实扣；用独立补偿事件/原批次规则                    | 上游若已收费，记平台损失，不改采购账单；部分成功按冻结合同只扣成功部分              |
| 用户在上游已受理后取消、内容审核拒绝、主动弃用结果 | 事先说明是否收费；按具体模型与已接受政策，不默认全退                           | 上游已花费用不因产品状态消失                                                        |
| 下载失败但原结果存在                               | 免费重试原交付；未恢复前明确状态                                               | 不重复生成；不能仅凭下载错误自动退款                                                |
| 钱包现金退款                                       | 建议允许未消费的购买本金按审核规则原路退；先冻结可退批次，可信成功后撤销使用权 | 已消费、其他消费已冻结/争议部分不计可退；赠分不折现，金额取原实收分摊，不按面值提现 |

“任务失败积分返还”是平台面向用户的服务政策，须评审具体失败定义；不能在当前实现中直接凭operation.status扣零。迟到上游退款仅调整采购成本；用户已被平台补偿不能再次返还。补偿与原实扣分列，原账单永久可追踪。

支付流程：服务端创建商品/金额快照和订单→支付渠道下单→用户支付→验签通知/主动查单→验证商户、订单、币种、实收金额、外部交易状态→同事务标记已支付、发行一次积分及Outbox→前端轮询自己的订单。网页跳转成功、截图或客户端上报不能作为入账依据。

重复通知按外部事件与订单去重；通知乱序不能把paid回退为pending。超时未付可关闭，但迟到成功款须查渠道真实状态并进入明确补记/原路退款核查，不能静默吞款。真实重复扣款、拒付和现金退款各有独立事件；退款请求先冻结可退余额，渠道可信成功才标完成，仅可信终态失败/撤销可解除相应冻结。HTTP超时、断连、处理中、查单失败均保持退款未决，用原外部退款身份/幂等键查证，不能先解冻或换键再退。

支付现金使用整数分，积分/面值使用微元。部分现金退款使用累计法：累计应退分=floor(原购买实收分×累计已撤销购买面值÷原购买面值)，本次应退=累计应退−已成功退款分；未决退款额度单独占用，禁止并发重复申请。只有原单全部购买面值对应使用权均撤销，累计应退才达全部实收；存在已消费部分时不能以“最后一次退款”为由补退其舍入余分。赠分不进入购买本金分母/退款额，累计退款不超过实收。会员退款中的工具权益与已用额度分配须商品快照明确；首版不提供未经定义的自动会员折算退款。

对账覆盖支付→发行、钱包→批次、消费→预算、销售→供应商账单四条链。日终只是核查频次，不是允许一天双花。差异进入有权限的核查队列，不能自动用未知数填0。审计记录与余额查询不包含密钥、签名秘密或用户私有媒体。

### 7.11 界面与服务合同

首屏维持现有简洁风格：可用积分、充值入口；明细提供全部/消费/入账/返还/到期筛选。消费条目展开见项目、模型、原任务、预留→实扣→返还链及批次，不把上游账单原文给普通用户。团队清楚显示付款组织和成员。

接口为拟议能力，具体路由在实施时统一注解及生成类型，不宣称现已存在：

- 查询账户概览/积分批次/流水；仅返回调用者授权账户，游标分页。
- 创建订单、查询订单；创建需幂等键，金额由商品版本推导，不接受客户端自报入账额。
- 支付通知入口；专用验签和重放保护，不复用用户会话充当渠道认证。
- 请求退款、查询处理结果；绑定原订单/消费，不接受任意账户入账。
- 模型/批量预览复用原报价服务；正式确认复用现有operation入口，不新增旁路扣款接口。

账户ID不能替代鉴权；入账、调整和退款分别授权。审计人员不得拥有随意改价和改余额的组合能力。全站及Agent用一份服务端费用投影，前端/LLM不另行计算权威总价。

### 7.12 已确认的实施合同

SRC-CREDIT-02确认1元=10积分、新确认任务按确认价封顶、平台承担超额、未知保留冻结。新预留保存封顶标记，历史预留按原策略结算。账户沿现有个人/团队创作空间归属，项目通过受控配置显式绑定账户。确认按既有operation/目标屏障顺序进入预算锁，再锁账户与批次。结算锁原operation、reservation、预算、账户与原分摊，发行只锁账户，绑定只锁项目/预算再锁账户。批次与分录跟原预留在同事务更新，禁止应用角色发行和改写流水。隔离验收使用受控赠送批次，真实支付渠道后续独立接入。

用户售价的既有规则增加可选`procurement_price_version_id`。它指向同一型号、相同用量单位和兼容的缓存及参考图维度的采购价格版本。发布时同时校验两个版本的来源、审核时间、适用参数矩阵和生效顺序。采购规则使用自身的原币与冻结汇率。同一份供应商用量分别按采购费率与销售费率计算，`operation.provider_call.procurement_cost_micros`记录采购计量金额，供应商实账后续单独对账。钱包项目的新生成使用带已审核采购版本的发布，恢复原结果按零费路径处理。GPT Image 2.5保持原接入边界，商业采购待可靠Token计量。新Seedance 2.5文本和全参考草稿采用明确的16:9默认比例，现有发布保留原参数快照。

`billing.bind_project_wallet`及`billing.issue_promotional_credit`由受控运维执行。发放绑定唯一来源、可选模型范围、期限和理由。`billing.compensate_wallet_consumption`凭审核理由将一笔既有实扣返还到原来源，同笔操作按原证据去重。项目已消费报表仍保留原实扣，供预算审计。过期批次首次返还冻结一次7天宽限截止。账本终态检查在事务提交时核对冻结及结算分摊，兼容历史预留并拦截旧写入器创建缺少钱包分摊的新预留。

会话验证后的`GET /api/billing/wallet`读取当前创作空间。个人账户和团队管理员可查看对应流水，团队成员可查看付款方及余额。通用、限模型、冻结与今日实扣分列，金额采用精确十进制字符串。单次和批量报价由服务端按模型范围预检可用批次，确认重新锁定并验证。


## 8. 实施与验收

按[Plan32](../plan/32-模型商业计费与积分系统实施计划.md)验证：报价精度/版本、资金与预算原子预留、支付重复/乱序、赠分范围/过期、退款/补偿不重复、Agent并发限额、采购超额不透支、权限与投影重建。商业数字、封顶责任、补偿定义及支付渠道确认后才切换真实资金准入。

上线不将历史项目预算兑换成购买积分；历史operation继续沿原路径结算。钱包仅对明确切换的新消费启用，并以锁定的项目付款策略决定，用户不能通过改API参数绕过。回退停止新订单/新钱包消费，保留已付订单查证、在途结算、退款和历史账目，不删除余额或释放未知消费。评审、文档检查、模拟渠道、隔离数据库、真实支付、真实模型与产品接受分开判断。
