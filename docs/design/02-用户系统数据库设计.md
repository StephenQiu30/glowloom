## 1. 命名、类型与演进原则

复用 PostgreSQL 及 identity/workspace/infra schema。主键 UUID 由应用生成；时间统一 timestamptz，由服务端 UTC 时钟提供；修改版本 bigint，从 1 开始，CAS 成功后加 1。下表 `?` 表示可空；未标 `?` 均 NOT NULL。共同字段 `create_time/update_time timestamptz DEFAULT now()`、`revision bigint DEFAULT 1 CHECK > 0` 只在注明“可变实体”的表添加。不可变事件不含软删和可编辑版本。

邮箱先限制为 ASCII、去首尾空白并小写，最多 254 字节；不删除点号或 + 后缀。email_key 用 text + 唯一索引，不能同时维护两套大小写规则。扩展阶段允许历史账号 email_key 为空且禁止新认证；新注册不可为空。账号软删除后继续保留邮箱唯一占位，不允许通过重新注册恢复旧身份或权限。

结构只维护于 `backend/db/schema.sql`，不另存增量定义。禁止对已有业务库重放该文件。用户 ID 与业务资源 ID 不改。旧 login_name/org_id/role 在所有消费者切换前保留，不能作为新授权回退。

### 2.2 identity.user_session（改造）

`id uuid PK`、`account_id uuid FK user(id) RESTRICT`、`token_hash bytea UNIQUE CHECK octet_length=32`、`credential_epoch bigint >0`、`created_at/last_active_at/absolute_expires_at timestamptz`、`persistent boolean`、`revoked_at timestamptz?`、`device_summary text`、`reauth_at timestamptz?`、`reauth_epoch bigint?`、`csrf_hash bytea CHECK octet_length=32`。device_summary 最长 256 字符且不含原始 UA/IP；首次 last_active_at=created_at，绝对到期晚于创建。

索引 `(account_id,last_active_at DESC,id)`，可用会话索引条件 `revoked_at IS NULL`；每次鉴权仍检查 idle 12 小时、absolute 7 天、账号状态及 epoch。不能把“索引有该行”视为未过期。普通请求更新活动时间可限频，不能延长绝对到期。

### 2.3 identity.auth_challenge（新建）

`id uuid PK`、`operation_id uuid`、`purpose text`、`email_key text`、`user_id uuid? FK user RESTRICT`、`email_version bigint?`、`credential_epoch bigint?`、`proof_digest bytea CHECK octet_length=32`、`proof_key_id text`、`flow_secret_digest bytea?`、`attempts smallint DEFAULT 0 CHECK 0..5`、`expires_at timestamptz`、`consumed_at/revoked_at timestamptz?`、`created_at timestamptz DEFAULT now()`、`invitation_id uuid?`、`invitation_revision bigint?`。

purpose 闭集：registration_code/registration_grant/password_reset/email_old/email_new/deletion_confirm/migration_bind。每个处理函数只接受自己的目的，operation_id 关联双邮箱证明。注册 grant 只能绑定一个邮箱；受邀注册绑定 invitation_id 与 invitation_revision，每一步和最终提交均重查邀请状态、版本、邮箱、发起者与团队邀请策略；关闭公开注册不阻断有效受邀流程。注册只创建普通账号，团队职责仍明确接受。令牌采用安全随机 32 字节，验证码 6 位用带密钥 HMAC 摘要，不能用裸 SHA 暴力枚举。

邮箱换绑复用email_old/email_new两行，无需额外迁移或永久操作表。双方在同一10分钟窗口，flow_secret_digest以操作ID为摘要域并绑定session_id/revision；user_id/email_version/credential_epoch必须仍与当前账号一致。consumed_at表示该side已验证，Complete要求双方已消费且未撤销/过期；成功后撤销该账号全部挑战。邮件投递pending/failed/expired等状态不会授予证明，submitted仅表示SMTP服务已接受，不能宣称用户已收信。

头像复用media.media_asset的个人ownership、PNG事实及moderation_detail.avatar `{version:1,method:'server_reencode_png'}`专用成品标记；输入仍接受真实静态JPEG/PNG/WebP≤5MiB且解码尺寸≤4096×4096；服务端按比例缩小到长边最多1024像素，不放大小图，统一转换8位NRGBA后重编码PNG。成品采用独立6MiB安全上界，尺寸与成品资格均以1024为限；1024×1024×4原始像素约4MiB，避免合法压缩输入因直接重编码膨胀而被拒。服务器保存归一化后的内容哈希/尺寸和现有个人image对象路径。普通图片即使当前用户拥有也不能当作头像绑定。profile CAS事务检查账号当前会话及media成品并保留锁；不新增头像数据库或公共bucket。

索引 `(operation_id,purpose)`、`(email_key,purpose,created_at DESC)`、`(expires_at)`；消费用带目的、未撤销、未消费、expires_at > now 的条件更新并检查影响行数。重发锁定地址预算且撤销前一挑战，错误次数不能靠换 operation_id 清零。

### 2.4 identity.login_guard / identity.email_budget（改造 / 新建）

login_guard 用 `login_key text PK` 保存邮箱的带密钥摘要，移除旧登录名正则；`failure_times timestamptz[]`、`locked_until timestamptz?`。按滚动 15 分钟 5 次失败锁定 15 分钟，未知邮箱同样记账；同一账号的 reauth_guard 由密码复验和主动改密共享，业务拒绝不得回滚失败/审计，锁内先拒绝且不续期。来源预算使用下面的独立桶，不能只锁已存在账号。

email_budget：`bucket_key text PK`（目的/地址/来源/全局分层摘要）、`sent_at timestamptz[] DEFAULT '{}'`、`failed_at timestamptz[] DEFAULT '{}'`、`revision bigint DEFAULT 1`。事务锁行后滑动窗口裁剪再计数；重发至少 60 秒，地址每小时 5 次、每天 10 次。来源/全局阈值为运行配置，未配置时注册发信入口关闭，禁止无限预算。

登录来源复用 email_budget 的独立 `login_source/<HMAC(peer)>` 桶，`failed_at` 在此桶记录所有接纳的登录尝试（含成功、错误密码、未知邮箱和格式错误邮箱），`sent_at` 不用于登录。持行锁裁剪 15 分钟之前的时间点，最多保存 100 条窗口内尝试；第 101 次在密码验证前返回 429，Retry-After 为最早时间点到期剩余时长，拒绝不续期。与 SMTP 桶/邮箱 login_guard 的键空间、计数和到期独立，不需要新表或迁移。阈值为本地候选值；来源为实际 RemoteAddr peer，忽略所有转发头，BFF 聚合共用额度；无 peer 的内部入口使用有界 unknown 桶。

## 3. 团队与空间

### 3.1 workspace.team（新建；可变实体）

`id uuid PK`、`name text CHECK char_length 2..50`、`avatar_asset_id uuid?`、`created_by uuid FK identity.user RESTRICT`、`status text DEFAULT 'active'`（active/archived/suspended）、`resume_status text?`（active/archived）、`governance_blocked boolean DEFAULT false`、`auth_epoch bigint DEFAULT 1 CHECK >0`、`invitation_enabled boolean DEFAULT true`。仅 suspended 时 resume_status 非空；恢复取该值后清空。治理冻结和归档不是同一状态。

索引 `(created_by,status)`、`(status,create_time DESC,id DESC)`。created_by 仅来源，不能当“永久超级管理员”；团队名称不唯一。

### 3.2 workspace.team_member（新建；可变实体）

`team_id uuid FK team RESTRICT`、`user_id uuid FK identity.user RESTRICT`、复合 PK `(team_id,user_id)`；`role text`（team_admin/member）、`status text`（active/suspended/removed）、`auth_epoch bigint DEFAULT 1 CHECK >0`、`joined_at timestamptz`、`joined_by uuid? FK identity.user RESTRICT`、`source text`（created/invited/migrated/transferred）、`last_team_activity_at timestamptz?`。

索引 `(user_id,status,team_id)`、`(team_id,status,joined_at DESC,user_id DESC)`、`(team_id,role,status)`。removed 后新邀请可在明确授权下复用该行，更新 joined_at/source 并保留审计；旧邀请不能恢复已移除或暂停的成员。

### 3.3 workspace.creation_scope（新建；可变实体）

`id uuid PK`、`kind text`（personal/team）、`owner_user_id uuid? FK identity.user RESTRICT`、`team_id uuid? FK team RESTRICT`、`physical_scope_id uuid FK workspace.organization(id) RESTRICT`。

CHECK：personal 仅 owner_user_id 非空；team 仅 team_id 非空。owner_user_id 和 team_id 各有非空唯一索引。一用户一个个人入口，一团队一个创作入口；不以 physical_scope_id 的相等推断授权。旧物理范围混合个人与共享资源时必须补充逐资源 owner_scope_id，不能建立虚假一对一映射。

项目、媒体、画布、任务等根资源增量增加 `owner_scope_id uuid FK creation_scope RESTRICT`，保留 `created_by uuid` 作者引用；派生资源通过父级追溯或冗余字段加一致性校验。需逐表盘点后列出增量，不对所有带 org_id 表机械替换。迁移验收要求每个可访问根资源恰有一个归属，无归属先隔离。

## 4. 邀请、授权与生命周期

### 4.1 identity.invitation（新建；可变实体）

`id uuid PK`、`kind text`（account/team）、`team_id uuid? FK workspace.team RESTRICT`、`email_key text`、`suggested_display_name text?`、`team_role text?`（member/team_admin）、`inviter_id uuid FK user RESTRICT`、`status text DEFAULT 'pending'`（pending/accepted/declined/revoked/expired）、`token_hash bytea UNIQUE CHECK octet_length=32`、`expires_at timestamptz`、`accepted_user_id uuid? FK user RESTRICT`、`membership_revision bigint?`。

CHECK：account 的 team_id/team_role 均为空；team 的二者均非空。投递失败是 mail_delivery 状态，不误改邀请终态。平台定向团队邀请记录 platform_issued，接受时复查发起者平台资格；普通账号邀请与团队邀请均不授予平台角色。mail_delivery 绑定 invitation_id/revision，worker领取前使撤回、旧版本和到期邮件失效并清空密文；已领取且实际提交的邮件无法召回，消费proof仍独立复查。部分唯一索引 `(team_id,email_key) WHERE kind='team' AND status='pending'` 与 `(email_key) WHERE kind='account' AND status='pending'`；重发/新建先锁定相关团队及邮箱、显式过期旧行再创建或换 token。索引谓词不使用当前时间；实际接受另查期限。[PostgreSQL 部分索引](https://www.postgresql.org/docs/current/indexes-partial.html)

### 4.2 identity.authority_proposal（新建；可变实体）

`id uuid PK`、`kind text`（platform_grant/team_transfer/platform_takeover）、`team_id uuid? FK workspace.team RESTRICT`、`source_user_id/target_user_id uuid FK user RESTRICT`、`status text DEFAULT 'pending'`（pending/accepted/declined/cancelled/expired）、`expires_at timestamptz`、`reason text`（5～500 字符）、`source_authority_revision bigint`、`target_revision bigint`（目标 platform_epoch）、`target_email_version bigint`、`target_credential_epoch bigint`、`team_revision bigint?`。

platform_grant 不含 team_id；其他必须含团队。目标必须是既有已验证账号；team_transfer 目标须是 active 成员，takeover 可在接受时由平台治理原子建立成员。提案不携带管理员业务令牌，邮件只引导本人登录接受。目标绑定使用 platform_epoch、email_version、session_epoch；登录或资料更新引起的普通 user.revision 增长不会让待接受提案失效。创建时 expected_revision 仍对当前用户/团队作 CAS，接受时继续复查账号 active/verified 与当前会话/近期证明、发起方和团队版本。建议有效期 48 小时，与邀请相同，作为本设计评审参数。索引 `(target_user_id,status,expires_at)`、`(team_id,status)`。

### 4.3 账号软删除

复用 identity.user 的 is_delete、deleted_at、status、session_epoch 和 platform_epoch。一个事务检查当前会话、近期密码复验、邮箱证明及最后管理员职责，然后软删除账号，撤销会话、挑战和团队成员权限。保留邮箱唯一索引、个人与团队资源及作者引用。不创建 account_deletion/deletion_item 表，不设冷静期、取消或物理清理任务。

复用 infra.idempotency_record，命名空间固定为 actor（公共入口为 flow 绑定摘要）+ endpoint action + scope + key。保存规范化请求哈希、结果资源 ID/安全响应、状态码、到期时间；不保存密码、邮箱证明或 Set-Cookie。秘密结果重试通过仍有效的 flow 绑定安全恢复或重新验证取得；不能把明文令牌放在通用响应记录。保留 24 小时为设计建议，超过窗口由业务唯一约束保障不重复创建。

## 6. 事务与并发约束

会话授权使用调用方显式注入的时钟函数，取得账号与会话行锁后才采样；近期复验、邮箱证明消费及相应动作时间在已取得身份事务锁的回调内刷新。不得用请求开始时刻校验等待后读到的 last_active_at，也不得把校验时间钳制到活动时间。`AuthSession.Valid` 的反时钟回退、idle 12 小时和 absolute 到期边界保持不变；等待期间到期必须拒绝。定向回归在现有数据库的外层回滚事务中，通过真实 HTTP 请求屏障重放“偏好请求等待、另一请求刷新会话、偏好继续”的交错，并在会话 SELECT 完成后推进注入时钟检查 idle / absolute / rewind / 近期复验边界。此证据属于实际 HTTP＋数据库的确定性顺序交错，不宣称跨连接并发或部署后的浏览器验收。

所有治理写入采用固定锁序：platform_settings 单例 → 相关 user 按 UUID 排序 → team 按 UUID 排序 → member → invitation/proposal/challenge → 幂等/事件。团队成员变化与账号禁用需遵守同一锁序；若锁前读取成员发现集合在锁后变化，重试整笔事务，不接受不完整集合。初期用这一简单串行治理路径保证正确性，后续仅凭压测证据拆细锁。

最后平台管理员：持单例锁重新统计 active+verified 的 platform_admin，再处理降权/禁用/注销。最后团队管理员：锁团队与候选账号，统计 active 成员+active verified 账号；普通移除/退出/降级拒绝归零，平台紧急禁用则原子设置 governance_blocked。临时登录锁定和 must_change_password 不从治理资格计数中剔除。行锁行为依据 [PostgreSQL 显式锁](https://www.postgresql.org/docs/current/explicit-locking.html)，业务锁协议须以 20 并发反例测试验证，不能仅靠 CHECK 实现跨行不变量。

expected_revision 不符回滚返回 409；唯一冲突转换成安全领域错误，不返回 SQL 文本。审计/必要任务插入失败回滚业务。事务外调用邮件/媒体供应商，禁止持锁等待网络。死锁/序列化冲突最多内部重试 3 次，同一幂等键保持不变，耗尽返回可重试 503。

## 7. 数据清理与验收

账号注销采用软删除，设置 is_delete、deleted_at、disabled 并推进权限版本；保留资料、邮箱占位和资源，不 CASCADE 到团队作品。FK 默认 RESTRICT；过期挑战载荷、已提交邮件敏感载荷及时清除。注销不触发物理清理或备份擦除。数据库角色不得读取密钥，密钥不可和载荷同库明文保存。

验收必须同时覆盖空库 schema 与既有库增量：主键/外键/唯一性、缺邮箱隔离、混合范围归属、20 并发消费/最后管理员保护、索引查询计划、运行时最小权限、恢复后撤权。方案通过不等于实际数据已迁移；演练证据由[测试与运行设计](04-用户系统测试与运行设计.md)定义。
