# 模型商业计费与积分系统实施计划

唯一来源PRD：[PRD23](../prd/23-模型商业计费与积分系统.md)。目标：在现有operation/billing上完成可追溯的资金准入、消费、返还和支付闭环。技术合同由PRD来源设计36持有，不在本计划复制另一套规则。实施状态、优先级及下一步仅见[BACKLOG](../../BACKLOG.md#commercial-credits)。

## 1. 前置与边界

实际编码前读当时AGENTS并重查Git、并行改动与现有账本。先明确DEC-CREDIT-01～06、支付渠道、退款条件、补偿定义与商品版本；封顶/补偿成本承担未经接受的模型不能开放商业消费。文档交付不自动开通支付、收费调用、业务库迁移或Git发布。

复用Go/PostgreSQL、现有billing/operation/catalog、Outbox与前端生成类型；不增加微服务、第二计价引擎或LLM扣费器。真实支付和供应商测试需精确账号、次数/金额预算及目标环境；模拟结果不能代替真实接受。

## 3. T-CREDIT-01 统一价格与精确显示

1. 固定反例：0.12元=1.2积分、1微元=0.00001积分、巨大微元超出JS安全整数、批量已知＋未知、部分输出和缓存互斥。
2. 先运行现有operation计价测试得到新增断言有效Red，最小修改使其通过；旧EstimatedCredits语义保留，新投影来自微元/冻结ratio。
3. 将采购成本计算与现有含markup的用户金额分开命名/持久化；用同一份原用量，冻结各自版本，不复制销售算法到前端。
4. 扩展显式销售封顶策略到非Token，用户实扣≤最高批准值，超额进入采购/平台差异。
5. 退出条件：CASE-CREDIT-01/02与现有Plan30相关回归通过。真实价表不因测试fixture自动发布。

## 4. T-CREDIT-02 钱包、批次与原子消费

1. 在最小wallet/lot/journal/hold模型写不变量测试：发行来源唯一、平衡分录、金额不溢出、非负余额、原分摊守恒及不可变更。
2. 增量只在隔离空库/代表性测试快照验证，迁移前后原budget、reservation及在途operation不变；不把预算限额转成积分。
3. 先列出原身份/目标屏障、operation、reservation、预算及新账户/批次的完整持锁矩阵，再按设计36统一所有共享路径；确认、结算、退款、过期、预算调整、恢复/撤销互相竞争，以及并发单/批量、跨项目同账户与故障注入，必须查数据库最终事实和死锁情况，不能只Mock成功返回。
4. 验证批次期限/范围、预留跨期、未到期返还、已到期补偿批及重复释放/结算/返还；反复占用取消不重置来源链的一次宽限截止，投影可由原日志复算。
5. 退出条件：CASE-CREDIT-04/05/06/09/12；旧消费恢复与未知屏障回归通过。

## 5. T-CREDIT-03 支付与现金退款

1. 冻结商品、现金分、积分面值和主体，创建幂等订单；先接一个已选择的渠道，凭据通过既有配置注入，不写进文档/测试快照。
2. 渠道模拟覆盖合法/非法签名、错商户、错金额币种、重复成功、通知乱序、查单并发、支付晚到、重复扣款和超时；只有可信paid事件能发行。
3. 现金退款先冻结可退购买批次，调用渠道后确认最终性；仅可信终态失败可解除退款冻结，超时/处理中沿原退款幂等身份查证。固定部分消费后退款、并发申请、多次小额退款与累计舍入反例，累计不超实收、不补退已消费部分余分。
4. 验证用户余额查询鉴权与渠道通知认证分离，客户端支付成功/账户ID不能自行入账。
5. 对账扫描按事件身份幂等记录差异，不自动发积分填差额；观测指标不含敏感字段。
6. 退出条件：CASE-CREDIT-03/10/12模拟与隔离库通过。再用明确预算做一笔真实小额购买、重复通知及原路退款，保存脱敏交易身份与到账证据；未完成时保持真实支付入口关闭。

## 6. T-CREDIT-04 消费返还与运营核查

1. 先明确“生成失败、部分成功、审核、取消、交付失败”的用户政策和采购结算差异，用例固定后实现独立补偿命令，不改原settle记录。
2. 同一消费已平台补偿再收到上游退款，只调整采购；重复、反序及迟到证据不重复返还。
3. 未知调用沿原operation核查；核查期限不解禁收费POST。平台保障若放回用户额度，原消费不再追扣；成本承担明确入账。
4. 退出条件：CASE-CREDIT-07/12及原PRD21未知、原交付恢复、权限回归；没有新的供应商幂等合同就不启用同键补交。

## 7. T-CREDIT-05 短剧预算与Agent

1. 人与Agent复用服务端批量预览；已知合计与未知数量分列，token/参考视频等不满足合同则不可自动执行。
2. 批准身份绑定模型范围、付款方、项目、期限、单项和总额；并发子operation在资金/预算事务中占额，不先本地扣计数再调用后端。
3. 断线、重启、超限、同节点改模型、换请求键和计划恢复均验证；未知调用保持原身份，不能借新预算新建重复付费。
4. 退出条件：CASE-CREDIT-08/09；预算卡片可用但未真实跑一集时不得称完成短剧商业验收。

## 8. T-CREDIT-06 产品界面与周期权益

先落地账户概览、入账/消费/返还明细、付款方、精确积分、充值与订单恢复，复用现有简洁费用确认；正常态不常驻技术JSON。验证320/390桌面、键盘/读屏及错误提示归因。会员未开放时不显示可购买假入口。

基础支付闭环后，按已评审单月商品实现subscription_period及幂等发放；先验证月底周年、关闭续费、本期有效、补发与购买积分独立，再开放。自动续费、年付、模型卡不随此任务默认开启。退出条件：CASE-CREDIT-11及共同页面接受条件。

## 9. 验证、迁移与退出

Go业务修改按Red→Green→Refactor，执行项目适用的格式、静态分析、相关单元/隔离PostgreSQL集成、并发Race及安全检查；前端执行对应类型/组件与关键浏览器检查。命令及结果由实际实施时记录，本文不预填通过。

迁移先区分历史预算消费与新付款策略，用服务端项目/账户策略切换；新消费才能要求钱包，旧operation保留原冻结和恢复合同。新旧请求并发不能绕过同目标屏障。回退拒绝新订单和新商业消费，继续处理已付入账、在途结算、原路退款和核查；不得删表、清账或静默转零。

退出条件：来源PRD对应场景逐项具备可复查证据，政策已确认、渠道与模型真实验收独立通过，之后才按明确范围开放入口。纯文档及研究检查不代替这些验收。


## 10. SRC-CREDIT-02 操作与验证合同

钱包结构由 `backend/db/schema.sql` 定义。部署前在隔离空库验证约束和授权。项目启用使用`billing.bind_project_wallet(project_id)`，由原创作空间确定付款方。发放仅用于审批后的赠送批次，调用`billing.issue_promotional_credit(scope_id, source_id, amount_micros, expires_at, model_key, justification)`。每笔已批准返还以原reservation和理由提交`billing.compensate_wallet_consumption`。现有应用角色可管理冻结和解冻分摊，并按授权读取流水。发行、绑定及消费返还由结构所有者控制。

模型管理页先保存有来源及审核时间的采购费率，再在用户售价选择该版本。保存售价后依既有流程创建发布并审核。报价和确认使用同一冻结售价，采购金额按已获得的原用量以绑定采购费率计算。未完成发布的采购引用拒绝入选，报价不能获得真实验证证据的场景仍受原启用门禁控制。

隔离回归重点包括`TestCommercialWalletQuoteConfirmationAndMockedSettlement`、`TestWalletReserveCapAndReplay`、`TestWalletConcurrentReserveDoesNotDoubleSpendAndRollsBackBudget`、`TestWalletExpiredReleaseKeepsOriginalGraceAndScope`及`TestWalletBoundProjectRejectsOlderUnfundedWriter`。分别核对模型商业准入、精确上限、报价不足、费用未知、并发扣减、原分摊返还、历史结算和旧写入器回退保护。支付渠道及会员政策按用户选择保持隔离验证范围。若停止新商业消费，应停用新确认入口并继续运行识别钱包分摊的结算服务。

隔离验收记录（2026-11-05）

- 独立 PostgreSQL 18 空库应用完整 schema，代表性旧库重复应用增量；钱包绑定、发行、实扣、补偿、跨项目竞争和旧写入器提交保护均通过隔离测试。
- 使用独立 PostgreSQL 数据库及本机 MinIO 执行 `go test -race -count=1 ./tests/billing ./tests/catalog ./tests/operation ./tests/agent/modelgateway`，四个测试包通过。Go vet、golangci-lint 通过，govulncheck 报告零个调用路径漏洞。
- 模拟供应商端到端用例验证未绑定采购费率时确认拒绝，确认后未知费用保持 1.2 积分冻结，可信回执产生 1.2 积分实扣及独立 ¥0.05 采购计量，重放只记录一次。
- 前端全量 Vitest 2,126 项通过，最后涉及页面与生成接口的 43 项通过，类型和定向 ESLint 通过。以主分支和本次改动的干净副本运行默认 Next.js 生产构建成功。浏览器模拟接口核对余额、流水游标和 390px 布局。

## 2026-11-06 独立创作与整数计费

1. 在独立 worktree 复核创作空间授权、内部归属和已有报价结算。冻结账本策略标记及存量迁移范围见[设计36](../design/36-模型商业计费与积分钱包设计.md)。
2. 验证已知金额向上取整、整次请求聚合、冻结上限与原金额保留。编写覆盖零、边界、溢出及旧账重放的定向测试。
3. 增量迁移钱包结构与权限，在隔离 PostgreSQL 演练结构预检和一次性事务增量，核对余额不增发和历史行不变。再次部署根据结构预检跳过已完成的增量。验证历史报价、旧冻结与新整数冻结并存。
4. 实现当前空间的独立执行容器、首页媒体生成、独立画布与项目内继承。agent-browser 实测零项目、项目内、刷新恢复、余额不足和整数报价。
5. 仅当隔离验证通过后才切换本机数据库与服务。复用 Seedream 5.0 Flash 已保存的采购/销售版本及发布草稿，逐模式验证，确认整数冻结及实扣后激活。
