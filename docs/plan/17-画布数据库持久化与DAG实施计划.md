# 画布数据库持久化与DAG实施计划

> 唯一来源PRD：[07-画布数据库持久化与DAG](../prd/07-画布数据库持久化与DAG.md)。进度与阻塞见[BACKLOG](../../BACKLOG.md)。

## 1. 目标

保存Yjs二进制状态、完整业务投影与持久回执，支持合法图、稳定素材引用及跨会话恢复。

## 2. 任务

| ID                       | 交付与退出条件                                                          |
| ------------------------ | ----------------------------------------------------------------------- |
| T-DATA-01 数据与读取合同 | 明确全部节点字段、schema、epoch、二进制状态和投影；同一接受版本完整读取 |
| T-DATA-02 原子接受       | 权限、图、引用、状态、修订及回执统一接受；同ID重放返回原结果            |
| T-DATA-03 图与素材完整性 | 验证标注、分组、依赖、删除、替换、项目复制及生成输入来源                |
| T-DATA-04 客户端适配     | 接通项目加载、素材服务、Yjs提交及保存反馈；全部内容真实入库后重开       |
| T-DATA-05 存量转换       | 原始快照、转换核对、备份恢复与epoch切换，旧客户端按版本门禁拒写         |
| T-DATA-06 联合接受       | 完成AC-DATA-01～08，与SYNC/COL共同验证真实数据库和浏览器链路            |

## 3. 实施顺序

数据合同与读写用例→持久状态和回执→图与素材校验→客户端接线→存量转换→联合验收。协作服务按计划19交付，实时通道按计划18交付。

## 4. 验证矩阵

覆盖完整字段读回、上传后图拒绝、素材替换、重复提交、回执丢失、事务故障、撤权与归档、非法依赖、未知结构、项目复制及服务重启。核对二进制恢复结果与投影的一致性。

### 4.1 原子接受验证方法

依据设计14 §7.4/7.7完成T-DATA-01/02/06：在隔离真实PostgreSQL中验证writerTerm/expectedCommitSeq、二进制与投影同事务、不可变回执、Outbox和恢复读回。故障注入覆盖commit前、commit后ACK前、commit后投递前；让旧owner继续提交并确认拒写。并发X→Y/Y→X应至多接受合法结果，不能只验证串行非法图。

记录数据库同步提交配置、候选hash、checkpoint/日志边界和投影hash；禁用内存持久适配器作为验收后备。新增DDL先在恢复副本演练，保留已有schema与增量迁移规范；本计划不授权直接操作业务库。跨端场景统一见[计划19](19-画布Yjs协作编辑实施计划.md#41-故障场景与退出条件)。

### 4.2 存储边界与未确认结果验证

按PRD07 §7.1完成T-DATA-03～06：逐类监测正式入口与迁入组件的localStorage、sessionStorage、IDB、Cache API、Service Worker及持久查询/日志队列，检查画布读取响应的no-store策略。给旧业务缓存写入测试标记，再打开正式入口，证明不会读入或上传该标记；同时证明登录与个人视图白名单不受误清理影响。

设置两种关闭重开情形：①发送前断网，输入仅在内存，重开只读服务器原内容；②数据库已commit、ACK被丢弃后关闭，重开读到服务器新内容。不能把两者统称“未保存均丢失”。隔离环境记录元数据与摘要，不将真实正文作为测试日志。与计划19 CASE-COL-07/11/13联合核对。

另测试过期基线的候选拒绝、新epoch恢复与旧回执查询、素材发布成功但图接受失败及迟到绑定；按PRD07验证无半笔写入、无错误绑定和无重复业务效果。检查点压缩后原回执仍可查，暂态数据库失败不固化为永久拒绝。

## 5. 数据转换

逐画布保留原始快照，转换后核对节点、正文格式、引用身份、素材与关系。以epoch启用唯一写入通道，演练切换中断、回退及旧客户端拒写。

## 6. 证据

记录命令、版本、环境、数据库回读、浏览器操作和失败分支。进度登记BACKLOG，验证证据保留日期和覆盖范围。

## 7. 验证证据

以下记录限定于列明日期、环境与覆盖范围，不能替代当前Yjs联合验收。

### 7.5 本地存量画布增量升级（2026-10-23）

用户报告真实画布 `dependency_unavailable`。只读检查本地 `glowloom` PostgreSQL 18.4 确认缺少 `canvas.document.schema_version`、`canvas.node.content_version`、`canvas.command_log.client_id`；文档与日志revision/base_revision仍为integer，文档operation_version默认值仍为0，回执保护触发器缺失且运行角色拥有整表UPDATE。

处理与验证：

1. 对本地库执行完整custom-format备份，保存到权限0700的本机私有目录；没有打印DSN、密钥或备份数据。备份在无网络的隔离PostgreSQL 18 Docker容器中成功恢复。
2. 另建空参考库，仅对空库执行schema.sql；比较全部canvas表的列、默认值、约束、索引与权限，依据差异编写[canvas_protocol_incremental.sql](../../backend/db/canvas_protocol_incremental.sql)。脚本只新增字段、扩展修订号类型、设置新文档默认值并保护回执。旧operation_version、历史client身份、业务节点和回执内容不重写。
3. 在恢复副本执行增量并与参考结构核对；逐表行数和原有JSON值摘要一致，覆盖document/node/edge/command_log/node_input/save_receipt及两张复制表。事务ROLLBACK、重复执行、受限角色禁止改写回执均通过。
4. 暂停Docker后端，在本地库以`psql --single-transaction -v ON_ERROR_STOP=1`执行增量；lock_timeout为5秒，statement_timeout为60秒，失败整笔回滚。随后通过Docker Compose启动后端并等待healthy。没有对存量库重放schema.sql。
5. 用户原Chrome登录会话的目标画布已实际读取：项目素材、历史图片生成节点、正文引用与连线均显示。该画布含本轮编辑器未支持的业务节点，因此只读展示，不修改图、不启动写入会话。
6. 升级后的本地库再次与备份恢复副本逐表核验，统一UTC时区和C排序后摘要一致：document 15、node 43、command_log 276、edge 14、node_input 41、save_receipt 275，两张复制表均为0。新增版本字段以外的原有值没有变化；隔离验证容器随后清理，私有备份保留。

应用统一用默认Docker Compose启动，基础依赖按用户确认保持现有服务。验证中发现前端开发缓存的API路由404，已保留旧缓存目录并重新编译；真实代理与页面随后恢复。健康检查不代替业务数据验证。

范围：本地存量库及目标画布只读恢复。未验证普通画布真实写入/撤销/多端，未实施历史生成节点编辑或其他环境升级，未提交或推送。数据库升级成功不等于完整画布能力已接受。
